# SmartDD 参考项目调研与选型建议

调研日期：2026-10-14。依据官方 README、官网及文档；尚未安装、运行或完成源码级可行性验证。本次不对星数、宣传效率或未经测量的成熟度作评分。

## 1. 结论

**建议先验证“现有跨端 Agent 底座 + 项目业务扩展”，验证通过后再确定是否需要完整自研。**

用户需要的项目、任务、会话和手机联控，与三个候选产品已有的部分能力接近。“以项目为起点”本身不足以说明必须从零开发。需要重点补齐的是项目多环境资源、禅道 Bug 生命周期、真实验证证据，以及提交版本到 Jenkins 产物、部署版本之间的关联。

首选验证 Paseo 插件方案；Yoda 候选进入二次开发比较；Orca 重点参考工作区与浏览器交互。这个排序是针对本次需求和当前公开资料的研发建议，不是实测后的最终选型。

Yoda 暂按 [lovstudio/yoda](https://github.com/lovstudio/yoda) 调研。用户补充“GitHub 上手工传的那个”，尚未提供可唯一确认的完整地址，故保留身份待确认。

## 2. 候选项目与证据

### 2.1 Orca

官方仓库为 [stablyai/orca](https://github.com/stablyai/orca)，官网为 [onorca.dev](https://www.onorca.dev/)。公开说明包含 Codex／Claude Code 等运行器、git worktree、差异、终端、Chromium 浏览器、SSH 远程工作区，以及 iOS／Android 手机联控；仓库声明为 MIT 许可证。[官方 README](https://github.com/stablyai/orca)

值得借鉴的设计：围绕任务展示代码工作区、测试页面和差异，让用户能同时理解 Agent 在改什么及实际界面发生了什么。

本次未核验它对项目自定义资源、禅道动作、Jenkins 专用记录的支持程度。内置浏览器存在，不等于已经支持用户现有 Browser Skill 或完整无人值守验收；需要独立实测。

### 2.2 Yoda 候选

[lovstudio/yoda](https://github.com/lovstudio/yoda) 的 README 描述了项目／任务、多个编码客户端、自定义 Agent、Skills／Hooks／Memory／上下文观测、工单集成及归档前 Skill；移动协作通过桌面 gateway、relay 和独立 Expo 客户端实现。仓库声明 Apache-2.0，SSH 远程开发注明仍处于早期阶段。[官方 README](https://github.com/lovstudio/yoda)

值得借鉴的设计：分开管理运行器与角色配置，显式展示 Skill 和上下文实际加载情况，任务作为会话、修改和收尾动作的容器。

README 指向 [lovstudio/yoda-mobile](https://github.com/lovstudio/yoda-mobile)，本次读取该移动仓库未成功，因此无法确认其源码可获取性、构建方式和手机端当前覆盖程度。不能据此判断仓库不存在或没有移动能力。

### 2.3 Paseo

[getpaseo/paseo](https://github.com/getpaseo/paseo) 描述了本机 daemon、桌面／手机／Web／CLI、Codex 与 Claude Code 等运行器、工作区、会话及 TypeScript SDK。文档给出加密中继或直接连接方案，仓库声明 Apache-2.0。[官方 README](https://github.com/getpaseo/paseo)

[官方插件文档](https://paseo.sh/docs/plugins) 明确支持客户端页面、侧栏、工作区面板、时间线及 daemon 侧 RPC；客户端扩展可运行在连接该 daemon 的手机客户端中。这为项目配置、禅道列表和任务阶段页面提供了直接的扩展候选。

值得优先验证的设计：复用已存在的跨端连接和运行器会话能力，通过插件及配套业务服务实现项目资源和交付记录。

文档中的能力声明不替代实测。插件能否承载持久化任务恢复、复杂配置、完整附件以及所需权限边界，仍要通过小范围原型验证。

### 2.4 腾讯 BrowserSkill

[Tencent/BrowserSkill](https://github.com/Tencent/BrowserSkill) 公开提供 CLI 与浏览器扩展，让能使用 Shell 的 Agent 操作已登录浏览器，并支持人工介入。这与用户已有本地浏览器验收方式方向一致，可作为跨运行器的统一浏览器通道候选。[官方 README](https://github.com/Tencent/BrowserSkill)

需确认用户现有版本、安装方式和实际宿主；不能把 BrowserSkill、Codex Desktop 内置浏览器及其他 Browser Use 产品混为一种能力。

## 4. 三种研发路径

| 路径 | 组成 | 适用条件 | 主要待验证问题 |
| --- | --- | --- | --- |
| 直接使用成品 | 现有产品 + 原有 Skill，通过会话执行各项动作 | 接受以对话为主、少量项目专用页面和报表 | 是否能稳定保持项目配置、业务阶段和交付记录 |
| 在现有底座上扩展（优先验证） | 运行器和跨端能力复用；业务配置、Bug、流水线和证据自建 | 需要专用项目页面和稳定闭环，同时希望减少底层开发 | 插件／扩展契约、权限、移动覆盖、持久化和升级兼容 |
| 完整自研 | Desktop + 手机 App + 本机 daemon + 适配器 + 任务服务 + 连接方案 | 现有底座的扩展机制、运行器或跨端能力无法满足关键验收 | 需要承担配对、重连、事件流、适配、升级及客户端发布 |

即使最终完整自研，也应复用已可用的运行器、Skill 和外部工具调用方式，不重新开发一套编码 Agent。

## 5. 推荐的最小技术验证

用一个非生产项目、一个真实且可复现的 Bug、一个既有 Jenkins 开发 Job 验证下表。执行前再核验并固定候选仓库 commit、依赖与文档版本，避免资料和安装版本不同。

| 验证项 | 实际操作 | 通过证据 |
| --- | --- | --- |
| 跨端连接 | 手机在非同局域网环境连接常驻 Mac | 能发起任务、收事件、返回既有会话 |
| 两种运行器 | 分别以 Codex、Claude Code 执行最小项目任务 | 目录、模型配置、结果与恢复能力明确 |
| Skill 继承 | 在两个运行器分别检测现有 Java、SSH、数据库、禅道和 Browser Skill | 真实调用记录；不能只展示文件存在 |
| 浏览器验收 | 启动本地服务、复现问题、截图并回传手机 | 明确页面、环境、登录态及结果 |
| 移动扩展页面 | 原型展示项目环境、Bug 列表和任务步骤 | 桌面和手机都可使用，非仅 Web 页面 |
| 任务持久化 | 断线、服务重启、重新进入任务 | 状态可恢复，已完成外部动作不重复 |
| Jenkins 版本关联 | 推送指定修改并触发实际 Job | 实际源码 SHA、构建编号和产物能对应 |
| 部署验证 | 部署产物到开发环境并复测 | 环境、实际运行版本、测试证据可对应 |
| 自动化边界 | 在允许范围内执行，在范围外观察实际限制 | 权限由实际工具通道支持，非仅提示词约束 |

验证中若只是业务对象和页面缺失，可以继续扩展；如果无法继承关键工具、无法在手机操作必要交互、不能可靠恢复任务或无法提供足够的执行边界，则考虑更换底座或完整自研。

## 6. 需要自建或明确适配的业务能力

1. **项目资源模型**：代码目录、多服务、命名环境、数据库、服务器、禅道、Jenkins 和凭据引用。
2. **任务阶段管理**：文档开发与 Bug 流程、复现结果分支、阶段依赖、等待、重试和完成标准。
3. **证据归集**：实际命令结果、截图、报告、代码版本和环境版本。
4. **禅道动作映射**：列表、详情、外部状态变化、未复现退回规则及完成后回写。
5. **交付关联**：commit、push、实际构建版本、产物、部署版本、部署后验证。
6. **资源和动作去重**：工作目录、浏览器、端口、发布互斥，以及断线后不重复触发外部动作。

这些能力的实现方式可以是插件、独立本机业务服务或候选项目的二次开发模块；是否必须修改底座源码，以验证结果决定。
