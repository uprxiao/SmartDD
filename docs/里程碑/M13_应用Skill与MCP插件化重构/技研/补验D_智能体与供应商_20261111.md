# 补验 D：智能体与供应商（需求补记 4、5 之后的补充研究）

日期：2026-11-11。依据：[需求 R0.3 补记 4、5](../需求.md)、[技术方案](技术方案.md)。用户 2026-11-11 同意做 R1–R6，并授权：用其 GPT 订阅跑少量 Codex 任务（R3）；用其提供的 SMG Key 做少量真实调用（R4、R5）。脚本与原始结果在 [实验/D_智能体与供应商_20261111](实验/D_智能体与供应商_20261111/)（含 `SHA256SUMS`）。

环境：macOS arm64；Claude Code 2.1.322、Codex 0.166.0，和 11-10 的技研版本相同，旧结论在版本上仍然有效。

## 边界与保护

- R1、R2 只用本机模拟服务器、隔离的 `CLAUDE_CONFIG_DIR`／`CODEX_HOME`、断网代理和诱饵值，零费用。没有对用户真实的 Claude 登录运行 `claude auth status`。
- R3 使用用户的默认 `CODEX_HOME`（这就是订阅智能体的产品设计），只用 `codex exec`、不打开交互界面，避免 Codex 往 `config.toml` 写入目录信任记录。运行前后逐字节比较了 `config.toml`、`auth.json`。归档结果里去掉了这两个文件的哈希值，只保留比较结论。
- R4、R5 的 Key 只经环境变量传给脚本；本机记录代理只记录“有没有带认证头”，不记录头的值；脚本输出前检查结果中不含 Key。Claude Code 的其他外连用断网代理挡住。
- R6 只读核对现有源码，没有运行。

## R1 Claude Code 怎么使用多个勾选的模型（零费用）

在 Claude Code 2.1.322 程序里找到一个设置项 `modelPicker`，官方说明是：“用自己的标签整理 `/model` 菜单：一个有序的模型列表，独立于内置模型阵容和 Claude Code 版本”。它只从托管设置、`--settings` 和用户设置读取，项目里的设置不生效。字段结构为：

- `modelPicker.options`：每行 `{ model, label?, description?, behavesAs? }`；
- `modelPicker.replaceBuiltInOptions`：为 true 时，“菜单只显示 Default 行和这些行，内置阵容、从网关发现的模型和 `ANTHROPIC_CUSTOM_MODEL_OPTION` 都隐藏”。

实测：模拟服务器加隔离配置目录，`--setting-sources user`，所有档位变量都设为 `m-default`，用伪终端打开真实界面。

| 编号 | 场景 | 结果 |
| --- | --- | --- |
| R1-1 | `replaceBuiltInOptions: true`，三行（带中文标签与说明） | 菜单只有“1. Default”和三行，标签与说明按设置显示；原生的 Fable、Opus 1M 等都不出现 |
| R1-2 | 不设 replace | 内置的 Opus／Fable／Sonnet／Haiku 四档也列出来（都显示 m-default），共 7 行，很乱 |
| R1-3 | 选“模型 C”后按 `s`（只对本次会话） | 下一次请求 `model=m-c`；`settings.json` 不变 |
| R1-4 | 选“模型 C”后按 Enter（设为默认） | **`settings.json` 写入 `"model": "m-c"`**（WillYou 管理的配置目录，不是用户的 `~/.claude`）；下一次请求 `m-c` |
| R1-5 | 选“Default”行后发消息 | 请求模型是 `m-default`，但**多带 `context-1m-2025-08-07` beta 头**（菜单上显示为 `m-default[1m]`） |
| R1-6 | 不碰菜单直接发消息 | 请求 `m-default`，**不带** `context-1m` |
| R1-7 | 所有请求的 beta 头 | 默认带 10 个（`claude-code`、`interleaved-thinking`、`context-management` 等），请求体带 `thinking`、13 个工具、`max_tokens` 32000；设 `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` 后只剩 3 个；程序里另有 `CLAUDE_CODE_DISABLE_1M_CONTEXT` |
| R1-8 | 行上加 `behavesAs: "claude-sonnet-4-5"` | 菜单提示该模型“不支持推理强度”，权限模式显示随之变化——`behavesAs` 会改变客户端对模型的处理方式，不能随便填 |
| R1-9 | 不认识的模型 | 程序里有提示“Claude Code 不认识这个模型，会假设一个上下文窗口并据此自动压缩”，可用 `behavesAs`、`CLAUDE_CODE_AUTO_COMPACT_WINDOW` 等调整；本次短会话里没有触发提示，**长会话的压缩表现未测** |

结论：

1. Claude Code 也能做到“菜单只列勾选的模型”：`modelPicker.options` 用勾选的模型、`replaceBuiltInOptions: true`。档位变量仍然都设为默认模型，所以后台请求用默认模型。
2. 菜单里那一行“Default”无法去掉；选中它会带 `context-1m` 头。建议同时设 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`（R4 已在 SMG 上带着这个变量跑通）。
3. 用户在菜单里按 Enter 会改写 WillYou 管理目录里的默认模型。启动时 WillYou 注入的 `ANTHROPIC_MODEL` 优先（11-10 实验 C1b），所以下一次启动仍以 WillYou 设置的默认模型为准。是否要把这个改动同步回智能体，待讨论。
4. 第三方模型的上下文窗口是 Claude Code 自己假设的；长会话的自动压缩是否合适，需要在正式开发时用长会话验证（列入风险）。

## R2 登录检测与环境变量冲突（零费用）

| 编号 | 场景（隔离目录、断网、诱饵值） | `claude auth status` |
| --- | --- | --- |
| R2-1 | 什么都不设 | 退出码 1，`loggedIn:false`、`authMethod:"none"`；约 0.2 秒 |
| R2-2 | `ANTHROPIC_API_KEY` | 退出码 0，`authMethod:"api_key"`；`--text` 显示“API key: ANTHROPIC_API_KEY” |
| R2-3 | `ANTHROPIC_AUTH_TOKEN` | 退出码 0，`authMethod:"oauth_token"` |
| R2-4 | `CLAUDE_CODE_OAUTH_TOKEN` | 退出码 0，`authMethod:"oauth_token"` |
| R2-5 | 配置里的 `apiKeyHelper` | 退出码 0，`authMethod:"api_key_helper"` |
| R2-6 | `ANTHROPIC_API_KEY`＋`ANTHROPIC_BASE_URL` | `api_key`，`--text` 另显示 base URL |
| R2-7 | 配置 `settings.json` 的 `env.ANTHROPIC_API_KEY` | `api_key` |

| 编号 | 场景 | `codex login status` |
| --- | --- | --- |
| R2-8 | 空 `CODEX_HOME` | 退出码 1，`Not logged in`（写在 stderr）；约 0.05 秒 |
| R2-9 | 只设 `OPENAI_API_KEY` 或 `CODEX_API_KEY` 环境变量 | 仍是 `Not logged in` |
| R2-10 | `codex login --with-api-key`（诱饵） | 退出码 0，`API key configured - decoy-r2***00000`（stderr，Key 脱敏）；`auth.json` 为 `auth_mode: "apikey"` |
| R2-11 | R2-10 之后再设另一个 `OPENAI_API_KEY` | 仍显示 auth.json 里的 Key |

已知（11-10 Codex 实验 E2b）：ChatGPT 订阅登录为 `Logged in using ChatGPT`。

结论：

1. **Codex 的订阅和 API 已经可以区分**：`Logged in using ChatGPT` 判为订阅，`API key configured` 判为 API，退出码 1 判为未登录。输出在 stderr。
2. **Claude Code**：`authMethod` 为 `api_key`、`api_key_helper`、`oauth_token` 时都来自环境变量或配置，判为 API。真实订阅（claude.ai 登录）和 Console 账号登录时的 `authMethod` 值仍未知，由用户后续单独测。
3. **检测必须和启动用同一套环境**：只要启动环境里有 `ANTHROPIC_API_KEY`，Claude Code 就判成 API，也会用它发请求。订阅/API 智能体启动时是继承还是清掉这些变量，待讨论（见文末）。
4. Codex 只设 `OPENAI_API_KEY` 环境变量时，状态显示“未登录”，但 `codex exec` 是否会用它，本次没有 Key、未验证。
5. 两个命令都很快、断网可用，适合在“启动任务前”检测。

## R5 “测试可用性”该怎么测（SMG Key）

原型里的测试：一次流式请求，强制调用一个工具，收到 `tool_use` 即判“可用”。与 R4 的 CLI 实际运行对比：

| 模型 | 原始测试 | CLI 实际运行 |
| --- | --- | --- |
| 6 个模型（pro、glm-5、kimi、qwen、MiniMax、GLM-4.7） | 可用（0.5–4 秒） | 可用 |
| deepseek-v4-flash-0731 | **不可用**（31 秒后 400） | **可用** |
| claude-haiku-5-5 | 不可用 | 不可用 |

诊断（`r5-diag.json`）：flash 的同一个“强制调用工具”请求，第一次 7 秒成功，紧接着第二次 31 秒后 400；改用 `tool_choice: auto` 或 `any` 也成功。pro 的所有写法都稳定成功。所以这次不一致是 **SMG 上游偶发失败**，不是参数问题。

结论：

1. 原始测试与 CLI 实际运行的判断基本一致，速度快 3–10 倍、费用低，可以继续作为“测试可用性”的方法。
2. **只测一次会把偶发失败误判成“不可用”**。建议：失败时自动重试一次；两次都失败才记“不可用”，并保留错误原文；“不可用”的模型仍可重测（原型已有）。
3. CLI 会带 thinking、10 个 beta 头、大量工具定义；某些网关可能只拒绝这些。建议测试请求带上与当前 CLI 版本相同的 beta 头和 `thinking` 参数，让结果更接近真实运行（SMG 都接受，这次没有出现差异）。
4. 本轮没有可用的 Responses 供应商（SMG 没有 Responses，用户没有 OpenAI Key，DeepSeek Key 需用户在测试实例里自己填），**Codex 一侧的“原始测试与 CLI 对比”未做**；11-10 经 Magpie 的数据（Codex 实验 M5）显示同样模式：只有 `claude-haiku-5-5` 上游拒绝。

## R6 插件调用时的任务与项目身份（只读源码）

核对 `src/main/core/applications/execution-context.ts`、`selection-service.ts`（M10／M11 的宿主桥接）：

| 需求 | 现有实现 | 结论 |
| --- | --- | --- |
| 每次调用知道来自哪个任务、项目 | Agent 调用经 `withAgent()` 生成执行上下文，带 `runId`、`taskId`、`projectId`，并用 `assertRun()` 校验运行仍然有效、任务与项目没有被替换 | **已具备** |
| 停用插件（全局或项目）后，运行中会话的调用立即被拒绝 | 每次调用都会计算 `policyStamp()`，其中 `requireApplicationEnabled(projectId, appId)` 在应用全局停用或项目关闭时直接报错；调用开始与结束时都检查 | **已具备**，提示文案需改成“插件已停用” |
| 切换连接时运行中任务继续用原连接 | 连接选择变化只增加连接或绑定的修订号，不影响 `policyStamp`；单次操作内的连接按开始时固定 | 与需求一致，正式开发时按新的“全局默认＋项目个性化”模型复核 |
| 插件更新后“下一次调用即用新版本，旧版即删”（松耦合） | 运行开始时把包按 `packageHash` 固定进运行快照（`snapshot.packages`），调用必须匹配快照里的哈希且包仍可信 | **不满足**：更新后运行中会话的调用会因旧包被删而失败。需要改成调用时按 `appId` 解析当前启用的版本，再按能力名（含 `legacyToolNames`）匹配；新版本新增的能力在会话重启前不可见，删除的能力调用时返回明确错误 |

结论：任务与项目身份、停用即拒绝已经具备；“按版本固定”与松耦合规则冲突，需要列入 P1 门槛和正式开发改造。
