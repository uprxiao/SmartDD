# 补验 E：智能体权限（2026-11-11）

来源：用户 2026-11-11 提出“各个智能体的权限”，参照 Codex 首页的权限选择（需求池 F31，[需求补记 8](../需求.md)）。本记录只写调研事实与供讨论的建议，规则由用户决定后再写入需求。实验脚本与原始结果见 [实验/E_智能体权限_20261111](实验/E_智能体权限_20261111/)（哈希见 `SHA256SUMS`）。

环境：macOS arm64；Claude Code 2.1.322；Codex 0.166.0（E2、E3），0.167.1（E4 的 `/permissions` 菜单及 E5、E6，原因见“事故”一节）。用户 2026-11-11 要求“实跑、充分验证”后补做 E5–E7；同日用户确认补测未覆盖项，补做 E8–E12（Claude 第三方真实模型经用户 `cw` 账户的 zenmux 网关，Codex 只读用用户 GPT 订阅）。

## 结论摘要

1. **两个 CLI 都有现成的档位，可以直接映射**：Codex 的 `/permissions` 菜单就是 Codex 桌面版的四档（请求批准、帮我批准、完全访问，再加只读；桌面版的第四项是“自定义 config.toml”）。Claude Code 有 `--permission-mode` 六种模式。
2. **Codex 的“请求批准”必须同时指定由用户审批**：用户本机 `~/.codex/config.toml` 设了 `approvals_reviewer = "auto_review"`，只传 `-a on-request` 时仍由自动审查代批。WillYou 选“请求批准”时须加 `-c approvals_reviewer="user"`（E3 实测）。
3. **Claude Code 的 `auto`（自动判断风险）在第三方供应商下不能完整工作**：项目内的编辑和命令可以直接执行，但需要服务端安全检查的操作在非交互下一律被拒绝（E1、E10）；交互界面先弹提示，用户选“留在 auto”后改为逐个批准（E11）。真实网关 zenmux 也不转发这项检查（E10）。订阅登录下是否可用，待用户测 Claude 订阅时一并核实。
4. **会话中都能切换**：Claude Code 按 Shift+Tab 循环切换，Codex 输入 `/permissions` 选择。WillYou 只能在启动时指定，运行中的切换发生在 CLI 内部，WillYou 读不到（E4）。
5. **完全访问已实跑通过**（E5）：Codex `--dangerously-bypass-approvals-and-sandbox` 与 `-s danger-full-access` 用用户订阅在 exec 和交互界面各跑一遍，项目外写入、联网都直接执行、不弹批准框。首次尝试被本机安全检查拦下，用户明确要求后实跑。Claude Code `bypassPermissions` 在非交互与交互界面都验证过（E1、E7）。
6. **结论：可以做，和供应商基本无关**。权限判断都在 CLI 本机完成；唯一与供应商有关的是“帮我批准”：Codex 的自动审查把审查请求发给**同一个供应商**，第三方供应商也能用，审查失败一律不执行（E6）；Claude 的 auto 依赖 Anthropic 服务端检查，第三方供应商下不完整（E1）。
7. **Codex 的“只读”也必须指定由用户审批**：只传 `-s read-only` 时，模型请求提权会被用户配置里的自动审查批准，项目外写入和联网照样执行（E12）；WillYou 选“只读”时须同时传 `-a on-request -c approvals_reviewer="user"`。

## E1 Claude Code 各模式的放行范围

方法：本机模拟 Anthropic 服务按顺序返回三个工具调用（Write 写项目内文件 → Bash 在项目内写文件 → Write 写项目外文件）；`claude -p --permission-prompts none`，凡是交互时会询问的操作都自动拒绝，所以“被拒绝”就是“交互时会询问”。隔离配置目录、断网代理，零费用（[e1m-claude.py](实验/E_智能体权限_20261111/e1m-claude.py)、[结果](实验/E_智能体权限_20261111/e1-result.json)）。

| 模式（`--permission-mode`） | 写项目内文件 | 项目内命令 | 写项目外文件 | 说明 |
| --- | --- | --- | --- | --- |
| `default`（2.1.322 帮助里叫 `manual`，`default` 仍可用） | 询问 | 询问 | 询问 | 每次都问 |
| `acceptEdits` | 直接执行 | 直接执行 | 询问 | 本例的 `echo … >` 写项目内文件被当作编辑放行；其他命令是否都放行未逐类测试 |
| `auto` | 直接执行 | 直接执行 | **拒绝** | 第三方供应商下服务端安全检查不可用，提示“Auto mode is unavailable: its safety check does not run for this session”，需要检查的操作都拒绝 |
| `plan` | 询问 | 询问 | 询问 | 只做计划，不执行写操作 |
| `dontAsk` | 拒绝 | 拒绝 | 拒绝 | 没有预先允许的都拒绝，不询问 |
| `bypassPermissions` | 直接执行 | 直接执行 | 直接执行 | `-p` 下不需要额外参数即可生效；交互启动时先弹“Bypass Permissions mode”警告，需用户选 “Yes, I accept”（E4） |

首次尝试经 SMG 实跑时，SMG 返回 401“Key 无效、过期或已停用”，没有反复重试，改用模拟服务（[记录](实验/E_智能体权限_20261111/e1-smg-attempt-401.txt)）。

## E4 会话中切换

- **Claude Code**（隔离配置、断网，不发请求）：启动 `--permission-mode default` 后按 Shift+Tab，底部依次显示 accept edits on → plan mode on → auto mode on → manual mode on，循环。带 `--allow-dangerously-skip-permissions` 启动时先出现 Bypass 警告框（未继续）。
- **Codex 0.167.1**：输入 `/permissions` 回车，菜单为“1. Ask for approval（读写工作区并运行命令，联网或编辑工作区外需批准）／2. Approve for me（只对检测到可能不安全的操作询问）／3. Full Access（可编辑工作区外文件、联网，无需批准）／4. Read Only（只读，编辑或联网需批准）”。本次以 `-a on-request` 启动，菜单仍把 “Approve for me” 标为当前，同 E3 的原因。未选择任何项，前后哈希不变（[结果](实验/E_智能体权限_20261111/e4-result-codex-0.167.1.json)）。
- WillYou 的终端就是 CLI 自己的界面：启动时由 WillYou 传参数，运行中用户在 CLI 里切换，WillYou 读不到，也不应假装同步。

## E6 Codex 接第三方供应商（模拟）时各档的行为

方法：隔离 `CODEX_HOME`，本机模拟 OpenAI Responses 供应商（[mockresp.py](实验/E_智能体权限_20261111/mockresp.py)），模拟模型按顺序调用 `exec_command`：①项目内写 ②项目外写 ③项目外写并请求提权（`sandbox_permissions: "require_escalated"`）④联网并请求提权 ⑤直接联网（[e6-run.py](实验/E_智能体权限_20261111/e6-run.py)，[结果](实验/E_智能体权限_20261111/e6/)）。零费用、可重复。exec 下默认审批策略为“从不询问”。

| 参数 | ①项目内 | ②项目外 | ③提权写项目外 | ④提权联网 | ⑤直接联网 |
| --- | --- | --- | --- | --- | --- |
| `-s workspace-write` | 成功 | 沙箱拒绝 | 拒绝（不询问策略） | 拒绝 | 失败 |
| `-s read-only` | 沙箱拒绝 | 沙箱拒绝 | 拒绝 | 拒绝 | 失败 |
| `--approve-for-me`，审查回“允许” | 成功 | 沙箱拒绝 | **审查后执行** | **审查后执行（200）** | 失败 |
| `--approve-for-me`，审查回“拒绝” | 成功 | 沙箱拒绝 | 拒绝（“unacceptable risk”） | 拒绝 | 失败 |
| `--approve-for-me`，审查请求返回 500 | 成功 | 沙箱拒绝 | 重试约 12 次后拒绝（“review failure”） | 同左 | 失败 |
| `--approve-for-me`，审查回复不是 JSON | 成功 | 沙箱拒绝 | 重试 3 次后拒绝 | 同左 | 失败 |
| `-s danger-full-access` | 成功 | 成功 | 拒绝（无需提权） | 拒绝 | 200 |
| `--dangerously-bypass-approvals-and-sandbox` | 成功 | 成功 | 拒绝（无需提权） | 拒绝 | 200 |

- **自动审查走同一个供应商**：审查请求带 3 个只读工具（`exec_command`、`write_stdin`、`view_image`），开发者消息为 “You are judging one planned coding-agent action…”，输入里以 `>>> APPROVAL REQUEST START/END` 包住待审操作，要求最终回复严格 JSON（低风险 `{"outcome":"allow"}`，否则含 `risk_level`、`user_authorization`、`outcome`、`rationale`）。样例见 [guardian-request-样例.json](实验/E_智能体权限_20261111/e6/guardian-request-样例.json)。
- 所以第三方供应商下“帮我批准”能用，但审查质量取决于该供应商的模型能否按要求回 JSON；回不好时操作被拒、不放行，用户看到的是“审查失败”。
- 驱动错误（保留）：attempt1 按工具名区分审查请求，审查请求同样带 `exec_command`，被当成主线程（[记录](实验/E_智能体权限_20261111/e6/attempt1-审查请求识别错误/)）；attempt2 各组结果写入同一文件互相覆盖（[记录](实验/E_智能体权限_20261111/e6/attempt2-结果被覆盖/)）。上表为修正后的 final。

## E7 Claude Code 交互界面

方法：模拟 Anthropic 服务按顺序请求 Write 项目内文件、Write 项目外文件；出现询问框时按 Esc（[e7-claude-tui.py](实验/E_智能体权限_20261111/e7-claude-tui.py)，[结果](实验/E_智能体权限_20261111/e7/e7-result.json)）。

| 模式 | 表现 |
| --- | --- |
| `default` | 第一步弹询问框：“1. Yes／2. Yes, and switch to accept edits (auto-approve file edits and common file commands) for this session (shift+tab)／3. No”；按 Esc 后本轮中止 |
| `acceptEdits` | 项目内直接写；项目外弹同样的询问框 |
| `auto` | 项目内直接写；项目外弹出 “Auto mode can't check actions in this session” 提示（安全检查在服务端，经第三方网关无法到达），给出三个选择：Enter 留在 auto，需要检查的操作逐个由用户批准；Shift+Tab 切到 accept edits；Esc 取消。**当前这一轮立即停止，等待中的操作不执行**，文件未写出（复核见下） |
| `bypassPermissions` | 启动先弹 “Bypass Permissions mode” 警告，选 “Yes, I accept” 后两步都直接执行；该配置目录的 `settings.json` 写入 `skipDangerousModePermissionPrompt: true`，**第二次启动不再弹警告** |

- `auto` 复核：首轮结果里看到的“写入内容预览”只是工具调用的显示。复核时记录了模拟服务收到的全部请求：只有主线程的两次请求，没有额外的安全检查请求。完整画面中出现上述提示，随后显示 “User rejected write …”，本轮结束。驱动在这次复核中没有按任何键（events 为空），说明是 CLI 自己停止了本轮，不是驱动按了 Esc。结论与非交互（E1）一致：第三方下需要检查的操作不会自动执行；区别是交互界面会提示用户改为逐个批准或切换模式（[复核1](实验/E_智能体权限_20261111/e7/auto-复核/e7-auto-recheck.json)、[复核2 完整画面](实验/E_智能体权限_20261111/e7/auto-复核/e7-auto-recheck2.json)）。“Enter 留在 auto 后逐个批准”这条路径没有按键实测。
- **更正（同日，E11 后追加）**：上一条“CLI 自己停止了本轮”说得过宽。E11 实测：按 Enter 留在 auto 后，被挂起的那个操作立刻改为逐个批准框，并且默认选中 No。E7 复核时驱动没有按键，但收尾时连发了 Ctrl-C；画面里的 “User rejected write” 更可能是收尾时取消了挂起的操作，不能证明是 CLI 自己拒绝的。以 E11 为准。
- 影响：WillYou 为第三方运行生成的独立配置目录若要用完全访问，第一次会在终端里看到这个警告并需要用户确认；之后记住。是否由 WillYou 预先写入这项，需用户决定（属于替用户确认风险）。

| `-s read-only`（隔离配置，无自动审查） | 沙箱拒绝 | 沙箱拒绝 | 弹框，Esc 后整轮停止 | 未到达 | 批准框 |

- 交互界面与 exec（E6）结论一致：第三方供应商下“帮我批准”能用，审查请求走同一供应商。
- 交互界面的批准框里 Esc 对应 “No, and tell Codex what to do differently”，会停下整轮而不是只跳过这一步。
- 交互界面还会发出不带 `exec_command` 工具的旁路请求。attempt1 把它算进步骤，导致步骤错位（[记录](实验/E_智能体权限_20261111/e9/attempt1-旁路请求混入/)）；attempt2 的驱动没有认出第二个批准框，这个框被收尾时的 Ctrl-C 取消（[记录](实验/E_智能体权限_20261111/e9/attempt2-第二个批准框未识别/)）。上表为修正后的结果。

## E10 Claude Code 接 zenmux 真实模型，非交互

方法：用户 `cw` 账户（`claude_with_account work`，zenmux 网关、Sonnet）。只借用它设置的环境变量，不经过 `ce`，因为 `ce` 在信任目录下会自动加 `--dangerously-skip-permissions`。隔离 `CLAUDE_CONFIG_DIR`，Key 只在子进程环境里传递；归档前扫描过，证据里没有 Key 及其片段。提示词要求依次：Write 项目内 → Bash 写项目内 → Write 项目外（[e10-claude-real.py](实验/E_智能体权限_20261111/e10-claude-real.py)，[结果](实验/E_智能体权限_20261111/e10/e10-result.json)）。四档合计约 0.12 美元。

| 模式 | 项目内 Write | 项目内 Bash | 项目外 Write | 退出码 |
| --- | --- | --- | --- | --- |
| `default` | 询问（拒绝） | 询问（拒绝） | 询问（拒绝） | 0 |
| `acceptEdits` | 执行 | 执行 | 询问（拒绝） | 0 |

## E11 Claude Code 接 zenmux 真实模型，交互界面

方法：同 E10 的环境，伪终端驱动交互界面，提示词要求 Write 项目内 → Write 项目外。普通询问框按 Esc；auto 的提示框按 Enter 留在 auto，之后的逐个批准框分别测 Esc 和 Yes（[e11-claude-tui-real.py](实验/E_智能体权限_20261111/e11-claude-tui-real.py)，[结果与画面](实验/E_智能体权限_20261111/e11/)）。

| 模式 | 表现 |
| --- | --- |
| `default` | 第一步弹询问框，Esc 后本轮停止，两个文件都没写出 |
| `acceptEdits` | 项目内直接写；项目外弹框：“Do you want to create outside.txt? 1. Yes／2. Yes, and always allow access to <目录> for this session (shift+tab)／3. No”，Esc 后未写出 |
| `auto`，留在 auto 后选 Yes | 项目内直接写；项目外先弹 “Auto mode can't check actions in this session” 提示框，按 Enter 留在 auto 后，**被挂起的操作立刻改为逐个批准框**：“Auto mode can't check actions in this session, so this one needs your approval / Do you want to create outside.txt? ❯ No / Yes”，**默认选中 No**；选 Yes 后写出 |
| `auto`，留在 auto 后选 Esc | 逐个批准框按 Esc 后未写出，本轮结束；再发一句“继续”，同一操作直接弹逐个批准框，不再出现最初的提示框 |

## 与现有设计的关系

- 技术方案 §3.1 已采用：第三方 Claude 运行用 `--permission-mode default`（直接询问）。若引入档位，这一条改为“按所选档位传参”，默认档位仍是询问。
- 生产代码 `src/main/core/applications/codex-effective-sandbox.ts` 已识别 `--approve-for-me`、`--full-auto`、`--dangerously-bypass-approvals-and-sandbox` 等参数，并只在 Codex 0.166.0 上核验浏览器 CLI 的临时沙箱；**档位参数与这套沙箱合并的方式需要正式开发时核对**（例如完全访问时没有沙箱可扩展）。
- WillYou 插件的写操作审批（宿主审批）与 CLI 权限是两层：CLI 档位只决定 CLI 内置工具（文件、命令、联网）是否询问；插件写操作仍按插件规则由宿主审批，不因选“完全访问”而跳过。（原为建议；用户 2026-11-11 在需求 R1.0 核对时决定照此执行。）

## 事故：误触 Codex 自动更新

- **经过**：E4 第一次运行 Codex 时，Codex 0.166.0 启动先弹出“Update available · 0.166.0 → 0.167.1”，驱动原本给“信任目录”准备的回车选中了 “1. Update now”，开始执行 `npm install -g @openai/codex`；随后驱动的 Ctrl-C 打断了安装：包已换成 0.167.1，但 `~/.local/bin/codex` 链接没建、平台包不完整，新终端找不到 `codex` 命令。已在运行的 Codex 会话不受影响。
