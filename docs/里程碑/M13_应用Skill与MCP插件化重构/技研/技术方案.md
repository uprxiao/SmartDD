## 3. AI 配置（R04–R06）

### 3.1 启动注入（按次，不写全局）

| | Codex | Claude Code |
| --- | --- | --- |
| 原生登录 | 默认 `CODEX_HOME`，不注入 Provider | 用户 `~/.claude`（默认配置目录） |
| 第三方 Provider | 默认 `CODEX_HOME`＋`-c model_provider="willyou_<id>"`、`-c model_providers.willyou_<id>={base_url,wire_api="responses",env_key}`、`-c model_catalog_json=<WillYou 目录文件>`、`-m <模型>`；**另加 `--disable plugins` 与 `-c analytics.enabled=false`**（消除 chatgpt.com／github.com 后台连接） | **WillYou 管理的独立 `CLAUDE_CONFIG_DIR`（每个 RunConfig 一个）**；`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN` 或 `ANTHROPIC_API_KEY`（依 Provider 认证类型其一）、`ANTHROPIC_MODEL` 与全部档位（OPUS／SONNET／HAIKU／FABLE、SMALL_FAST、SUBAGENT）映射到该 Provider 允许的模型；**`--setting-sources user`**（只读 WillYou 管理目录的 `settings.json`）＋`--add-dir <项目>`＋`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`（找回项目 `CLAUDE.md`）；`--strict-mcp-config`；`--permission-mode default` |
| 密钥 | 只经进程环境（`env_key`），不进 argv、不落盘 | 同左 |

- **继承变量清除**：Claude 清除 `ANTHROPIC_*`、`CLAUDE_CODE_OAUTH_TOKEN`、`CLAUDE_CODE_USE_BEDROCK／VERTEX／FOUNDRY` 等云端切换变量后再注入；Codex 清除 `OPENAI_API_KEY` 等与所选 Provider 无关的认证变量。修改 `ISOLATED_ENV_PREFIXES` 为“前缀＋精确名单”。
- **独立配置目录由 WillYou 生成并校验**：启动前校验 `settings.json` 无 env 认证项、无 `apiKeyHelper`；为任务项目写入信任（交互模式下 `headersHelper` 需要）；发现异常拒绝启动并提示。
- **项目／本地设置不参与第三方运行（审核二 F01）**：Claude 设置来源中，项目设置的 `env` 覆盖进程环境、命令行 `--settings` 覆盖项目设置（补验 B1 R0／R4 实测；本地与其余层级按 CLI 说明）；项目或本地 `.claude/settings*.json` 的 `env` 可改写 `ANTHROPIC_BASE_URL`／认证变量，实测只改地址就把注入的 Key 发往其他端点。因此第三方运行用 `--setting-sources user` 只加载 WillYou 校验过的用户来源（补验 B1：项目／本地改地址、改 Key、`apiKeyHelper` 均无效，Key 只到所选端点）。对照：仅用 `--settings` 固定地址时，项目 Key 仍以 `Authorization` 与宿主 Key 同时发出，且 `HTTPS_PROXY`、自定义请求头等可改流量的变量是开放集合，不采用。代价：项目 `CLAUDE.md` 改经 `--add-dir` 找回（已实测）；项目 `.claude/skills` 不再自动加载，改由 §4.2 按次投影；项目 `.mcp.json` 由 §4.3 纳管后注入（配合 `--strict-mcp-config`）；项目设置中的权限规则与钩子不生效（用户 2026-11-10 确认可接受）。原生登录运行不受影响。
- **Provider 缺认证**：启动前拒绝，不交给 CLI。
- **Claude 权限模式（已采用）**：第三方 Provider 下服务端 auto mode 分类器不可用，每次操作都会先弹说明再确认（默认 No）；采用 `--permission-mode default`（直接询问、默认 Yes），第二轮审核同意。仍是询问，不等于预先批准；逐工具限制与用户批准策略照常注入。
- **Codex `--disable plugins` 的代价（审核二 F09）**：第三方运行中 Codex 原生插件（含其自带 Skill／MCP）不可用；WillYou 在运行配置与能力页标示“第三方 Provider 下 Codex 原生插件不可用”，用户需要的插件自带 Skill／MCP 可经 §4 发现后按来源纳管投影，不静默消失。

### 3.2 Provider 一键接入

1. 预设：Magpie（`http://127.0.0.1:3425/v1`，令牌 `magpie-codex`／`magpie-claude`，Codex 目录取 `/v1/codex/models`）、DeepSeek（`https://api.deepseek.com/`，Responses 与 `/anthropic`，Codex 目录用内置官方条目）。
2. 自定义“地址＋Key”：`GET {base}/models`→`{base}/v1/models`；空请求探测 `/responses`（Codex）与 `/anthropic/v1/messages`、`/v1/messages`（Claude）。探测结果只作**候选协议**：结构化错误体（如 Anthropic `type:error`、OpenAI `error.type`）配合 422／400 标“候选支持”，404 标“候选不支持”，401 标“Key 可能无效”，403 等其他状态只提示原文；最终兼容以第 5 步的最小流式＋工具调用为准（审核二 F08）。空请求在 DeepSeek 实测未形成模型调用，不推广为任意服务不计费的保证。
3. 失败：401→“Key 无效”；超时／连接失败→“服务不可达”；空列表或 404→允许手填模型 ID。
4. Codex 目录生成：预设用来源目录；其余以内置模板＋`/models` 元数据（名称、上下文、模态、推理档位）覆盖生成；缺字段用模板默认并可在高级设置调整。
5. 接入后自动生成可用组合的 RunConfig（如 Codex·DeepSeek、Claude Code·DeepSeek），提供逐模型“测试可用性”（一次最小工具调用）。
6. 刷新：每次启动任务前随可达性预检比对并刷新目录（默认模型已下线时提示改选），另有手动“刷新模型”。

### 3.3 运行中失败

Codex 服务不可达会无限重连，Claude 失效 Key 会长时间重试；WillYou 监测运行中连续失败（CLI 输出与原生会话记录），提示“服务异常，是否中断／切换配置”，不自动重放写操作。

### 3.4 恢复与全局模型变化提醒

- 恢复模型：Claude 取最后一条非 `isSidechain`、非 `isApiErrorMessage` 的 assistant 记录顶层 `requestedModel`，无则取最后非 sidechain 的 `attachment.identity.modelId`（不在全文中搜字符串；解析器与真实生成的最小夹具见补验 B7）；Codex 取最后 `turn_context.model`；以 `--model`／`-m` 显式传入，并重新注入同一 Provider 稳定 ID。原生会话 ID 与 TaskSnapshot 绑定，不按最新文件猜测。
- Codex `/model` 回车写全局：启动前用 TOML 解析器（沿用项目依赖 `smol-toml`）**只读**记录顶层 `model`、`model_reasoning_effort` 的存在性与值；会话结束后再次只读解析，若有变化则提醒“原来是 X，现在是 Y”，提供可复制的还原方法与打开配置文件入口，由用户自行修改；解析失败只提示“无法读取”。**WillYou 不写回全局配置**（第四轮审核 H01／H02：自动写回无法防止已打开文件句柄的并发写入丢失，挪走式替换中断会使配置持续缺失；用户决定采用提醒方案）。补验 B4／C2 的写回算法仅保留为实验记录，不进入实现。

### 3.5 旧配置迁移

按变量名与选项名分类：Claude “`BASE_URL`＋单一认证变量＋已知模型映射／已知高级变量＋无未知参数”→ Anthropic Provider＋RunConfig；无 env 与参数→原生登录；Codex 无 env 且仅已知选项→原生登录（选项保留为高级参数）；其余整体保留为高级 RunConfig。保留原配置 ID 与任务引用，凭据引用不改写，迁移版本号保证幂等，失败不改动原记录。本机 4 个配置试运行均可拆分。

## 4. 能力统一管理（R03）

### 4.1 发现与纳管

发现时机：任务／终端会话结束、进入能力页、手动重新扫描；静态读取，不启动 MCP 或脚本。新发现项经用户确认一键纳管，可开“以后自动纳管”；冲突始终交用户。纳管记录写在目标根目录的 `.willyou-managed.json`（不写入源目录）；再次扫描时以记录＋链接真实路径识别本方产物，不重复纳管；悬空链接自动清理。

### 4.2 Skill 落点（符号链接指向来源原件，单向跟随）

| 目标 | 落点 |
| --- | --- |
| Claude，第三方 Provider，用户级来源 | `$CLAUDE_CONFIG_DIR/skills/<名>`（同一 RunConfig 的各项目共用） |
| Claude，第三方 Provider，项目级来源（含任务项目自身 `.claude/skills`） | 每个任务本次运行的 `--plugin-dir`（`<WillYou 数据>/runs/<任务>/willyou-run/skills/` 内链接），名称带 `willyou-run:` 命名空间 |
| Claude，原生登录（用户 `~/.claude`） | 本次会话 `--plugin-dir`（WillYou 生成的 `willyou-run` 插件，`skills/` 内链接），不写用户目录，名称带 `willyou-run:` 命名空间 |
| Codex，用户级来源 | `~/.agents/skills/<名>` |
| Codex，项目级来源 | `<项目>/.agents/skills/<名>`（有条件采用，见下）；不得落到用户级目录 |

- **作用域（审核二 F02，补验 B1 S1–S3）**：项目级能力只投影到该任务本次运行的插件目录，不进共用根；同一 RunConfig 两个项目并发时各自只看到“用户级＋本项目”Skill，取消纳管后下一次运行即消失。不在共用目录里启动前轮换链接。
- **Codex 项目落点条件（审核二 F09）**：以 `git rev-parse --git-path info/exclude` 取得真实 exclude 路径（兼容 worktree／submodule），只追加本方生成的具体链接路径；目标路径已存在（用户文件或已跟踪文件）即标冲突、不覆盖；纳管记录写明所有权，取消纳管只删除仍指向本方来源的链接并移除对应 exclude 行；非 Git 项目照常工作但提示会出现在项目目录。exclude 只影响 Git 显示，不提供隔离：同项目中其他终端里的 Codex 同样会加载这些 Skill，界面如实说明。
- Codex 不支持按次加入 Skill 路径且同名项并列显示：链接前检查其全部加载根目录，有同名即标冲突。插件自带 Skill 随插件管理，不独立同步。M11 统一 Skill 库（标准 Skill）继续按现有方式交付，本方案只新增外部来源的纳管。

### 4.3 MCP 转换与注入

1. 源配置解析为中间表示（字面量／模板）；Claude 源 `${X}`、`${X:-d}` 为引用，Codex 源 `${…}` 为字面量，`env_vars`／`bearer_token_env_var`／`env_http_headers` 为引用。
2. 启动时按源语义**以服务器为单位**求值：先整台求值、全部成功后才分配私有槽并生成；任一必需变量缺失（无默认）、command 含 `${`、URL 不合规（第 4 项）→ 整台不生成并标原因，已分配的槽一并回滚，其他服务器照常（审核二 F04，补验 B3）。
3. stdio：统一经 WillYou 启动包装（随 App 分发的 `wy-mcp-launch.sh`，现行为 v3，[脚本](实验/C_审核三修正_20261110/wy-mcp-launch.sh)）。**生成器**：每台服务器的值放入本服务器私有槽 `WY_MCPV_<服务器序号>_<n>`（Codex 侧列入 `env_vars`）；MCP 自有环境变量用 `--set <变量>=<槽>`；模板参数和含 `$` 的字面参数（Claude 会展开 mcp-config 中的 `${}`）放槽并用 `--arg <位置>=<槽>` 指明替换位置，其余字面参数原样写在命令之后；附加 `--unset` 本次注入的模型凭据与 WillYou 内部令牌、`--unset-prefix WY_MCPV_`，需要时 `--cwd`。**包装器**：控制信息只从 `--` 之前的选项读取，命令之后的参数一律当数据原样传递、不识别任何标记；`--set`／`--arg` 的来源只允许 `WY_MCPV_` 槽，缺失退出 65、非法名称／越界退出 64；执行顺序固定为 ①读取槽值（按位置替换参数、暂存 `--set` 来源）→ ②清除继承凭据与全部私有槽 → ③注入该 MCP 自有变量 → `--cwd` → exec。因此 MCP 自有变量与模型变量同名时保留自有值，来源参数即使形似控制标记也读不到其他 MCP 的值（依据补验 B2、C1）。
4. http：Codex `env_http_headers`；Claude `headers:{h:"${WY_MCPV_n}"}`，值含字面 `${` 时用 `headersHelper`（Claude 会对槽值再次展开，必须走 helper；补验 B6 旧红／新绿）。**URL 不承载凭据（需求补记，用户决定）**：含用户名／密码、疑似凭据的查询参数（如 `token`、`api_key`、`access_token`、`secret`、`sig`）或片段参数、或含变量引用的 URL，标“不支持转换：URL 含凭据”，整台不生成，提示改用请求头／环境变量鉴权；合规 URL 原样写入。
5. 注入：Claude `--mcp-config <0600 文件>`，Codex `-c mcp_servers.<名>={…}`；均不写目标全局配置；生成后自校验字段名（Codex 静默忽略未知字段）。
6. 审批：默认不预先批准（TUI 询问，非交互拒绝且零执行）；来源已允许或纳管页开启“自动批准”→ Codex `tools.<工具>.approval_mode="approve"`，Claude `--allowedTools mcp__<服务器>__<工具>`；来源禁用→ Codex `disabled_tools`，Claude `--disallowedTools`。
7. 不迁移：命令位于其他应用包内、依赖宿主专用变量、已停用、SSE→Codex、需 OAuth 的远程服务（标“需在目标 CLI 单独认证”）。

## 5. 插件（R01、R02）

- 包格式 `willyou-plugin/v0-draft2`：`.willyou-plugin/plugin.json`（身份、版本、`hostApi`、图标浅深、权限、providers、projectPolicy、capabilities＋Schema、共享 Schema、legacyToolNames、runtime、skills、ui）＋`schemas/`、`runtime/`、`skills/`、`assets/`。示例见 [demo-tracker](实验/插件协议_20261110/demo-tracker/) 与 [禅道](实验/A5_插件声明_20261110/zentao-plugin/)。
- 运行：独立子进程（Electron `ELECTRON_RUN_AS_NODE`），stdio JSON-RPC（`initialize`／`verify`／`execute`）；宿主保留授权、Schema 校验、审批、账本、超时与重启；插件只收到本次绑定连接的配置与凭据；环境仅白名单。
- 隔离：沙箱禁止读写 WillYou 数据目录与密钥，插件包只读、私有数据目录可写、可联网；沙箱不可用则拒绝启动。用户其他文件依赖安装确认。
- 界面：声明式列表／详情／资源／动作，宿主通用渲染；安装时做界面语义校验（字段路径按能力 Schema 解析，模板仅允许 `tab`／`row`／`value`／`connection` 作用域）。
- 安装、版本、停用、卸载、禅道迁移：见 [A5 生命周期与数据设计](补验A5_插件声明与设计_20261110.md#生命周期与数据设计供技术方案采用)。
- 需拆除的宿主硬依赖：编译期模块元组与生成的 appId／连接配置类型、`retained` 服务后门、禅道业务表归属、渲染层禅道面板映射与 `appId` 分支、禅道专用 RPC。邮件、浏览器维持内置路径。

## 6. 开发顺序与门槛
