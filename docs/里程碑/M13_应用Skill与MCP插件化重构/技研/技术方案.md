## 3. AI 配置（R04–R06）

实现核验（2026-11-12）：当前原生Codex0.167.1加载自定义`model_catalog_json`时，除`model_providers.<id>.name`不可为空，还会验证每个模型必须提供`base_instructions`或`model_messages.instructions_template`，仅依据ModelInfo可选字段生成目录不足。生产生成器使用WillYou自有的通用代码助手指令，不采纳模型列表返回的任意指令模板；实际隔离app-server已读取准确勾选集合并正常退出。此结果只验证目录加载，后续必须验证真实工具调用及会话切换／恢复，不代表模型行为已经通过。原失败和当前证据见[Provider服务批次](../验收/证据/M13-AI-provider-20261112-a1/environment.json)。

### 3.1 启动注入（按次，不写全局）

| | Codex | Claude Code |
| --- | --- | --- |
| 订阅/API（CLI 自身登录） | 默认 `CODEX_HOME`，不注入 Provider | 用户 `~/.claude`（默认配置目录） |
| 第三方 Provider | 默认 `CODEX_HOME`＋`-c model_provider="willyou_<id>"`、`-c model_providers.willyou_<id>={base_url,wire_api="responses",env_key}`、`-c model_catalog_json=<WillYou 目录文件>`、`-m <模型>`；**另加 `--disable plugins` 与 `-c analytics.enabled=false`**（用于关闭已知插件同步和统计；当前原生版本仍观察到公告请求，零外连要求 T056 尚未通过） | **WillYou 管理的独立 `CLAUDE_CONFIG_DIR`（每个 RunConfig 一个）**；`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN` 或 `ANTHROPIC_API_KEY`（依 Provider 认证类型其一）、`ANTHROPIC_MODEL` 与全部档位（OPUS／SONNET／HAIKU／FABLE、SMALL_FAST、SUBAGENT）映射到该 Provider 允许的模型；**`--setting-sources user`**（只读 WillYou 管理目录的 `settings.json`）＋`--add-dir <项目>`＋`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`（找回项目 `CLAUDE.md`）；`--strict-mcp-config`；`--permission-mode` 按所选权限档位（§3.8，默认 `default`） |
| 密钥 | 只经进程环境（`env_key`），不进 argv、不落盘 | 同左 |

- **受管 Claude 后台流量（2026-11-13 实现复验）**：第三方 Provider 的按次环境注入 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` 与 `CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL=1`，后者关闭官方市场首次自动安装；不改变原生登录分支，不关闭显式 WillYou 插件／Skill 投影。原未设市场开关的真实运行虽已有 essential/updater 开关，仍有 CDN 请求；App036 原六认证分支全生命周期未观察到外连，详见[原红及修正复验](../验收/证据/M13-T060-six-branch-I-20261113-a1/coordinator-verdict.json)。[显式插件／Skill 独立真实CLI回归](../验收/证据/M13-App036-explicit-Skill-I-20261113-a1/coordinator-verdict.json)已通过：项目纳管Skill经生产`--plugin-dir`激活成功，标准库可并存；未执行诊断脚本，不代替整条标准Skill或 App A。
- **继承变量清除**：Claude 清除 `ANTHROPIC_*`、`CLAUDE_CODE_OAUTH_TOKEN`、`CLAUDE_CODE_USE_BEDROCK／VERTEX／FOUNDRY` 等云端切换变量后再注入；Codex 清除 `OPENAI_API_KEY` 等与所选 Provider 无关的认证变量。修改 `ISOLATED_ENV_PREFIXES` 为“前缀＋精确名单”。
- **独立配置目录由 WillYou 生成并校验**：启动前校验 `settings.json` 无 env 认证项、无 `apiKeyHelper`；为任务项目写入信任（交互模式下 `headersHelper` 需要）；发现异常拒绝启动并提示。
- **项目／本地设置不参与第三方运行（审核二 F01）**：Claude 设置来源中，项目设置的 `env` 覆盖进程环境、命令行 `--settings` 覆盖项目设置（补验 B1 R0／R4 实测；本地与其余层级按 CLI 说明）；项目或本地 `.claude/settings*.json` 的 `env` 可改写 `ANTHROPIC_BASE_URL`／认证变量，实测只改地址就把注入的 Key 发往其他端点。因此第三方运行用 `--setting-sources user` 只加载 WillYou 校验过的用户来源（补验 B1：项目／本地改地址、改 Key、`apiKeyHelper` 均无效，Key 只到所选端点）。对照：仅用 `--settings` 固定地址时，项目 Key 仍以 `Authorization` 与宿主 Key 同时发出，且 `HTTPS_PROXY`、自定义请求头等可改流量的变量是开放集合，不采用。代价：项目 `CLAUDE.md` 改经 `--add-dir` 找回（已实测）；项目 `.claude/skills` 不再自动加载，改由 §4.2 按次投影；项目 `.mcp.json` 由 §4.3 纳管后注入（配合 `--strict-mcp-config`）；项目设置中的权限规则与钩子不生效（用户 2026-11-10 确认可接受）。原生登录运行不受影响。
- **发现器与生成参数一致（2026-11-13）**：只接受顶层唯一的 `--setting-sources user`（含等号形式）为受支持的 user-only 来源；忽略项目 settings，而项目 Skill／命令清单仍单独发现。顶层 `--strict-mcp-config` 排除隐式 MCP，显式 `--mcp-config` 仍检查。解析区分标量／多值参数的值、`--` 和提示正文；未知或重复来源、`--settings` 等未建模覆盖继续拒绝，不能将参数值冒充控制项。实际启动计划经原生上下文发现器的软件集成及 App026 runtime 核对，工具调用结果另见 T070 原账。
- **Provider 缺认证**：启动前拒绝，不交给 CLI。
- **Claude 权限模式（已采用）**：第三方 Provider 下服务端 auto mode 分类器不可用，每次操作都会先弹说明再确认（默认 No）；采用 `--permission-mode default`（直接询问、默认 Yes），第二轮审核同意。仍是询问，不等于预先批准；逐工具限制与用户批准策略照常注入。需求 5.3「权限档位」引入后，这里的 `default` 是“请求批准”档的取值，用户选“完全访问权限”时改传 `bypassPermissions`（§3.8）；任何情况下都不传 `auto`。
- **Codex `--disable plugins` 的代价（审核二 F09）**：第三方运行中 Codex 原生插件（含其自带 Skill／MCP）不可用；WillYou 在运行配置与能力页标示“第三方 Provider 下 Codex 原生插件不可用”，用户需要的插件自带 Skill／MCP 可经 §4 发现后按来源纳管投影，不静默消失。

### 3.2 Provider 一键接入

1. 预设：Magpie（`http://127.0.0.1:3425/v1`，令牌 `magpie-codex`／`magpie-claude`，Codex 目录取 `/v1/codex/models`）、DeepSeek（`https://api.deepseek.com/`，Responses 与 `/anthropic`，Codex 目录用内置官方条目）。
1a. SMG（SmartModelGate，用户 2026-11-11 提供的内网网关；补验 D R4 已用 Claude Code 实测）：Anthropic 地址 `http://<SMG 内网地址>`（Claude Code 请求 `/v1/messages`），OpenAI 兼容 `…/v1`；公开的 `/openapi.json` 只有 Messages、Chat Completions、Models，没有 Responses，Codex 0.166 也已不支持 `wire_api = "chat"`，所以只适用 Claude Code；Codex 经 Magpie 使用 SMG 的模型（用户确认 Magpie 中的“Ultrapwor云”就是 SMG）。`/v1/models` 为 Anthropic 格式（`id`、`display_name`），ID 带版本后缀，推荐模型按前缀匹配。认证 `Authorization: Bearer`（`ANTHROPIC_AUTH_TOKEN`）与 `x-api-key`（`ANTHROPIC_API_KEY`）都可以（补验 D R4-a），正式实现用 `ANTHROPIC_AUTH_TOKEN`。
2. 自定义“地址＋Key”：`GET {base}/models`→`{base}/v1/models`；空请求探测 `/responses`（Codex）与 `/anthropic/v1/messages`、`/v1/messages`（Claude）。探测结果只作**候选协议**：结构化错误体（如 Anthropic `type:error`、OpenAI `error.type`）配合 422／400 标“候选支持”，404 标“候选不支持”，401 标“Key 可能无效”，403 等其他状态只提示原文；最终兼容以第 5 步的最小流式＋工具调用为准（审核二 F08）。空请求在 DeepSeek 实测未形成模型调用，不推广为任意服务不计费的保证。
3. 失败：401→“Key 无效”；超时／连接失败→“服务不可达”；空列表或 404→允许手填模型 ID。
4. Codex 目录生成：预设用来源目录；其余以内置模板＋`/models` 元数据（名称、上下文、模态、推理档位）覆盖生成；缺字段用模板默认并可在高级设置调整。
5. 接入后**不自动生成** RunConfig（需求 5.2「添加供应商」）：用推荐模型为每个协议兼容的工具各做一次最小流式＋工具调用测试，结果写入该工具的可用性；完成页列出模型表并提供“创建智能体”，由用户按“Code Agent → 订阅或供应商 → 勾选模型”新建。之后可逐模型、逐工具测试或重测。删除 Provider 时，同时删除使用它的 RunConfig（先列出），默认按 §3.6 交接。
6. 刷新：每次启动任务前随可达性预检比对并刷新目录（默认模型已下线时提示改选），另有手动“刷新模型”。

### 3.3 运行中失败

Codex 服务不可达会无限重连，Claude 失效 Key 会长时间重试；WillYou 监测运行中连续失败（CLI 输出与原生会话记录），提示“服务异常，是否中断／切换配置”，不自动重放写操作。

2026-11-13 实现：沿用当前运行精确原生会话的增量 SessionTail，结构化 API 错误累计三次才提示，实际回复后清除；用户／工具文本、sidechain、恢复前旧行不计，UUID 去重。Claude2.1.322 的 Native `system/api_error`（`source=request_retry`、`retryAttempt`、`error.status`）经[真实诊断](../验收/证据/M13-T067-native-diagnostic-20261113-a1/coordinator-verdict.json)确认，与 print 的 `system/api_retry` 区分；诊断只验证503，不宣称断连或交互App已通过。运行通知只保存计数和时间，不向UI发送错误正文／地址／认证。中断操作在主进程核对任务及原PTY，过期提示不得停止后来的运行；点击后等真实停止再显示既有恢复选择，不自动重试。原生最终 API 错误继续复用健康分类器，打包端到端及另一CLI实时载体按原用例验收。

2026-11-13 交互红测修正：上述print载体不能直接推广到TUI。[原App031红测](../验收/证据/M13-App031-T067-red-20261113-a1/coordinator-verdict.json)中交互Native没有system/api_error。现增加本次绑定会话、repl_main_thread的结构化api-request观察：两分钟内四个不同请求ID、同shapeHash及requestDigest、期间没有正常assistant回复，提示“CLI正在持续重试”。这只识别重复尝试，不据此判定具体HTTP错误；实际503由受控服务原件另证。新请求体断组、真实回复清除、重复ID去重、早于本次启动的请求及不同session忽略。UI不展示请求正文或摘要值，显式中断的原PTY校验保持。原Native回放仅为U；交互打包复验仍须执行。

### 3.4 恢复与全局模型变化提醒

- 恢复模型：Claude 取最后一条非 `isSidechain`、非 `isApiErrorMessage` 的 assistant 记录顶层 `requestedModel`，无则取最后非 sidechain 的 `attachment.identity.modelId`（不在全文中搜字符串；解析器与真实生成的最小夹具见补验 B7）；Codex 取最后 `turn_context.model`；以 `--model`／`-m` 显式传入；默认保留原来源，明确改选后使用已确认的新来源。Codex 恢复第三方配置时另从准确原生会话首条 `session_meta` 校验会话 ID、读取 `model_provider`；本次 `model_provider` 沿用该原生标识，其定义仅映射到已确认的当前供应商地址、当前 Key 的环境变量及 `requires_openai_auth=false`，不复制原来源认证，不修改历史或用户全局配置。元数据缺失／身份异常拒绝启动，fork 前重验，不能由这一兼容名称绕过来源变更确认。原生会话 ID 与 TaskSnapshot 绑定，不按最新文件猜测。
- 恢复决策（审核 Q01）：上述“最后使用的模型”仍在所选 RunConfig 的勾选列表里就沿用，即使该 RunConfig 的默认模型已改；不在列表（或改选了其他 RunConfig 且不含该模型）时才用所选 RunConfig 的默认模型，并在恢复前提示。决策结果写入本次运行模型，界面提示与实际启动使用同一结果。
- 恢复时的插件与连接（审核 Q02）：按恢复时的项目启用、插件启停与生效连接重新加载并生成本次运行的插件快照（需求“会话生效规则”）；创建时的快照不用于恢复后的运行。

### 3.6 订阅/API 检测、首页显示、排序与默认交接（需求 5.1、5.3）

- **检测命令与判定**（补验 D R2）：`claude auth status`（JSON，退出码 0 已登录、1 未登录）的 `authMethod` 为 `api_key`、`api_key_helper`、`oauth_token`（来自 `ANTHROPIC_API_KEY`、`apiKeyHelper`、`ANTHROPIC_AUTH_TOKEN`／`CLAUDE_CODE_OAUTH_TOKEN`）时判为 API；真实订阅与 Console 登录的取值待用户实测，取到前只能判为“本机登录”。`codex login status`（输出在 stderr）：`Logged in using ChatGPT` 为订阅，`API key configured - …` 为 API，退出码 1 为未登录；只设 `OPENAI_API_KEY` 环境变量时显示未登录。两条命令断网可用、0.05–0.2 秒。**检测必须使用与启动相同的环境**（启动环境里有 `ANTHROPIC_API_KEY` 时 Claude Code 会判为 API 并用它发请求）；订阅/API 智能体启动时**照常继承用户环境、不清除**（需求第二章「订阅／API 智能体」），检测与启动使用同一环境；`authMethod` 为 `api_key`／`oauth_token`／`api_key_helper` 时按 API 命名并注明来源变量。

- **时机**：应用启动、进入智能体页、手动“重新检测”、启动任务前（启动前检测到未登录则拒绝启动并提示，不交给 CLI 去报错）。

### 4.2 Skill 落点（符号链接指向来源原件，单向跟随）

- Codex 不支持按次加入 Skill 路径且同名项并列显示：链接前检查其全部加载根目录，有同名即标冲突。插件自带 Skill 随插件管理，不独立同步。M11 统一 Skill 库（标准 Skill）继续按现有方式交付，本方案只新增外部来源的纳管。

### 4.2.1 Codex 原生插件的只读能力发现（2026-11-13 实现）

按所选 CLI 的真实 CODEX_HOME 扫描 plugins/cache，只认配置已登记的插件或有效本地远程安装标记；不把任意缓存当已安装，不用标记推断远程启用／会话加载。版本选本地 local 优先，其余按语义版本与合法目录边界读取。便携 schema 1.0.0 与旧式声明分别解析 Skill／MCP，不执行安装脚本、hooks 或插件运行时；路径越界、未支持协议／策略和非法声明可见诊断，不静默放宽。MCP 凭据只在主进程保留定义，界面不含值，后续仍走原纳管转换与审批。

实现参考固定 [Codex store](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/core-plugins/src/store.rs)、[manifest](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/core-plugins/src/agent_plugin_manifest.rs)及[便携 MCP 解析](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/codex-mcp/src/agent_plugin_config.rs)。本地状态只是来源库存，第三方任务仍关闭 Codex 原生插件；经 WillYou 纳管的 Skill／MCP 才通过既有投影使用。当前软件层通过，正式 I＋A 以 T068 实际结果为准。

### 4.3 MCP 转换与注入

1. 源配置解析为中间表示（字面量／模板）；Claude 源 `${X}`、`${X:-d}` 为引用，Codex 源 `${…}` 为字面量，`env_vars`／`bearer_token_env_var`／`env_http_headers` 为引用。Claude HTTP 请求头遵循实际两次展开语义，空值与缺失分别处理。来源身份包含实际引用的环境变量、裸命令 PATH 与权限；同物理源只有有效环境一致才合并，未知的已保存秘密按来源配置分开。普通供应商智能体实际使用的托管 Claude 目录也参与发现，不能只扫旧配置表。
2. 启动时按源语义**以服务器为单位**求值：整台成功后才分配私有槽和配置。任一必需变量缺失、command 含变量、URL 不合规、来源停用或权限不能等价表达时整台不注入，其他正常服务器继续。扫描与详情仅提供静态、无值的目标诊断，不解密、不运行命令或认证脚本；只有启动中本 MCP 确实引用来源已保存的秘密时才在主进程解析。
3. stdio：生产使用随包源码 `resources/runtime/wy-mcp-launch.cjs`（2026-11-13 工程修正，旧 shell v3 的控制／数据分离原则保留，载体替换原因见下）。每台生成独立 `WY_MCPV_<登记身份摘要>_<n>`，所有参数和自有环境值均进本台私有槽；Codex 显式列入 `env_vars`。公开 0600 JSON plan 只保存命令、cwd、槽引用与要清除的变量名称，载体只接受准确 `--plan PATH`，使用无跟随打开、文件类型／权限／用户核验。不同服务器槽不能互相引用；未知参数标记始终当数据。先求出参数与自有值，再清除模型凭据、宿主令牌和全部私有槽，最后注入该 MCP 的自有值（同名自有 Key 保留）并以 `shell:false` 启动。自有变量不赋给包装器自身环境或控制变量；PATH 只从来源明确补充，绝不复制整包来源认证环境。相对命令按有效 spawn cwd 定位。信号转发、等待子进程原数值退出及有界后备收尾分别留证，不冒充强隔离。
4. HTTP：Codex 非空头使用 `env_http_headers` 私有槽；实际发现 Codex 会省略空环境头，因此空头单独用 `http_headers` 的空字面量保留语义，非空认证值仍不落盘。Claude 全部使用固定 `headersHelper` 调用受控 CJS 读取私有槽输出 JSON，避免字面 `${…}` 被再次展开。**URL 不承载凭据**：用户名密码、疑似凭据 query（含 `x-api-key`、签名、token 等变体）、片段参数或变量引用均整台拒绝，提示改用请求头／环境变量；值不进入诊断、配置或 argv。
5. 按次注入：Claude `--mcp-config <0600 文件>`，Codex `-c mcp_servers.<名>={…}`，不写入目标 CLI 全局文件。控制文件仅在本次私有运行目录独占创建；取消纳管使后续新建／恢复不再分配本项配置，已加载会话按统一重启生效规则处理，历史公开控制文件不能当作仍生效的全局配置。任务快照只记录已配置 ID 与无值原因，配置、原生加载、调用成功分别判断。
6. 审批：默认 prompt；Codex 用 `default_tools_approval_mode` 和逐工具覆盖，Claude 用准确服务器／工具的 allowed／disallowed 以及按次 `permissions.ask`。来源 deny 优先于自动批准，来源 ask 不被自动批准吞掉；名称不能注入权限语法，不能等价表达的规则明确拒绝本台转换。实际 Native 权限必须从运行上下文核实，传入 on-request 不等于已生效；当前 Codex exec 实际会转为 never，不能拿它代替默认交互审批验收。
7. 不迁移：其他应用包内命令、已停用、依赖认证脚本、需目标 OAuth 认证、SSE→Codex，以及不能等价表达的来源工具白名单／匹配规则。原声明不修改；目标提示单独认证或配置，失败不静默降级。

工程依据：[MCP 开发与部分原生证据](../验收/证据/M13-CAP-MCP-implementation-20261113-a1/coordinator-verdict.json)、[App018 构建基线](../验收/证据/M13-CAP-App018-build-20261113-a1/coordinator-verdict.json)。旧 shell v3 对自有变量 cmd／cwd／k 等发生控制变量碰撞，生产改用对象和独立进程环境；旧写法与理由保存在[历史方案](../历史/技术方案_MCP_shell方案_20261113.md)，实验原件不改。空头修复 U 已过，正常 Native 档位的复验、未测目标及系统层仍按唯一用例账保留缺项；工程接线和构建不等于全部验收通过。

## 5. 插件（R01、R02）

- 包格式 `willyou-plugin/v0-draft2`：`.willyou-plugin/plugin.json`（身份、版本、`hostApi`、图标浅深、权限、providers、projectPolicy、capabilities＋Schema、共享 Schema、legacyToolNames、runtime、skills、ui）＋`schemas/`、`runtime/`、`skills/`、`assets/`。示例见 [demo-tracker](实验/插件协议_20261110/demo-tracker/) 与 [禅道](实验/A5_插件声明_20261110/zentao-plugin/)。
- 运行：独立子进程（Electron `ELECTRON_RUN_AS_NODE`），stdio JSON-RPC（`initialize`／`verify`／`execute`）；宿主保留授权、Schema 校验、审批、账本、超时与重启；插件只收到本次绑定连接的配置与凭据；环境仅白名单。
- 隔离：沙箱禁止读写 WillYou 数据目录与密钥，插件包只读、私有数据目录可写、可联网；沙箱不可用则拒绝启动。用户其他文件依赖安装确认。
- 界面：声明式列表／详情／资源／动作，宿主通用渲染；安装时做界面语义校验（字段路径按能力 Schema 解析，模板仅允许 `tab`／`row`／`value`／`connection` 作用域）。
- 安装、版本、停用、卸载、禅道迁移：见 [A5 生命周期与数据设计](补验A5_插件声明与设计_20261110.md#生命周期与数据设计供技术方案采用)，其中**版本规则按需求 2026-11-11 补记改为松耦合**：不按任务固定插件版本；升级时正在执行的调用按旧版完成，之后所有调用使用新版，旧版随即删除；激活失败回滚不变；安装检查对比新旧能力清单，删除或改名的能力须有 `legacyToolNames` 映射，否则提示。卸载时正在执行的调用完成后即不可调用。
  - **停用与会话（需求 3.1「会话生效规则」）**：A5“停用：不再注入能力与 Skill”只覆盖新会话。宿主在每次插件调用时读取插件当前状态：停用或卸载后，运行中会话的调用立即被拒绝并返回“插件已停用／已卸载”；升级后下一次调用使用新版本。会话启动时已注入的 Skill 与 MCP（含插件自带 Skill）不在运行中摘除，重启会话后按最新状态注入。切换连接仍按“运行中任务继续用启动时的连接”。项目关闭插件按该项目范围的停用处理（调用时同时读取项目绑定状态，全局停用优先）。插件全局停用后，宿主拒绝该插件声明页面的数据读取与动作，页面渲染“已停用”状态。界面提示的受影响会话数按插件可用项目、项目、技能作用域、纳管目标工具计算（需求补记 3 B1–B3）。
  - **调用时解析版本（补验 D R6）**：现有宿主在运行开始时按 `packageHash` 把包固定进运行快照，调用须匹配快照中的哈希，与松耦合冲突。改为：调用时按 `appId` 解析当前启用的版本，按能力名（含 `legacyToolNames`）匹配；会话重启前看不到新版本新增的能力，调用已删除的能力时返回明确错误。任务与项目身份（`withAgent()`／`assertRun()`）与停用即拒绝（`policyStamp()` 中的 `requireApplicationEnabled()`）已具备，沿用。列入 P1。
  - **安装与更新（需求 3.1「插件安装与更新」）**：安装检查按插件 ID 区分新装与更新；从“更新 <插件>”入口进入时只接受同 ID 的包。版本低于已安装版本时拒绝（不允许降级），同版本提示无需更新，均不改动；更新页的变化清单由新旧声明比对得出（能力、Skill、权限的增删），新增权限经用户确认后才激活。回退方式为卸载时“保留数据”后安装旧版本，按新安装处理；旧版本能否读取新版本写入的私有数据由插件自行负责，宿主只提示风险。首期不检查、不提醒新版本（需求池 F30）。更新不改变启用状态，停用中的插件更新后仍停用，新增权限在更新时确认（需求 3.1「插件安装与更新」）。更新后权限、能力、Skill、界面等元数据全部以新包声明为准，不与旧版合并；新声明中的空列表表示全部删除，并列入更新页的删除清单（需求补记 7，审核 N05）。
- 插件连接：连接统一在插件管理，必须有全局默认；项目记录“跟随全局／个性化”状态与可选的个性化连接；改全局默认时只同步跟随全局的项目；运行中任务继续用启动时绑定的连接（规则见需求 3.1「连接与项目使用」）；删除连接时按运行中任务快照里的连接判断是否阻止，任务停止后不再计入（审核 N07）。邮件草稿按项目归属，项目关闭邮件插件后草稿只读，发件人取该项目实际生效的 SMTP 连接（需求补记 7）。
- 需拆除的宿主硬依赖：编译期模块元组与生成的 appId／连接配置类型、`retained` 服务后门、禅道业务表归属、渲染层禅道面板映射与 `appId` 分支、禅道专用 RPC。邮件、浏览器维持内置路径。

### 5.1 P1 首批实现契约（2026-11-11）

本节记录正式开发中的工程选择，业务范围与 §5 保持一致。生产入口为 `src/shared/plugins.ts` 与 `src/main/core/applications/plugins/`；尚未接入完整 App 界面和既有 Agent 路由，不将基础测试算作端到端通过。

- 包校验只接受 `willyou-plugin/v0-draft2`，目录与 ZIP 生成同一份完整清单。包含每个文件的内容、路径与可执行标记的 SHA256；保留脚本可执行位。拒绝链接／特殊文件、路径越界或大小写冲突、`.node` 等原生库及改名的原生二进制；ZIP 在内存中逐项限量、核对大小与 CRC，不按不可信路径落盘。
- 包库复用 `owned-bundle.ts` 的归属与完整性校验，位于 `plugins/packages/<id>/<version>/<hash>/payload`。包的发布和当前版本的激活分别处理：复制与验证完成才登记，登记失败后仅允许复用完全匹配的受管目录；删除先原子移入受管 trash，SQL 回滚或中断后可恢复。插件包不加入 compiled builtin 的 trusted 注册。数据库迁移为 `0031_external_plugins`；安装与变更表、进程占用与健康状态由生命周期执行器使用，真实 App 的接入仍待完成。
- JSON-RPC 为逐行 UTF-8 JSON，`initialize` 请求携带 `hostApi` 与 `protocol`；返回必须匹配 `protocol`、`plugin`（ID）、`version`。`verify` 接收 `{provider, config, secret?}`；`execute` 接收 `{capability, input, connection}`。输入和输出由宿主按该包独立 Schema 编译器核验，跨包不复用 `$id` 缓存。
- 每帧（含请求）最多 256 KiB，每个进程代际的 stdout＋stderr 总计最多 4 MiB；同一进程最多 4 个未完成请求。整个宿主最多 16 个插件进程，每个插件最多 2 个（为升级时旧／新版交接预留）；首期插件不能再创建子进程，第一次 fork／spawn 就被操作系统拒绝。初始握手最多 5 秒，执行／连接验证最多 30 秒；超时或取消结束该进程组，先 SIGTERM、250ms 后仍未退出则 SIGKILL。只有观察到 close 才释放进程预算。
- 进程启动强制使用 macOS `sandbox-exec` 包装真实 Electron `ELECTRON_RUN_AS_NODE`；保护宿主数据根，仅放行本包与本插件私有目录；包、宿主程序与钥匙串目录禁止写入，钥匙串目录同时禁止读取，并禁止 securityd／secd 等服务的 Mach lookup。运行环境只有固定 PATH、私有 HOME／TMP／XDG、插件 ID／目录与 Electron Node 开关，不继承宿主环境。路径、沙箱或包哈希不符时拒绝启动。目录和文件侧隔离已有 I 层验证，**真实签名打包 App 的 safeStorage 系统条目访问仍待 S 层验证，不能据此宣称该门槛已过**。
- 错误不返回插件 stderr／JSON 解析原文，避免把凭据拼入诊断。请求提交前失败保留原错误；写操作一旦已提交，异常、超时、取消或输出契约失败均标“结果未知”，不自动重放。三次崩溃暂停、升级交接、宿主账本与运行身份已接入；默认写确认器的生产装配与派发边界见 §5.5，真实打包 App／Agent 联动仍待验收。

### 5.2 P1 生命周期与宿主接入边界（2026-11-11）

- `PluginLifecycle` 管理安装确认计划（候选哈希＋预期修订＋变化集摘要）、更新、启停、保留／删除数据卸载及显式重启；版本比较不依赖浮点数。更新保持原启停状态，直接降级／同版／错 ID／过期确认拒绝；卸载后装旧版作为新安装允许。删除能力或旧别名没有新映射时列为破坏兼容的变化。`legacyToolNames` 同时接受旧工具名与旧能力 ID，目标必须是当前真实能力。
- 更新先预留该插件的变更，等待已接受调用（包括审批等待）结束并确认相关进程 close，再复制私有数据到受管候选目录；候选初始化只接触该副本。成功后记录 `prepared`／`swapping`，原目录原子移到 backup，候选移到正式位置，随后在同一个 SQLite 事务里提交当前包指针、状态钩子及 `committed`；提交失败回滚原目录和原版本。目录 dev／inode 写进日志，恢复中断的回滚时能识别“原目录已恢复”，不会凭路径名删除不明内容。提交后的故障仅继续清理，不回退已提交的新版本。
- SQLite 连接在插件服务初始化时显式设为 `synchronous=FULL`，切换前继续检查，确保文件切换前的状态决定可持久化。数据复制按普通文件逐块进行，保留内容和 owner 可执行／只读位，目录为私有 0700；拒绝符号链接、硬链接和特殊文件，不读取其目标；预算为 1 GiB、20000 项、32 层，超限保留旧版并明确报错，不截断。
- 卸载先拒绝后续调用，等待已接受调用和子进程退出。保留路径不删私有数据和关联元数据；删除路径通过同库同步 `deleteMetadata` 钩子删除关联元数据，与卸载提交一起回滚或提交，私有数据由受管备份和变更日志衔接。**当前测试的状态／删除钩子使用合成元数据，真实连接、项目设置与加密密钥行现已接线并有事务回滚的软件验证（§5.3、§5.7）；历史引用与真实 App 验收仍按原用例补齐，不能据此认为 T006 已整条通过。**
- `PluginRuntimeSupervisor` 写持久化进程占用。`reserved` 明确尚未尝试启动，可在证明原宿主退出后释放；真正调用 OS spawn 前先记 `launching`，取得 PID 后用原生 helper 记录内核出生身份。close 失败或未知身份不据此删资源；恢复只处理已证明退出的原宿主，对匹配的原子进程等待实际退出，对 PID 复用不发送信号，对未登记／未知身份保留占用。跨宿主使用或变更该插件时拒绝争用私有数据。
- 每分钟三次异常退出后持久暂停，只有显式重启或成功升级清除；正常停用、取消和更新收尾不记崩溃。`withInvocation` 在宿主认证后预留本次包和数据代际，供授权、Schema、审批及账本流程使用。等待审批时不启动插件，拒绝后释放预留；真正派发前复核启停／卸载状态，同一预留只派发一次，预留结束后不能再使用。此 API 只提供内部执行约束，**不构成外部请求的认证接口**。

### 5.7 P1 外部插件连接、默认与项目跟随（2026-11-12）

- `PluginConnections` 只从当前已安装、已校验包的 providers／JSON Schema 构造宿主数据校验器，复用 `ApplicationConnectionService` 的加密暂存、服务／账号核验、测试后保存、同身份编辑与凭据清理。宿主仍不执行包提供的配置解析代码／转换器；内置应用注册边界不被任意 RPC 放宽。新增同事务、无凭据参数的提交钩子，让连接保存和首个默认／项目绑定一起提交或回滚。
- `verify` 参数为 `{provider, config, secret?, authMode?}`：`config` 不含宿主保留的 `kind`／`authMode`，包声明不得占用它们；认证方式按该 provider 的 `secret.modes` 校验，无 modes 时取 `secret`。只给本次实际沙箱预留传当前候选配置和密钥，返回须为 `{identity:{serviceId,accountId}}`，宿主补实际 provider 与身份契约版本。旧身份连接不能编辑成另一服务／账号，须新建。可选凭据按 `required:false` 处理；无认证 provider 不接收 secret。
- 测试不自动保存／选用。候选回执绑定真实主 frame 所有者、包哈希、连接修订和有效期；取消、中途关表单、超时、失败与过期会废弃候选及暂存密钥。保存只接受原 operation／candidate hash，不再次提交明文密钥；包已更新、所有者不符、字段改变或修订变化均须重新测试。未确认候选不在宿主重启后恢复为可保存授权，旧加密暂存沿既有日志清理。
- 未发布的 0031 增加 `plugin_connection_defaults`（一个插件一个当前默认与修订）及 `plugin_project_preferences`（跟随／个性化）。有效绑定仍使用原 `application_project_bindings`，凭据仍使用原 SecretsStore，连接 ID／身份修订不另造。第一条连接保存时自动成为默认并绑定启用中的跟随项目；以后新连接不抢默认。新项目首次设置／运行时在事务中初始化跟随当前默认；保留数据卸载、更新、恢复不丢掉已有个性化状态。

### 5.13 P1 私有 Agent 后端身份与控制端点隔离（2026-11-12）

- `RunBackendAuthority` 是宿主内部能力，不接受 RPC 的 runId／PID 作为归属证明。只有当前 `CapabilityRunRegistry` 实际签发、仍属于本实例的普通 Codex 运行句柄可以预留后端；原生 history/fixed 守护和结构复制的句柄不能取得权限。它在 fork 前分别预留 launcher 与 server 的持久 `bridge` 窗口，启动方必须先 arm 两者再发起 OS spawn；不能在发现一个共享 server 后补造受管身份。
- launcher 必须已由其原启动句柄登记 PID／出生身份；server 从宿主实际持有的 Unix 控制连接取得内核 peer 证明，同 UID、准确 launcher 祖先出生身份、宿主指定的原生可执行路径及 SHA256 都必须匹配。程序文件在接受前校验全量摘要，随后以 inode／设备／大小／模式／纳秒修改与状态时间封印拒绝变化；一次绑定后不能更换控制连接或进程身份。
- 原来的 PTY CLI 祖先路径继续保留。MCP 桥与独立 CLI 端点仅在该路径不匹配时询问同一宿主私有 authority；没有已绑定的对应后端时仍然拒绝。新增路径只允许该 server 的后代，且本次原生 TUI 必须已 active、其出生身份仍存活；原令牌、桥程序／CLI 二进制、能力入口、当前业务授权和写审批不变。服务本身、其他运行、复用 PID、未知进程、变化程序及结束运行不能使用此路径。
- 控制连接断开立即撤销新增路径并停止本次运行，但连接关闭／发送信号都不是进程退出证明。只对准确出生身份仍 running 的已登记进程发信号，unknown 或 PID 已复用时不发。持续核对并确认原进程 stopped 后才关闭持久占用；失败或未知保留原窗口。任务停止和宿主关闭已接该监督器；旧宿主恢复继续沿用持久运行／进程账，不借用旧 authority 或接管共享 daemon。
