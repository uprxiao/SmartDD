## 1. 目标与使用场景

目标：让 WillYou 里的 Agent 能在应用内的浏览器里打开、观察和操作网页，并带着登录态完成实际工作。

用户提供的典型场景（2026-11-02）：从禅道拉回 Bug → 读出其标明的环境与用户名 → 打开浏览器复现 → 复现成功则分析修复；复现不了则用禅道 MCP／Skill 驳回（**本阶段不可用**：M10 禅道只读，见 R08.2）→ 修复后再次复现验证。定时任务（M13）开启后也在当前环境内做同样的事。

## 3. 依赖与目标平台

- 依赖：M10（禅道只读数据、MCP／Skill）、M11（Skill／SOP 与能力声明标准，细节待对齐）。
- **网关前置改动（U3，2026-11-03 用户先定在 M11 修，同日改为在 M12 内修）**：`willyou-app` 运行令牌 30 分钟过期且不续期，超过 30 分钟的任务后续命令全部被拒（`src/main/core/applications/cli-gateway.ts`）。用户决定：M11 已发布的分支、文档与用例账不动；网关代码只有一份，修改作为 M12 的开发内容在 `feature/0.1.1` 上进行，缺陷与证据记在 M12（[执行与缺陷记录](验收/执行与缺陷记录.md) M12-D01），受影响的 M11 用例作为 M12 回归重跑、不回写 M11 账。同样在 M12 内完成的网关改动：大结果写文件返回路径、`willyou-app` 读标准输入、允许无连接的内置模块。
- **范围（U1、U2，2026-11-03 用户确认）**：网页标签只属于任务，项目视图打开文件面板时不显示网页标签；没有所属项目的任务不提供浏览器（这类任务没有 `willyou-app`），标签栏不显示“新建网页标签”。
- 支持的 Agent（C3，2026-11-02 用户确认）：**首版仅 Codex**，与 M10／M11 当前验收范围一致；Claude Code 作为后续，其沙箱与 Skill 机制需单独调研适配。
- 目标平台（D1，2026-11-02 用户确认）：**macOS arm64 与 macOS x64**，两种架构都打包并验收；Windows、Linux 不在首版验收承诺内，写入遗留项，代码保持跨平台写法。

## 5. 验收条件（初稿，待用例展开）

内置浏览器可打开并操作真实页面；Agent 通过 Skill＋CLI 完成“打开 → 登录态复用 → 观察 → 操作 → 等待 → 取证”的闭环；旧元素引用不会误操作（R03.2）；不同 profile 登录态互相隔离、不同项目互相隔离（O10、P4b）；重启后登录态与标签按设计保留（R01.9、R05.9）；Cookie 导入、证书例外、站点权限只能由用户在界面完成（R06.4、O3、O4）；跨任务访问须弹窗批准且仅限同项目（P4）；暂停后 Agent 命令返回 `BROWSER_PAUSED`（R07.6）；未复现只产出说明不写禅道（R08.2）。不设护栏的部分（D4、O7、O11、O12）按决定**不做限制**，验收只核对其行为与 Skill 说明一致。具体用例在评审后编入[测试用例](验收/测试用例.md)。

### 7.3 M12-R03 页面观察与元素引用（草稿）

**依据**：Orca `src/main/browser/agent-browser-bridge-core-commands.ts`、`-capture-commands.ts`、`-interaction-commands.ts`、`-process.ts`、`-types.ts`，`src/shared/runtime-browser-contracts.ts`，`src/cli/specs/browser-*.ts`。读源码，未运行；agent-browser 本机未安装，其快照文本格式、iframe／Shadow DOM 覆盖未实测。

**事实：谁在产出观察结果**（避免移植错误分支）：Orca 现役启动的是 `AgentBrowserBridge`（`startup/main-process-ready-runtime.ts`）。`snapshot`、`screenshot`、`click` 等由外部辅助进程 agent-browser 执行，Orca 只补上页面 ID；`full-screenshot`、`pdf`、`eval` 是 Orca 自己用 Electron／CDP 实现的。Orca 另有一套自带的无障碍树快照实现（`snapshot-engine.ts`，含 iframe 会话与可点击元素补全），只被备用的 `CdpBridge` 使用，不在现役路径上，仅作为 D6 退回自研时的参考。

**R03.1 `snapshot`**：返回当前页的无障碍树文本，并给可操作元素分配引用（形如 `@e3`）。结果字段（Orca `BrowserSnapshotResult`）：`browserPageId`、`snapshot`（树文本）、`refs[]`（每项 `ref`、`role`、`name`）、`url`、`title`。人读格式先打印“页面 ID，标题 — 地址”，再打印树。无参数；作用域为目标页（R02.5）。

**R03.2 引用的生命周期**：引用由 `snapshot` 分配，只属于一个标签页；页面导航、切换标签后失效（写入 Skill）。引用无效时返回 `BROWSER_STALE_REF`，不得对其他元素操作。
- **Orca 的实际做法有一个弱点**：它不自己校验引用，而是匹配 agent-browser 返回的错误文字（含 `unknown ref`、`ref not found`、`element not found: @e` 才归为 `BROWSER_STALE_REF`，其余一律是 `BROWSER_ERROR`）。agent-browser 升级改了措辞，Agent 就收不到可恢复的错误码。
- **SmartDD 要求**：固定 agent-browser 版本；为该错误文字写合同测试（版本升级必须重跑）；验收必须包含“页面变化后用旧引用，要么报 `BROWSER_STALE_REF`，要么证明操作的仍是原元素，绝不能静默点到别的元素”。Orca 没有证明这一点。**已决（用户选择）：首版对标 Orca＋合同测试＋上述验收证明；若验证发现会误点，再追加指纹校验**（Paseo 的做法是给引用附带指纹校验，可作为补强参考）。

  - **R0.10（review2 D01，[E4](技研/E4_旧引用等待副作用长输入_20261103.md) 实测）：已触发补强条件，启用宿主侧引用身份校验。** 实测 agent-browser 的引用是“角色＋名称”的语义定位：页面把按钮整体换成同名新按钮后，旧 `@e4` 静默点中新按钮，没有报错。规则改为：宿主在每次 `snapshot` 后，经该页 CDP 读取无障碍树，记录每个引用对应的节点编号（`backendDOMNodeId`）；任何带引用的动作执行前再查一次，编号不同或节点不存在，返回 `BROWSER_STALE_REF`，**不发出动作**（未开始）。页面导航后该页全部引用作废。实测这一信号在页面其他部分变化、同一节点文字重设时保持不变，替换为新节点时改变，查询约 2ms。另外，引用名称改变时 agent-browser 报 `Could not locate element with role=… name=…`，Orca 的匹配规则漏了这句，宿主一并归为 `BROWSER_STALE_REF`。

**R03.3 覆盖范围（待验证）**：Orca 注释说明 agent-browser 能解析 iframe 与 Shadow DOM 内的引用（用于 `fill`／`clear`），但快照是否列出这些内部元素没有证据。禅道等老系统大量使用 iframe，**技研必须用真实页面实测**；不通过则需要补强或记为已知限制写入 Skill。

  - **R0.6（2026-11-03，[E3](技研/E3_待核实事实_20261103.md) 第 1 项）**：实测通过。同源、跨源 iframe 与开放、封闭 Shadow DOM 内的元素都列入快照并可 `fill`／`click`；不需要补强，T053 防止升级退化。

**R03.4 `screenshot`**：当前视口截图，`--format png|jpeg`（默认 png）。结果字段：`data`（Base64）、`format`。Orca 的做法是 agent-browser 先写临时文件，Orca 再读出转 Base64；源码里没有看到图片大小上限。**O6 已决：SmartDD 不内嵌 Base64，保存为任务数据目录下的文件并返回路径、尺寸、字节数。**`full-screenshot` 与 `pdf` 同样处理（`pdf` 结果由只有 `data` 改为返回文件信息）。

**R03.5 `full-screenshot`**：整页截图（超出视口部分），格式同上。Orca 自己用 CDP 实现，截取期间暂停绘制保证画面稳定。

**R03.6 `pdf`**：把当前页导出为 PDF，Orca 用 Electron 原生打印（含背景、尊重页面 CSS 页面尺寸），结果字段只有 `data`（Base64）；SmartDD 按 O6 改为返回文件信息。

**R03.7 `eval`**：`--expression <JS>` 在页面上下文执行，等待 Promise，结果按值返回（对象转 JSON 字符串，原始值转字符串，无值时返回描述），并带 `origin`（当前页地址）。执行出错返回 `BROWSER_EVAL_ERROR`；执行期间页面被替换返回 `BROWSER_TAB_CHANGED`，Agent 应重试；命令被取消时终止页面内的执行。**`eval` 只作用于页面，不接触应用本身；按 D4 不设额外护栏。**

**R03.8 读取类命令**：`get --what <text|html|value|url|title|count|box> [--element <ref>]` 读取元素或页面属性；`is --what <visible|enabled|checked> --element <ref>` 检查元素状态。二者属于观察，不改变页面。

**R03.9 超时与稳定性**：helper 命令整体超时 90 秒（大于其内部导航 30 秒与等待 25 秒）；同一页面连续 3 次超时后，Orca 会重置该页面的 helper 会话（`CONSECUTIVE_TIMEOUT_LIMIT`）。命令按页面串行（R02.10）。`type` 把长文本按 64KB 一块分批输入（E3 更正）；经 CLI 调用时总长受 `willyou-app` 单次请求 256KB 限制（含 `--stdin` 读入的内容），宿主内部的剪贴板文本上限为 16MB。

  - **R0.10（review2 D03，[E4](技研/E4_旧引用等待副作用长输入_20261103.md) 实测）更正：64KB 一块的 `type` 不可行。** `keyboard type` 逐字模拟按键，越长越慢且不成比例：4096 字约 0.7 秒、16384 字约 5.5 秒，65536 字在 62 秒后 agent-browser 通信失败（review 实测在 16932 字处中断）。`keyboard inserttext` 写入 65536 字只用约 10ms 且完整。现行规则：`type` 每次调用最多 16384 个字符，宿主按 2000 个字符一块依次交给 agent-browser，并记录已输入的字符数；超过上限返回 `INVALID_INPUT`，提示改用 `inserttext`（不触发逐键事件）。中途失败时结果为未知，回执带已输入字符数，Skill 要求先 `get value` 核对，不重发整段。`inserttext` 单次上限受 CLI 请求 256KB 约束。

  - 历史：R0.4 曾写 8KB 分块；R0.6 按 [E3](技研/E3_待核实事实_20261103.md) 第 5 项更正为 64KB（实测 21KB 逐字一致、约 14 秒）。

**R03.10 状态外显**：Orca 在页面里为 Agent 的动作画一个“Agent 光标”（`browser-pane/agent-cursor`），让用户看见 Agent 正在点哪里。O15 已决：本阶段只做活动标记，不做光标（R07.2、R07.3）。

- `keypress --key <名称>`（如 `Enter`、`Escape`、`Tab`）；
- `clear`、`select-all`、`focus`（均 `--element`）；`select --element --value`（下拉框）；`check`／`uncheck --element`。

**R04.3 语义查找 `find`**：`find --locator <类型> --value <文本> --action <动作> [--text <文本>]`，不先 `snapshot` 就按角色／文字等定位并执行动作。可用的 locator 类型与 action 由 agent-browser 决定，**本机未安装，未核实**，技研按固定版本列出并写入 Skill。

  - **R0.6（2026-11-03，[E3](技研/E3_待核实事实_20261103.md) 第 2 项）**：locator 为 `role`（`--name`、`--exact`）、`text`、`label`、`placeholder`、`alt`、`title`、`testid`、`first`、`last`、`nth`；action 为 `click`、`fill`、`type`、`hover`、`focus`、`check`、`uncheck`。`find` 不进入 iframe；`nth … focus` 实测报 `Unknown subaction`。两条写入 Skill 的已知限制。

**R04.4 `wait`**：条件可组合：`--selector <CSS>`、`--text`、`--url <子串／模式>`、`--load <状态，如 networkidle>`、`--fn <JS 条件>`、`--state hidden|visible`、`--timeout <毫秒>`；默认 25 秒，超时返回 `BROWSER_TIMEOUT` 并说明等待了多久；结果 `{waited: 布尔}`。Skill 要求异步变化后优先用 `wait`，不用裸等待。

  - **R0.10（review2 D02，[E4](技研/E4_旧引用等待副作用长输入_20261103.md) 实测）**：`--fn` 的条件脚本能写页面，而且在等待期间被反复执行（实测计数 0→2→6）。因此 `wait` 不再接受 `--fn`，仍为读命令；新增写命令 `willyou-app browser wait fn --fn <js> [--timeout <ms>]`，`operation-receipt`、不自动重试，P4 的 observe 授权下拒绝。不靠检查脚本文本判断是否只读。

**R04.5 文件上传与下载**：`upload --element <ref> --files <路径,…>` 设置文件输入框；`download --selector <ref> --path <路径>` 下载元素指向的文件。**Orca 对这两个命令的路径没有任何限制**：Agent 给什么本机路径就上传什么，也能写到任意路径。结合 D4（不设护栏），这是把本机任意文件发往任意网站的通道，O7 已决：对标 Orca，不限制路径（风险见 O7）。

**R04.6 对话框**：`dialog accept [--text <输入>]`／`dialog dismiss` 处理页面的 alert／confirm／prompt。

**R04.7 取证**：
- `console [--limit n]`：读控制台消息；`network [--limit n]`：读网络请求记录。**Orca 里 `--limit` 参数被接收但完全没用**（实现忽略），而它的 Skill 却推荐 `console --limit 50`；O8 已决：SmartDD 对标 Orca，接收但忽略，Skill 不再推荐该参数。
- `capture start`／`capture stop`：录制 HAR（网络档案）；结果文件按 O6 的方式交付。
- `intercept enable [--patterns …]`／`disable`／`list`：Orca 源码有一条 TODO，明确写着“逐请求放行／阻断需要 agent-browser 支持”；`enable` 只取第一个匹配模式；`list` 实质是读取网络请求。也就是说**“拦截”目前只是记录，不能 mock、阻断或改写**，其默认行为（对匹配请求会不会被拦住）本机未实测。O9 已决：保留三条，明确写“仅记录”。注意 `exec` 透传（P2）可直接调用 agent-browser 自己的网络路由命令，可能具备 `intercept` 之外的阻断或改写能力（未核实）；Skill 的表述应为“`intercept` 这三条命令只记录”，不得声称“本浏览器无法阻断请求”。

**R04.8 输入与结果的约束**：所有交互命令受 R02.10 同页串行、R02.9 取消语义约束；`fill`／`type` 对文本大小的约束见 R03.9；动作失败按 R02.7 的错误码返回。

**R04.9 Orca 与研究包设计的差异**（避免错配）：研究包 `02-Electron接入设计.md` 建议“动作后回读验证”；Orca 现役做法是**不回读**，只返回确认，由 Agent 自己再观察。本阶段 D5 已决对标 Orca，所以首版不做动作后回读；若 R03 的引用失效验证发现问题，再考虑追加。

### 7.5 M12-R05 登录态与环境隔离（草稿）

**依据**：Orca `docs/site/content/docs/browser/profiles.mdx`、`src/shared/browser-workspace-types.ts`、`src/shared/browser-profile-scope.ts`、`src/main/browser/browser-managed-session-profiles.ts`、`src/main/browser/cookies/**`、`src/renderer/src/components/settings/BrowserUseCookieImportStep.tsx`、`src/cli/specs/browser-advanced.ts`。读源码，未运行。

**R05.1 profile 模型**（Orca `BrowserSessionProfile`）：每个 profile 有 `id`、`scope`（`default`＝共用默认；`isolated`＝空白隔离；`imported`＝从其他浏览器导入）、独立的存储分区 `partition`、`label`、来源 `source`（浏览器种类、浏览器内 profile 名、导入时间；手动为 `manual`）、可选的 `owner`（由 Orca 按仓库或工作树自动创建的 profile，随所有者删除而删除）。每个 profile 独立保存 Cookie、localStorage、缓存，互不泄漏。

**R05.2 profile 命令**（7 个）：`tab profile list`；`create --label <名称> [--scope isolated|imported]`；`delete --profile <id>`；`set (--page <id> | --worktree <选择器>) --profile <id>`（把某个页面或某个工作树的页面切到该 profile）；`show --page <id>`；`use-default --page <id>`；`clone --profile <id> [--page <id>]`（复制一个 profile，含登录态）。`tab create --profile <id>` 在新建时指定。页面一旦绑定 profile，该页面上的 Agent 命令都沿用其登录态。

**R05.3 SmartDD 的归属粒度（O10 已决：按项目一个）**：Orca 的自动创建 profile 以“仓库／工作树”为所有者；SmartDD 的对应物是“项目／任务”。D8 已决网页标签按任务隔离，但**登录态若也按任务隔离，同一项目换任务就要重登**。**C1 补充（2026-11-02 用户确认）**：项目 profile 是默认；当某个任务需要的账号与项目 profile 当前登录的账号不同时，Agent 为该任务新建独立 profile 并在其中登录，不改动项目共用的登录（规则写入 Skill，见 R08.1 第 4 步）。任务独立 profile 的生命周期（任务结束后是否保留、何时清理）技研定。

**R05.4 Cookie 导入的实际机制**（D2 的技研前置，已读源码）：
- 来源：Chrome、Chromium 系（Edge、Arc、Brave 等）、Firefox、Safari、Cookie 文件；SmartDD 按 D2 只做 **Chrome 与 Edge**；
- macOS 上通过系统命令 `security find-generic-password -s "Chrome Safe Storage" -a Chrome -w`（Edge 为 `Microsoft Edge Safe Storage`）读取钥匙串里的浏览器加密口令，**会触发 macOS 钥匙串授权弹窗**，命令超时 30 秒；再用 PBKDF2 派生密钥解密浏览器的 Cookie 数据库（AES-128-CBC）；
- 导入界面选“浏览器＋浏览器内 profile”，**没有域名选择**：导入该 profile 全部 Cookie，仅**排除 Google**（`google.com` 及其子域，另按 Cookie 名排除设备绑定的会话 Cookie）；YouTube 仍可导入。写入时只替换导入内容里出现过的域名，目标 profile 里其他站点的登录不受影响；
- 导入结果统计：总数、已导入、已跳过、跳过的 Google 数量、因分区不可读而保留的数量；
- 导入入口：Orca 在设置（导入到默认 profile）、profile 行和浏览器工具栏菜单；SmartDD 按 O10 没有全应用共用的默认 profile，**“默认”指当前项目的 profile**——导入默认进当前项目的 profile，`tab profile use-default` 把页面切回当前项目的 profile（建议，随评审确认）；
- **Agent 能否看到导入的 Cookie**：`cookie get` 返回的每个 Cookie 带 `name`、`value`、`domain`、`path`、`expires`、`httpOnly` 等，**没有对 value 脱敏**。这意味着导入的全部站点会话令牌都可被 Agent 读取，D4、O7 不设护栏的情况下风险叠加，O11 已决：对标 Orca，接受该风险。
- SmartDD 的 Google 登录：Orca 在“清理后的身份”下对 Google 登录域使用 Firefox 身份，并说明系统 Passkey 不支持；是否沿用待技研（见 R01 浏览器身份）。

**R05.5 Cookie 命令**（3 个）：`cookie get [--url <地址>]` 列出当前页面所属 profile 的 Cookie；`cookie set --name --value [--domain --path --secure --httpOnly --sameSite --expires]`；`cookie delete --name [--domain --url]`。

**R05.6 存储命令**（6 个）：`storage local|session get --key`、`set --key --value`、`clear`，作用于当前页面来源（origin）的 localStorage／sessionStorage。

**R05.7 环境模拟**（11 个中除 `dialog`，后者见 R04.6）：`viewport --width --height [--scale] [--mobile]`；`geolocation --latitude --longitude [--accuracy]`；`set device --name <设备名>`；`set offline [--state on|off]`；`set headers --headers <JSON>`；`set credentials --user --pass`（HTTP 基本认证凭据）；密码用 `--stdin pass` 从标准输入传入（C5），Skill 要求一律如此，`--pass` 保留以对标 Orca；`set media [--color-scheme dark|light] [--reduced-motion reduce|no-preference]`；`clipboard read`、`clipboard write --text`（读写的是系统剪贴板，O17；经 CLI 单次请求不超过 256KB，宿主内部上限 16MB）。`viewport --mobile true` 等开关写显式值（R02.3）。

**R05.8 浏览器身份 `browser identity get|set --mode clean|native [--reset]`**（2 个）：设置的是**整个应用**的浏览器身份（User-Agent），Orca 要求重启后生效；`clean` 去掉 Orca／Electron 标记以兼容导入的会话，`native` 保留 Electron 身份（部分 Cloudflare 保护站点需要，但 Google 登录不可用）。该命令让 Agent 能改变全应用设置，O12 已决：对标 Orca，开放给 Agent。

**R05.9 保存与删除**：profile 与其存储分区持久保存，重启后保留；删除 profile 会同时清除其登录态（影响范围与有页面正在使用时的处理由技研核实，Orca 的 `deleteProfile` 行为本阶段未读完）。

  - **R0.6（2026-11-03，[E3](技研/E3_待核实事实_20261103.md) 第 8 项）**：Orca 删除时清空分区存储与缓存、忘掉站点权限，默认 profile 不可删。WillYou 规则见[技术方案](技研/技术方案.md) §5：删除任务 profile 时正在使用的页面先回落到项目 profile；删除任务时删其任务 profile；删除项目时删项目及其任务的全部 profile；任务只是结束时都保留。

**R05.10 profile 的归属与权限（R0.9，review R11）**：profile 的所有者是项目或任务，宿主按运行计划给出的“调用方任务／项目”检查 `--profile`，不信任参数：
- `tab profile list` 只列出调用方项目的项目 profile、调用方任务的任务 profile；经 P4 授权操作另一任务时，再加上该任务的任务 profile；
- `set`／`show`／`use-default`／`clone`／`delete` 以及 `tab create --profile` 只接受上述可见范围内的 profile ID，其他项目或未授权任务的 ID 一律 `SCOPE_DENIED`（不区分“不存在”与“无权”，避免探测）；
- `clone` 只能复制可见范围内的 profile，新 profile 归调用方任务；不能克隆其他项目的 profile；
- `create` 新建的 profile 归调用方任务（C1），`--scope imported` 只建空 profile；
- 删除被同项目其他任务页面引用的任务 profile：只有其所有者任务（或经 P4 control 授权）可删；被引用的页面回落到项目 profile 并重新加载（技术方案 §5）。

### 7.6 M12-R06 授权与安全边界（草稿）

**依据**：M11 [架构设计](../M11_应用接入标准化/技研/架构设计.md) §4.1（manifest v2 与规则 1–8）、§4.2（受信模块）、§5.3（写保护）、§6.2（CLI 身份与运行级令牌）、§9.1（运行计划）、§10（界面影响）；Orca `BrowserCookieImportResult` 等类型。D2–D4、O7、O11、O12 已决定的“不设护栏”部分此处不再重复论证，只汇总其落地约束。

**R06.1 浏览器作为 M11 的一个应用（建议，依赖 P1 最小验证）**：`appId` 为 `browser`；以受信模块 `src/main/core/applications/modules/browser/` 实现（M11 §4.2：包不携带执行代码，允许改的只有新包、新模块和注册表一行）；每个命令是一个能力，能力标识 `browser.<名词>.<动作>`，CLI 命令第一段等于 `browser`，如 `willyou-app browser goto`、`willyou-app browser tab profile create`。每个能力需要 M11 要求的输入／输出 JSON 契约（80 对），可由 Orca 的命令定义转换生成。项目在“项目选用”页选用该应用后，运行计划才把它放进允许表；未选用的项目里，Agent 调用得到 `ENTRY_NOT_ACTIVE`／`SCOPE_DENIED`（O13 已决：新项目默认选用，可在项目里取消）。

**R06.2 与 M11 语义规则的对齐（重要）**：M11 要求每个能力声明 `read`／`write`／`external-write`；`write` 必须有业务级保护，`external-write` 还必须有“宿主观察到的用户授权”，且二者都不能有降级入口。浏览器动作如果诚实地归为 `external-write`，每次点击都要用户批准，与 D4（不设护栏）直接冲突；而它又没有“发送意图”那样的业务对象。建议的归类（需 M11 侧确认，纳入 P1 最小验证）：
- **`read`**（20 个，`safe-read`，可有界重试）：`browser identity get`、`snapshot`、`screenshot`、`full-screenshot`、`pdf`、`wait`、`get`、`is`、`console`、`network`、`tab list`、`tab show`、`tab current`、`tab profile list`、`tab profile show`、`cookie get`、`storage local get`、`storage session get`、`intercept list`、`clipboard read`；
- **`write`**（60 个，不重试）：其余全部，包括导航、点击输入类、`eval`、`exec`、标签与 profile 的创建／切换／删除、Cookie／存储写入、环境模拟、`upload`、`download`、`dialog`、`capture`／`intercept` 的开关、`browser identity set`；
- **一律不归 `external-write`**，也就没有逐次审批——与 D4 一致，但**这是语义上的选择，不等于这些动作没有外部影响**（点击可以提交表单）。保护方式采用 `operation-receipt`：宿主按操作编号持久记录每次命令的结果，结果未知时可查询，不自动重发；
- 说明：`clipboard read` 读取的是哪个剪贴板（页面还是系统）本阶段未核实，技研核实后若是系统剪贴板，应改归 `write` 或单独评审；`wait --fn` 会在页面中执行条件脚本——R0.10 已拆为写命令 `wait fn`，`wait` 只保留无副作用的条件（R04.4）。
  - **R0.6（2026-11-03，[E3](技研/E3_待核实事实_20261103.md) 第 4 项）**：实测为**系统剪贴板**（读写都是）。按本条约定单独评审，O17 已决（用户 2026-11-03 选 A）：对标 Orca 保留，记为已接受风险，Skill 写明只在用户要求时读写；分类不变。
**R0.6（2026-11-03，用户确认）**：按上述 20 读／60 写＋`operation-receipt` 执行（网关改动已在 M12 内进行，由用户在 M12 确认，不再等 M11 侧评审）。

  - **R0.9（review R04）未知结果的查询闭环**：宿主在 M11 调用记录之外，按 `(运行, requestId)` 持久保存每条浏览器写命令的状态（已受理／成功／失败／未知）与结果摘要（截断后的结果，文件类给路径）。`willyou-app` 在“请求已发出但结果未返回”（退出码 5）时，把本次请求的 `requestId` 一并输出（M12-D03，开发 S1 修复）。新增读命令 `willyou-app browser operation get --request <requestId>`，只能查本次运行自己的请求，返回 `succeeded`／`failed`／`unknown`／`not-found` 及已知结果；`unknown` 时 Agent 不得重发，先 `snapshot` 观察页面再决定。读命令因此为 21 条。**R0.10（review2 D07）查询范围**：`operation get` 只在发起请求的同一运行内有效（CLI 断连后在同一终端会话里查询）；App 重启或运行结束后原令牌失效，新运行查询旧 `requestId` 返回 `not-found`，不跨运行开放。持久记录仍保留 7 天，用户在界面的活动记录里可以看到这次操作及其“未知”状态（R06.6）。
原写法：若 M11 不同意上述归类，选项是扩展 M11 的 manifest（新增“交互会话”类语义：无业务级保护、无审批、不重试），这需要 M11 侧评审，不属于本阶段单方面决定。

**R06.3 任务归属与跨任务授权（P3 已决：提供；P4 设计建议）**：M11 规定任务、项目、权限一律来自运行令牌绑定的运行计划，参数里的标识只作对照、不一致即拒绝。因此“跨任务”不能靠一个 `--task all` 参数实现，建议复用 M11 已有的“宿主观察到的用户授权”：
1. 默认只能操作调用方自己任务的页面，其他任务一律 `SCOPE_DENIED`；
2. Agent 需要看或操作别的任务的页面时，先发起一条访问请求（新增命令 `browser access request --task <任务> --mode observe|control`，不在 Orca 的 80 个之内），宿主在界面弹出提示，由用户决定；
3. 用户同意后，授权绑定到**当前运行令牌**：限定任务与模式，运行结束、终端退出、用户撤销即失效，不写入长期配置，不复用旧运行的授权；
4. 授权通过后，对应命令可带 `--task <任务>` 指向该任务的页面（`tab list --task <任务>` 同理），审计记录标明授权来源；
5. 定时任务（M13）无人值守时无法弹窗，默认拒绝，是否允许预授权由 M13 决定；
6. **P4 已决**：授权方式为弹窗逐次批准（绑定当前运行令牌），范围仅限**同一项目内**的其他任务，跨项目一律拒绝（`SCOPE_DENIED`）；因登录态按项目共享（O10），同项目内授权后看到的是同一 profile 下的页面。
7. **R0.9（review R03）申请与使用分开**：`access request` 只检查调用方身份、目标任务存在、与调用方同项目、不是调用方自己，通过后才弹窗；**它不要求已有授权**。其他命令带 `--task` 时才检查授权；`--task` 等于调用方自己的任务时视同省略，不需要授权。弹窗 60 秒无人处理按拒绝；拒绝、超时、运行结束时返回 `SCOPE_DENIED`。授权在命令出队执行前再检查一次，撤销后已排队的跨任务命令返回 `SCOPE_DENIED`。

**R06.4 Cookie 导入的确认流程（仅界面，Agent 无入口）**：导入不是 CLI 能力，没有对应命令，Agent 无法触发；`cookie set`／`cookie delete` 是单个 Cookie 的读写，另算。流程（依据 Orca 的行为与 D2、O11）：
1. 入口：设置中的浏览器 profile 行或浏览器工具栏菜单，选择目标 profile（默认当前项目的 profile，O10）；
2. 选择来源：列出本机已安装的 Chrome、Edge（SmartDD 按 D2 只支持这两个）；浏览器内有多个 profile 时再选一个；
3. **风险确认对话框**（必须）：说明“将导入该浏览器 profile 的全部 Cookie（Google 除外）；Agent 将能读取这些站点的会话令牌；macOS 会请求访问钥匙串中的‘Chrome Safe Storage’，请只在你本人发起时允许”，用户点确认才继续；
4. 系统钥匙串弹窗（命令 30 秒超时）；拒绝或超时 → 失败，不写入任何 Cookie；
5. 导入过程中对目标 profile 的写入有锁，同一 profile 同时只允许一次导入；失败不破坏已有 Cookie。**R0.9（review R13）具体做法**：先把来源 Cookie 全部读出并解密到内存、逐条校验，任何一步失败都不开始写入；开始写入前，把目标 profile 中将被替换的域名的现有 Cookie 备份到本次导入的日志文件；写入中途失败、磁盘满或 App 退出，下次启动或当场按日志恢复备份，再删除日志；导入期间该 profile 不能被删除（删除按钮置灰，CLI `tab profile delete` 返回 `RESOURCE_BUSY`），页面对这些 Cookie 的读写不受阻，导入结果以最后写入为准； **R0.10（review2 D09、D10）补充**：日志记录**完整变更集**——每个将写入的 (name, domain, path) 的原值或“原本不存在”，以及导入写入的新值；恢复时对每一项先比对当前值：仍等于导入写入的值才恢复原值（原本不存在的删除），已被页面改写的保留并在结果里列为冲突，不覆盖用户在导入期间的登录或登出。日志用 Electron `safeStorage`（应用身份 `SmartDD`）加密后写入，文件权限 0600，先写临时文件、`fsync` 后改名；启动时在任何页面使用该 profile 之前先恢复，恢复失败则该 profile 标为“需要处理”，使用它的页面显示提示且 Agent 命令返回 `BROWSER_UNAVAILABLE`，日志保留待处理，成功后删除；
6. 结果摘要：总数、已导入、已跳过、Google 跳过数、因分区不可读而保留数、涉及域名列表；
7. 失败与警告原因：钥匙串被拒／超时、找不到浏览器或其 profile、Cookie 库无法读取、解密失败（`cookies-undecryptable`）；macOS 上不存在 Windows 的 app-bound 加密问题，但应显示未知原因的通用失败；
8. 导入完成后给出提示通知（对标 Orca 的导入完成 toast）。

**R06.5 日志与活动记录脱敏（建议）**：M11 的威胁模型明确要防“凭据进入 Skill／参数／日志”。浏览器命令里有明显的敏感参数：`set credentials --pass`、`cookie set --value`、`storage … set --value`、`fill --value`（密码框）、`set headers` 中的认证头、`cookie get` 返回的 value。建议：活动记录与诊断日志对这些参数和返回值做脱敏（只记录“已脱敏”与长度），完整内容只保留在本次命令的返回中。这不改变 Agent 能读到明文的事实（O11、C2）。**C5 已决（2026-11-02），现行写法（R0.9）**：敏感值用 `willyou-app` 通用参数 `--stdin <字段>` 从标准输入读取（`fill … --stdin value`、`set credentials … --stdin pass`；M12-D02 已实现），Skill 要求密码一律走标准输入，使其不进入进程参数与终端命令。历史：R0.4 曾写 `--value-stdin`／`--pass-stdin`，不再提供。

**R06.6 审计**：每个浏览器命令进入 M11 的活动记录：运行、任务、页面编号、命令名、结果状态（成功／失败／未知）、耗时；截图、PDF 等大结果记录文件路径。授权请求（R06.3）与 Cookie 导入（R06.4）各自记录发起者、时间与结果。

**R06.7 本阶段不覆盖**：域名白名单／黑名单、写操作逐次审批、上传下载路径限制（均由 D4、O7 决定不做）；Windows／Linux 的 CLI 身份实现（M11 的身份助手目前仅 macOS，与 D1 一致）。

### 7.7 M12-R07 用户与 Agent 共用页面（草稿）

**依据**：Orca `docs/site/content/docs/browser/overview.mdx`（“same browser you interact with, same tabs”）、`src/shared/browser-agent-activity-contract.ts`、`src/main/browser/browser-agent-activity.ts`、`src/renderer/src/components/browser-pane/agent-cursor/**`（约 1000 行）、`skill-guides/orca-cli/references/browser.md`、`src/cli/specs/browser-advanced.ts`（`tab switch --focus`）。读源码，未运行。**Orca 在“用户暂停／接管 Agent”上没有找到对应机制**（已在 `main/browser` 内搜索 takeover、userInput、human 等关键字）。

**R07.1 同一个页面**：Agent 操作的就是用户在右侧工作区看到的网页标签，不是后台另开的浏览器。Agent 新建的标签立即出现在该任务的网页标签栏，用户的手动操作（输入、点击、登录）与 Agent 的操作作用于同一页面与同一 profile。

**R07.2 Agent 活动标记**（依据 Orca）：页面被 Agent 驱动期间，标签与页面显示“Agent 正在操作”的标记。Orca 的规则：从 Agent 命令入队开始，到命令结束为止一直保持；最后一条命令结束后仍保持 **20 秒**，用来覆盖 Agent 两步之间的思考时间；Agent 完成、失败或断开后在该时间内清除。只有来自 Agent 身份的命令才产生标记（SmartDD 里 CLI 只能由受管运行调用，天然是 Agent 身份）。活动状态由主进程决定，界面只负责显示。

**R07.3 Agent 光标**：Orca 在页面上画出一个带动画的光标，短距离直接滑过去、长距离沿曲线飞过去，按下时有点击效果；只在页面处于可见且命令正在执行时显示。该功能的实现量较大（约 1000 行动画与路径代码），**O15 已决：本阶段只做活动标记，不做动画光标**（见 R07.2），光标作为后续增强。

**R07.4 “先显示、再操作”的握手**（O15 已决不做光标，本条不适用，仅记录 Orca 行为）：窗口可见时，指针移动命令先把目标位置发给界面，界面画完光标移动并回报“已到达”，主进程才继续执行，**最长等待 1.5 秒**；按下和拖拽的后续步骤不再等待；窗口不可见时不等待。这会给每次指针移动增加可见延迟，不采用光标则没有此延迟。

**R07.5 切换任务与后台页面（SmartDD 新增要求）**：D8 决定网页标签按任务隔离。用户切换到别的任务或收起右侧工作区时，**原任务里正在被 Agent 操作的页面必须继续存在并能执行命令**，不能因界面卸载而丢失页面或中断命令（与 M9 R01.5 对终端的“不因布局变化重建 PTY”同类）。Orca 为此保留已创建页面并在截图时暂停绘制以保证画面一致；SmartDD 的具体做法与限制（后台页面数量、内存、窗口不可见时的绘制行为）技研核实。

  - **R0.6（2026-11-03）**：实验证实页面不在屏幕上绘制时，Agent 点击多等 2.5–5 秒、截图卡住到超时（[D6 核实与 E1](技研/D6_agent-browser核实与E1实验_20261103.md) §3.2）。因此任务切到后台时，宿主把该任务的页面视图移入一个已显示但完全透明、不可聚焦、不接收鼠标、不出现在任务栏的停放窗口，保持原尺寸继续绘制；切回任务时再挂回右侧工作区。用户不得看到或误点停放窗口；Agent 的 CDP 连接只能看到目标页面，不能看到停放窗口或 WillYou 界面。多显示器／全屏空间／调度中心下的可见性、长时间停放的资源占用、切回时是否闪烁，列入系统层用例。

  - **R0.5（2026-11-03）**：实现约束——页面由主进程持有（`WebContentsView`），按任务常驻；文件面板卸载或切换任务时只隐藏不销毁；界面只负责上报显示位置（[冲突核对](调研/WillYou冲突核对_20261103.md) K1、K3）。

**R07.6 并发与用户介入**：Orca 没有锁——用户和 Agent 可以同时操作同一页面，互相可能干扰（例如 Agent 正在填表时用户点了别处）。**O14 已决：增加“暂停 Agent”**，规则如下：
- 浏览器标签上，当 Agent 正在驱动本任务的页面时，显示“暂停 Agent”按钮；暂停后改为“恢复”；
- 暂停后**不再开始新命令**：排队中和之后到达的浏览器命令立即返回新错误码 `BROWSER_PAUSED`（说明“用户已暂停，请等待用户恢复”）；已经开始执行的**写类**命令执行完当前这一条，不中途打断；正在进行的**只读等待**（如 `wait`，可长达数十秒）立即结束并返回 `BROWSER_PAUSED`，避免暂停迟迟不生效（建议，见 §9 C7）；
- 暂停作用于该任务的全部网页标签（范围粒度在原型阶段确认是整任务还是单个页面）；暂停以**页面所属的任务**为准：经 P4 授权从别的任务来操作这些页面的 Agent 同样被暂停（建议，见 §9 C7）；
- 暂停状态只在本次运行内有效：运行结束、终端退出或应用重启即清除，不持久化；
- 暂停期间用户可在页面手动操作（登录、处理弹窗），完成后点“恢复”，Agent 的 Skill 要求在收到 `BROWSER_PAUSED` 后停止重试并告知用户；
- 不做“请求用户接管”命令（O14 选项 C 不采用），登录等仍由用户主动暂停后处理。
- **R0.9（review R07）**：暂停时宿主清空该任务所有页面的待执行队列，每条排队命令立即返回 `BROWSER_PAUSED`；命令出队执行前再检查一次暂停状态。验收要求先排入多条写命令再暂停，站点事件日志中暂停后零执行（T113）。

**R07.7 停止**：停止任务、终止终端或 CLI 进程时，宿主取消在途命令（R02.9）；页面保持当前状态，不回滚、不关闭；运行结束后活动标记按 R07.2 的规则清除；跨任务授权随运行结束失效（R06.3）。

**R07.8 不抢焦点**：Agent 命令不应把用户从当前任务拉走。Orca 的 `tab switch` 默认只切换页面，加 `--focus` 才把界面焦点带过去；`tab create` 默认是否激活该标签本阶段未核实，技研核实后沿用“默认不抢焦点，需要时显式聚焦”。

  - **R0.6（2026-11-03，[E3](技研/E3_待核实事实_20261103.md) 第 7 项）**：Orca 的 `tab create` 默认不激活（渲染层只在 `activate === true` 时切换）。WillYou 定为 `tab create`、`tab switch` 默认都不抢焦点，`tab switch --focus true` 才切换（WillYou 开关参数写显式值，R02.3）。

**R07.9 需要用户处理的提示**：页面弹出 HTTP 基本认证框、站点权限提示（R01.8）、外部应用打开提示、证书错误页时，这些由用户在界面处理，Agent 不能代答（JS 对话框除外，用 `dialog accept|dismiss`）。命令在等待用户处理时按 `wait`／命令超时规则返回 `BROWSER_TIMEOUT`；Skill 要求 Agent 此时告知用户“页面在等待你处理”，而不是反复重试。

### 7.8 M12-R08 与禅道流程衔接（草稿）

**依据**：用户 2026-11-02 描述的工作流；M10 需求 §M10-R03／R04、`resources/applications/definitions.mjs`（禅道 3 个只读工具）、`src/shared/zentao-presentation.ts`（Bug 字段）、M10 README 与总索引中 2026-11-01 “本期禅道只读，T12／T57 写动作暂缓”的决定。本条只定义**衔接场景与边界**，不新增禅道能力，不改 M10 已验收范围。

**R08.1 端到端场景（复现并验证 Bug）**
1. 用户在任务里要求 Agent 处理某个指派给自己的 Bug。
2. Agent 通过 M10 的禅道只读能力读取 Bug：`work_list`（列表）、`object_get`（详情：`fields` 含 `os`、`browser`、`hardware`、`openedBuild`、`product`、`module`、`severity` 等；正文、历史、附件以资源引用返回）、`resource`（分块读取正文、历史、附件）。
3. Agent 从**重现步骤正文**或**自定义字段**中找出被测环境地址和测试账号（用户确认：位置不固定，可能在正文，也可能在自定义字段，**没有标准字段**）；找不到或有歧义时，Agent 停下来问用户，不猜。
4. 在项目的浏览器 profile 中打开环境地址。若页面要求登录：**Bug 里写明了该账号的密码时，Agent 自己填写登录表单登录**（C2，仅限 Bug 写明的账号，应用不保存密码，D3 不变）；没写密码时由用户完成（先“暂停 Agent”再手动登录，或使用已导入的登录态）。登录后 Agent 用 `snapshot` 核对页面显示的当前账号与 Bug 标明的账号一致。**若 Bug 要求的账号与项目 profile 当前登录的账号不同**（C1）：Agent 不得在项目共用的 profile 里登出或换号，而是为本任务新建一个独立 profile（`tab profile create`，再 `tab profile set` 或 `tab create --profile`）在其中登录，避免顶掉同项目其他任务的登录。
5. 按重现步骤执行：`snapshot` → 操作 → `wait` → 再 `snapshot`；用 `screenshot`、`console`、`network`、`capture` 取证，文件按 O6 保存到任务数据目录。
6. 判断结果：
   - **复现成功**：Agent 在终端里分析并修复代码（本阶段不涉及，沿用现有终端能力）；
   - **未复现**：见 R08.2。
7. 修复后验证：在同一 profile 里按同样步骤再执行一遍并取证，对比结果。被测环境两类都有（用户确认）：本机服务（localhost）由 Agent 在终端重启后直接验证；共享的远程测试环境需要用户先部署，部署不在本阶段范围，Agent 在环境未更新时只能验证旧代码。
8. 向用户报告：复现／验证结论、使用的环境与账号、步骤、证据文件路径。

**R08.2 “未复现就驳回”目前做不到（须明确告知）**：M10 的禅道只有读取能力。打回（驳回）、备注根因、“解决并指派”三类写动作只是“场景已记录”（M10-R04-02/03/04），2026-11-01 用户已决定本期禅道只读。因此在本阶段：
- 未复现时 Agent **不能**自动在禅道里打回或备注；
- Agent 产出一份**未复现说明**（环境、版本、使用账号、执行步骤、实际结果、证据文件路径）放在任务会话里，由用户自己到禅道操作；
- 证据文件（截图、HAR）无法自动附回禅道；
- 禅道写能力在 M10 之后由其自身阶段恢复，届时本场景的 6、8 两步可以自动化，本阶段不预留接口也不做占位命令。

**R08.3 SOP（Skill）协同**：浏览器应用提供一份“复现 Bug”SOP，内容为 R08.1 的步骤与注意事项（环境信息在哪找、登录核对账号、遇到 `BROWSER_PAUSED`／登录页如何处理、未复现说明的格式、不猜不明环境）。该 SOP 同时引用禅道只读能力和浏览器能力：M11 的 Skill 以应用为单位渲染入口，**一份 Skill 能否引用另一个应用的能力、两个应用都选用时如何渲染**需要技研与 M11 对齐（纳入 P1 最小验证）。

  - **R0.6（2026-11-03，[E3](技研/E3_待核实事实_20261103.md) 第 9 项）**：M11 Skill 模板只渲染本应用的能力，不能嵌入禅道调用方式。“复现 Bug” SOP 放在浏览器应用，读 Bug 用文字引导 Agent 使用会话中的禅道 Skill；禅道未选用时请用户提供环境与账号。不修改 M11。

**R08.4 与定时任务（M13）的衔接约束**（本阶段只记录依赖，不实现调度）：无人值守运行时，（a）登录过期——D3 不存密码；Bug 里写明了密码时 Agent 可重新登录（C2），否则任务只能失败并报告原因；（b）跨任务授权默认拒绝（R06.3）；（c）暂停按钮无人点击，不影响运行；（d）任务切到后台时页面必须继续存活（R07.5）；（e）Cookie 导入、权限提示、证书例外都需要用户在界面操作，无人值守时不可得，应在运行前由用户准备好。M13 需求细化时据此评估。

**R08.5 验收场景（用于测试用例）**：使用受控夹具而不是真实业务系统：本地起一个带登录页的测试站点和一个预置了“环境地址／账号写在正文里”的合成 Bug 数据；覆盖“复现成功”“未复现”“环境信息缺失需询问用户”“登录页需用户登录”“账号不一致”“修复后验证”六条路径；真实禅道仅用于只读数据读取，沿用 M10 的真实资源边界与授权，不新增真实业务写入。
