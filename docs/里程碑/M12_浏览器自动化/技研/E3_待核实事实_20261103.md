## 1. 结论一览

| # | 问题（需求位置） | 方式 | 结论 | 对需求或用例的影响 |
| --- | --- | --- | --- | --- |
| 1 | iframe 与 Shadow DOM 内的元素能否列入快照、能否操作（R03.3） | 实测 | **全部可以**。同源 iframe、跨源 iframe、开放和封闭的 Shadow DOM，里面的输入框和按钮都出现在 `snapshot` 中并有引用；`fill` 和 `click` 都成功。同源 iframe、两种 Shadow DOM 的输入值已用页面脚本读回确认；跨源 iframe 的点击效果已在快照中确认，输入值没有单独读回 | 禅道这类 iframe 页面不需要补强。T053 保留，用来防止版本升级后退化 |

> **第 1 项范围更正（2026-11-03，[Review 20261103-1542](../../../review/review-20261103-1542.md) D06）**：E3 的“跨源 iframe”是同一 `127.0.0.1` 的不同端口，属于同站跨源，不是跨站的独立进程 iframe（OOPIF）；跨源输入值只核对了“快照某处出现相同文字”，其他输入框也填了同样的文字，不能证明写进了目标 iframe。所以“全部可以、不需要补强”说得过宽。review2 用 `127.0.0.1` 主页面加 `localhost` 子页面另行验证：跨站 iframe 成为独立 CDP 目标，子页面自身回显 `frame:VERIFY-cross`；封闭 Shadow DOM 经内部事件回显 `closed:VERIFY-closed`。这支持全局 CDP 路径下的两个场景，每页代理下仍须在 S1 验证（T053）。
| 2 | `find` 支持哪些定位方式与动作（R04.3） | 实测＋帮助 | 定位方式：`role`（可带 `--name`、`--exact`）、`text`、`label`、`placeholder`、`alt`、`title`、`testid`、`first`、`last`、`nth`。动作：`click`、`fill`、`type`、`hover`、`focus`、`check`、`uncheck`。实测通过：`role`、`text`、`label`、`placeholder`、`testid`、`first`。两个限制：① `nth 1 button focus` 报 `Unknown subaction: focus`，和帮助说明不一致；② `find` **不进入 iframe**，对 iframe 内的标签返回 `Element not found` | Skill 写明 iframe 内的元素先 `snapshot` 再按引用操作，不用 `find`；`focus` 动作的问题写入已知限制。T065 按此列出组合 |
| 3 | `intercept enable` 的默认行为（O9） | 实测＋源码 | Orca 的 `intercept enable` 就是 agent-browser 的 `network route <模式>`，**不带 `--abort` 或 `--body`**。实测这样不会拦住请求：页面照常拿到真实响应，服务器收到 1 次请求，`network requests` 能看到记录。再加 `--abort` 时请求失败（`Failed to fetch`） | O9“仅记录”成立。C10 也得到证实：经 `exec` 调 `network route --abort` 能阻断请求。Skill 的说法为“`intercept` 三条命令只记录”，不得写“无法阻断” |
| 4 | `clipboard read` 读的是哪个剪贴板（R06.2、R05.7） | 实测 | **读写的都是系统剪贴板**。先在系统剪贴板放入标记文字，`clipboard read` 读到的就是它；`clipboard write` 之后，系统剪贴板变成写入的内容 | **O17 已决（用户选 A，对标 Orca）**。Agent 能读到用户复制过的任何内容（可能包括密码），也能覆盖用户的剪贴板。按 R06.2 的约定回到评审，见 §2 |
| 5 | 长文本 `type` 的分块大小与上限（R03.9） | 源码＋实测 | Orca 每块 **64KB**（`browser-text-insertion-chunks.ts`），不是需求原写的 8KB；剪贴板文本读写上限都是 16MB（`clipboard-text.ts`）。实测一次 `keyboard type` 输入 9000 字（21KB UTF-8）逐字一致，用时约 14 秒（约 1.6ms／字） | 更正 R03.9：分块为 64KB。耗时随长度增长：64KB 一块约 40 秒，在 90 秒命令上限内；Skill 建议长文本用 `inserttext`。T060 按此调整 |
| 6 | `javascript:`、`data:` 链接是否进入“外部应用”提示（R01.6） | 源码 | 都不进入。Orca 的外部应用提示排除了一组协议（`browser-external-app-launch.ts` 的 `NEVER_EXTERNAL_APP_PROTOCOLS`），其中包括 `javascript:`、`data:`、`file:`、`blob:`、`view-source:` 等。网页发起的 `data:` 顶层导航被直接拦下，不提示；`javascript:` 链接按普通网页行为在页面内执行，不算导航 | R01.6 补上结论。T014 的预期据此写定 |
| 7 | `tab create` 默认是否激活新标签（R07.8） | 源码 | 默认**不激活**。Orca 的 CLI 不传 `activate`，渲染层只在 `activate === true` 时才切到新标签（`renderer/src/hooks/ipc-events/browser-request-ipc-bridge.ts:97`）。`tab switch` 也只在带 `--focus` 时才切换界面 | R07.8 定为：`tab create` 与 `tab switch` 默认都不抢焦点。T115 的预期据此写定 |
| 8 | 删除 profile 的处理（R05.9、O10） | 源码 | Orca 不允许删除默认 profile。删除其他 profile 时，会忘掉它记住的站点权限和站点显示信息，再清空该分区的全部存储和缓存（`browser-session-registry.ts:281`、`browser-session-profile-retirement.ts:31`）。随所有者（工作树）一起删的 profile 走同一路径（`browser-managed-session-profiles.ts:39`）。正在使用该 profile 的页面怎么办，Orca 没有专门处理 | WillYou 设计（见[技术方案](技术方案.md) §5）：删除任务独立 profile 时，正在用它的页面先切回项目 profile 再清理；删除项目时一并删除项目 profile 和其下各任务的 profile；任务结束时保留任务 profile，任务删除时再删除 |
| 9 | 一份 SOP 能否同时引用禅道与浏览器两个应用（R08.3） | 源码 | **不能**。WillYou 的 Skill 模板只渲染本应用自己的能力（`application-skill-template.ts:25-36`，参数只来自本应用的 manifest）。不过两个应用都被项目选用时，各自的 Skill 都会交付给 Agent | “复现 Bug” SOP 放在浏览器应用里：读 Bug 的步骤用文字写“使用本次会话中的禅道 Skill 读取 Bug”，不嵌入禅道的调用方式。禅道未选用时，SOP 告诉 Agent 请用户提供环境和账号。不需要修改 M11。T126 按此写定 |

## 2. O17：剪贴板命令（已决：用户 2026-11-03 选 A）

事实：`clipboard read` 读、`clipboard write` 写的都是 macOS 系统剪贴板，Orca 也是这样（它直接调用 agent-browser）。

风险：用户复制过的密码、令牌、聊天内容都可能被 Agent 读到；Agent 写剪贴板会覆盖用户刚复制的内容。在 D4、O7、O11 不设护栏的前提下，这又多了一条外传路径。

选项：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| A（建议） | 对标 Orca，两条命令都保留，读写的仍是系统剪贴板。按已接受风险记录（和 O11 同类），Skill 写明“剪贴板是用户的系统剪贴板，只在用户要求时读写” | 风险同上，只靠 Skill 文字约束 |
| B | 两条命令保留，读写的只是本页面范围内的模拟剪贴板，不碰系统剪贴板 | 和 Orca 行为不同；页面里的“粘贴”测试场景（需要真实系统剪贴板）会失效 |
| C | 不提供这两条命令，标为不适用 | 少 2 条命令，需用户按 D5 确认 |

分类方面：如果选 A，`clipboard read` 仍按“读”处理（它不改页面，也不改剪贴板），`clipboard write` 本来就归“写”，20／60 的分类不变。
