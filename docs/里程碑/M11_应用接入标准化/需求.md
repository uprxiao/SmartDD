# M11 需求：应用接入标准化

修订：**R0.9 评审通过基线**，2026-11-01。来源：[F19-D](../../需求池.md)及[讨论备忘](../../F19D_应用接入标准与CLI_MCP双入口.md)。[阶段入口](README.md)。本文为本阶段具体需求的唯一维护位置；本轮用户已确认原型、设计及用例评审通过，授权按本范围开发与验收。

## 1. 背景与整体目标

将已接入应用的业务能力与 Agent 调用方式分开，形成后续应用可遵守的接入标准。最新目标为：**应用 SOP／Skill 说明用法 → Agent 按应用声明调用受管 MCP 或 CLI → 统一能力服务校验并执行 → 上游适配器 → 三方系统**。两种入口均为正式支持目标，不强制 MCP 先经过 CLI。Skill 不持有凭据或执行权限，入口不自行复制业务逻辑。

每个应用交付一套 SOP，可按任务拆为多个 Skill；其中说明用途、操作步骤、当前可用入口、实际命令或工具、结果和失败处理。用户例子中的“SDK 指导 Agent”按后续明确的 Skill／SOP 理解，不要求每个应用新增程序 SDK。

上游提供 MCP 时由受管适配器接入；提供 CLI 时优先原样调用官方工具，在 WillYou 侧增加声明与映射。首版新增的通用接入标准先覆盖这两类；现有禅道 API、Foxmail 本机数据和 SMTP 服务继续作为底层数据与发送来源，不要求改造成第三方先提供 MCP／CLI，也不扩张为本阶段新增更多通用上游类型；但**现有禅道与邮件两个应用本身属于本阶段交付对象**：底座重构后须按新标准重新交付 SOP／能力声明／入口绑定（见 M11-R13、R14）。

## 2. 已确认方向、范围与排除项

**用户已确认：**底座应可扩展；能力、权限、结果统一；应用通过 Skill／SOP 指导不同 Agent，按应用声明选择 MCP 或 CLI；官方 MCP／CLI 尽量复用；首版在 WillYou 内使用；未来系统终端／iTerm 只预留接口；产品继续叫“应用”。

**本初稿建议范围：**定义 SOP、能力及入口声明，补充受管 CLI 并规范已有 MCP，复用现有禅道／邮件服务；实现官方 MCP／CLI 通用适配机制并用隔离测试服务／工具核验。首批以现有禅道与邮件作为标准的真实样本（见 §2.1），不另造新应用；两者的入口、能力和读写清单按 §2.1 确认的方向锁定细节，具体命令／参数在技研与评审时补齐。

**本阶段不包含：**系统终端／iTerm 实际登录与调用、独立后台常驻服务、第三方包市场及任意未审核代码导入、Nacos／Redis／RabbitMQ／Jenkins 的真实生产接入、禅道写动作、M12 定时任务。是否另选一个真实新应用验证标准，仍需另行明确目标、部署版本及授权范围；本阶段默认以现有禅道与邮件作为样本。

M10 的 T09／T10 非空 Story 数据缺项继续保留；本阶段不通过重新编号消除旧缺项。现有邮件发送与审批语义须保持兼容；发送纳入首批（见 §2.1）。真实 Agent 测试只用 Codex，不因扩展目标追加其他 Agent 实测。

### 2.1 首批样本、入口分配与确认（2026-11-01 用户确认）

- **目标双重性：**本阶段既是底层能力优化，也是现有禅道、邮件两个应用的接入优化。底座完成后，两者按新标准重新交付；迁移后用户可见行为不得弱于 M10 已验收结果。
- **一能力一入口：**同一应用的每项能力只声明一个入口（MCP 或 CLI），不同时开放两个入口（例外：只读能力可声明一个降级入口，见 §2.4）；建议同一应用的全部能力使用同一入口，避免 SOP 讲两套、Agent 选错或重复写入。底座本身两种入口都支持。
- **邮件：**首批入口为 MCP（沿用已验收的审批链与桥票据），不依赖 CLI 身份实验。
- **禅道：**目标入口为 CLI，用于跑通新的 CLI 路径。传输路径已由 S0a 在真实 Codex 0.166.0 会话（模拟宿主）中验证可行（见 §2.3）；仍以 WillYou 宿主集成及 §2.3 未验证项通过为前提，不通过时禅道保持 MCP，CLI 路径改用受控工具验证，不影响邮件。入口最终以技研验证结果确认。
- **邮件由两个连接组成：**同一“邮件”应用有 `foxmail`（本机账号目录，只读）与 `smtp`（发件服务，密码认证）两个独立连接槽，凭据与故障面分开。能力声明须写明各自需要的槽；可用性按能力判断，只配其一时另一类能力明确报告“未配置”，不使整个应用失效。回复草稿需要 `foxmail` 读取原邮件来源，新邮件草稿不需要，发送需要 `smtp`。
- **发件地址强一致（新增产品规则）：**所选 SMTP 的发件地址必须与同项目所选 Foxmail 账号一致。当前代码两个连接独立配置，本规则不是现状；校验位置与已有不一致配置的处理由技研定稿，建议在项目选用时和发送前各校验一次，已有不一致配置在发送时拒绝并给出明确原因。
- **邮件发送进首批，但带证据链门槛：**宿主须能完整保留并核验原始用户指令、冻结草稿修订、审阅结果与具体发送意图；入口自报“已批准”无效。验证不通过时回到本文评审，不得悄悄放宽审批，也不得悄悄移除发送。
- **禅道 Story：**Story 查询作为禅道能力的一部分纳入开发（底层读取已支持 bug／story 两类对象）。对应测试用例同步编写，但**暂不执行**，登记为“已生成、待补测”；待用户提供 Story 数据后，与 M10 的 T09／T10 一并补测。未执行不计通过，也不得因此缩小范围。禅道写动作仍不在本期；现有 `smartdd_zentao_write_v1` 的实际状态需技研核实，不得直接迁为可写入口。

用户期望的跨 Agent 场景：在同一项目启动 Cloud Code 配 DeepSeek，要求访问禅道时发现相应 Skill 并按声明执行；再启动 Codex，也发现同一套 SOP 并使用相应入口。模型选择不应要求重写应用 SOP。不同 Agent／版本的 Skill 发现、MCP 配置或本地命令执行仍有宿主适配工作；当前按此前要求仅用 Codex 实测，其他组合保留未验证状态。

### 2.2 R0.5 补充确认（2026-11-01 用户确认）

- **清单：**采用以“能力”为中心的新清单（v2），每个能力只绑定一个入口；旧包与旧会话不动，仅新出的禅道、邮件包使用 v2。
- **邮件发送：**仍走 MCP。发送授权只来自宿主观察到的来源（页面真实点击，或宿主读取受管会话中的用户原话），与调用入口无关；门槛是迁移回归（草稿修订、审阅哈希、授权方式、未知结果处理与现有行为一致，对应 T20），不是新建证据机制。
- **发件地址强一致：**设项目选用、选发件身份、发送前三个校验点，共用一个比较函数；比较规则开发前先读取 Foxmail 账号标识的真实样本再定（只读账号标识，不读邮件内容）；若账号标识不是完整邮箱地址，改为选用时由用户显式确认两者属于同一身份。
- **入口混用：**默认不允许，例外须显式声明并评审。
- **开发顺序：**先做隔离探针 S0a（可在本机现有 Codex 版本上运行，必要时与 0.162.1 对比），结果经用户查看后再决定后续步骤；Agent 适配层抽象（R15）排在 CLI 底座之后。
- **已关闭事项：**`smartdd_zentao_write_v1` 仅存在于测试夹具，生产与资源包中没有；迁移不会引入禅道写入口。

### 2.3 CLI 传输与沙箱放行（2026-11-01 S0a 验证结果，用户已接受局部放宽）

- **约束：**Codex 默认沙箱中，命令不能连接沙箱外的 Unix socket；MCP 服务由 Codex 作为子进程启动，不受命令沙箱约束，所以 MCP 不受影响。
- **方案：**启动受管 Codex 时，由 Agent 适配器通过命令行临时配置，**在用户有效沙箱的基础上只追加放行宿主的 CLI 专用 socket**（与 MCP 桥 socket 分开），不修改用户的 `~/.codex/config.toml`，不降低原有文件权限，不放宽其他网络权限。用户已于 2026-11-01 接受这一局部放宽。
- **已验证（真实 `codex exec` 0.166.0，模拟宿主，假数据）：**命令可连上被放行的 socket；放行路径不匹配则连不上；对外直连 TCP 仍被阻止；经代理访问未放行域名被代理拒绝（curl，403）；环境变量（含名称带 TOKEN 的）可达；令牌值不出现在输出；两个并行会话令牌互相隔离；使用项目已有的原生助手做进程树校验，树外盗用令牌被拒（读取 1–4 毫秒）；用户 `~/.codex/config.toml` 未被修改。证据见[技术方案 §11](技研/技术方案.md)。
- **已知代价：**放行需同时启用 Codex 网络代理功能，命令环境会出现代理变量。
- **交互式会话（2026-11-01 用户本人运行）：**模拟 WillYou 的启动方式（交互式、沿用用户配置），注入后 CLI 连通、工作区仍可写、MCP 桥端点不可达、联网行为与不注入时一致、无审批或信任提示、用户配置未改。
- **未验证（进入验收前必须补）：**WillYou 宿主中由适配器注入该配置（生产代码，须开发授权）；用户会话原本可联网时注入不减少联网能力；npm、pip、docker 等命令在代理变量下的行为；Node `fetch` 经代理的结果不明确。
- 其他 Agent 的沙箱机制不同，不能从本结论推出；各自在适配器中单独验证（R15）。

### 2.4 R0.7 补充确认（2026-11-01 设计复审后用户确认）

- **降级入口：**只读能力可在主入口之外声明一个降级入口（例如禅道主入口 CLI、降级入口 MCP）。降级只在每次运行启动时按 Agent 适配等级决定，运行期间不切换、不在一次调用中切换、不跨入口重发；Skill 按本次运行生效的入口交付，Agent 只看到一个入口。写能力不允许降级入口。
- **Codex 基线：**不再使用 0.162.1，以最新版 Codex（2026-11-01 为 0.166.0）为基线。现有 Codex 适配器只声明 0.162.1，0.166.0 下应用能力目前整体不交付；M11 须先把 0.166.0 纳入适配器（实施拆分 S0b），并在 0.166.0 上重新证明“已确认读取 Skill”与聊天原话授权，通过前这两项保持关闭，发送退回页面点击授权。M10 的回归改在 0.166.0 上执行。
- **CLI 传输细化：**CLI 使用与 MCP 桥分开的独立端点；适配器按用户会话的有效沙箱生成配置，只追加 CLI 端点放行，不降低工作区写入等原有权限（详见 §2.3 与架构设计 §6.2.1）。
- **发件地址比较依据：**取 Foxmail 来源所在账号目录名（实测为完整邮箱）与 SMTP 发件地址比较；目录名不是邮箱时由用户在选用时确认。

### 2.5 R0.8 补充确认（2026-11-01 Codex 评审后用户确认）

依据 [Codex 评审](../../review/review-20261101-0848.md) A01–A12，全部采纳；用户确认以下四项：

1. **新增应用的边界：**新增应用＝新包＋一个受信模块＋一条注册项；宿主通用逻辑与通用页面不改；不运行包内任意代码。以全新 appId 的受控样本应用证明。
2. **Agent 抽象范围：**补全为运行器生命周期加能力交付两组接口，用假第三 Agent 契约夹具验证，不启动真实第三个 Agent。
3. **防重：**框架只保证同一入口内按调用编号防重；每个写能力必须声明业务级保护；删除“跨入口返回原回执”的承诺。
4. **只配 SMTP 时发送：**必须有已确认的发件身份；没有 Foxmail 或账号目录名不是邮箱时，由用户在项目选用时确认；确认绑定连接编号与修订，变化即失效。

另据评审修正：页面、Agent 运行、内部任务分别签发调用身份（A03）；CLI 网关先认证、后业务（A01）；沙箱注入完整继承用户有效策略，无法证明等价则不注入（A02）；邮件资源读取按资源类别区分是否依赖 Foxmail（A07）；运行计划与服务端入口允许表（A11）；上游适配须有完整契约与参考实现（A12）。

## 3. 当前现状

- 现有禅道／邮件 Skill 引用 `smartdd_*_v1` 工具；[MCP 运行入口](../../../src/main/core/applications/bridge-runtime.ts)通过私有 Broker 调用宿主服务。
- 禅道底层访问 API；Foxmail 从本机账号目录读取；邮件发送使用 SMTP，带草稿修订、审阅与原始用户授权核验。
- [工具服务](../../../src/main/core/applications/tool-service.ts)、[执行上下文](../../../src/main/core/applications/execution-context.ts)及连接服务已有作用域、权限、受控错误、调用记录等基础；受管 CLI 业务入口尚未实现。
- 当前内置适配执行器只加载已索引的受信包，并非第三方代码沙箱；不能以“已有适配器”为由直接运行任意上游包。

## 4. 需求项与可判定目标

下表为待细化的阶段需求。除第 2 节明确的用户方向外，具体实现和兼容策略均按本阶段评审定稿。

| 编号 | 需求 | 目标与验收条件 |
| --- | --- | --- |
| M11-R01 | 产品与接入对象 | 可见产品入口仍称“应用”；区分应用能力、技术适配实现与具体连接配置；同一应用可使用多个连接，不改已有内部身份来迁就命名 |
| M11-R02 | 应用 SOP 与双入口 | Skill 说明应用能力、步骤、入口、参数、结果和失败处理；Agent 按固定应用声明调用受管 CLI 或 MCP，不自行猜测入口；声明、实际发现与授权一致；同一 SOP 不按模型厂商复制；同一应用每项能力只声明一个入口 |
| M11-R03 | 统一能力声明与执行 | 每项能力声明稳定标识、版本、输入输出 schema、操作语义、权限、槽依赖、业务级保护和上游映射；页面、MCP、CLI 共用同一业务执行与授权规则，但调用身份分别由宿主签发（页面、Agent 运行、内部任务），页面不借用或虚构 Agent 运行，未启动任何 Agent 时页面照常可用；未声明能力不可执行 |
| M11-R04 | 受管 MCP 与官方适配 | Agent 可按 Skill 使用纳管后的 MCP 工具；可将选定上游工具映射为受管能力，校验参数／结果、版本和权限；上游新发现工具不自动获权；上游适配须满足凭据交付、资源范围、会话复用、凭据轮换、取消与销毁规则（架构设计 §8），并以受控参考实现与样本应用验证后才称为接入标准 |
| M11-R05 | 官方 CLI 适配 | 优先保留官方可执行文件；在 WillYou 侧声明工具版本、固定子命令、参数和结果映射；上游 CLI 运行在每连接私有配置目录，不读取用户日常配置或钥匙串，无法隔离的判为不支持原样复用；输出或认证不满足时明确所需薄适配与不支持原因 |
| M11-R06 | 现有业务复用 | 禅道 Bug、邮件读取等首批能力复用原服务，保持本人范围、日期范围、分页、引用和有界资源读取；首批命令表在评审前补齐；Story 查询一并纳入；已有草稿／发送行为不因入口改变放宽 |
| M11-R07 | 身份、权限与凭据 | 宿主验证调用身份，再绑定项目、连接、环境、会话及动作上限；CLI 参数／Skill／普通日志不包含三方密钥；跨项目、已撤销、已停用及过期身份拒绝调用 |
| M11-R08 | 结果与错误契约 | 统一机器结果、来源修订、完整性、分页与资源；保留原始值和可读说明的区分；JSON stdout、诊断 stderr、退出码与业务效果对应；新契约不静默改写旧 MCP v1 |
| M11-R09 | 生命周期与写操作 | 调用具有操作身份、截止时间和取消语义；只读重试受策略限制；框架只保证同一入口内按调用编号防重，**每个写能力必须声明业务级保护**（业务意图、修订号或上游幂等键），未声明不得注册；写操作沿用审批与固定修订，结果未知时按业务对象查询、不自动重发；停止／撤销后旧授权不可复活 |

## 5. 使用流程与状态

1. 用户通过现有应用配置与项目选用指定连接和权限；宿主启动受管终端／Agent，交付同一套应用 SOP／Skill 及本次有效的 MCP 配置或 CLI 调用上下文。
2. Agent 读取 Skill，按固定应用声明选择入口并提交类型化参数；宿主验证调用身份、当前连接及动作权限，再解析固定能力版本。项目名称或连接编号本身不产生授权。
3. 宿主通过选定上游适配执行，校验和规范化结果，记录来源、修订、效果与审计；CLI 使用 JSON stdout／诊断 stderr，MCP 使用其工具结果格式承载同一业务契约。
4. 失败、取消、断连和超时返回可区分结果；写操作可能已生效时保留“未知”，提供原操作查询方式。不得以空列表伪装错误，或在入口间隐式重发写操作。
5. 正常停止、撤销、切换连接和重启按既有权限与固定会话策略处理；具体在途调用收尾规则需在技研后补齐状态表。

调用状态与授权状态分开：已启动进程、已交付 Skill、已认证、已执行和外部系统已接受不是同一状态。MCP／CLI 的传输成功不能替代业务成功。

## 6. 前台、保存恢复与平台边界

主改底层能力、CLI、Skill 交付和适配机制。现有[会话应用诊断](../../../src/renderer/features/applications/session-applications.tsx)写有“MCP 配置”；引入 CLI 后可能需要少量诊断字段、状态和文案调整，因此不承诺前台零修改。需要改变已确认页面交互时，先同步本阶段原型说明与共享原型。

已有连接、凭据和项目选择继续由原服务维护。CLI 不另存一份可漂移的业务配置。新资源身份、旧会话恢复和可能的数据迁移，必须有明确升级／失败恢复方案后实施；当前尚未确定需要新增哪些表或字段。

首版以 macOS arm64、WillYou 运行期间的受管终端为验收平台（用户已于 2026-11-01 确认；真实 Agent 为 Codex 0.166.0）；不以 Mac 结果证明其他平台或外部终端已支持。
