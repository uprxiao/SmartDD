# M11 R1.0 技术方案：应用与 Skill 即时生效、统一存放

依据：[需求 §2.6、M11-R16／R17](../需求.md)（2026-11-04 用户确认）；需求池 F25；分支 `feature/0.1.2`（基于 `bca2dd70`）。状态：**已批准开发（2026-11-04）**：用户确认按本方案落地开发与测试，恢复按钮需要做。

## 1. 要解决的问题

| 现象（用户实际遇到） | 直接原因 | 根因 |
| --- | --- | --- |
| 首页提示“共享发现目录仍被运行使用，本次未发布”，无法发送 | 有运行中任务登记为共享目录读者时，发布新 Skill 等待 3 秒后放弃（`discovery-catalog.ts` 576–593 行） | 版本化多份副本＋启动时禁用名单的设计，必须阻止运行中会话看到新增目录 |
| 已有会话用不上之后开启的应用 | 网关按启动时固定的运行计划判断（`cli-gateway.ts` 49、61 行），快照 `packages=[]` 即永远拒绝 | R10“每次运行固定运行计划”的规则 |
| 同一 Skill 出现多份（本机 `~/.agents/skills` 6 份对应 4 个 Skill） | 目录名含版本哈希，升级只新增不替换；Claude 每任务生成独立插件目录 | 同上 |
| 点击发送到进入 Codex 约 0.65–0.9 秒 | CPU 采样中约 60% 为协调锁反复 `fsync`（每次取锁 3 次、释放 1 次，单次启动多次取锁） | 发布、读者登记、快照各自取锁 |

## 2. 实测依据（2026-11-04，隔离临时目录，测后删除）

| 编号 | 场景 | Codex 0.166.0 | Claude Code 2.1.318 |
| --- | --- | --- | --- |
| E1 | 会话中途向共享 Skill 目录新增 Skill | 下一轮出现且默认启用 | 插件目录中途新增：不出现；恢复后出现 |
| E2 | 会话中途原地替换 Skill 内容 | 下一轮读到新内容 | 插件目录：恢复后读到新内容 |
| E3 | 启动时用 `skills.config` 禁用某 Skill | 重新扫描后仍禁用 | —— |
| E4 | 用 `skills.config` 指向共享目录以外的 Skill | **不支持**（只能启用／禁用已有 Skill） | —— |
| E5 | 是否读取 `.agents/skills` | 读取 | **不读取**；`.claude/skills` 中的**符号链接**可正常读取 |
| E6 | 会话中途 MCP 服务新增工具并发 `notifications/tools/list_changed` | **不刷新**，同一会话仍只有原工具 | 下一轮即出现新工具 |

补充：Codex 0.166.0 的 MCP 工具为嵌套延迟加载，模型须查 `ALL_TOOLS` 才能看到（E6 首轮因提问禁止调用工具而误得“none”，已按驱动错误修正后重测）。

**结论：**
- Skill 统一放 `~/.agents/skills`（Codex 直接读），Claude Code 用 `~/.claude/skills` 链接（E4、E5）。
- 运行中会话何时生效：

| 入口 | Codex | Claude Code |
| --- | --- | --- |
| CLI 入口的应用（禅道） | 下一轮 | 恢复一次（Skill 需重新读取） |
| MCP 入口的应用（邮件） | 恢复一次（MCP 工具不刷新） | 恢复一次（Skill 需重新读取；工具本身已能刷新） |

## 3. 目标设计

### 3.1 Skill 统一存放（R16）

- **唯一实体：**`~/.agents/skills/willyou-<appId>-<skillId>/`（标准 Skill 为 `willyou-<skillId>`），内含 `SKILL.md` 与包内文件，以及归属标记 `.willyou-owned.json`（appId、skillId、包版本、内容哈希）。
- **渲染：**不再按“本次运行”渲染。模板参数改为该应用声明的全部能力；每项能力写出生效入口及其降级入口（例如“优先 `willyou-app zentao …`；若本会话没有该命令，改用 MCP 工具 `…`”）。是否允许由宿主在调用时判定，Skill 不承担授权。
- **原子替换：**写入同目录临时目录 → 校验哈希 → `rename` 交换；旧目录移入 WillYou 私有回收区后删除。替换在应用库锁内串行完成，不再需要读者登记。
- **Agent 链接表：**在 Agent 适配器声明中新增 `skillDirectory` 与 `readsSharedAgentSkills`：
  - Codex：`readsSharedAgentSkills=true`，不建链接。
  - Claude Code：`skillDirectory=~/.claude/skills`，为每个实体建同名符号链接 `willyou-*`。
  - 新增 Agent：按 §7 验证清单实测后，在适配声明中登记下表字段，宿主据此决定链接位置与界面提示，不另写交付逻辑。

| 字段 | 含义 | Codex 0.166.0 | Claude Code 2.1.318 |
| --- | --- | --- | --- |
| `readsSharedAgentSkills` | 是否读取 `~/.agents/skills` | 是 | 否 |
| `skillDirectory` | 不读共享目录时建链接的 Skill 目录 | —— | `~/.claude/skills` |
| `resumable` | 能否恢复原会话并保留上下文 | 是 | 是 |
| `skillsReloadInSession` | 运行中新增／替换 Skill 下一轮是否可见 | 是 | 否 |
| `mcpReloadInSession` | 运行中 MCP 工具变化下一轮是否可见 | 否 | 是 |

- **版本范围（2026-11-04 用户确认）：**库交付适配器（`skillDelivery: "library"`：codex 1.4.0、claude-code 1.2.0）对该 Agent 所有版本生效；`cliVersions` 只表示“CLI 沙箱参数已实测”的版本，未列版本按 best-effort 只交付 Skill＋MCP（禅道降级走 MCP）。
- **标准 Skill（2026-11-04 用户确认）：**内置标准 Skill 以 `willyou-<skill>` 放入统一库，取消项目开关（界面改动随 S5）。
- **同名冲突：**目标路径已存在且无 WillYou 归属标记（用户自有）→ 不覆盖，应用页提示冲突并跳过该 Skill。
- **触发时机：**应用添加／升级／移除、标准 Skill 随 App 升级、启动时自检（幂等，内容一致则不写）。

### 3.2 授权即时化（R17）

- **运行身份：**每个受管运行仍由宿主签发 token，token 只映射 `{runId, taskId, projectId}`；运行停止即撤销（保留 R07 的撤销、过期、跨项目拒绝）。
- **每次调用判定：**CLI 网关与 MCP 桥在调用时读取项目**当前**的应用启用、连接选用与权限，替代固定运行计划的 `allowed`／`planHash` 比对。项目未开启时返回 `APP_NOT_ENABLED`，消息为“请到项目「<项目名>」的‘应用’页开启<应用名>”。
- **入口始终可用：**每个受管运行启动时都签发 CLI 身份、都挂载 WillYou 应用 MCP 服务（即使当时没有应用），使之后开启的应用不需要改启动参数：
  - CLI 入口：Codex 下一轮可用。
  - MCP 入口：工具列表按项目当前设置动态返回，项目应用变化时发送 `tools/list_changed`；Claude Code 能即时刷新工具，Codex 需恢复。
- **写操作不变：**邮件发送仍走草稿修订、审阅、逐次授权；业务级防重不变。

### 3.3 移除的旧机制

| 移除项 | 位置（主要） |
| --- | --- |
| 共享发现目录的读者登记、发布等待、清单／待发布记录 | `discovery-catalog.ts`、`discovery-catalog-lock.ts`、`legacy-discovery-inventory.ts`、`native-discovery-exclusions.ts` |
| 版本化投放名（含哈希） | `application-skill-template.ts`、`session-projector.ts`、`@shared/application-session` |
| 启动时 `skills.config` 禁用名单与冲突检查 | `resources/agent-adapters/codex/*/base-planner.cjs`、`capability-service.ts` |
| Claude 每任务插件目录 | `claude-delivery.ts`、`capabilities/runtime/*` |
| 固定运行计划的授权比对 | `cli-gateway.ts`、MCP 桥、`run-plan.ts` 中的 `allowed`／`planHash` 约束 |
| 旧版本占用检查与清理流程中依赖共享目录的部分 | `version-maintenance.ts`、`resource-graph-maintenance.ts` |

快照表保留为历史记录（会话诊断读取），不再参与授权与交付。

### 3.4 迁移与清理（幂等，可中断续做）

启动时执行一次：
1. 写入新的统一 Skill 实体与链接。
2. 删除旧投放：`~/.agents/skills/smartdd-*`（必须含 `.willyou-owned-bundle.json` 或 `.smartdd-owned.json` 归属标记）、`~/.agents/smartdd-runtime/`、`capabilities/runtime/*` 每任务插件目录。
3. 无归属标记的同名目录一律不动，记入诊断。
4. 每步写进度记录，中断后下次启动从断点继续；全部完成后标记迁移版本。

### 3.5 界面

- 应用页“项目中使用”说明改为“启用后，Codex 会话下一轮即可使用；Claude Code 会话恢复一次后生效”，移除“旧会话保持原固定能力”。
- 项目“应用”页移除“旧会话保留创建时的版本”。
- 项目应用变化后，对需要恢复才能生效的运行中任务（按适配声明 `skillsReloadInSession`／`mcpReloadInSession` 与该应用入口判断），在终端上方显示“应用已更新，恢复会话后生效”和**“恢复”按钮**（2026-11-04 用户确认需要按钮）；点击后按原会话恢复，上下文保留；任务正在执行时先提示“将中断当前回复”再确认。
- 保存连接后的提示文案改为“…选用后即可在任务中使用”。

在隔离临时目录中（不改用户真实目录；涉及凭据的副本测后删除）对目标 Agent 版本执行，结果写入适配声明与本方案：

1. 启动时能否读到 `~/.agents/skills` 中的 Skill；不能时，其 Skill 目录中的符号链接能否读到。
2. 会话中途新增／原地替换 Skill，下一轮是否可见并读到新内容。
3. 会话中途 MCP 服务新增工具并发 `notifications/tools/list_changed`，下一轮是否可见（工具为延迟加载时，提问须允许查询工具列表）。
4. 恢复原会话后，2、3 是否可见，上下文是否保留。
5. 不满足“恢复后可见”的 Agent，不能声明支持即时生效；不读共享目录且无可链接目录的 Agent，需单独评估交付方式。

**S2 勘察结论（需三层一起改）：**
1. `cli-gateway.ts`：`issue()` 要求运行计划已有 CLI 入口才签发（49 行）；token 绑定 `planHash`，每次调用要求与固定计划一致（61 行）；`requirePlanEntry` 只放行计划内能力（75 行）；`authorizationStamp` 在项目应用设置变化时**撤销**整个运行（76 行），与 R17 相反。
2. MCP 桥：工具清单与允许范围同样来自固定运行计划（`run-registry.ts` `bridgePreparation`）。
3. 工具执行：按会话快照 `snapshot.packages` 中固定的包哈希取包；启动后新开启的应用不在快照中，即使放行也找不到包。

**S2 做法：**新增“当前授权视图”——按 `runId → projectId` 读取项目当前的应用启用、连接选用、已激活包版本与权限，生成与现有 `ApplicationRunPlan` 同形的结构，供网关、MCP 桥、工具执行在**每次调用时**使用；token 只校验身份（存在、未过期、未撤销、内核对端属于本运行进程树）；删除 `planHash` 比对与 `authorizationStamp` 撤销；每个运行都签发 CLI 身份并挂载应用 MCP；项目未开启时返回 `APP_NOT_ENABLED` 引导。先写失败测试：启动后开启应用 → 同一运行调用成功；关闭 → 下一次调用被拒；跨项目／伪造／撤销仍拒。

**S2 实现要点与边界（2026-11-04）：**
- 视图仅对有启动计划且快照为 schema 3 的运行生效；启动计划只提供运行身份与 Agent 入口可达性（`grades.cli`／`grades.mcp`、沙箱、CLI 版本），应用列表与允许表全部取当前设置。
- 视图下不再使用启动时的 `applicationScope` 收窄（原用于共享目录冲突，S3 随旧机制删除）。
- `bridgePreparation` 仍返回启动计划，供启动链路使用；S3 改写启动链路时一并处理。
- 测试改写（按 R17 新语义，原判据保留于 Git 历史）：启动器“项目授权变化后旧 token 永久失效”改为“同一 token 随当前设置：关闭得引导、重开可用”；“渲染 Skill 字节”改读启动计划。
- 验证：类型检查通过；受影响 56 个测试文件并行首跑 1486 通过／21 失败（18 项为 5／10 秒超时，2 项为上述语义改写，1 项 broker 时序）；改写后单独重跑 5 个失败文件 517 通过／8 超时（broker 已过）。剩余超时在原版 HEAD `32c6cdce` 副本对照：邮件“SMTP 回执丢失不自动重发”原版同样超时（11.0 秒）；启动器 7 项同负载对照两边结果一致，均为 3 项超时（“修复原发布后再应用新选择”“用户禁用原 Codex Skill”“恢复已提交的 Codex 迁移镜像”，耗时相差 <0.4 秒），其余 4 项两边均通过。结论：无本次引入的失败；上述 4 项为**既有超时**（测试默认 5 秒上限不足），未改动，留待后续处理。

**接续方式：**在 `../SmartDD-0.1.2` 打开新会话，先读本节与 §4，从 S4（迁移：清理旧副本，把 R1.0 前创建的会话转为库模式）开始，随后 S3d 删除旧机制及其测试；依赖与 `pnpm test:prepare` 已就绪（新增适配器后已重建）。
