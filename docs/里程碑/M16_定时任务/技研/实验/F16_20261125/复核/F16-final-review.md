# Review Report

## 摘要

只读复核 F16 的 R1.0 §1–5、T1.0 B 段、A1.0 及原 R0.3/D0.2。实际核对 A01–A52 为 52 个唯一、连续编号；E06/E09 发现的原 Agent 接受门槛、工作区、空项目、原工具、任务树、权限与通知接线均有正式验收覆盖。发现五项需要明确的高/中风险收口点。以下编号可直接增补现有用例，无需另增验收总数。

## 问题清单

### 高 H1：尚未实际接受的旧领取与管理操作竞态缺判据

- R1.0 §3.5/§3.7（需求.md:84、98–99）冻结已开始运行，暂停/删除后停止后续触发。原 D0.2 历史/F16技术方案_D0.2_20261125.md:117–118 明确未接受旧领取要校验有效性，删除使旧领取失效。
- T1.0 B4.2（技研/技术方案.md:313–315）只在 claim 校验 plan revision/启用，prepare 后真实 accept 段仅再次核 task 状态、选择修订。
- A37–A39（测试用例.md:63–65）主要测试已经工作中的运行，缺 claim 完成后、prepare 未完成或已完成但未受理原输入阶段同管理操作竞争的场景。

建议明确可判定的开始/受理线性化边界，在实际接受事务复核原 occurrence 的合法性及计划修订。A37–A39 加准备/受理前可控门闩，验证暂停/删除/编辑先到时按规则阻止旧输入，已真实受理先到时当前执行快照保留，资源和账本真实一致。不要扩大已确认删除/暂停规则，界定尚未实际开始的准备即可。

### 高 H2：无项目选择一个已登记项目路径时，原投影器会按路径识别其项目能力

- R1.0 §3.2（需求.md:46–47）允许无项目选本机已有目录，明确不自动继承项目能力。
- src/main/core/capabilities/capability-registry.ts:162–165 以物理路径作为 projectRoot 筛选；src/main/core/capabilities/skill-projection.ts:33 和 mcp-projection.ts:72 都直接传 cwd。E09 能力实验使用真正未登记的另一路径，因此只证明在那个前提下原 registry 可复用。
- T1.0 B5.1（技研/技术方案.md:329–330）已选择显式 standalone，但应明确将真实归属传给投影。A43/A44（测试用例.md:69–70）目前仅写不同目录/不同项目的 C/J/X。

建议 A43 增同一物理目录两种归属的对照，关联项目可用符合原授权的项目工具，无项目只投影适用 global，不因 cwd 恰好匹配项目目录而自动纳入项目作用域。明确选择策略和实际配置核对，包括原执行器项目本地配置加载的有效边界。A44 增同一个计划在同一目录连续 new 两个任务仍保持不同浏览器分区/权限，reuse 同一真实任务保留身份。避免以假项目或同目录作为真实业务授权依据。

### 中 M1：手动运行的 eligibility 在技术方案与需求冲突

- R1.0 §3.7（需求.md:98、101）允许 paused/ended 的计划立即运行；A37/A40 已有相关明确预期。
- T1.0 B4.2 claim（技研/技术方案.md:313）统一写“有效启用”与 due/手动 request key，未分自动和手动前置。

建议写明自动领取要求有效启用且到期；手动允许有效暂停和已结束计划，仍须满足当前配置、修订、未删除、非需修正及同计划/绑定任务空闲等原合同。手动不推进自动 due。

### 中 M2：计划专属工作树的所有权独立及固定基准未充分体现到测试步骤

- T1.0 B3/B5.1（技研/技术方案.md:294、331）正确决定 owner=plan，并明确 E06 第一候选任务当 owner 只是试验。E06 实际发现旧 agent_workspaces 任务 FK RESTRICT、childTask 查询、实际后续顶层任务无完整工作树关联。
- A12/A14（测试用例.md:38、40）验证同一树、准备失败、停止/删除计划保留，但没验证新建任务模式首个实际任务被正常删除/清理生命周期后专属树仍由计划稳定拥有；A13 则验证每次新建工作树推进基准引用。

建议在隔离 A12 专属+new 子场景完成第一轮后正常归档/删除实际任务（观察旧历史不可用），后续仍复用相同登记路径/分支，不阻止第一任务按普通规则删除；在下一轮前推进选定基准引用，专属工作树不重新建立/重置基准（与 A13 每次工作树重新解析对照）。连续复用绑定目标被删除则应保留 A19 需修正规则。

### 中 M3：独立新任务计划权限编辑的“明确重新确认”需原合同与验收具体化

- 历史 R0.3 第六轮（历史/F16需求_R0.3_20261125.md:74）确认计划和绑定任务权限配置变更都须重新确认，不隐式提升。
- R1.0 §3.3（需求.md:60、62）明确了默认请求批准及绑定任务身份/权限变化后的确认，直接修改每次新建任务计划的权限未明确。
- A18（测试用例.md:44）覆盖 existing/reuse 目标变更，A38/A46（行64、72）覆盖快照/审批但没有直接编辑 new 计划 ask→full 的取消和真实明确确认判据。

建议明确普通计划编辑时权限改变的本人确认/保存语义，无需额外专属权限体系。A38/A46 直接改行为档位，取消不提升、已开始运行快照保持原权限、用户明确确认后只对以后运行生效，审批上限仍有效。
