## 一、参考产品如何执行计划任务

### T3 Code

- 计划数据有名称、提示词、启用状态、日程、项目 ID、可选已绑定线程、工作区策略、模型选择、运行模式和交互模式。原生触发器有固定间隔（最低一分钟）、指定时间及星期、仅执行一次和 Webhook。固定时间使用执行服务器时区，间隔使用经过的实际时长。来源为 `packages/contracts/src/scheduledTask.ts`、`apps/server/src/scheduledTasks/Schedule.ts`。
- 计划落 SQLite `scheduled_tasks`；表保存下次执行时间、最近结果、次数等字段，对启用和到期时间建索引。独立 Scheduler 每五秒调度已登记的工作源，单个工作源有并发保护；`runDueTasks` 在无到期任务时利用缓存提示减少 SQL 查询。来源为 `apps/server/src/persistence/Migrations/OrchestrationV2/ScheduledTasks.ts`、`apps/server/src/scheduling/Scheduler.ts`、`ScheduledTaskService.ts:1314`。
- 到期时重读当前计划，检查删除、暂停、时间变化。启动时先登记 `running`，通过现有 `threadLaunch.launch` 或 `threadManagement.sendToThread` 派发消息，生成可追溯命令号和消息号，更新下次时间。一个绑定线程已有相同计划的待发消息时，避免每次周期无限累积。`runNow` 复用派发逻辑。来源为 `ScheduledTaskService.ts:976–1218`、`:1768`。
- 三种任务去向分别是每次新建线程、持续在同一线程续聊、同一线程每次使用新 Provider 会话并清除先前上下文。首次未绑定的后两种会创建线程并保存绑定；已绑定线程使用该线程的当前模型。T3 区分消息已接受和真实运行终态，`recordRunOutcome` 追踪对应消息和运行，运行失败修订最近状态，一次性计划实际完成后删除其计划并保留线程。来源为 `scheduledTask.ts:231–265`、`ScheduledTaskService.ts:915–970`、`:1068–1165`。
- 固定时间错过超过 10 分钟，记录错过并进入下一周期。间隔和一次性计划走各自的时间语义。服务器启动时处理仍标为 running 的旧记录，以失败或中断等状态收尾，避免永远卡住。服务器停止期间无需假定电脑会自行运行。Webhook 另有待交付记录、请求校验、过滤和去重，机制远超普通本地定时。来源为 `Schedule.ts:73`、`ScheduledTaskService.ts:1314–1418` 及 `apps/server/src/scheduledTasks/` 下的 Webhook 模块。

### Orca

- Orca 的 `Automation` 定义区分执行主机（本地主机服务、SSH bridge、远程主机服务）、项目与工作区策略、基准分支、Agent 及启动配置、会话复用开关、RRULE 和时区、下一次运行与补跑宽限。编辑器按工作区、会话、日程、时间和宽限组织字段。日程有每小时、每天、工作日、每周、自定义规则等预设。来源为 `src/shared/automations/automation-definition.ts`、`src/shared/automations/scheduling/automation-schedules.ts`、`src/renderer/src/components/automations/authoring/AutomationEditorSettingsSidebar.tsx`。
- `AutomationService` 在主进程默认一分钟 tick；启动先协调遗留运行，再进行到期检查。调度使用 evaluating 标志、生命周期代次、唤醒门及每个 automation 的派发通道。`runDueAutomations` 查询有效计划，`runScheduledOccurrence` 找到最近一次应发生的时点，宽限外记录 `skipped_missed` 并推进日程；在宽限内保存 pending 运行再交给派发通道。来源为 `src/main/automations/automation-service.ts:50–180`、`automation-due-runs.ts`、`automation-trigger-runs.ts:44–74`、`dispatch/dispatch-refusal.ts:148`。
- 计划运行可以复用已绑定工作区，也可为每次运行新建工作区；会话复用适用条件随工作区及启动类型确定。实际调用既有聊天或终端启动器，区分提交和真实执行完成，由观察器核对。来源为 `src/main/automations/launch/automation-workspace-create.ts`、`automation-chat-session-reuse.ts`、`src/main/automations/dispatch/automation-launch-runner.ts`。
- 保存定义与运行历史是不同记录。每条运行可以保留应触发时间、触发来源、绑定 workspace、chat session、终态、失败原因等。未确认的旧终端派发在重启后不会被当成可直接续派；目标不可用、需要交互认证等有明确跳过状态。来源为 `src/main/persistence/loading-store/automation-state/automation-persistence.ts`、`src/shared/automations/history/automation-run.ts`、`src/main/automations/runtime-automation-service.ts`。

## 二、对 WillYou 设计的启发

| 场景 | T3 Code | Orca | WillYou P0.1 建议 |
| --- | --- | --- | --- |
| 定义计划 | 项目、模型、线程去向 | 工作区、主机、Agent、会话 | 名称、提示词、项目/目录、智能体（含 Provider）、模型、推理强度、执行时间 |
| 工作目录 | 原工作区/新工作树策略 | 既有 workspace 或每次新建 | 沿用 M14 已有目录体系；Git 目录可选择基准分支和工作树；SVN 与普通目录仅原目录 |
| 会话去向 | 新线程、继续、同线程新 Provider 会话 | Fresh/Reuse | 每次新任务（默认）、首次新建后复用同一任务、指定现有任务。指定既有任务时锁定其目录与配置，变化后重新确认。是否支持同一任务的全新原生会话待研究 |
| 日程 | 间隔、指定时间、一次、Webhook | 周期/自定义规则、事件 | 固定间隔、每天、工作日、每周指定星期、仅一次；工作日暂指周一至周五 |
| 时区 | 执行主机时区 | 捕获时区、可显式指定 | 支持本机时区及明确 IANA 时区；当前时间/下一次预览。夏令时重叠和不存在时间需实验 |
| 主机 | 运行所在服务器 | 本机/远程，包括 SSH | 初版只演示此计算机；后台常驻、远程调度和退出后的执行策略需确认 |
| 休眠错过 | 固定时间 10 分钟宽限 | 可配置宽限，补最近一次 | 宽限可选不补跑、10 分钟、1 小时（草案默认）、12 小时；只补最近一项，超出时记录跳过 |
| 并发 | 不重复累积线程内待发消息 | 每计划派发通道与目标归属 | 同一计划前次正在运行或等待处理时跳过周期，记录原因；多个计划按资源边界执行，独立任务的并发量另行设计 |
| 结果 | 线程关联、最近状态、运行回执 | 独立历史、状态和失败信息 | 计划列表＋计划详情＋逐次运行记录。明确触发、已派发、真实任务终态；延续现有任务记录 |
| 任务安全约束 | 运行及交互模式 | 目标与启动约束、认证前置 | 沿用 WillYou 现有授权。首版演示请求批准，待处理时暂停本次；M14 移入的不允许无人值守跨任务网页授权及插件写入/邮件发送验收判据继续有效 |

## 三、WillYou 的复用点和待选技术方向

- 现有界面在 `src/renderer/lib/layout/workspace.tsx` 通过时钟进入 `scheduled`，目前为占位；共享原型在 `prototypes/m6-codex/src/App.jsx` 有相同入口。M16 在此扩展计划列表和详情，保留三种执行器场景和统一任务 UI，沿用 M14 模型目录与 Provider 图标。
- 任务创建、回合接收、原生执行器和历史已集中在 `src/main/core/agent/agent-task-service.ts` 与 `controller.ts`。`create` 校验已有智能体及目录，`submit` 使用 `clientInputId` 和 `expectedSelectionRevision` 关联原回合，目前按用户输入归属处理；另有宿主消息入口 `enqueueHost`。正式实现需要明确独立的计划触发身份及持久化调用入口，避免把自动消息当本人审批或把定时任务做成第二套 Agent 系统。
- 建议计划定义和每次运行两张持久表，运行有唯一计划／计划时点标识、配置快照、任务 ID 和输入 ID。到期事务先领取并记待运行，再交现有 Agent 服务；结果订阅现有回合/停止/等待处理状态，失败在运行账保留。恢复先对照旧运行落库及实际任务再决定，未知提交结果保持待核对；预防重复派发的实验需覆盖崩溃窗口与并发。
- 主进程调度服务由应用生命周期管理。优先考虑到期索引和有限间隔或可重置的下次唤醒，独立测试时间计算与持久领取；是否应用关闭后可持续运行、主机休眠后的准确处理及跨平台行为先做实验。生产方案须在 [技术方案](../技研/技术方案.md) 定稿，本次不选定最终计时实现。

## 四、本次原型与评审问题

P0.1 已演示创建/编辑计划、目录与会话模式联动、频率与下一次时间、暂停/恢复、删除后保留历史、立即运行、周期触发及宽限期内外唤醒、任务运行结果。模型、目录和运行均为合成。点击运行记录打开合成结果卡，正式产品将关联统一任务区的实际任务和回合。

需要用户评审的业务决定：

1. 是否首版就加入 Webhook/自定义 Cron，以及是否允许普通计划使用 `/goal`。现行 M14 对计划任务设定目标有限制，P0.1 沿用该限制。
2. 本机运行的生命周期：最小化、关窗口、完全退出、电脑睡眠分别需要怎样处理。是否接受先做到 App 运行及唤醒后的补跑。
3. 三种任务去向及配置变化处理是否合适。复用旧会话对历史关联和费用有影响，是否需额外增加同一任务的新原生会话模式。
4. 宽限默认值、跳过还是合并一个待运行、运行记录保留、失败重试与通知。原型当前为保留每次记录，由用户手动再运行。
5. 无人值守权限与插件/浏览器边界如何在现有 M14/M15 合同内细化。哪些业务只读可自动完成、哪些等待本人批准。

评审入口见 [原型说明](../原型/原型说明与变更.md)，确认后再补专项实验、正式技术方案和完整验收用例。
