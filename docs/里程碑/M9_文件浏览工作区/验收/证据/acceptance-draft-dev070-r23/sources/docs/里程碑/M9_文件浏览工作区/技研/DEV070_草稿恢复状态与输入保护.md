# DEV070 草稿恢复状态与输入保护

依据 M9 R3.4-20261017 / R3.4-P1、R07.10及H29/H30，沿用既有范围内开发/复验授权。共享原型的 clean/dirty/conflict及内存历史边界不变，不新增恢复业务、界面或外部服务。

## 复现

原实现 restoreDraft 总设置 writeRequired=true 并重建 EditorState，只按缓存revision判断基线。结果：与磁盘逐字节相同的clean草稿仍dirty并安排写回；同内容内存历史丢失；尚未收到watch事件时忽略真实外改；草稿读取期间新输入可能被迟到结果替换。还需保护未决unknown保存恢复记录，不能通过“恢复干净草稿”抹掉它。

新增原生存储红测3过2败（clean、兼容历史）；buffer红测先21过4败，补保护场景后21过5败。真实App首轮脚本虽然输出passed，但clean候选等于当前正文，等待正文不能证明异步restore已完成；该轮clean结论撤回，从未计入正式通过。修正为等待恢复卡片消失并核对inode/mtime后，原r22真正复现clean被标dirty。第一轮实际SIGKILL/磁盘字节/写失败的原始数据保留，不拿无效clean结果判完整用例通过。

## 实现

恢复先检查未决保存、正在保存及输入门禁，再读取独立草稿与新的权威磁盘字节。每次等待后核对请求代际、buffer版本/内容/BOM/base/ref和输入状态；有新输入则拒绝旧恢复，已销毁或过时请求不落状态。提交新恢复时使旧load/refresh失效。磁盘不能无损UTF-8读取时保留草稿及原编辑器，明确拒绝；只读/超可编辑预算不因恢复而升级可写。

clean且同base的精确候选不强制write；同base且内容不同保持dirty；base不同保留候选和fresh disk冲突。只在恢复内容/BOM与当前内存完全相同的条件下沿用EditorState/历史，否则新建历史。历史仍不跨App进程序列化。版本单调增加，干净候选仅按精确native receipt清普通checkpoint；不触碰unknown/conflict恢复物。
