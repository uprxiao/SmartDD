## 现有 App 的 PTY 归属缺口已修

原 `src/main/index.ts` 通过通用事件总线接收 `ptyId` 后直接 write/resize，总线省略了 Electron sender；`pty.kill` 也没有来源/任务校验。现在：

- 主进程用 [PtyAccess](../../../../../src/main/pty-access.ts) 接收原生 IPC event，只接受当前主窗口的主 frame 和精确受信文档 URL；子 frame、其他窗口、导航到其他文档、已销毁窗口均拒绝。
- 输入/resize 必须同时提供 taskId/ptyId，主进程逐次查真实运行映射并检查 native PTY 存活。任务结束、停止/归档过程、删除及重新打开后，旧身份不能写入；没有逐键数据库查询。
- 全部 task RPC 经 scoped sender 检查，PTY kill 经同一归属校验并调用 TaskService，避免直接 kill 绕过任务状态。停止抛错会恢复原先的可输入状态。
- renderer 发送成对的 taskId/ptyId。普通键盘 Ctrl/CJK/粘贴行为仍属于原始键盘通道；文件上下文必须另做控制符清理、限额、不追加回车及回执，不能因为来源校验完成就跳过内容保护。

验证：受影响的4个测试文件 **40/40**，类型检查及 App 构建通过。[真实 Electron/PTY 探针](pty-access-probe.mjs) 在独立临时 profile 的隐藏窗口和自建 raw-mode PTY 中执行 [6/6 原生检查](pty-access-result-20261017-r3.json)：主 frame 中文/emoji 原样到达、未追加 Enter、另一窗口和真实子 frame 拒绝、错任务/旧 PTY 拒绝、合法 resize、受控 kill。前两轮4/6源于合成 Node 子进程的换行转义错误；修正脚本并要求真实 READY 行及活进程后重跑，失败报告保留。没有操作 Codex 或启动任何用户 CLI。

全套 `pnpm test` 首跑422通过、15失败、11跳过，失败均涉及沙箱禁止监听127.0.0.1。核对测试为本机合成服务器后，在允许本机监听的环境复跑4个受阻文件 **60/60**，见[日志](../../验收/证据/r34-app-loopback-tests.log)。合并覆盖为446通过、2个原有真实CLI探针未启用；这是首跑加定向复跑的覆盖结果，不描述为单次全套448通过。M9正式425条验收总账仍未执行，未用这个探针冒充打包应用完整端到端验收。

## 保存竞争：撤回“冲突时自动换回”的保证

[新脚本](save-recovery-probe.py)、[最终结果](save-recovery-result-20261017-r2.json)：**7项保护/恢复检查通过，1项旧实现缺陷负对照**。SR02明确重现：交换后，进程A继续写旧fd，进程B按目标路径写新inode；旧方案发现A的版本不符后再次交换，再删临时文件，会删除B更新的内容。旧 AFS04–06 的单写入者成功不能推广为多写入者保证。

收口方案是“保留版本并报告恢复冲突”：提交前持久化独立草稿及准备日志；目录fd锚定创建恢复区/暂存文件；交换后保留被换下的inode并回读当前路径。任何不一致均停止后续自动保存，不再次无条件交换或删除冲突版本。SR03验证当前路径上的B内容、旧inode上的A内容和独立草稿三者都可恢复；SR04验证返回后继续写旧fd仍能落在保留inode中；SR07验证交换后异常不会触发finally清除恢复物。预先可见的版本冲突与目标symlink在写入前拒绝。

实现约束：交换不是系统级 CAS，不能承诺并发写者下目标路径自动恢复到某个版本；回读后的外改仍依赖 watch/重扫。生产恢复日志必须有 opId、目录/文件身份与哈希，启动时重核 prepared 状态，不盲信日志中的路径；恢复区不授权给第三方viewer。需确定容量上限、保留期和满盘时拒绝新保存策略，不能假定有限时间后外部fd必然关闭，不能默默删尚未解决的冲突版本。目录fsync请求已执行，但断电、真实进程崩溃、满盘、ACL/xattr/owner和Linux/Windows未验；本实验不是对具有同等系统权限的恶意进程的隔离保证。

该修订维护“我的草稿与外部修改不被静默丢失”的既有目标，纠正不可靠的实现方法；不改变用户已确认的 CLI 自主文件操作权限。需求R07.17、技术方案和Y02预期按此同步，旧实验与快照保留。

## 恢复容量与清理的工程默认值

为让生产实现不再等待模糊“合理容量”，本轮冻结以下起始参数。它们是工程默认值，不是新增产品范围，也不是整机磁盘空间保证；后续实际负载超出时重新测量并保留修订。

| 参数 | 默认与依据 |
| --- | --- |
| 项目/全局恢复额度 | 512MiB / 2GiB，包含活动预约与尚未清理的实际恢复数据。实际10MiB文本、40MiB候选样本三版本及准备日志尺寸验证，预约按保守逻辑bytes，不依赖APFS压缩/克隆收益 |
| 每次预约 | currentBytes + 2×candidateMaxBytes + 64KiB元数据；候选超过预约必须在提交前追加额度，否则拒绝，不先覆盖再补记 |
| 磁盘余量 | 除预约外至少128MiB余量；statfs只是提示，真实写入/fsync的ENOSPC仍须逐步处理并保留可恢复状态 |
| 并发及幂等 | 主进程SQLite事务统一项目/全局额度，同一opId同一载荷不重复预约，改变载荷拒绝；启动时对照真实日志/文件重建，不能仅相信旧计数 |
| 已解决历史 | 已确认保存或明确放弃、且重扫身份/哈希无新变化的记录最多保留7天、每文档最近2份；满足可删除条件的旧项才回收。7天/2份为工程保留策略，不是对外部进程旧fd生命周期的保证 |
| 未解决数据 | dirty、conflict、prepared/inflight、失败或哈希发生变化的恢复物不按年龄自动淘汰；满额时阻止新保存并保留内存草稿，提供明确原因及安全处理入口，不静默抛弃修改 |

[额度及真实尺寸实验](recovery-quota-probe.py)、[结果](recovery-quota-result-20261017-r2.json) **6/6**：两档真实文件尺寸；5个SQLite并发连接预约40MiB候选时仅4个成功；opId重放/变载荷；配额拒绝前原件不变；跨项目2GiB上限。这里验证了额度逻辑与尺寸，没有填满真实磁盘，也没有执行生产TTL清理、系统断电或证明所有外部fd已关闭。那些仍是生产恢复实现与故障验收，不能从本探针推断通过。
