## 2. 文件系统实测，不是仅检查自写函数

主要结果来自[本机 R3 JSON](filesystem-result-20261017-r3.json)：9 项观察通过、2 项负对照复现。另有[受限环境 R4](filesystem-result-20261017-r4-sandbox.json)的真实 polling 回退通过；其中目录原生 watch 仍失败，不能把 R4 写成全绿。

| ID | 实际操作与证据 | 对正式实现的影响 |
| --- | --- | --- |
| FS01 | 实际中文/空格/点文件保持 CRLF；拒绝越界 `..`、绝对路径、盘符、UNC、URL、NUL；根外 symlink 拒绝，根内别名识别为同文件 | 使用真实根/目标身份与路径边界；字符串 `startsWith` 不足。该结果只证明静态拓扑场景 |
| FS02 | 不同项目相同相对路径不同身份；同根 symlink 别名共享文件身份；host 不同不合并；实验 registry 拒绝错误 owner/generation | 文件身份与 task UI scope 分开。**本条没有验证 Electron IPC sender/frame**，仍须正式 controller 集成测试 |
| FS03 | 原根被 rename，同路径新建另一个目录后，旧 lease 以 dev/ino 不符拒绝 | root generation 不能只比较显示路径；旧 task 的 cwd 归属须明确 |
| FS04 | 独立 Node 子进程写入等长内容并恢复同 mtime；mtime/size 完全相同，hash 变化；旧 revision 保存返回冲突 | mtime 或 mtime+size 不能单独代表内容版本；可编辑文件在基线读取/提交校验中包含内容 hash |
| FS05 | 临时文件完整写入并 fsync，故障注入在 rename 前；原文件不变、临时文件清理；成功保存保持 BOM/中文/CRLF 和 mode `640` | 生产保存要完整 bytes/编码保真与 precommit 清理；未证明 ACL/xattr/所有者保持、目录 fsync 或断电耐久性 |
| FS06 | 32 次 256 KiB 原子替换；独立读取子进程观察 66 次，0 次半内容、0 次读取错误 | 支持本机同目录 rename 的完整内容可见性，不证明跨平台或跨进程 CAS |
| FS07 | 外部独立进程在最终校验前写入；保存返回 conflict，外部内容不被覆盖 | 最终 revision 重检有真实作用，但必须再看 FS08 |
| FS08 | **负对照**：外部进程在最终校验后、rename 前写入；随后 rename 覆盖了外部写入 | 已证 `hash + 原子替换` 仍存在竞争窗口，不能在产品/测试写“绝不丢外部并发修改” |
| FS09 | **负对照**：允许路径完成检查后，父目录被换成指向根外的 symlink；仅最终组件 `O_NOFOLLOW` 仍写到了根外的合成 sentinel | Node 路径重检及 final-component no-follow 不是对抗性目录拓扑保证；必须补平台原生、目录描述符锚定策略及相同攻击探针 |
| FS10 | 获准本机执行时目录 watch 收到多次 rename 类通知；取消订阅后无新通知。受限环境多次未收到 | 事件是失效提示而非确定操作账；需健康/覆盖声明、snapshot rescan、错误与 polling 回退。原生 watcher 的安装包行为尚未验 |
| FS11 | 绑定文件 inode 的 watch 在 atomic rename 后只报 rename，后续新 inode 的编辑没有被观察到 | 不能永久只 watch 文件本身；观察父目录并重绑/补扫 |
| FS12 | 即使目录原生 watch 不工作，有界目录快照 polling 仍发现编辑、原子替换、新文件 | fallback 可行；实验仅 2 个文件/50ms，不能将该频率的全项目 hash 扫描直接用于生产 |

### 2.1 需要固定的工程取舍

1. **本地 Provider 安全边界**：Electron main 负责 lease/owner/generation；纯 Node 方案先作为原型服务算法，不标为完整防逃逸。正式可写 Provider 要验证目录组件逐级打开、句柄锚定操作、根/父身份变动及 symlink 策略。POSIX 与 Windows 需要各自能力探针，不能用 JS 类型替代。只读 preview 也不允许任意路径兜底。
2. **保存的两种保证分开**：完整文件替换降低半写风险；版本校验降低旧基线覆盖风险；它们不共同组成系统级 CAS。应用内用 canonical file 串行队列和 opId 幂等；跨程序还需受控锁/平台协调机制，并验证不合作的写入者边界。未消除的窗口显式进入风险与验收，保持原始基线/草稿/失败恢复，不能宣称已证明绝对无丢失。
3. **watch 健康必须显式**：`coverage: native|poll|none` 与 `resyncRequired` 是实际能力，不是 UI 文案。只扫描展开目录和已打开文件，原生事件做失效触发；后台变化/原子替换后重新 stat/revision。轮询按可见性、目录数与预算退避，停止订阅后释放 timer 与在途请求。
4. **身份策略固定为同窗共享模型**：同一 window 下 canonical file 相同的多个 task 视图可共用 DocumentRegistry，UI tabs/树独立；如实现阶段选择 buffer 分离，必须像不同窗口一样通过 revision 进入冲突。不能只用 `main + relativePath` 或全局 activeProject 推断文件归属。

## 3. Office 同格式往返与独立读取

[office-probe.py](office-probe.py) 用 python-docx/openpyxl/Pandoc 生成三种自有文档，添加带 OPC relationship 的未知二进制 sentinel，在 XML 中只改一个已知标记，其余输入部件保持原 bytes。LibreOffice 读取并重新输出同格式，再转 PDF。检查器包括不同实现的 python-docx/openpyxl、标准 ZIP/XML、pypdf 与 Poppler，而非仅让同一引擎自读自写。

最终结果见[Office R3](office-result-20261017-r3.json)。`exitCode=0` 不是唯一成功条件；实际输出存在、ZIP/XML 有效、内容标记、部件变化和独立读取均记录。

| 类型 | 已观察结果 | 不能推出的结论 |
| --- | --- | --- |
| DOCX | 修改标记、中文、1 个表格、1 张内嵌图保留；PDF 2 页，pypdf/Poppler 都读到标记；**未知 opaque 部件丢失**；stylesWithEffects/webSettings 等部件也有省略/重写 | 不能用于无检查覆盖任意 DOCX；没有做版式逐像素、复杂修订/公式/字体/批注/签名验证 |
| XLSX | 2 sheet、`SUM(A2:B2)`、结果 5、带前导零的长字符串、`0.00` 格式、A4:B4 合并、批注文本、1 个图表部件保留；本 fixture 的 opaque 保留；PDF 3 页且标记可提取 | 原部件名变化不自动等于语义丢失；相反，仅本 sentinel 保留也不证明所有未知部件、宏、外部连接/透视表无损 |
| PPTX | 2 slides、1 张图片、编辑标记保留；PDF 2 页，中文及标记能提取；本 fixture 的 opaque 保留；tableStyles/theme2/viewProps/custom props 等部件有省略/重写 | 不能证明动画、备注、主版、图表、字体、对象坐标和未知关系无损；没有视觉验收 |

首次受限运行全部 abort，获准运行的初版输入 DOCX/PPTX 仍失败。原初版通过通用 XML 库重序列化了 OPC namespace；R3 改为保留原 namespace 写法，仅插入固定自有关系后可读。历史脚本/结果保留，**不能把旧 fixture 失败当成格式不可实现，也不能隐去准备方式对结果的影响**。

## 4. 真正的文档编辑命令探针

仅做转换不足以证明编辑适配。新增[UNO 探针](office-uno-probe.py)使用现有 LibreOffice 的官方 Python/UNO runtime，启动随机本地 pipe、独立 profile、Hidden 文档、禁止宏与文档外链更新。它不连接用户现有 Office 实例，不调用图形界面。

[实际结果](office-uno-result-20261017.json)：三类均完成 **创建→首次保存→关闭→重开→原生文档模型编辑→同格式保存→PDF→独立 Poppler 标记检查**，引擎正常退出。

UNO 的 `storeAsURL` 会改变文档持久化位置，纯导出使用 `storeToURL`；adapter 必须区分“编辑副本的持久化”与“预览 PDF 导出”，不得把后者标成原文档已保存。[官方 XStorable 契约](https://api.libreoffice.org/docs/idl/ref/interfacecom_1_1sun_1_1star_1_1frame_1_1XStorable.html)

| 命令模型 | 本次真实编辑 | 实测结果 |
| --- | --- | --- |
| Writer `Text.String` | 重开 DOCX 后替换正文 | 修改标记在 OOXML 和 PDF 中均可读 |
| Calc `Sheets/cell.String/cell.Value/calculateAll` | B2 从 3 改为 10；A2=2，SUM 随之计算 | 结果 12.0，2 个工作表；修改标记保存并可独立读回 |
| Impress `DrawPages/TextShape.String` | 重开 PPTX，定位含旧标记的文本对象并改写 | 2 个幻灯片保留，修改标记保存并可独立读回 |

这证明**本机已有可编程的实际编辑后端**，不是只有 PDF 预览或前端 mock。没有证明 Codex 风格的光标/选区/拖拽、复杂格式工具、撤销历史、流式物化、Office 协同、Electron 打包、各平台库加载或任意文件保真；这些必须继续通过 adapter/fixtures 验证，不能把 3 个最小命令等同全部编辑器完成。

## 6. Office adapter 可执行落点

拟增加的 `OfficeEngineAdapter` 是后续正式开发契约，本轮未放入 `src`：

```ts
interface OfficeEngineAdapter {
  probe(): Promise<{engine:string; version:string; capabilities:CapabilitySet}>;
  open(input:{assetId:string; revision:string; intent:'preview'|'edit'}): Promise<OfficeSession>;
  inspect(sessionId:string): Promise<PackageFeatureManifest>;
  apply(sessionId:string, operation:TypedOfficeCommand, expectedStateVersion:number): Promise<StateVersion>;
  render(sessionId:string, pageOrSheet:string, scale:number): Promise<RenderAsset>;
  materialize(sessionId:string, stateVersion:number): Promise<{uploadId:string; manifest:PackageFeatureManifest}>;
  close(sessionId:string, disposition:'flush'|'discard-confirmed'): Promise<void>;
}
```

- `apply` 首批契约覆盖探针已验证的 replace text、set cell value/formula、replace slide text；后续逐项加样式/表格/幻灯片命令与撤销日志，不能先声称完整工具条可用。禁止接收任意 service name、URL、脚本或宏。
- Office 引擎只读 revision 固定的临时副本，materialize 到新临时产物；正式写回仍走 main 的 root lease、revision、opId、队列。UNO `storeAsURL` 不直接得到用户项目路径。
- 初始压缩包做 entries/relationships/content-types/宏/外链/签名/未知部件 manifest；导出再次比对。路径名变化与语义变化分开判，不仅比部件数量。
- 发现无法解释的丢件/关系断裂，保存进入 `blocked/persistence`，原件不覆盖、buffer/编辑日志保留；提供可查看的损失清单。若用户选择“另存有损副本”，该副本动作不能把原文件标成 saved。完整原格式写回目标仍保留，需替代引擎或可验证的部件保留实现补齐。
- 不可盲目把丢失 ZIP 条目追加回新文件：关系 ID、对象引用、签名、主版可能已改，字节被加回不等于语义有效。PPTX/XLSX fixture 要用不同读取器及渲染差异再验。
- 进程预算、取消、崩溃、超时、temp/profile 清理与不执行外链/宏单独验证。UNO私有pipe减少误接用户实例，**不是完整进程沙箱证明**。

### 8.1 保存与目录安全（[脚本](anchored-save-probe.py) / [结果](anchored-save-result-20261017.json)）：10 项，9 通过、1 残余窗口

| ID | 实际操作 | 结果 | 对实现的约束 |
| --- | --- | --- | --- |
| AFS01 | FS09 重放：已持有目录 fd 后把父目录 a 改名并换成指向根外的 symlink，再提交写入 | 内容落在被持有 fd 指向的原目录（现名 a.moved），根外 sentinel 未变、根外无新增 | 提交使用 `dir_fd` 的 `openat/renameat`，不能用路径字符串；提交后须复核“根内该路径仍指向同一目录”，不一致要提示，因为落点是安全的但未必是用户期望的路径 |
| AFS02 | symlink 在逐级打开之前已存在 | 逐级 `O_NOFOLLOW\|O_DIRECTORY` 拒绝（ELOOP） | 根内合法 symlink 策略要单独产品决策；默认拒绝 |
| AFS03 | 根目录被改名后新建同名目录 | fd 的 dev/ino 与路径的 dev/ino 不同 | 可作为 lease/generation 失效依据，与 FS03 一致 |
| AFS04 | 交换式提交（写临时→`renameatx_np(RENAME_SWAP)`→校验被换下的 inode→删除）无竞争 | 保存成功，目录无临时文件残留 | 需要 macOS `renameatx_np`；Linux 对应 `renameat2(RENAME_EXCHANGE)` **本机未验证**；Windows 无等价调用，需另寻方案 |
| AFS05 | FS08 重放：外部进程持有旧文件 fd，在最终校验之后、提交之前写入 | 被换下的旧 inode 与基线 hash 不符 → 换回并返回 conflict，外部内容保留 | 把 FS08 的“静默覆盖”变成“检测并还原”；还原动作本身也有极短窗口 |
| AFS06 | 提交之后外部进程仍向旧 fd 写入 | 数据落在被换下的 inode，被检测并换回，不丢失 | 同上 |
| AFS07 | 交换后、校验前，另一进程按路径新打开并截断写入（原先的负对照）。**加入“提交后回读”后重测** | 回读发现内容不是我们写的 → 返回 conflict（kind=overwritten-after-commit），对方内容保留，不再显示“已保存” | 把“静默丢失保存”变为“可见冲突”；调用方保留本地草稿 |
| AFS10 | **负对照**：回读结束之后才发生的写入 | 保存已成功，无法在保存时刻区分；只能由监听发现 | 残余窗口缩小到“回读与返回之间”，**宽度未测量**；产品仍不得承诺“绝不丢失外部修改” |
| AFS08 | 同一 opId 重复提交 | 返回同一结果，不重复落盘 | opId 幂等由 controller 保证 |
| AFS09 | 保存含 BOM/中文/CRLF 的内容，原文件 mode 640 | 字节与 mode 保持 | **不保证** ACL、xattr、owner、目录 fsync、断电耐久性 |

结论：方案可从“hash 重检 + 原子 rename”升级为“目录 fd 锚定 + 交换式提交”，FS09 被消除（落点在原目录），FS08 中“已持有旧 fd 的写入者”的覆盖被消除；**按路径新打开写入的不合作进程：回读前的写入被检测为冲突（AFS07），回读后的写入仍无法在保存时刻发现（AFS10）**。这需要 native broker（Node 标准库没有 `openat`/`renameat`，Python 只是验证可行性的手段），生产要用 N-API/子进程代理并在三个平台各自实现与验证。

### 8.3 解析引擎成本（[脚本](engine-cost-probe.mjs) / [结果](engine-cost-result-20261017.json)）：8 通过

对象是原型实际使用的 markdown-it 14.1.0 + markdown-it-texmath 1.0.0 + KaTeX 0.16.22 + js-yaml 4.1.0（经 `file-markdown-model.mjs`）。样本由固定种子生成并记录 SHA-256。耗时是 **Node 主线程**，不是 Chromium 主线程，不能直接当界面卡顿结论。

| 样本 | 块数 | 解析 p50 | 全量渲染 p50 |
| --- | --- | --- | --- |
| 100KiB | 2,225 | 4.7ms | 10.4ms |
| 1MiB（含公式） | 22,575 | 26.1ms | 66.5ms |
| 1MiB（无公式） | 21,079 | 26.0ms | 5.7ms |
| 10MiB（5 次） | 223,522 | 327.8ms（p95 336.1ms） | 666.8ms（p95 804.8ms） |

- 公式是渲染成本的主要来源（1MiB：66.5ms vs 5.7ms）。原型每次文本变化会重新解析全文，10MiB 时单次约 0.33s，必须防抖/Worker/按块缓存，不能照搬。

- 损坏/极端输入（NUL、孤立代理对、5000 层引用、500 层列表、2MB 单行、2000 列表格、5 万个 `*`、未闭合围栏）均不抛错、字节往返，最慢 21.5ms。没有发现灾难性回溯，但这不是对抗性模糊测试。
- 内存：10MiB 解析峰值约 +17MiB RSS，连续 5 轮解析后 RSS 仅增长 1 MiB（强制 GC 后），未见累积；这是 Node 进程内数字。
- 依赖体积：markdown-it 749KiB、texmath 103KiB、KaTeX 3891KiB、js-yaml 395KiB、mermaid 64519KiB（安装体积，不含传递依赖）；全部 MIT。构建产物里 mermaid 是按需加载（`mermaid.core` 506KB / gzip 142KB，另有 100 多个图表分包），主包 1,552KB（gzip 466KB）。
- 本组测试**没有**覆盖 PDF.js、LibreOffice 的耗时/内存与取消，它们留在 GAP-04/05。LibreOffice 的耗时、内存和跨平台分发仍未测量。

**重要发现（发现自实验脚本的一次误判）：** XLSX 共享字符串表中“唯一匹配”不代表只有一个单元格在用。第一版脚本的“字节替换应被拒绝”判据没有成立，原因是样本里 `SHARED_TEXT` 去重后在字符串表只出现 1 次，朴素替换成功并**同时改掉两个单元格**。因此规则是：改共享字符串前必须统计所有工作表中的引用数，引用数不是 1 就追加新字符串并改指向。同样，样本曾因新版 openpyxl 写内联字符串而不含共享字符串表，使 OP06/OP07 一度无意义，已改为转换成真实 Excel 的共享字符串写法后重跑。另外窄列会让渲染器截断文本，标记需放得进列宽。

**仍未证明（保持未关闭）：** 新增/删除行列、新增幻灯片/对象、合并单元格、公式编辑与依赖链重算、图表数据、修订的接受/拒绝、批注新增、样式变更、字体、复杂版式的渲染保真、真实 Word/Excel/PowerPoint 产出的文件（本实验只用 python-docx/openpyxl/pandoc 生成并手工注入）、数字签名（任何改动都会使签名失效，需明确提示）、宏（只保留，不执行）、加密/密码保护文件、以及 Windows/Linux。结构化补丁越复杂，越需要 OOXML 模式校验和 Word/Excel/PowerPoint 本体的打开验证，本机没有 Microsoft Office，无法验证“能否被 Office 本体打开”。

## 11. R3 第三批：与 SmartDD 业务的接入闭环（M9-GAP-07）

2026-10-17。四个隔离实验，均默认 Bash 权限、macOS（Darwin 25.6.0）arm64、Node v22.23.1、不提权、不连接任何真实主机或模型。**它们验证的是“适配层怎么探测、限制、降级和清理”，不是 Claude Code / Codex 的真实行为。**

### 11.1 把文本放进终端输入（[脚本](terminal-injection-probe.mjs) / [结果](terminal-injection-result-20261017.json)）：8 项，7 通过 + 1 个负对照

真实 PTY（SmartDD 同一个 node-pty 1.1.0）＋真实 zsh 5.9＋受控子进程；清理与拼装逻辑取自原型的 [file-reference-model.mjs](../../../../../prototypes/m6-codex/src/file-reference-model.mjs)（与 145 项单元测试同一份实现）。

| ID | 实际操作 | 结果 |
| --- | --- | --- |
| TI01 | 启动 zsh | 输出含 `ESC[?2004h`：括号粘贴是否启用要看目标程序实际发出的这个序列（xterm 的 `modes.bracketedPasteMode` 即由它而来） |
| TI02 | 括号粘贴多行 `touch A\ntouch B` | 粘贴后两个文件都**不存在**；用户按 Enter 后才执行——提交永远是用户的显式动作 |
| TI03 | **负对照**：不清理，文本里带 `ESC[201~\ntouch INJECTED` | **注入的命令真的被执行了**（哨兵文件被创建）。括号粘贴本身不能防住内容里的结束标记 |
| TI04 | 同样文本经 `pasteData` 清理 | 命令没有执行，粘贴区内部不再含 ESC |
| TI05 | 非括号模式、两行 `first\rsecond\r` | **危险**：两行都被当作回车提交（`GOT:first`、`GOT:second`）。折叠成一行后粘贴不提交，用户 Enter 后只提交一次 |
| TI06 | `^C` 写入前台 `cat` | **危险**：未清理时前台进程被中断退出；清理后进程保持存活 |
| TI07 | 7,900 字符（12,060 字节，中英文+emoji）括号粘贴给受控 raw-mode TUI | 逐字节等价到达（长度与 SHA-256 相同），耗时约 50ms，未被提交 |
| TI08 | 各种结尾换行的输入 | 括号与非括号两种数据都不以回车/换行结尾——**永不自动追加回车** |

**规则（已写入需求 R05.10）：** 来自文件的文本一律不可信，放进终端前必须清理：去掉 ESC、除 `\t` `\n` 外的 C0 控制字符、DEL、C1 控制字符（含 0x9B）、双向控制字符，孤立代理对替换为 U+FFFD；括号粘贴模式保留换行，否则折叠为空格；永不追加回车；总长上限 8,000 字符、所选文字上限 4,000 字符/200 行，超限给出明确提示。

**这条路径在生产里还没有：** `src/main/index.ts:133` 的 `events.on(ptyInputEvent, …) → ptys.write(ptyId, data)` 对渲染进程发来的任意 `ptyId`/`data` 不做任何校验。文件引用不应复用这条原始写入通道，而应该是一个专用的、有校验的“终端插入”RPC（校验 ptyId 属于运行中的任务、清理、限长、不回车）。**这是文档里的设计要求，不是已实现的修改。**

**未验证：** Claude Code / Codex 真实 TUI 对括号粘贴与 `@路径` 的处理（`@` 提及与行号写法需分别验证，原型默认使用不依赖任何 CLI 专有语法的通用写法）；CLI 正在忙于输出时插入文本会进入它的输入缓冲，没有可靠的“忙/闲”检测；Windows ConPTY；多字节在极端分片下的行为（本次一次写入）。

### 11.2 语言服务（LSP）适配（[脚本](lsp-adapter-probe.mjs) / [结果](lsp-adapter-result-20261017.json)）：11 项全部通过

真实服务 typescript-language-server 4.3.4 + typescript 5.9.3（装在仓库外的 `/tmp/m9-lsp`，**没有加入 SmartDD 依赖**），自写最小 LSP 客户端。

| ID | 结果 |
| --- | --- |
| LS01 | 握手约 53ms；只对服务端声明的能力发请求（`definitionProvider`、`referencesProvider`、`hoverProvider`），未声明的方法在客户端即拒绝 |
| LS02 | 跨文件 definition 定位到 `a.ts` 第 2 行；references 3 处（2 个文件）；hover 返回类型文本 |
| LS03 | **列必须是 UTF-16 单位**：emoji 之后的符号，按 UTF-16 列（11）命中，按字符数（10）则无结果 |
| LS04 | 请求发出后文档版本变化，旧响应被丢弃（`stale`），新请求正常 |
| LS05 | `$/cancelRequest` 后请求正常结束，不挂起 |
| LS06 | 20 次 definition：p50 0.3ms、p95 4ms；服务进程约 56MiB（tsserver 子进程另计，单项目小样本，预算未冻结） |
| LS07 | definition 指向 typescript 内置 `lib.dom.d.ts`，被分类为 `outside-root`（只读展示，不进根内标签、不获得保存能力） |
| LS08 | 强杀服务父进程：未完成请求 2ms 内以 `EXIT` 拒绝；3 个子孙进程约 50ms 内自行退出；重启后可继续 |
| LS08b | 服务自成进程组后 `kill(-pgid)` 一次清掉 4 个进程（约 52ms）。Windows 需另用 `taskkill /T`，**未验证** |
| LS09 | `shutdown`+`exit`：退出码 0，整棵进程树即时退出 |
| LS10 | 无响应服务（SIGSTOP）：请求在 600ms 预算内以 `TIMEOUT` 拒绝，清理后无残留 |

**过程更正：** 初版 LS08/LS09 曾报“强杀后 tsserver 孙进程遗留”，**这是我的检查方式造成的误判**——当时数的是系统里所有 `tsserver`，混进了别的实验的进程。按进程树精确追踪后，孙进程在父进程被强杀后约 50ms 内自行退出，并没有遗留；进程组清理被保留为可选的稳妥做法，而不是必需。**没有验证：** 其他语言服务器、服务器的安装/分发/版本管理、项目配置（tsconfig 之外）发现、大项目的索引耗时与内存、Windows。

### 11.3 扩展 viewer（MCP）适配（[脚本](mcp-adapter-probe.mjs) / [受控服务](mcp-fake-server.mjs) / [结果](mcp-adapter-result-20261017.json)）：13 项全部通过

真实服务只用于握手与关闭（本机已装的 `rea mcp`）；适配策略取自原型的 [file-viewer-policy.mjs](../../../../../prototypes/m6-codex/src/file-viewer-policy.mjs)，与单元测试同一份实现。

| ID | 结果 |
| --- | --- |
| MC01 | 真实 `rea mcp`：握手 742ms；声明能力只有 `tools/completions/prompts`，**没有 resources → viewer 不可用**（配置了的 MCP 服务 ≠ 可用 viewer）；`tools/list` 返回 207 个工具、**3,087,986 字节** |
| MC02–03 | 关闭 stdin 后进程树在预算内退出；未声明的 `resources/list` 返回 `-32601`，被识别为“不支持” |
| MC04 | 受控服务：能力门控后列出并读取会话资源 |
| MC05 | `file:///etc/passwd`、`viewer://doc/../secret`、其他资源、`http://` 在发送前被拒绝，服务端日志里**没有**对应的读取请求 |
| MC06 | 传输层单行上限（由最大资源 20MiB×4/3 推导，约 28.2MB）：30MiB 资源以 `TOO_LARGE` 在约 120ms 内拒绝，连接仍可用；服务声明 `size=10` 但实际 3MiB 时，按**解码后真实字节**拒绝 |
| MC07 | 写回：旧 `ifMatch` → `conflict`；新 `ifMatch` → `saved` 并更新基线；只有 `saved` 才更新基线；超限 → `too-large` |
| MC08 | 未声明 resources：不可用，且适配层没有发出任何 `resources/*` 请求 |
| MC09 | 无响应请求在 500ms 预算内 `TIMEOUT`；服务稍后的迟到响应被丢弃，不污染后续请求 |
| MC10 | 服务在请求中途退出：请求立即以 `EXIT` 拒绝；重启后可继续 |
| MC11 | 5,000 条通知洪峰：每秒上限 200，丢弃 4,800 且计数可见；之后请求 10ms 内响应 |
| MC12–13 | 非 JSON、半截 JSON、20 万字符超长行不会打死客户端；服务退出后新请求以超时/`EXIT` 失败而不是挂起 |

**这一批发现的两个对设计有实际影响的事实：** ① 真实服务一条 `tools/list` 响应就有约 3MB，**我最初设的 1MiB 单行上限让真实服务的响应被丢弃**（MC01 因此超时）——传输层上限必须按最大资源推导（约 28MB），超限时必须立刻让对应读请求失败而不是等超时；② viewer 适配层只需要 `initialize` 和 `resources/*`，**不应该请求 `tools/list`**。另：`rea mcp` 握手返回的 `serverInfo.version` 是 6.5.0，而命令行 `rea --version` 是 6.1.0，我没有查原因，只如实记录。

**没有验证：** viewer 在浏览器侧的隔离宿主/沙箱 UI（此前只有静态证据）、资源订阅、真实第三方 viewer、文件系统上的“viewers.write”契约（MCP 标准本身没有写接口，用的是受控服务里自定义的 `viewer_write` 工具，**这不是标准能力**）、Windows。超限那一行（约 40MB base64）仍会被完整读入内存后丢弃，生产应在传输层按字节计数尽早断开。

### 11.4 远程文件 provider（[脚本](sftp-provider-probe.mjs) / [结果](sftp-provider-result-20261017.json)）：9 项，7 通过 + 2 个观察到的缺口

客户端是 SmartDD 的同一个依赖 ssh2 1.17.0；服务端是 **ssh2 自带的最小 SFTP 服务**（回环、临时目录、随机端口与随机凭据），**不是 OpenSSH**，真实服务器的 SFTP 扩展、rename 语义、权限、符号链接、编码都可能不同。本机没有可用的 sshd（22 端口关闭）。

| ID | 结果 |
| --- | --- |
| SF01 | 主机密钥固定：指纹匹配才完成握手；不匹配在认证前被拒绝（服务端没有收到任何认证尝试）。**生产的 `src/main/core/connections/ssh-tester.ts` 明确写着“M2 不校验主机密钥，只报告指纹”**——远程读写源码之前必须补上首次固定与变更拒绝 |
| SF02 | 列目录、stat、读取含中文/空格文件名与 UTF-8 内容 |
| SF03 | 能力探测：目标已存在时 rename 是否覆盖（规范行为为失败）→ `atomicReplace=false`；覆盖型服务器 → `true`；`compareAndSwap` 恒为 `false`（SFTP 没有条件写）；探测文件在两种服务器上都被清理 |
| SF04 | 不能 rename 覆盖时：默认**拒绝写回**、原文件不变；用户明确允许才走“删除再 rename”的非原子路径 |
| SF05 | 远程内容已变化：写回返回 `conflict`，不覆盖 |
| SF06 | **观察到的缺口**：校验之后、rename 之前的外部写入被**静默覆盖**（SFTP 没有条件写）。远程 provider 必须声明 `compareAndSwap=false`，界面不得承诺“不丢失外部修改” |
| SF07 | **观察到的缺口**：上传中途连接被切断，**裸 ssh2 的写回调用一直挂起（3 秒后仍无结果）**；加“连接关闭/超时”保护的 provider 2ms 内以 `CLOSED` 失败，原文件不变，遗留临时文件在重连后被清理，基线仍有效 |
| SF08 | 服务端不再响应读取：provider 自加的 1.2s 超时触发，销毁连接后可重连并继续读取（ssh2 的 SFTP 请求自身没有超时） |
| SF09 | 错误密码被拒绝；凭据不出现在实验结果里 |

**没有验证：** OpenSSH 真实行为、公钥/Agent 认证、符号链接与权限、大目录/大文件吞吐、远程变化监听（SFTP 没有监听，只能轮询）、Windows 服务器；以及“远程工作区”这个产品能力本身是否要做、范围多大（需求 D07，待评审）。

### 11.5 这一批的局限

- 以上四组都是 **macOS、Node 22、回环/本地** 的结果。
- 没有任何一组使用真实 CLI（Claude Code、Codex）、真实模型、真实第三方 viewer 服务或真实 SSH 服务器。
- 实验脚本自己犯过的错都已修正并记录在[执行记录](../../验收/执行与缺陷记录.md#10-r3-第三批gap-07-业务接入闭环)：参数解析把 `-1` 当有效下标、LSP 误数进程、MCP 单行上限、ssh2 指纹是十六进制而我拿它比 base64。
