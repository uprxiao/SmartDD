# 开发前 08：保存与恢复

## 2026-10-18 生产接续：改名后同名重建（DEV060）

本段是正式开发后的发现与修复，不改写下方开发前实验的历史结论。依据 R3.4-P1 的 R02.7/R04.4，L18 原生红测与旧 r12 实际 App 复现：a 改为 b 后，立即用同样字节创建新 a，旧引用没有观察到路径缺失，clean 视图会接受新 a，dirty 视图仅成为普通内容冲突。

生产 `FileService.documentRequest` 在物理身份变化时只读取当前父目录：若原 device/inode 仍以另一名字存在，将旧 capability 标记为 missing/changed。异步目录读取后再次核对引用与 revision，旧标签保留原身份、正文及独立草稿；显式保存和保留本地修改都不能写入新 a。这里采用已批准的 missing 策略，没有自动跟随改名，也不增加 DTO 或持久化字段。普通 clean 原子替换、原 inode 返回及独立草稿恢复仍按既有回归验证。

已验证同目录 a→b→新 a 的 clean/dirty 分支；不据此声称具有全根改名图、任意跨目录历史追踪或跨进程原子 CAS。r13 的源码、红测、真实 App 原步骤与保存/Office 回归见[完整证据](../验收/证据/m9-acceptance-l18-b20-dev060-r13-20261018.json)。

2026-10-17，依据 R3.4 的 R07.1–R07.10、R07.17/R07.18 与 D06。结论：**保留冲突版本的保存路线、启动核对与故障处理已具备可实施契约**。在既有7项保护检查和6项额度实验基础上，当前修订 [10/10 检查通过](../验收/证据/predev-save-crash-result-3.json)，包括真实子进程 SIGKILL、真实 FIFO／非普通文件拒绝与坏记录隔离。先前 [R2 的7/7结果](../验收/证据/predev-save-crash-result-2.json)保持历史事实，不把两轮重复项累计为17项。生产 broker、下述分区布局与跨卷复制未实现，系统断电／物理满盘仍未验。

## 整体思路及现状

源文件与用户草稿分开；提交前先保留独立草稿、候选与准备日志；平台提交后保留被换下的 inode，核对路径身份和版本。发现竞争、超时或提交后异常时停止自动保存，保留所有可见版本，向用户说明恢复冲突。恢复过程先读后判断，不自动把某个版本交换回目标路径。

CLI仍直接按自身规则操作磁盘，文件区独立刷新；本方案仅保护 WillYou 右侧手工编辑与可写查看器，不增加CLI批准流程。旧“发现竞争就再换回”的负对照仍保留，不能复用其错误恢复代码。

## 生产存放布局：与探针目录明确分开

**D06 的独立草稿与权威日志仅在本机 userData，不能放入项目目录。** 现有 `save-recovery-probe.py` 和本次故障探针把所有材料放同一自有临时目录，是为了复现交换／中断，不是生产目录方案。不能把它的 `root/.m9-recovery/*.draft/*.json` 原样搬进 App。

| 材料 | 生产位置与身份 | 必须遵守的规则 |
| --- | --- | --- |
| 独立 draft、权威 journal、索引／额度、已获取的恢复快照 | `userData/file-recovery/v1/<opaqueProjectId>/<opId>/`；目录0700、内容0600；严格内部ID，不拼用户文件名 | 草稿不可与新目标共用 inode；日志记录可信根／目录／文件身份、内容版本和操作状态，不能把任意路径字符串当授权。userData 迁移或不可写时停止提交、保留内存输入 |
| staging 与 displaced 原 inode | 目标文件所在同一卷、目标父目录内的私有目录，例如 `.willyou-recovery-<installationId>-<randomId>/`；只在 broker 注册并核验 owner、目录身份、无symlink、卷身份后使用 | 临时物化候选必须与目标同卷，交换可以跨这两个受信目录fd。被换下的原 inode 保留在该私有目录，不能为迁入 userData 而跨卷 `rename` 或提前 unlink。目录名冲突／预存外来目录不能自动接管 |
| 目标文件 | 可信 root／parent fd 下的原 leaf | 仅候选通过且准备日志／草稿完成同步后才提交；不把目标移到 userData，不依赖跨卷原子替换 |

权威 journal 记录 `userDataDraftRef`、`volumeId`、`targetParentIdentity`、`transactionDirectoryIdentity`、各内部 leaf 和 inode/hash。每次恢复重新解析主进程签发的文件引用；没有可信登记或身份不符的项目内隐藏目录只是用户目录，不能凭名字认领、隐藏或清理。私有目录建立后要先在 userData 登记并同步，再在其中创建 staging；登记与实物不一致作为未完成事务报告。

userData 与目标分处不同卷时，采用以下明确顺序，不假设存在跨卷事务：

1. 在 userData 预约容量，写独立 draft 并同步；在目标卷预约候选空间，写同卷 staging 并同步；再同步含两端身份的 `prepared` 日志。任一步失败都不修改目标。
2. 用目标父目录fd与已核验事务目录fd执行该平台的同卷提交，保留 displaced inode。userData 日志的状态写入与目标卷提交不原子，所以启动恢复以两端实物的 inode、内容哈希及日志共同判定，不能只看 `prepared/saved` 标签。
3. 若要把 displaced 内容带入 userData，在**额外预约其实际大小＋日志开销**后，经已锚定的原 inode fd 复制到新临时快照。复制前后检查身份、大小及版本；完成写入、同步和哈希核对后才登记 `snapshotAt/sourceIdentity/sourceVersion/hash`。空间不足、卷断开或读到变动版本时记录失败／待重试，保留源 inode和已有草稿；不能把半份副本当可恢复版本。
4. 该快照只表示某个时刻读到的内容，**不能代替仍可能被外部旧fd继续写入的 displaced inode**。复制成功不授权删除源 inode。原卷暂不可用时，恢复页仍能展示 userData 草稿／已核验快照，并明确原版本待卷恢复；不自动把快照覆盖到新出现的同名路径。
5. 清理仅针对已确认解决、重新核验身份与哈希的记录，沿用保留规则；未解决、源卷失联或版本又变化时不按年龄清除。有限保留期不是对外部任意时长持有fd的安全保证。

**树、搜索、导出统一按受信内部对象登记过滤。** userData 的恢复子树与 broker 自建并登记的同卷事务目录／对象不提供普通 fileRef，不进入名称枚举、全文搜索、最近文件或将来的文件归档。应在后端遍历前和返回前校验身份，不能只在 UI 隐藏；任何搜索 mask 都不能重新纳入这些内部对象。普通隐藏用户文件继续按 R02.4 显示，不能用 `.willyou-*` 通配符误藏用户同名文件。当前 M8 项目导出只序列化项目配置，未递归打包磁盘目录；正式接入时维持其显式字段白名单，不加入恢复索引、草稿或快照。若将来另有文件打包功能，需共享同一内部对象过滤接口并独立验收。

上述私有目录是应用的数据管理边界，不是对同一系统用户的 CLI 的强制隔离；CLI 仍可按其权限直接操作磁盘。内部目录被替换／修改／删除时，broker 必须记录恢复异常，不能盲信自己的目录名称。

## 状态与操作契约

| 状态/阶段 | 必须保留与校验 | 失败时结果 |
| --- | --- | --- |
| dirty | 内存source、base revision、file identity、编码/EOL/BOM、buffer revision | 失败不丢输入；不能因旧保存回执清掉更新的dirty |
| queued/preparing | 按文件身份串行；验证lease/源版本；事务预约容量；独立draft与staging写完并同步；记录准备日志 | 提交前失败不改目标；保留内存草稿并说明失败，禁止返回saved |
| prepared | 记录root身份、原目标inode、候选inode、base/draft哈希、opId、严格内部文件名；同步日志及目录 | 中断后启动检查，可识别尚未提交，不能仅凭日志state判断磁盘 |
| committing | 目录fd锚定、逐级无跟随；仅操作核实目标和候选；同步平台目录 | 接口超时仅表示unknown，不能因此重写、回滚或删除恢复物 |
| saved | 已核对当前路径/源版本、被换下版本及候选内容，返回权威revision和本次buffer revision | 新输入仍保持dirty；后续外改由watch/重扫发现；不是系统CAS保证 |
| conflict/unknown | current、displaced、独立draft及日志保留；自动保存暂停 | UI区分提交前冲突和提交后恢复冲突；即便current等于candidate，也不自动清除未决竞争记录 |
| recovery | 启动重核两端根／事务目录身份、内部文件名白名单、普通文件类型/大小/inode/hash和额度；打开日志及内容时无跟随、非阻塞并立刻fstat | 准备未提交、内容冲突或提交后需复核分别展示；坏记录逻辑隔离并报告，继续检查其他健康记录；不顺着日志任意路径读取/删除 |
| resolved/cleanup | 确认解决后重新核对各版本身份/哈希，满足保留规则才清理 | dirty/conflict/prepared/inflight/失败及发生新变化的恢复物禁止按年龄淘汰 |

幂等键为opId＋文件身份＋输入版本/候选哈希。同键同载荷返回该次已知结果，变载荷拒绝；幂等回执只描述原操作，不保证文件此刻仍是那个版本。提交后unknown不得因超时自动重发；恢复完成前禁止下一次自动保存越过冲突。

草稿及恢复记录与route分开。拟建持久记录字段为 `schemaVersion, opId, project/task/file identity, leaseGeneration, rootIdentity, originalIdentity, candidateIdentity, baseHash, draftHash, userDataDraftRef, volumeId, targetParentIdentity, transactionDirectoryIdentity, staging/displaced internal names, snapshot metadata, byte counts, state, createdAt, resolvedAt, lastVerifiedIdentity/hash`；这是待生产实现的数据设计，不声称已有数据库表。额度预约/恢复记录索引应由主进程统一管理，启动按已登记身份核对磁盘实物重建，不能扫描任意目录后依名字认领。迁移失败时保留旧日志并禁写，不丢弃旧数据。

恢复读取先以 `O_NOFOLLOW|O_NONBLOCK` 打开，立即 `fstat` 拒绝 FIFO、目录、socket、设备等非普通对象，再按大小上限分块读；读取前后版本变化则不认定为一致快照。`O_NONBLOCK` 防止 FIFO 在类型检查前卡住，**并不保证普通磁盘读取不会因故障阻塞**；生产恢复任务另放入受监督的独立 worker，设截止时间和终止升级，并逐条汇报进度。坏记录的“隔离”指不允许该事务续写或自动清理，保留原始材料及错误，不代表主动搬动／删掉它。一个坏事务不能遮住其他健康事务的恢复结果。

## 容量、编码与元数据

沿用已测默认：项目512MiB、全局2GiB；基础事务预约 `currentBytes + 2×candidateMaxBytes + 64KiB`，覆盖 displaced、独立draft、staging与基础日志；额外创建userData恢复快照时另预约快照实际大小及日志开销，不能重复使用原预约假装有空间。userData卷与目标卷分别检查可用空间，另有128MiB可用空间提示余量；实际write/fsync仍须处理ENOSPC。已解决且复核无变化的历史保留7天/最近2份；未解决版本不按年龄清除。参数不是对外部进程长期持有旧fd的安全回收证明。

文本以原始字节与可编辑source分别维护；解码失败或未支持编码不能默认替换字符后覆盖。UTF-8/BOM与CRLF/CR/LF映射由03编辑器专项验证；保存时保持未编辑行的原行尾，新增行采用文档主行尾，映射与旧undo不兼容时不套用旧历史。编码能力不足必须明确只读/失败，不能伪装无损保存。

替换候选提交前保留权限、owner/group与需要保留的xattr/ACL；复制或核对失败则在提交前停止。新mtime反映修改，不要求伪造旧mtime。本轮仅验证同用户/组、0640和自有合成xattr，**没有完成任意ACL、资源分叉、平台标志与用户元数据全覆盖**；正式平台适配必须保留并复验这些行为。不同平台不能照抄macOS交换原语：Windows/Linux须提供对应实现与真实故障证据，当前结果仅macOS。

## 新增实验与证据边界

[predev-save-crash-probe.py](实验/predev-save-crash-probe.py) 在自有临时目录调用既有真实交换算法：

- 在准备日志完成、交换刚结束、函数返回三个阶段，真实fork子进程并SIGKILL；启动只读恢复均能找到BASE/DRAFT，重复恢复不改任何文件。
- 注入提交前ENOSPC，原件保持BASE；注入提交后目录fsync EIO，记录必须进入需复核状态，BASE和DRAFT均保留。
- 篡改日志的内部草稿路径被拒绝；不根据日志中任意路径读写。
- 0640及一个自有xattr复制并回读通过。
- R3 新增：同一日志目录内放入真实 FIFO、目录、symlink、截断 JSON、超大普通文件、非对象 JSON、错误类型 opId 与过深嵌套 JSON，8 条坏记录均隔离，另一健康记录仍恢复；真实子进程内读取耗时1.96ms，预先冻结截止时间1秒，目录和外部合成 canary 均未修改。
- R3 新增：在完全符合内部命名规则的 draft 路径放入 FIFO，1.5ms内拒绝，另一健康事务不受影响；既校验日志，也校验候选／草稿对象，不能只检查名字。
- R3 新增：prepared阶段杀掉保存进程后，原目标 inode不变但内容被外部改写，依据hash进入 `recovery-conflict`，不误称可以继续提交；无自动恢复写入。

## DEV126 提交与回读的保证范围（2026-10-19，当前本机实现）

依据R07.17/R07.4与L15/Y03。当前Mac native对完整路径写入的分类补齐为可选回执kind=overwritten-after-commit，恢复日志允许并保留此字段；新读取器继续接受旧的无kind记录。该字段不改变原有冲突、unknown或恢复材料保护策略，也不是系统CAS。

| 时间或参与者 | 当前代码及真实测试所证明的边界 |
| --- | --- |
| 应用内提交 | FileService按规范路径与物理documentKey串行；同opId重放旧回执，不再次提交。独立原生草稿/准备日志完成后才交换 |
| 已持有旧fd的写入者、最后检查后至交换前的外写 | 交换保留被换下inode；回读检测其hash不等基线时返回冲突，保留当前路径、被换下版本及独立草稿，不盲目再次交换 |
| 交换后至提交后回读前，另一进程重新打开目标并截断写入 | 当前目标hash不等本次候选时返回conflict，kind=overwritten-after-commit；界面保留本地修改/草稿而非已保存成功 |
| 本应用对目标的整文件替换 | 候选在同卷事务目录中完成并同步，以RENAME_SWAP交换；本应用不会把候选的半写内容作为已提交目标 |
| 提交后回读完成之后的外写 | 已完成的回读无法发现未来写入，saved/revision仅表示该次核验快照。后续由watch或显式重扫取得当前版本；干净buffer可重新加载，存在新本地修改时进入外改冲突 |

外部进程在返回后继续写旧fd、修改新目标或替换路径的行为，不属于应用内队列控制；当前提交通道不提供操作系统级跨进程CAS。受管理材料按既有额度和解决状态保留，不能把有限保留策略说成无限fd寿命下的安全回收。读回后的外写、断电和其他平台必须分别记录，不外推当前Mac结果。完整原生I及打包App复验的分支、源快照、包哈希和实际结果见[DEV126验收报告](../验收/证据/m9-acceptance-save-windows-dev126-r73-20261019.json)；该批仅结案L15/Y03，不代替Y01/Y02的完整矩阵。

## DEV128 中断后的交换前版本识别（2026-10-19）
