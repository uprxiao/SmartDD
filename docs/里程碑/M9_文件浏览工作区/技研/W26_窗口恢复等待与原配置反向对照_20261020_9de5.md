# W26 窗口恢复等待与原配置反向对照

依据 R3.4/P1、W26（R07.18/R08.7），接续[原三格式失败记录](W26_三格式Worker与渲染超时_20261020_9de5.md)。本批补齐原正常引擎的三格式 I，**3/3 通过、零跳过**；正常 App 仍复现 DOCX 原 20 秒超时，W26 继续失败。正式仍 **307/419（73.27%）**，105 未完整、1 失败、6 阻塞，余 112；目标 active，独立优先、用户协作最后，未完成、未发布。见[186 项证据](../验收/证据/m9-diagnostic-office-state-20261020-9de5.json)。

## 新增的业务证据

复用正常 r121。原三格式 I 未开采样、未使用诊断原生副本：DOCX/XLSX/PPTX 的真实 Worker 缺入口、原 15 秒成功回包门闩、重试、迟到原消息、真实损坏 XML/未修复重试/关闭后修复全部通过，分别 7/8/8 个实际 Worker。三个超时分别 15002/15002/15000ms。DOCX 真正产生两页 PDF，独立 ZIP/XML/Poppler 比较通过；XLSX/PPTX 各真实保存并独立重开，非目标部件/结构及旧消息不覆盖新会话的断言保留。I 成功不替代 A。

新正常 App 完整矩阵中，浅色 DOCX 启动恢复与消息超时恢复两组通过，损坏文件原错误/未修复重试也可识别；按原步骤关闭、修复后，再次打开时原 `openOfficePages` 返回 native 20 秒超时，等待真实 canvas 的原断言失败。未继续到后续主题/格式，不把请求的 18 组写成执行通过 18 组。原 r118 XLSX 浅深六组等历史成功保留，当前完整 W26 仍失败。

另两次定向 DOCX 诊断分别只有 1 组和 0 组成功，均在浅色 timeout 恢复阶段再次失败。三个失败 App 的 19 个源分别独立复核：只有首轮明确关闭后修复的 `light-corrupt.docx` 从原 corrupt hash 换回原有效源 hash，其余源 hash 不变；第三轮原生采样、原 spawn/输入/回执及 handler 恢复均留证。失败清理不冒充正常退出。

## 超时前的实际等待位点

第三轮在实际 `office-render` 开始后 9042ms，先核对 vendor 直接子进程 PID、父 PID 与完整固定可执行路径，再采样两秒。1761/1761 主线程样本停在：

```text
NSApplication ... _handleAEOpenEvent
NSPersistentUIManager.hasPersistentStateToRestore
NSPersistentUIRemoteStorageClient.stateDirectoryAtLaunch
dispatch wait / kevent
```

配对的 `NSPersistentUIRemoteStorageClient` 队列在 `preserveStateDirectoryAtLaunch` 等待同步 XPC 回复。随后同一原生进程仍返回原 20 秒 TIMEOUT。它证明该次超时发生在 AppKit 窗口恢复服务等待，不是仅凭 stderr 猜测文档解析、字体或某个权限；**尚未证明服务为什么不回复，也未证明某项 entitlement 是原因**。

初次早期两秒采样主要包含启动过程，不能代替此晚期证据。原生单次正常渲染后来成功时，HIServices/ClientCallsAuxiliary 提示仍存在，因此该提示也不能单独作为失败原因。全部样本仅来自本批自有进程，不查询或操作日常 App。

诊断驱动第一次错误地观察 `stdin.write`，而实际 broker 用 `stdin.end` 发送请求：记录了原进程但未捕获操作类型，该轮不能声称采到了晚期栈。纠正后原请求/结果继续原样转发，才捕获上述实际等待；错误版本及失败均保留。一次外部有界晚期观察没有捕获符合条件的进程，仅作“未采到”，不作“没有卡住”。

## 私有对照及其边界

[Apple 旧版 AppKit 文档](https://developer.apple.com/library/archive/releasenotes/AppKit/RN-AppKitOlderNotes/)将 `ApplePersistenceIgnoreState` 描述为用于自动化测试/调试的用户默认值；[Apple 开源 CF 的 home 选择](https://github.com/apple-oss-distributions/CF/blob/main/CFPlatform.c)优先考虑 `CFFIXED_USER_HOME`，再考虑 passwd/Home。这些历史资料只用于提出假设，不视为当前系统必然行为或生产修复依据。

| 对照 | 实际结果 | 结论 |
| --- | --- | --- |
| 原 broker，仅在新私有 job/home 写入该首选项 | 原 20 秒超时，原件不变 | 单独设置未解决 |
| 私有 broker，仅增加 `CFFIXED_USER_HOME=job/home` | 原 20 秒超时，原件不变 | 单独设置未解决 |
| 两者组合，初次带采样 | 测试 75 秒驱动超时，缺最终业务结果 | 效果未知；不能写成 native 成功或失败 |
| 同一组合，直接 Electron-as-Node 入口、关闭采样 | 两页/73676 bytes，native 9427ms | 仅为私有诊断成功 |
| 紧接着恢复原 broker、原输入、同一直接入口/无采样 | 同样两页，native 3375ms | **组合的因果修复未成立，不应用生产** |
| 私有命令行参数 `-ApplePersistenceIgnoreState YES` | 原厂 CLI 明确拒绝该选项，exit 1 | 不采用 |

所有对照保持原 native 20 秒、broker 30 秒及引擎总预算、原签名/资源验证、原 sandbox/IO/进程/RSS限制。私有 native 副本仅增加上述环境/命令参数，无 TEST 宏；源码、编译参数及二进制 hash 记录在证据中，二进制仅留 `/private/tmp`。没有更改 vendor bundle、全局/用户首选项、系统服务、锁屏状态、安全策略、生产源或正常包。

75 秒驱动失败后先核对原 runner：当时只剩自身的 pnpm/`ps -A` 清理链，后续确认均已结束，再使用与原 `scripts/run-tests.mjs` 等价的直接 Electron-as-Node 入口补该组合结果。没有因观察超时立即重建/重启整轮。另一份已写失败终态、App 与子进程均已退出但 driver 未退出的旧诊断，仅清理精确自有 PID 66275；信号退出单列，不作正常通过。
