# 启动资源与历史引用分离验证

日期：2026-11-14。补 R02／R08／R10、Q13／Q48。**仅研究；没有产品、原型或用户数据改动。** [结果](result.json) attempt-lVNrld 五项限定检查完成；[原件](raw-evidence.tar.gz)、[摘要](evidence-manifest.json)、[审计](audit.json)、[构建](build.json)和[源码基线](source-review.json)可复核。

## 为什么补这批

上一批实际 R17 实验证明，启动选中的应用包可以不同于历史快照。统一绑定候选却从历史快照提取准备引用；此前十一项并未包含启动选择改变。此次将两者放到同一个隔离资源库，检查第二次升级默认包与 GC 的交互。

实际执行包安装／激活、v1 运行计划构建器、资源协调锁与 GC 物理删除。创建／迁移／准备和保留读取器沿用前批候选，父运行仍用 FixtureProcessReader，子任务没有启动。启动计划采用受控选用包数据模拟前批已实证的 R17 不同集合；未直接接入完整 ManagedTaskCapabilities 或持久化新的 programmatic run-plan。计划 JSON 是实验记录，不签发运行权限。

## 五项结果

| 项目 | 证据及含义 |
| --- | --- |
| L01 | 历史包为 1.0.0，启动计划选 3.0.0；准备只持有历史 refs。默认包再升级 4.0.0 后，实际 GC 删除 3.0.0，binding 仍为 preparing，历史包仍存在；受控的后续 adapter 文件读取报 ENOENT。检查通过表示“仍需读取该包”的候选风险已复现，不表示现有 launcher 一定还要读取此包 |
| L02 | 准备时额外持有启动包引用，默认版本升级后仍不可清理；历史 snapshotHash 不变。只证明准备阶段合并保留可保护该包 |
| L03 | 将这组 refs 直接传给前批 finish，启动包引用被复制进 source revision 的历史引用，虽然原 snapshot 内容未列该包。保留更保守，但来源和释放时机尚未区分，不能当完整修正 |
| L04 | 明确尚未 fork 的准备取消，历史和启动准备 refs 一起释放；旧启动包随后实际可清理。没有真实子 Agent／未知进程的取消证据 |
| L05 | 若包只用于 launch 审计、没有后续文件读取，清理后实际 verifyApplicationRunPlan 仍能核验原记录；仅列在 applications 中不构成必须保留文件的证据 |

每项使用独立夹具；初始 setup 的 2.0.0 默认包只是排除旧默认保护的辅助条件。3.0.0／4.0.0 是合成应用包版本，不是 SDK／CLI 版本。实际删除只发生在实验临时目录，不能表述为当前用户项目已经被误删。

## 对设计的要求

准备保留集合由实际消费依赖决定，不能只读历史快照或把 launch.applications 全部当文件依赖：须含源历史依赖、启动交付确实仍要消费的资源、对应执行程序／适配器及投影依赖。求并集用来保留，但每条保留理由要保留来源与生命周期；不能把所有启动资源永久塞进历史快照 refs，也不能在 source cap 提交后提前释放仍待使用的启动资源。

新运行计划必须区分 source revision、delivery plan 和 live run／operation lease。启动引用向真实运行租约交接需在同一协调边界原子完成；未知派发或 owner 未排空继续保留；释放某一个理由不影响同资源的其他历史、启动或运行占用。R17 的后来业务调用仍使用当前政策和自身执行占用，不被启动包永久锁定。

初版 attempt-VucAtz 只有四项；复核实际 launcher／FrozenPluginSkills 后，追加 L01 的受控迟后文件读取与 L05 的纯审计对照。现有 R16 内置 Skill 使用共享库，FrozenPluginSkills.describe 会先读取并复制插件字节进独立 bundle；已完整复制并验证后，保留对象可以是冻结产物，不必永久保留原包。因此不得仅由“包可清理”推断现有产品存在错误。

本批尚未实现带独立生命周期的最终关系，也未验证完整新 run-plan、两端 SDK 投影、原生派发或真实运行接管。这是新发现的设计缺口及准备阶段替代保护证据；不能把五项计为资源生命周期整体通过。
