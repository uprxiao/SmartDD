# 统一绑定准备与资源保留验证

日期：2026-11-14。补 M14-R02／R06／R08／R10、Q13／Q24／Q48。**技术研究与隔离实验；产品、共享原型和用户配置均未修改。**

本批将前两批分别使用的 planned binding 与历史 binding 改为同一个候选关系；不把两批绿色结果直接相加。[最终结果](result.json) attempt-P6uqkn 十一项通过；[原始归档](raw-evidence.tar.gz)保留所有尝试、SQLite 和驱动；[摘要](evidence-manifest.json)、[审计](audit.json)、[构建](build.json)可核验。

## 真实与候选边界

真实部分：现有 32 份 SQL、合法 v2 Schema、runFixture 的应用包与运行时安装、实际 CapabilityRunRegistry 的父任务 prepare／停止、C 资源协调锁、ResourceStore、GC 计划和实际临时目录删除。父进程身份由 FixtureProcessReader 提供，不是原生 Agent。清理器仍只在内存构建中插入候选保留读取器，真实产品文件不变。

候选部分：使用实际 tasks／ai_profiles 表的同库逻辑创建／receipt／outbox，与迁移产生的 binding／cap／revision／ref 在一库关联；增加准备阶段、冻结内容和临时资源引用。配置是直接插入的隔离行，runner 为夹具的 claude-code，不证明产品配置编辑器或其 runner 映射已兼容。子快照从合法父快照生成受控输入，改 taskId、MCP 名和投影路径，通过实际 Schema／摘要检查，但未调用完整子能力选择器、建立 Skill/MCP 物理投影或启动子 Agent。

每项先由实际父注册器建立活动 run，候选接受并重复返回同一 child，再停止父 run。随后仅在夹具中释放父历史引用、切换新默认应用包，避免父引用或共享 runtime 掩盖子资源保护。这个释放步骤不是产品归档／迁移授权，也不证明父历史可以在实际产品直接删除。

## 十一项检查

| 项目 | 实际证据 |
| --- | --- |
| U01 | planned 目标无 cap、无资源占用，不触发全局损坏 hold；重复接受返回同一子任务 |
| U02 | 准备阶段持久占用必需资源，旧 GC 计划失效；这时仍无可执行 cap |
| U03 | 准备转历史在同一事务；插入 revision 后注入异常回滚，临时引用保留；成功后正式引用接管，tombstone 继续保护 |
| U04 | 尚未派发时显式取消准备，拒绝迟到完成；旧应用包实际删除，新默认保留 |
| U05 | 配置行在准备中删除，提交拒绝且不回落到别的目标；引用保留到显式取消 |
| U06 | 资源 generation 在准备前或提交前变化，分别拒绝；后者保留可解释的 unresolved 保护 |
| U07 | outbox 已为 dispatching 时不能使用派发前取消释放；此项只改候选状态，未真的启动子 Agent |
| U08 | prepared 绑定的历史被夹具删除后触发 hold，与合法 planned 区分 |
| U09 | 快照列有应用包、引用却遗漏该包，准备阶段即拒绝，整组无半提交 |
| U10 | 准备之后更换 allowedOperations 及摘要，提交拒绝；原冻结计划仍可提交 |
| U11 | 真实独立 Node 进程提交准备记录后，捕获其 PID 并 SIGKILL；引用继续阻止 GC。从数据库冻结内容恢复计划，错误 token 拒绝，原计划可显式完成 |

U11 的新进程只完成候选准备事务，退出点在 C 锁释放和提交之后；没有测试锁内退出、原生 fork、子执行 owner 接管或自动调度。恢复完成表示能力历史记录持久化成功，不等于恢复了活运行权限。正式 owner、完整准备计划和实际 outbox worker 仍待联合验证。

## 反例与修正

attempt-rK5jYs 的八项通过只覆盖初版状态衔接。扩展 attempt-Rua8VP 的 U09 失败：只验证提供的引用，没有从快照核对必需集合，缺应用包仍能进入准备。补集合完整性检查后 attempt-HLvzz8 的 U10 又失败：只存资源引用、不冻结能力内容，提交可换入另一份允许操作列表。最终加入持久冻结快照、精确摘要、选择摘要及 token 核对，attempt-gQeywD 十项通过；随后追加实际宿主退出恢复，最终十一项通过。两个缺陷均为本批候选问题，不能归为当前产品已经发生的故障。

## 设计结论与剩余项

planned 目标、准备中资源占用、持久能力历史、真实运行权限是不同事实；不可用“没有 cap”统一判坏，也不可用“已有 binding／cap”授权执行。准备前确定必需资源闭包并在协调锁／短事务中固定资源身份与代次；文件复制等异步工作在锁外做，提交前复核目标配置、完整内容与资源，正式引用接管和临时引用释放应原子完成。派发或结果不明时保留占用，禁止超时自动释放。

本候选只覆盖首次准备与旧历史迁移关系，不能直接作为完整 Schema：同 task 多个新配置／重试代次、完整能力／投影路径与权限校验、H/C 跨根锁、历史资源统计、受管 SDK 版本、真实 fork 与恢复仍待补。候选准备记录不替代现有 run-plan，也不替代进程所有权。未再运行前批全部跨 run 去重／并发创建／迁移崩溃用例，不能声称它们已在新表结构上全部复验。
