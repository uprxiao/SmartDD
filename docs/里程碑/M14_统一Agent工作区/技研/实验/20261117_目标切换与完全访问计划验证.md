## 1. V17 目标进行中切换执行器（AR10）

| 组 | 操作 | 实际结果 |
| --- | --- | --- |
| Codex A | 目标运行 2 轮后宿主不再发输入（模拟“切走”但不暂停），观察 30 秒 | Codex **在后台继续自动开新回合**：30 秒内又开 2 轮、文件 2→4，目标仍 active |
| Codex B | 回合结束事件到达时 `thread/goal/set paused`（对孤立回合 interrupt），关闭 app-server；新进程 `thread/resume` 后查目标 | 恢复后目标 **paused、目标文本保留**；10 秒内不自动开回合；`set active` 后接着做（文件 3→5） |
| Claude R1 | `/goal` 运行 1 轮后用 Stop 回调让会话停下（模拟切走）；恢复会话，发无关消息“1+1 等于几” | Claude 先回答“2”，随后**被目标拉回继续做目标**，一直做到 maxTurns（文件 1→6）。即 Claude 目标存于会话，任何新消息都会让它继续追目标 |
| Claude R2 | 同上，恢复时发 `/goal clear` | 回复“Goal cleared…”，0 回合、无新文件 |

过程说明：Claude R1 首次运行时 SDK 在 `error_max_turns` 结果上抛出，脚本中断于 R1 之后；R1 的原生记录完整，结论取自记录；R2 加异常包装后单独重跑。

**事实要点**

1. Codex 目标只要是 active，就算宿主不发输入也会自己继续跑——“切走”必须先暂停（并处理孤立回合），否则旧执行器与新执行器会同时写同一目录。
2. Codex 的暂停可跨进程恢复，切回后状态可靠（paused，等用户继续）。
3. Claude 没有“暂停”，只有“清除”。目标残留在会话中，切回 Claude 后任何一句话都会让它继续追旧目标，这对用户是意外行为。
4. 现行技术方案已规定切换只在空闲边界发生；但目标进行中几乎没有真正的空闲边界（Codex 回合之间间隔很短），所以“运行中不许切换”本身不足以覆盖目标。

**可选做法（待用户定）**

- **甲：有目标时不允许切换（推荐）**。目标为进行中或已暂停时，切换执行器按钮置灰并提示“先清除目标或等目标完成后再切换”；回合运行中本来就不能切换。规则简单，两种执行器行为一致；代价是想换执行器时要先清除目标（目标文本可复制后在新执行器重新设置）。
- 乙：切换时自动处理目标——弹确认后宿主对 Codex 暂停、对 Claude 发 `/goal clear`，切回 Codex 时显示“已暂停，点继续”。Claude 侧切回无法恢复，只能重新设目标；两端不对称，易让用户以为 Claude 的目标也能继续。
- 丙：切换时清除目标并把目标文本作为普通消息带给新执行器。新执行器未必支持目标（ACP、旧版本），语义会变。

## 2. V18 完全访问（bypassPermissions）下计划批准（AR11）

| 组 | 配置 | 实际结果 |
| --- | --- | --- |
| run1（无效，保留） | bypass，**未传 canUseTool** | SDK 不提供 EnterPlanMode／ExitPlanMode／AskUserQuestion（init 21 个工具），Claude 自述“没有该工具”改为文字计划。生产必然提供 canUseTool，故此组不作结论 |
| 对照 | default／acceptEdits／dontAsk／bypass，均传 canUseTool | 四种模式 init 都含 EnterPlanMode、ExitPlanMode（24 个工具） |
| A | bypass＋canUseTool，对 ExitPlanMode 返回拒绝 | **ExitPlanMode 经过 canUseTool**（bypass 也不跳过）；拒绝后无任何写入，Claude 回复“计划已提交，等待你在请求面板中批准” |
| B | bypass＋PreToolUse 回调对 ExitPlanMode 返回 deny | 回调被调用 1 次，拦截有效，无写入 |
| C | bypass＋`disallowedTools` 去掉两个计划工具 | 计划工具不出现，Claude 以文字给出计划并等待，无写入 |
| 批准路径 | bypass＋canUseTool 对 ExitPlanMode 挂起 5 秒后放行 | 挂起期间工作区无新文件；放行后同一回合接着 Write×2＋Bash，hello.txt、world.txt 建成 |

另见：计划模式下 Claude 写的计划文件在会话 HOME 的 `.claude/plans/` 下，不在项目目录；进入计划模式期间一次只读 Bash 也经过了 canUseTool（计划模式临时改变了权限模式），完全访问档宿主需对这类调用直接放行。

**事实要点**：完全访问下计划批准可以照常进入统一请求面板——宿主在 canUseTool 中把 ExitPlanMode 作为原生阻塞请求挂起，用户批准即放行、拒绝即拒绝；PreToolUse 也可作为第二道。原先的兜底（完全访问下禁用计划工具）不再必要，但作为版本不支持时的降级仍可用。

**可选做法（待用户定）**：甲（推荐）完全访问与其他档位一致，计划批准都进请求面板，经 canUseTool 实现；乙 完全访问下不提供计划（disallowedTools），Claude 以普通文字给计划。

## 3. 未覆盖

ACP 执行器的目标与计划、Codex 新版本行为变化、目标进行中用户停止后再切换、多子任务等待中的切换（与 E11⑥ 一起测）。

## 4. 用户决定（2026-11-17）

- AR10：选甲——任务有目标（进行中、已暂停或等子任务自动暂停）时不允许切换执行器，清除目标后才可切换；同执行器内换模型不受限。确认不影响多 Agent：委派其他执行器的子任务是独立任务，不算切换；等子任务期间锁定反而保证结果回来后在同一绑定自动续跑。
- AR11：选甲——完全访问与其他档位一致，计划批准进入请求面板，经 canUseTool 挂起 ExitPlanMode。
