## 对正式设计的影响

GC 计划、planHash、版本引用统计和最终物理清理须共享完整的保留依据：旧引用、新绑定所有历史修订、未解析历史／未知 schema、active／tombstone、依赖闭包、实际运行及 UI／索引等租约。归档、切换 Provider 或运行停止不自动释放历史引用。当前资源的“新默认版本”与旧绑定的“仍被历史依赖”分别记录。

新引用入库与清理必须遵循同一协调顺序，最终事务再次核资源身份、hash、generation、ready／valid。已进入 deleting 不允许新增引用；绕过入口出现的新引用／损坏历史仍必须由最终删除和恢复检查阻止。只扩展计划器或只禁用一个清理按钮都不够。

本批已经将实际旧包／运行时的物理删除路径纳入隔离证据，但没有执行 ApplicationVersionMaintenance 的新引用展示、完整新运行计划／Skill 投影／资源回收接线、候选 SDK／native 二进制安装与回退、历史导入或产品归档入口。独立 SDK／CLI 资源种类仍需明确清理合同，不能把应用 runtime 的证明直接推广到全部执行器资源。

## T3 参考边界

本地 T3 CodexInstallation 记录版本／平台／校验摘要和受管安装路径；ProviderInstallationGate 在实例有工作或更新时协调互斥。见[源码哈希](t3-reference.json)。这为 WillYou 区分受管版本和在用运行提供参考，不能替代 WillYou 的业务能力快照、历史引用或实际删除保护；本批没有运行 T3 安装／GC 测试，也没有宣称它与本候选使用相同资源图。

跨批复核发现：原子创建实验的 m14_binding 是 planned 目标记录，本批同名表则是旧原生绑定及能力历史关系，两者列与约束不同；实际数据库 DDL 已录入 audit.json。两批证据不能组合成“已经跑通同一个新数据模型”。本批读取器对所有缺 cap 的绑定采取保守 hold；未区分正常未准备的 planned 目标，不可直接接入前批创建路径。统一 Schema 必须显式区分未准备目标、已有历史绑定与损坏记录，并逐项验证准备中、取消、失败及恢复时的资源保留。不能只因 native_id 为空就放行，未绑定原生身份的旧快照也可能持有资源。

正式迁移在统一引用读取、计数展示、写入门槛和实际删除服务全部接好并验证前，仍保留旧 refs。未知历史要有可追溯的核查／解除方式，不能用永远禁止所有清理掩盖缺失映射。后续 54 条产品用例仍未执行，本批不计产品实现或验收通过。
