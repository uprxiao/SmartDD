# 数据库版本阻挡与迁移恢复：独立技术验证

当前实际 SmartDD 迁移规划器、执行器、维护锁、外部占用预检、备份、协调器及 macOS openManagedDatabase 的七项检查通过。使用全部 37 个当前迁移和一个合成未来后缀；不是完整 M14 Schema、旧安装包或应用降级验收。未接触日常数据库。

| 检查 | 实际结果 |
| --- | --- |
| V01 迁移协调 | 真实维护门闩＋前后两次实际 lsof 占用预检；协调器产生 0600 备份、核验摘要并提交第 38 个合成迁移 |
| V02 旧读者拒绝 | 当前 37 迁移的规划器／执行器及实际 macOS 受管启动均拒绝第 38 条记录；逻辑数据库指纹未变 |
| V03 已提交恢复 | 显式将文件镜像置回 backed-up，当前协调器按数据库提交记录修复镜像，后续历史／业务行不丢失，没有恢复旧备份 |
| V04 备份边界 | 备份没有之后的业务行／未来表，保留 pending 维护状态；仅复制到独立目录只读检查，未覆盖原库，也未宣称副本可直接启动旧 App |
| V05 无登记研究表 | 当前迁移器看不到未登记的额外表；仅建 M14 实验表不能证明产品版本阻挡生效。不是说所有新增表都不兼容 |
| V06 回执失败 | 实际 runMigrations 的提交回调注入异常，Schema、业务行、迁移账一并回滚 |
| V07 同长度冲突 | 合成相同条数但最后 hash 不同的迁移账被当前规划器／执行器拒绝，数据库未变 |

设计结论：复用原正式迁移链和启动协调，不再建立平行“已迁移”判断。M14 数据结构、提交收据和水位按同事务要求接入，变更旧记录或只写候选 m14_migration 表都不能代替 __drizzle_migrations。UI／后台业务服务只能在启动校验及维护交接完成后启动；非 macOS 的普通入口同样有迁移账检查，但本轮未跑对应平台包装路径。

数据库备份不是整机／业务回滚：原生 transcript、应用数据文件、密钥与工程目录各有来源／引用，不能只覆盖 smartdd.db；备份自身携带的维护状态、store identity、迁移日志也要核验。保留新库与新历史，优先使用兼容版本或只读导出。明确恢复必须使用独立恢复副本及一致的业务资源，保留时间切点之后的数据；当前没有实现自动数据反向迁移。

T3 的层级不同：servicePreflight 会拒绝更高 migration id 或未知／冲突历史；databaseMigrationHead 只读取得记录；Migrations.test 明确包含底层迁移器在更高 V2 id 下返回空变更的用例。故不能把 T3 底层 runMigrations 的返回当作安全降级承诺，参考的是启动／更新预检与迁移执行分层。这里只读核对 T3 源码及测试，没有执行 T3 运行时。

限制：合成未来表用于验证版本机制，不含最终 M14 全表。镜像回退为显式夹具，提交回调为注入，不是本轮进程崩溃。macOS arm64 单机；历史安装包、全部平台、外部旧宿主竞争、库外文件统一恢复及完整交接仍待验。Q50 从待验变为部分，不能声称任何旧版均安全或产品降级已可用。

首轮驱动缺 ResourceStore 导出，在建立隔离基线库后失败，未执行维护迁移。补充导出后七项通过；首轮脚本／构建记录／数据库保留。复跑：在 SmartDD cwd 运行 build.mjs，再运行 probe.mjs；所有数据库、门闩及备份均位于探针 attempt 目录。
