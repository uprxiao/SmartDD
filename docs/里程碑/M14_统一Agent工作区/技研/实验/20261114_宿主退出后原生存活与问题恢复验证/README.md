# 宿主退出后原生存活与问题恢复验证

日期：2026-11-14。关联 D02／D06／D08、Q11／26／27／32／56。实际当前 run-recovery、运行预留门禁、ResourceStore 与 Mac 进程身份读取器，联合既有候选问题账。未修改产品代码。

## 四项检查

| 检查 | 实际结果 |
| --- | --- |
| L01 旧宿主尚活 | Claude 与 Codex 两个真实表单同时 pending；问题恢复拒绝接管，实际 run 恢复报告 running |
| L02 宿主死亡、原生仍活 | 精确终止研究宿主后，两个实际 native PID／出生身份仍存活；问题 expired、无取消意图／答案／活句柄；实际 run 为 orphaned、租约 recovery-required，两个新 run 预留均 RESOURCE_BUSY |
| L03 原生身份未知 | 只对已捕获的两原生身份注入 unknown 观测；实际进程仍活，恢复继续保留 orphaned／租约，不重新产生问题回调 |
| L04 原生确认退出 | 精确终止研究原生进程，内核 NOTE_EXIT 事件及 Mac 出生身份均确认停止；实际 run 恢复至 stopped、旧租约 released；显式新预留可建立后按未 fork 路径取消，旧问题不重发、不复活 |

最终四项通过，两个本机合成模型请求产生两个真实 pending 表单，没有发送任何用户答案。研究宿主按计划 SIGKILL，两个原生进程均已停止，退出观察器退出 0；最终库及各状态现场保留，最终 SQLite 完整性／外键检查通过。新预留只验证准入，没有 prepare／fork 或新模型回合。

## 实验方法与证据边界

工作宿主直接捕获 native ChildProcess／出生身份并登记实际 run。两表单 pending 后，对这两个已拥有进程发 SIGSTOP，使它们在宿主死亡后确定仍存在，阻止其继续行动。上层驱动先注册 macOS kqueue NOTE_EXIT，再终止自己创建的宿主；恢复检查后只清理记录中身份仍精确匹配的两个原生 PID。没有按名称或路径搜寻／批量终止进程。

SIGSTOP 是受控故障条件，不是产品处理方案。running 在本实验表示 OS 进程身份仍存在，并不表示进程正在执行指令。L03 的 unknown 是观测替身，不是实际制造内核身份读取失败。两端是 Claude SDK 0.3.321／native 2.1.321 和 Codex app-server 0.167.1，仅本机合成模型与 MCP，隔离 HOME／配置，无付费调用。

本轮证明“问题不能再回答”和“运行仍需保留资源”可以同时成立；不是完整执行范围清理或业务恢复。未覆盖发送中回答、在途邮件／插件写入、独立后台子进程、动态委派后代、自动接管旧原生连接、供应商请求或产品 UI。现有运行恢复结束 run 活动账也不能推导外部副作用失败／未执行；业务结果账仍须单独恢复。

## 首次驱动失败

初轮 Python 观察器用 `with select.kqueue()`，本机对象没有 __enter__，观察器启动失败；恢复断言未执行。清理又等待已经退出观察器的通知，产生 WATCHDOG:cleanup native。修正为显式 try／finally 关闭 kqueue、观察器失败立即拒绝 readiness、清理不等待已死观察器。按已捕获 PID／出生身份补清理并确认旧宿主和两个原生均停止后，才执行最终复验。原 stderr、检查点、补清理及失败审计归档，未伪造初轮正常结果。

## 设计落点

恢复先分清问题宿主与原生执行范围。确认旧问题宿主已死亡后，可以结束失效回答入口而不产生取消／批准；旧原生或身份不明时，实际 run／资源维持待恢复，拒绝新写入运行和资源回收。只有实际执行范围满足原协议的结束条件，才能释放相应租约。UI 同时显示“旧问题已失效”和“运行待恢复”，不要用前者覆盖后者。
