# 执行配置修订与凭据原子性：独立技术验证

日期：2026-11-14。对应 R02／03／08／11，Q06／20；设计 §3.2.11、验证账 §4.42。仅在临时目录运行，未改产品、共享原型、用户配置或真实凭据。

## 关键发现

现有 AiProfileService.update 的 Drizzle 事务已涵盖配置行和 SecretsStore 对 app_secrets 的写入。safeStorage 是密文生成／解析接口，数据库内实际保存密文；这里不是“数据库事务必须原子修改系统钥匙串”的跨存储问题。可复用现有事务，不重做凭据服务。

独立候选以每个 profile 的单调 execution revision 跟踪 runner、executable、env、args、commandPending，以及当前引用的密钥记录变化。名称、颜色、默认项和普通健康信息不推进修订。版本与配置／密文在同一事务变动；删除保留失效记录，防止同 ID 再插入恢复旧许可。修订只用于失效判断，不计业务操作次数；一次保存可以递增多次，重写同明文但生成不同密文也可以保守失效。

本批以数据库触发器验证写入覆盖，既覆盖实际服务，也覆盖现有导入中绕过 AiProfileService 的直接表写入顺序。触发器不是完成的正式迁移器；完整 schema 版本／触发器完整性检查、旧宿主写入门槛、升级回退及性能仍须接最终设计。不能只包装设置页 update 方法便声称覆盖所有配置入口。

## 实跑结果

`attempt-rNdxxF` 的 V01–V12 全部通过，无失败后重跑。构建使用实际配置／密钥服务与现有全部 SQL 迁移；未使用的 node-pty 发现依赖仍为必抛错 stub，假加密器／固定时钟与合成值都有明确边界。

| 项 | 实际证明 |
| --- | --- |
| V01 | 不装候选表时，实际 update 先删除／写入部分密钥，再在下一次加密故障后，配置和全部密文整体恢复 |
| V02 | 候选迁移保留原数据，初始化修订；同一版本的简单重复调用不重置修订 |
| V03 | 改名称／颜色／默认／普通健康信息保留修订；相同 updatedAt 下改启动参数仍使旧句柄失效 |
| V04 | 实际 SecretsStore 直接换 Key，无需改 profile 时间戳即可使旧句柄失效 |
| V05 | 数据库等其他业务密钥、别的 profile 和当前未引用的密钥不影响该 profile |
| V06 | 候选修订与实际配置／密钥在中途加密失败时一起回滚 |

| V10 | commandPending 变动推进修订；禁止在调用者的旧事务快照内作“当前”配置核验 |
| V11 | 按实际导入源码顺序先密钥后 profile 插入，得到有效初始修订；事务失败都回滚，未执行完整 TransferService |
| V12 | 已有无效 JSON 在迁移前明确拒绝，保留原始数据，不留下部分新表 |

## 来源捕获与边界

候选 capture 先读修订，调用实际 resolve，再读修订；不一致即拒绝，无自动重选。明文只留在私有 WeakMap 内，公开句柄仅 profileId／revision；consume 再核当前修订与句柄来源。本批 consume 为同步断言回调，未启动 Agent，也未将该修订接入上一实验的 ExecutionPlan／delivery 或 SDK fork。两连接交错不等于真实多进程崩溃验证；没有 SIGKILL、系统钥匙串或外部配置文件的动态变化实验。

已有 SQLite read transaction 可能维持旧视图，候选直接拒绝在外部事务中捕获／核验；正式事务协调需要与资源协调锁和启动入口统一。数据库修订看不到 CLI 配置文件、继承环境、系统代理、外部凭据提供方或 executable 替换，完整目标来源向量仍需单独处理。已启动进程拿到的旧环境不能靠修订号撤回；运行中改 Key 的后续回合／恢复策略与取消清理仍需联合验证。

T3 本地 Registry.reloadWhere 对成功读取且确实变化的秘密重建实例；普通重读失败会保留已有可用实例及旧值。此为源码事实，不代表 WillYou 的新派发可以绕过缺 Key 检查，也不是 T3 提供了本候选数据库修订机制。实际安全存储、外部秘密源和完整原生生命周期仍按各自条件验证。
