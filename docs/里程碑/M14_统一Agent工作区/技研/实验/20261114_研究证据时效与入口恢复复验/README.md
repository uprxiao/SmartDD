# 研究证据时效与入口恢复复验

日期：2026-11-14。关联 D01／D04、Q49／50 及业务恢复边界。当前 SmartDD 基线 `5a9e04382441e24624cb94635f9d902c543a03d7`。本轮为证据审计与既有隔离实验复验，不是产品验收或新增功能。

## 为什么补跑

逐一核对验证账 §4.74–4.87 对应的 14 份实验归档：归档摘要、内部文件清单及各文件摘要全部匹配。只比对 source-review 中明确记录的仓库绝对路径，不把临时相对路径解析成仓库文件，也不推断未记录输入。入口交接有 8 条、业务恢复有 10 条已记录源码摘要与当前源码不同；其他批次所记录的仓库来源未发现差异。这不是对全部历史实验或所有运行依赖的时效背书。

两批旧结果保留原基线；在全新临时子目录复制原驱动，分别以当前源码重建 actual bundle，未修改原断言。入口交接驱动、候选 migration／DDL 与业务恢复驱动均与原件摘要一致。浏览器候选只在内存变换清理 SQL，不修改产品源码。新构建的全部 379／387 条输入与输出在运行后再次核对一致。

## 当前源码复验

| E01–E05：运行停止、真实子进程退出、业务活动排空、未知写门禁、身份抢占、并发交接与封闭旧入口 | 5 项通过；受控 Node 子进程 exit 0。未知业务行由夹具注入，尚未接 SDK adoption、真实 PTY 或完整持久恢复 |

两套 SQLite 最终完整性和外键检查通过。邮件租约释放不等于发送结果确定；只查 application_invocations 仍会遗漏浏览器、邮件及项目级写入。这些结论可继续用于当前设计，但不升级为完整交接服务通过。

## 设计修正

源码复核另发现：当前 CapabilitySessionRegistry 已支持带可信 ClaudeRestoreReceipt 的历史复制交接，保留旧根的历史身份占用，并要求 Task 指针提交回调。旧设计“状态根必须保持一致”过于绝对。技术方案 §11.2 改为默认保持原根，已有受管复制路径须保留来源、目标、收据、旧根占用及原子提交；该路径涉及原生历史，不是复制整个 SVN 工程。

本批没有实际执行历史复制／adoptLibrary 路径；其与 M14 多 binding 的别名冲突、复制后提交失败、重启及回退还需隔离验证。不能由函数存在或 E04 的普通身份冲突证明这些分支已通过。

## 复现

归档中的 handoff、recovery 两目录分别运行 `node build.mjs`；recovery 追加 `node build-candidate.mjs`；随后各执行 `node probe.mjs`。需原记录所列固定 esbuild／SQLite 依赖及本机进程身份助手。audit.py 默认审计历史 §4.74–4.87，后续源码变化会如实记录差异，不能把新摘要回填旧实验。
