建议先收口以下行为，供正式需求／原型评审，不能仅由底层实现默默决定：

1. 按现行 T0.1 §7.2 的候选合同，父空闲、原运行已排空且无未知交接／结果投递时，可切换父 Provider；尚未领取的子结果归属父逻辑任务，领取时才固定接收 binding／generation。活动子任务不单独构成“一律禁止”的理由，但目录占用、待审批、已发送未确认结果等仍可能阻止下一次运行。此组合行为及提示仍待原型评审和联合验证，不能写成已获产品验收通过。
2. 单→多在下一次安全启动时加入宿主委派能力；多→单先停止接受新委派，现有子任务完成或明确取消后转换。若执行器不能热更新工具，使用受控重连并保留上下文，不假设在线增删工具必然生效。
3. 本期记录协作输入及规则来源，目标在启动时复核；未来模板如需固定修订，应同时核对角色选择与引用的 Skill 内容版本。固定修订不能保留已撤销的授权，模板持久化本期不实施。
4. Skill 中的步骤和验收要求属于可复用协作规则；并发上限、目标范围、写入协调和业务权限由宿主强制。本期不建设通用强制业务阶段引擎或模板管理页面。
5. 宿主委派作为可跨执行器管理的主要路径；执行器内置子 Agent 如允许使用，应标明观察、取消和恢复的能力边界，不能未经证明纳入同一个“完全可控”任务树。

## 3. 原业务必须保留的适配边界

这部分是 D04 的设计检查范围，不替代现有业务合同。

| 业务 | 新运行接口要衔接的地方 | 必须保持的行为 |
| --- | --- | --- |
| 浏览器与自动化 | `browser/access.ts` 的真实 run 授权与结束撤销；父子任务访问其他任务页面仍走现有授权 | 页面、登录状态和用户浏览入口保留；不能把父任务授权复制成子任务授权，也不能因换 Provider 清空浏览数据 |
| 文件目录／编辑／查看 | 文件来源、选中 cwd、打开窗口、引用插入和保存版本检查；`terminal-context.ts` 的 PTY 绑定须有新运行映射 | 浏览／编辑不依赖某个 Agent 正在运行；worktree 文件与原目录文件来源可辨；切换或子任务结束不关闭无关查看器 |
| 插件与业务能力 | `session-registry.ts`、`task-capability-launcher.ts`、`run-registry.ts`、`write-approvals.ts` 的身份链、资源保留与审批回执 | 安装、更新、停用、旧会话能力生效、连接和凭据规则保持；拒绝或过期审批不能执行；旧审批不能批准新 run |
| Skill、第三方 MCP 与业务 CLI | 当前能力发现、配置转换、冻结目录及真实进程交付分别映射到 SDK／app-server | “目录可见”与“实际执行”分开证明；脚本／相对资源可用；目标缺能力须明确显示，不能悄悄丢失或额外加载未选配置 |
| 文件查看器 MCP | `files/mcp/service.ts` 的窗口 owner／generation 与独立 MCP 客户端 | 不与 Agent MCP 的停止、重连、凭据或配置合并管理 |
| 邮件、数据库／SSH、语音、导入导出等 | 复用现有业务服务；新增结构化输入／引用时保持真人来源、项目范围及既有审批 | 上下文交接、工具输出或子任务结果不成为新真人授权；保留既有项目／Agent 配置包的明确加密凭据迁移；默认 Agent 导出不带 Key，运行票据／登录态／审批不随包迁移；当前已交付行为逐项回归，未交付内容不冒充已有功能 |

MCP 至少区分四个所有权域：Agent 使用的第三方 MCP、WillYou 私有业务桥接 MCP、文件查看器 MCP、宿主委派 MCP。可共享通用连接代码，但不混用凭据、授权与生命周期。原终端继续作为旧运行方式及普通终端功能存在，新任务运行控制不靠解析终端文字。

## 5. 技术实验与通过条件

每组记录具体版本、平台、输入和实际结果。模型端可模拟的先使用本地端点与合成凭据；服务状态用确定性夹具验证。真实执行器不等于真实模型，协议模拟也不等于打包 UI 通过。暂缺凭据或平台的组合记未执行，不用其他组合替代。

### E01 程序化运行、配置和所有者（D01／02）

- 输入：首批 Claude SDK＋CLI 与 Codex app-server 精确版本／资源组合；临时 HOME、配置根和两个合成端点；普通审批及首版拟支持的权限档位。
- 步骤：初始化→两轮含工具对话→原生提问／批准／拒绝→中断→关闭→恢复；记录客户端、真实执行进程、原生会话与 run；改变配置来源、代理与 cwd；同一配置启动两个不同会话，另试同一原生会话重复控制。
- 通过：真实控制与执行身份一致；每轮输入／事件可关联；只访问选定端点；原生权限拒绝后零执行；中断和退出有真实终态，资源可释放；独立会话不串配置，同一原生会话拒绝双控制。Claude 首次 full 权限确认如纳入支持，必须证明与原规则等效。
- 证据／影响：协议请求响应、事件、进程身份和清场记录。能力不等效的组合保持原 CLI 可用并标不支持，不能降低原权限规则；阻塞对应新适配器接入。对应 G01／02／03／06／08、V1。

### E02 Skill／MCP／插件与业务 CLI 实际交付（D04）

- 输入：冻结 Skill（含相对脚本与资源）、合成 stdio／HTTP MCP、现有插件夹具及业务 CLI；两个配置、两个并行 run；显式选择与未选择能力各一组。
- 步骤：从真实程序化执行器发现并实际调用；检查 cwd／环境、工具命名和回包；停用／更新插件，再恢复旧绑定；取消其中一个 run，继续另一个。
- 通过：应启用能力实际有效，未选能力不被加载；环境及凭据符合各自合同；业务调用归属真实 run；旧能力名称／资源持有和更新生效符合原规则；取消一个运行不删除另一个所需资源。
- 证据／影响：执行器请求、MCP／业务服务回执、资源版本与释放记录。每条按“可发现／实际调用／真实模型使用”分层，不以列表替代执行；失败阻塞受影响业务迁移。对应 G02／03、V1／8。

### E03 多绑定、迁移与 A→B→A（D01／05）

- 输入：隔离 SQLite 中的旧任务、固定能力快照、原生身份和资源引用；A、B 两个配置；先用运行适配器夹具，再接 E01 的候选。
- 步骤：迁移并重复启动；A 写入上下文→切 B→回 A；覆盖同配置换模型、同执行器不同账号／供应商、跨执行器；在创建绑定、变更活动指针和接收原生 ID 之间分别注入失败；尝试 busy 时切换。
- 通过：逻辑 taskId／历史保持；原生身份按兼容策略复用或新建，旧保护仍有效；能力快照不被覆盖；迁移幂等、失败不留半个活动绑定；旧 SDK／CLI 入口互斥；busy 不偷偷换执行器。
- 证据／影响：迁移前后行与约束、事件、身份映射、资源引用差异；不把 key 值写入证据。未通过前不能定稿数据迁移或开放同任务切换。对应 G05、V2／3／9。

### E04 上下文投递、来源与未知结果（D05）

- 输入：真人消息唯一 ID、两条相同文本但不同 ID 的输入、文件变更标记、工具结果、子任务结果、附件和超预算历史。
- 步骤：检查 B 的实际输入，再检查回到 A 的增量；分别模拟不支持原生注入、明确拒绝、已发送但 ACK 丢失、发送前失败和应用重启；夹带历史中的审批／邮件发送指令。
- 通过：已确认内容不重复，遗漏与附件限制可见；未知投递不盲目重放；替代会话或内联交接按明确策略执行；系统交接和历史不冒充新真人消息，不能获得业务写权限。
- 证据／影响：脱敏后的原生输入、投递账、覆盖／遗漏项 ID 和业务拒绝回执；模型口述“记得”不是充分证据。失败阻塞续聊开放及权限接入。对应 G04、V2／4／8。

### E05 通用组合与宿主委派入口（D02／06）

- 输入：能力目录中 A1、A2 为同执行器不同配置，B1 为另一执行器，另有缺工具／失效目标；使用角色标识而非品牌指定分工。
- 步骤：A1→A2、A1→B1、B1→A1，互换主／评审角色；先用适配器夹具覆盖目录和目标解析，再由首批真实执行器实际调用宿主委派工具；目录查询后撤销目标配置或权限再启动。
- 通过：同一委派服务处理所有组合；目标、模型和账号与选择一致；启动前复核；不支持给出原因，不静默改目标；结果可关联父任务。运行期原生子 Agent 与宿主子任务标识不混淆。
- 证据／影响：目录结果、请求／run 绑定、工具调用及返回关联。证明架构通用无需穷举所有模型；未接入的执行器不能因夹具通过便宣称已支持。对应 V5。

### E06 Skill 协作复用与后续模板接入边界（D03）

- 输入：一份使用通用能力查询／委派入口的协作 Skill，两种已接入执行器及无效目标配置；不在 Skill 中存放 Key。
- 步骤：加载 Skill、确认实际内容与相对资源可用，输入具体任务触发委派；重新打开任务后再次使用；互换主／子目标，撤销目标或权限；以相同服务请求检查未来规则驱动入口无需另建任务内核。
- 通过：规则实际进入运行，工具调用抵达同一委派服务；身份与目标正确、无静默替换；不能用 Skill 绕过宿主限制。是否强制每个业务步骤不作为本期成功条件，不宣称已交付完整模板产品。
- 证据／影响：Skill 来源／内容身份、加载与调用记录、目录与启动复核、请求／run 关联及明确失效状态。原 P08 模板持久化研究保留为未来输入；模板 CRUD、依赖图循环、升级、版本库和管理页验收延后，不计本期通过。

### E07 子任务、结果、问题与取消恢复（D06）

- 输入：可控服务夹具：重复委派请求、父回合结束但子仍运行、两子同时完成、父有活动回合、待审批子任务、父子在启动／结果投递时崩溃。
- 步骤：用明确事件推进排队、完成和提问；重发同一请求；停止单次回合及整个子树；重启宿主；与 E09 的写入等待联动。
- 通过：相同请求只建一次子任务；结果只触发一次有效接续；父忙时排队不串话；问题送到正确父／用户，业务审批仍由原授权主体决定；取消后不会因迟到结果自动重启；父回合结束不误报任务树完成；无孤儿写进程。
- 证据／影响：持久化事件、去重／排队账、审批关联与清场记录；最后用最小真实委派链补协议证据。失败阻塞多 Agent 生命周期定稿。对应 V6。

### E08 业务授权与新 UI 接口兼容（D04／08）

- 输入：既有浏览器、文件、插件／邮件和能力夹具；两个 task／binding／run；一个独立文件 MCP 查看器；旧任务快照。
- 步骤：经新结构化输入与运行接口触发业务操作，覆盖允许／拒绝／过期／切换／结束；测试旧 run 审批迟到、子任务引用父页面、文件版本冲突、插件在途更新；关闭 Agent 后继续查看文件／页面。
- 通过：每个操作归属正确主体，审批不可跨 run；窗口和业务数据保留；冻结资源按原生命周期释放；文件引用不误指 worktree 或别的子任务；语音／业务插入保留来源且不擅自提交。各现有业务按 §3 补齐回归映射，不能只测聊天成功。
- 证据／影响：输入来源、业务回执、窗口 owner 和变更记录；真实页面操作在 E10 补齐。M13 组件未变部分核对证据适用性，不机械重跑全部系统实验。对应 G04、V8／9。

### E09 SVN／共享目录写入交棒及大项目代价（D07）

- 输入：无 `.git` 的合成 SVN 工作副本；同目录注册两个项目、父子目录、符号链接别名；受监督后台写命令；一个文件体积与一个文件数量维度的合成大型目录。真实公司项目仅在实际执行范围允许时只读采样，不复制整个项目。
- 步骤：父委派子写入并等待，另一任务同时申请写入；取消／崩溃并恢复；只读分析期间变更其已读文件；尝试从 shell、MCP 和业务入口绕过写入限制；单独核对 Git worktree 的脏文件边界与成果保留。
- 通过：重叠范围至多一个受管写入者，后台写仍占用；父等待前交出写入权，无父子互等；写进程未确认结束不能因超时把锁让出；实际只读做不到则串行；读取依据过期后重读；没有 Git 也能完成单 Agent、切换和多 Agent 任务。
- 性能判据：同一固定操作在空闲切换／委派阶段不触发全目录复制、扫描或 hash；记录文件枚举数、读取字节和新增磁盘量，区分任务主动搜索的成本。新增宿主开销应随任务元数据／明确交接文件变化，不能随整库字节量线性增长。UI 延迟预算在取得同机基线后评审，不编造已通过数值。
- 证据／影响：写入租约及进程轨迹、版本校验和 I/O 对比；宿主租约不能锁住外部 IDE 或手工 SVN，需明确版本冲突检测范围，不宣称文件系统全面隔离。失败先收紧为串行，不改成默认复制 10GB 项目。对应 V7 与专项调研 §16。

### E10 打包、真实模型与完整 UI（D08）

- 前置：E01–E09／E11 中拟开放组合的架构必要项通过；形成最小统一 UI、切换、任务树与协作 Skill 入口原型及对应实现；沿用项目真实 App 验收方法。
- 步骤：同一候选包从桌面启动，核 SDK／原生程序路径、配置／代理与退出；通过真实界面完成两执行器单会话、A→B→A、一次跨执行器委派、协作 Skill 重开复用和受影响业务回归；真实模型使用授权配置且采用最小有判定力的任务。
- 通过：UI 与宿主／原生回执一致，工具流、审批、切换失败和任务树状态不丢失；长对话／工具大输出按分页／批量策略呈现，输入与滚动无明显退化并保留对比；候选包退出无自有遗留进程；其他平台分别取证。
- 证据／影响：包与版本标识、协议／业务证据、实际 UI 操作记录及平台边界。属于后期集成验收门槛，不要求在技术选型前做完完整产品；模拟端点通过不能替代真实模型／实际界面。对应 G06／07、V10。

### E11 运行资源交付与 SDK／CLI 版本兼容（R11）

- 输入：没有全局 CLI 的 PATH／隔离 HOME；SDK 自带程序或宿主管理的精确版本；用户显式指定已有 CLI；已验证、能力不足、已知坏版、未知新版、缺资源／损坏资源和不支持平台的组合。
- 步骤：记录 SDK、程序、平台资源、适配器各自版本／hash；实际新建／两轮／工具／恢复／中断；核 URL／Key／登录根、Skill／MCP 来源；模拟下载中断、校验失败、离线与资源更新；在活动 run 和旧任务恢复期间尝试更新／回退。
- 通过：没有全局安装也能使用已交付受管组合；显式选择的来源不静默变为 PATH 的其他版本；程序缺失时在派发前给出恢复入口；在用资源不被替换；旧记录与配置不被覆盖；未验证能力明确标识或阻止，不因版本号较新就宣称全支持。代理、签名及打包路径仍需各平台候选包证据。
- 证据／影响：依赖锁、程序来源和实际 spawn、协议能力与版本矩阵、安装／升级故障回执。T3 的兼容范围只作参考，不能直接作为 WillYou 的支持声明；默认安装方式及逐能力／版本规则已按 T0.1 §12／F15 收口；不存在统一的所有模型最低版本承诺。与 G06、T31／35 交叉，但本组新增独立安装与资源生命周期合同。

## 7. 执行顺序与设计定稿条件

1. **先收口身份、接口与资源组合，完成 E01／E02／E11 的架构必要验证，并用隔离数据验证 E03。** 已有分组内的局部证据按适用范围复用，继续补具体未决分支，不机械重跑整个分组。E11 的版本／资源来源决定执行器能否稳定启动，不能等到发版才决定；完整安装包与各平台 UI 属于后续产品验收。实验不引入生产接线。
2. **随后验证 E04／E05／E07／E09。** 重点是续聊投递、通用委派和 SVN 交棒；目录、状态、租约与 Skill 复用 E06 可先用无模型夹具完成，避免用模型不稳定性掩盖宿主逻辑问题。
3. **整合唯一技术方案、详细需求与原型。** 按 D01–D08 逐项给出确定契约，将确认后的建议写回唯一需求；未通过组合明确排除或保留原入口。新旧运行入口、协作 Skill 入口／来源、任务树活动中切换限制和单／多转换必须在原型可见。
4. **E08 中影响身份、授权和释放设计的服务联合分支继续在隔离环境验证；正式开发后做完整 E08／E10 及 E11 平台安装验收。** A0.1 已有逐条用例与证据要求，实际接线后执行；技术研究完成不等于整个 M14 已开发／验收。当前只维护原型说明，不修改共享原型或产品代码；可操作原型及视觉批准保留为后续阶段门槛。

设计定稿至少需要：D01–D08 有唯一现行正文，D08 同时覆盖 E11 的资源交付与版本策略；E01–E09／E11 中决定所选架构的可独立验证问题有足够结果，剩余产品集成项目有明确前置、责任边界和验收步骤；没有把“不支持／未知”当成成功的自动回退；三核心目标、Skill 协作复用及原业务保留均有明确验收入口。若某适配器受阻，可先推进已验证的公共部分，但不以单 Agent UI 交付代替 M14 完成。

执行记录每组至少保存：需求与设计修订、源码／驱动／程序／SDK／资源版本及哈希、平台、合成输入、完整原始回执的位置、预期与实际结果、失败原因、收尾结果、可复用范围。日志不记录真实 Key；首次失败与后续修复分别保留。实验结果回填本计划对应编号并链接原始记录，不能回写历史证据使其显得已经验证新能力。
