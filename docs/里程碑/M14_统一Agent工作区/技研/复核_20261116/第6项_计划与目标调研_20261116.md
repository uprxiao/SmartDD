## 2. 本机实测

- **V11（新增）**：Claude Code 2.1.325 在默认权限下就把 `EnterPlanMode`／`ExitPlanMode` 提供给模型。要求“先计划”时，模型自己进入计划模式、只读调研、用 `ExitPlanMode` 交出完整 Markdown 计划（另有 `planFilePath`），这一步走审批；不提计划的多步任务，模型直接动手，没有进入计划模式。
- **V10（已有）**：Codex 只有客户端把这一轮的 `collaborationMode` 设成 plan，才会产出 `plan` 条目；默认模式下没有。
- 结论：**不做任何计划入口时，Claude 只在用户要求“先出计划”时才有计划卡，Codex 永远没有。**

## 3. 分析

### 3.1 停止键与目标

- Codex：停止＝停掉当前这一轮并把目标设为“已暂停”（照 T3）。点“继续”把目标设回进行中，Codex 自动开始下一轮。
- Claude：目标不能暂停。停止只停当前这一轮，目标仍然存在；下一次有回合运行时（如用户再发一条消息），Claude 会接着按目标判断。界面上 Claude 的目标只提供“清除”。停止后是否会自己再开一轮，需验证（G3）。
- OpenCode：本次未核对，开发时按其能力声明处理。

### 3.2 等待审批时能否“先做能做的”

- 多 Agent 下天然成立：一个子任务停在审批上，主任务和其他子任务继续跑（T3 的 wait 模式遇到审批也立即把控制交回主任务）。
- 单个 Agent 内部：本次没有在协议里看到“审批挂起时同一 Agent 继续执行其他工具”的机制；Codex 目标有 `blocked` 状态。是否会因长时间未批准而转做其他部分，需验证（G4），不能先承诺。
- 用户习惯“完全访问 + 目标”：结合第 4 项决定，此时只有“最高允许＝请求批准”的操作（发邮件）和执行器自身必须确认的内容会停下等待。

### 3.3 写入并发：按文件串行是否可行

Agent 改文件有两条路：

1. **文件工具**（Claude Edit／Write，Codex apply_patch，OpenCode edit）：调用时就知道路径，宿主有机会在执行前判断；Claude 的编辑工具本身还会检查“读取后文件是否被改过”。
2. **shell 命令**（`sed -i`、构建、`npm install`、代码生成、git 操作）：事先不知道会写哪些文件，宿主无法逐文件加锁，只能事后从每轮改动记录（§11）发现。

**按“写到哪个文件再锁哪个文件”会死锁**：A 持有 f1 要 f2、B 持有 f2 要 f1，两边都无法回滚。避免死锁的通用做法只有两种：一次性拿全部（开始前声明范围），或者拿不到就立即返回、不等待。

**建议方案（替换方案 B 的“整个目录只允许一个写入者”）——“声明范围、冲突才排队、执行中不等待”**：

- 派写入子任务时，主任务在委派里写明修改范围（文件或目录）。宿主比对正在运行的写入子任务：范围不重叠就立刻并行启动；重叠就排在冲突的那个后面。子任务启动时一次性拿到整个范围，执行中不再申请，所以不会死锁。
- 主任务（目标照常运行）不占整个目录，只是不能写正在被子任务修改的范围：用文件工具写到这些文件时宿主立即拒绝并说明“该文件正由子任务 X 修改，先做别的或等它完成”，不让它等待。
- 子任务用文件工具写到自己范围之外：同样立即拒绝。用 shell 写到范围外：无法事前阻止，本轮结束后从改动记录发现，通知主任务。
- 委派时没写范围：按整个目录处理，也就是退回现在方案 B 的串行行为。
- 写入前拦截依赖执行器的执行前回调：Claude 的 PreToolUse hook（完全访问下是否仍触发需验证），Codex 在 `never` 审批下是否有可用的执行前 hook 需验证（G1）。拦截不了的执行器，只能事后发现，在界面上注明。
- 对比：worktree（T3 的 isolation）可以彻底避免冲突，但需要 Git，合并时可能冲突，且 D4 已定后续再做。

### 3.4 目标与委派

- 采用 T3 的自动联动：主任务这一轮结束、在等子任务结果时，宿主自动暂停目标；子任务结果回来唤醒主任务时自动恢复。全程不需要用户操作。
- 配合 3.3，主任务不再占整个目录，写入子任务不必等主任务回合结束，不会出现“目标一直跑、写入子任务一直排队”的互相等待。
- Claude 的目标不能暂停：主任务在等子任务时，Claude 的 Stop hook 可能让它继续开新回合空转。按 3.3 写入不再被它卡住，但会多花轮次；是否空转需验证（G3）。

### 3.5 打回重做

需要新增宿主工具（对应 T3 `t3_thread_send`）：主任务检查子任务结果后，可以把意见发回**同一个子任务**，子任务在自己的会话里接着改（保留它的上下文），改完再通知主任务。现有的查询、创建、观察、取消四个工具不支持这一点。

## 3.6 补充调研（用户追问，2026-11-16）

### T3 为什么共用目录不加锁

源码里唯一的锁是检查点恢复（回退文件）期间不让重叠目录的新回合启动，“回合启动之间互不等待”（`apps/server/src/workspace/workspaceLease.ts:28、110–114`）。T3 没有写明不加锁的理由，从代码和注入给 Agent 的说明（`packages/provider-core/src/server/orchestrationInstructions.ts:7–13`）能看到它靠三件事：

1. **少并发写**：说明第一句是“普通编码任务不需要 T3 工具”；同一执行器的子任务优先用执行器自带子 Agent（Claude `Agent` 前台运行、Codex `spawn_agent` 后等待）；需要独立写的用 `isolation:"worktree"` 单独工作副本。
2. **工具自带冲突检查**：见 V12。
3. ~~能回退~~（**更正，2026-11-16**：共用目录时 T3 **不允许回退文件**，见下节，所以回退不是共用目录的兜底。）

### T3 检查点与回退（追问后核对）

- **怎么存**：用项目自己的 Git 仓库，临时索引 `write-tree`→`commit-tree`→`update-ref` 写到私有引用，不动用户的分支、暂存区（`apps/server/src/vcs/GitVcsDriver.ts:1070–1726`）。**项目不是 Git 仓库就没有检查点**（`CheckpointStore.isGitRepository`；`CheckpointService.ts:253–271`）。
- **何时存**：每个线程有自己的检查点范围，开工前存基线，每次运行后再存一个，并记下这次改了哪些文件（`CheckpointService.ts:108–140、455–475`）。委派子任务是独立线程，各有自己的范围。
- **怎么回退**：把整个目录恢复到某个检查点（还原文件并 `git clean -fd` 删掉新增文件），可同时回退对话（`GitVcsDriver.ts:1768–1950`）。恢复期间独占重叠目录（`workspaceLease.ts`）。
- **共用目录不准回退文件**：线程没有自己的工作副本（在项目根目录跑）就一律视为共用；有工作副本但别的线程也用过，也算共用。共用时只允许回退对话，文件回退报错“File restore requires an isolated worktree…”（`CheckpointRestoreSafety.ts:9–80`；`Orchestrator.ts:13878–13900`）。原因：回退是恢复整个目录，会把别的线程的改动一起抹掉。
- 所以 T3 的文件回退**只在独立 worktree 的线程里可用**；共用目录的并发写入在 T3 里同样没有回退兜底。

### T3 的 worktree 与多 Agent（用户追问：Git 项目照 T3 做）

**能否自动识别 Git 并启用 worktree**
- 不会自动启用。委派的 `isolation` 默认 `shared`；只有调用时写 `isolation:"worktree"` 才建。项目不是 Git 仓库时，解析父提交失败，直接报错“Unable to resolve the parent checkout commit”，不会自动退回共用（`apps/server/src/mcp/OrchestratorMcpService.ts:2629–2656`）。
- 用户手动新建任务时可选“Current checkout／New worktree”，设置里有默认值 `defaultThreadEnvMode`（local／worktree）（`packages/contracts/src/environment.ts:54`、`settings.ts:1213`；`apps/web/src/components/BranchToolbar.logic.ts:94–96`）。

**谁触发、谁拆分**
- 由**主 Agent 自己判断**：注入说明规定什么时候用 `delegate_task`（另一个执行器的模型、用户要求的设置、需要单独工作副本、用户点名委派），否则用执行器自带子 Agent；“普通编码任务不需要 T3 工具”（`packages/provider-core/src/server/orchestrationInstructions.ts:7–13`）。
- 拆几份、交给哪个执行器，由主 Agent 在调用时决定。`target` 不填就用主任务同一个执行器；要换执行器先调 `orchestrator_capabilities` 列可用执行器和模型，说明里要求“不要擅自切换”，通常是用户点名或任务需要时才换（`OrchestratorMcpService.ts:1450–1494`；`toolkits/orchestrator/tools.ts:75–88`）。T3 没有“自动把一个任务分给 Claude、Codex、OpenCode 三家”的逻辑。
- 是否用 worktree 同样由主 Agent 按说明选择（“需要单独的工作副本或每个子任务一个 PR 时用 worktree”）。

**怎么避免冲突**
1. 子任务的 worktree 从**主任务当前提交（HEAD）**新建，在新分支上工作；**主任务未提交的改动不会带过去**（`orchestratorMcp.ts:176–181`；`OrchestratorMcpService.ts:2631–2656`）。
2. 每个子任务一个独立目录和分支，执行期间互不干扰，不需要锁。
3. **T3 不负责把子任务分支合并回来**：服务端没有合并子分支的逻辑（唯一的 `merge --ff-only` 是拉取远端后刷新当前分支，`GitVcsDriverCore.ts:5385–5410`；`thread.merge_back` 是侧聊对话合并，不是代码）。合并靠 PR、用户或 Agent 自己用 git 完成；设置里有“分支合并后清理 worktree”（`settings.ts:1149–1161` `worktreeOnMerge`）。
4. 冲突因此被推迟到**合并时**，由 git 的三方合并明确报出来，而不是执行中静默覆盖。T3 并不保证没有冲突。
5. 配套：文件回退只在独立 worktree 可用；复核用新委派；子任务不再派子任务（“As a subagent or child, do the work yourself”）。

### V12 实测：同时改同一文件

- 文字层面不会“改串”成乱码：Claude 的 Edit／Write 写入前检查“读取后是否被改过”，Codex 的补丁要求上下文匹配，冲突时失败，Agent 重读后再改或停下报告。
- 真正的问题有三类：①**同一行／同一决定，后写者覆盖前者**（版本号四组全是后写者赢）；②整文件写入被拦下后 Agent 可能直接停下，**该改的没改**；③**shell／脚本写入没有任何检查**，读-改-写重叠时会丢掉别人的改动（本次时间未重叠，没复现，但机制上存在）。

### T3 的计划模式

- 有过：Labs 里的“计划模式”开关，按执行器下发 Claude `permissionMode: plan`、Codex `collaborationMode: plan`、OpenCode plan agent；计划完成后有“按计划实施”的后续提示（切回默认模式再发送）。
- 2026-11-08（`521ac7c218`）删掉了开关和“按计划实施”提示（`ChatView.logic.ts` 的 `resolveComposerInteractionMode`、`shouldShowPlanFollowUpPrompt` 等）。
- 现在计划卡只在两种情况出现：Claude 自己调用 `EnterPlanMode`（用户说“先出计划”时会，V11），批准它的 `ExitPlanMode` 即开始实施；委派子任务被指定为计划模式。**Codex 的普通任务在 T3 里已不会出现计划卡。**
- 计划卡本身保留复制、下载、保存到工作区（`apps/web/src/components/chat/ProposedPlanCard.tsx`）。

### 打回重做

- T3 的 `t3_thread_send` 给**已完成**的子任务线程发消息，会在该子线程里开新任务，子任务保留自己的上下文；给运行中的子任务可插话或排队。目标的档位不能高于发送方（`toolkits/orchestrator/tools.ts:278–289`）。
- T3 说明里另有一条：**复核／复查**要用新的委派，不用 `t3_thread_send`；小问题主任务自己改（`orchestrationInstructions.ts:11`）。意思是独立复核不要沿用原执行者的上下文，**并不禁止把修改意见发回原子任务**。
