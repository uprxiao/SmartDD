T3 `packages/contracts/src/orchestrationV2.ts` 中 `OrchestrationV2TurnItem` 共 25 种条目。T1.0 §4 覆盖了其中 20 种（含 `dynamic_tool` 改名为 `tool_call`，可以接受），**漏掉 5 种**，却写了“全部保留”：

| `thread_created` | 委派时创建子线程（目标、模型） | **相关**：宿主委派创建子任务的可见记录 | 纳入，或说明并入 `subagent` |

| `link_request` | Agent 请求连接另一台机器 | 本期无远程环境 | 写明删减理由 |

### 2.2 C15：方案 B“父暂停”需落到执行器并补真实验证（必须补）

T1.0 §6 要求“父可写运行委派写子时，先暂停到适配器可证明的无可写执行边界、排空工具，再释放写入槽”。但：
1. **没写清楚 Claude SDK、Codex、ACP 各自用什么作为这个边界。** 现有候选测试只是内存队列里的 `pausedNoWrites` 布尔值。
2. **同步与异步委派的取舍没定。** 复核探针的 `wy_delegate` 是同步的（父阻塞在工具调用里等子结果）；T1.0 §6 写的是异步（返回收据、父空闲后再投递）。两种做法的暂停点不同：
   - 同步：边界是“父阻塞在委派调用中，且同一消息里没有其他在途工具”。风险是 Claude、Codex 都可能并行发起多个工具调用，而且长时间子任务可能撞上父端的 MCP 工具超时（Codex 的 `tool_timeout_sec`，需实测默认值）。
   - 异步：父继续执行会一直占着写入槽，自然边界是“父回合结束”，写入型子任务要等父回合结束后才启动。
3. **建议**：写入型子任务默认在**父回合结束**后启动（不需要执行器支持暂停，所有执行器都能做到）；只读子任务立即并行。如果要支持同步等待，必须单独说明工具超时与并行工具的处理方式。
4. **补一个真实模型实验**：Codex 父（可写）委派 Claude 子（可写）在同一目录，以及反向组合各一次。核对四点：子任务在父释放槽之前不启动；父与子没有交叠写入；结果回到父；父续跑时能看到子写入的文件。

## 3. 本次补充的真实验证 V09

探针：[probes/real-turn-override.mjs](probes/real-turn-override.mjs)（同时给 `lib/agents.mjs` 的 `turn()` 加了可选的每轮参数，原有调用不受影响）。环境：本机 codex-cli 0.169.0、ChatGPT 订阅，用户 `~/.codex` 中设有 `approvals_reviewer=auto_review`。

做法：`thread/start` 和 `thread/resume` 都**不传** reviewer（即继承 auto_review），只在每次 `turn/start` 下发 T3 “approval-required” 档位 `{approvalPolicy:'untrusted', approvalsReviewer:'user', sandboxPolicy:{type:'readOnly'}}`。

| 步骤 | 结果 |
| --- | --- |
| A 新线程：审批送到客户端（没有被 auto_review 接走） | 通过（2 次请求，没有出现 autoApprovalReview 事件） |
| A 拒绝：文件未写入 | 通过（模型被拒后又申请一次，仍拒绝，回合正常完成，符合“拒绝本步、回合可继续”） |
| B 新进程恢复同一线程：线程 ID 不变 | 通过 |
| B 每轮下发后审批送到客户端 | 通过 |
| B 批准：文件写入 | 通过 |

结论：T1.0 §7.2 的“每轮显式下发、恢复线程后重发”在真实 Codex 上成立。
