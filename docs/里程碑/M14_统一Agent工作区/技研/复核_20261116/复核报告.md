复核对象：[需求 R0.2](../../历史/需求_R0.2_20261116.md)、[技术方案 T0.1](../历史/技术方案_T0.1_20261116.md)、[全局设计验证账](../历史/全局设计验证账_V0.3_20261116.md)、[实验目录](../实验/)（130 个）、[原型说明 P0.1](../../原型/历史/原型说明与变更_P0.1_20261116.md)、[用例 A0.1](../../验收/历史/测试用例_A0.1_20261116.md)。

## 0. 结论

1. **总体方向正确，与 T3 一致**：宿主统一任务、同一任务挂多个原生会话、显式交接摘要、宿主 MCP 委派、业务权限由 WillYou 服务裁定、Provider 差异限制在适配器内。这些都已有可复现证据；本次复核又用真实模型补充验证。
2. **关键研究结论成立，记录诚实**：复跑 22 个原实验（SDK 类 10 个、业务桥／插件／邮件／浏览器类 12 个），全部通过；其中 6 个换成本机新版 CLI、8 个用当前 SmartDD 源码重新打包后也通过，说明 M13 后续改动没有推翻业务桥、插件审批、Skill 交付、执行计划等结论。130 个实验的结果文件与 README 结论一致，失败记录如实保留。
3. **主要问题不是“做错”，而是“做偏、做重、缺了界面层”**：
   - 设计重心放在身份、竞态、未知状态和迁移恢复上，支撑 T3 式界面的**展示模型基本缺失**（§3 C01）。
   - 用户新确认的范围让一大块设计失去前提：旧任务迁移、受管运行资源下载等（§3 C03、C04）。
   - 若干对新需求关键的点尚未设计：消息与文件／浏览器联动、继承用户 Codex 配置的影响、按版本开关功能、额度受限状态等（§3）。
   - 文档体量过大（T0.1 约 38 万字节、验证账约 29 万字节），正文混有演进叙述，不能直接作为实施依据（§3 C10）。
4. **新补的真实模型证据**（研究阶段几乎全用模拟模型）：
   - Claude（DeepSeek）↔ Codex（订阅）委派 4/4；
   - OpenCode（ACP）作主 Agent、作子 Agent 3/3；
   - A→B→A 切换续聊 7/7（含负对照）；
   - Skill 在 SDK 模式下被真实调用，相对路径脚本执行 9/9；
   - 审批收回到宿主 5/5。

## 3. 问题清单

严重度：**高** = 不改会导致核心目标做不出来或做错；**中** = 会造成返工或体验问题；**低** = 文档与可维护性。

### C01｜高｜统一界面的展示模型缺失

**现状**：T0.1 §4.2 的规范事件只有“消息、工具、文件变更、待回应请求、回合状态、实际模型、usage、诊断”。原型说明 S01–S09 讲的是状态保护，没有消息时间线怎么组织。候选转换器（`实验/20261114_规范事件与请求合同验证/adapters.mjs`）只映射了文本、工具、MCP 调用和终态。

**证据（V04）**：本机 CLI 加真实模型产生了 35 种原生事件，候选转换器只映射了其中 11 种。未映射的包括：
- Codex `commandExecution`：命令执行，T3 界面的核心条目；
- `item/agentMessage/delta`：流式增量，180 条，不映射就无法逐字显示；
- Claude `thinking`：思考过程；
- `userMessage`；
- `thread/tokenUsage/updated`：对应上下文用量表；
- `hook/*`、`turn/started`、`warning`、`mcpServer/startupStatus`。

**T3 对照**：T3 `packages/contracts/src/orchestrationV2.ts` 的条目类型为 `user_message`、`assistant_message`、`reasoning`、`proposed_plan`、`todo_list`、`user_input_request`、`file_change`、`command_execution`、`file_search`、`web_search`、`approval_request`、`checkpoint`、`run_interrupt_request/result`、`system_notice`、`error`、`compaction`、`handoff`，外加 `subagent` 执行节点和 usage。前端 `MessagesTimeline` 把一次运行内的工具类条目折叠成“Worked for Ns”，可以展开。

**要求 Codex**：
1. 在 T0.1 新增“统一时间线模型”一节：条目类型表，每类写清字段、来源映射（Claude 和 Codex 各自哪个原生事件）、流式更新规则、折叠与分组规则（一次运行内的工作条目怎么聚合，耗时怎么算），以及终态（完成、停止、失败、受限）。直接以 T3 的条目类型为基线，删减时写明理由。
2. 交接（`handoff`）、切换 Provider、子任务（`subagent`）要作为时间线上可见的条目，界面才能显示“此处切到了 Claude”“委派给了 Codex”。
3. 用 `probes/real-events.mjs` 采集的真实事件（Claude、Codex 各一份），加上一次切换和一次委派的录制，作为回放夹具，验证新转换器的覆盖率。目标：用户可见的事件类型全部映射，诊断类事件明确列为“不展示”。

### C02｜高｜消息与右侧文件、浏览器的联动没有设计（新需求）

**现状**：需求、T0.1、原型、用例都没有涉及。T0.1 只在审批场景提到 URL。

**证据（V05）**：直接复用 T3 `packages/shared/src/markdownLinks.ts` 和 `fileLinks.ts` 的实际代码处理真实 Agent 输出：
- 能正确识别：带行号的 Markdown 链接、行内代码中的 `路径:行:列`、正文中的绝对路径、`file://` 链接、目录链接（Codex 桌面端风格，如“当前目录是：[SmartDD](/abs)”）、普通 URL；
- 会拒绝：`javascript:`、`mailto:`；
- 项目目录以外的路径、不存在的路径，需要 WillYou 自己定规则；
- **只有文件名的行内代码（如真实 Codex 输出里的 `` `notes.txt` ``）按 T3 规则不算链接**。

WillYou 现有接口可以支撑：文件侧有 `FileWorkspaceStore.open(root, relativePath, …)` 和目录展开、树定位；浏览器侧有 `rpc.browser.create` 加 `navigate`，以及 `openNewBrowserTab` 现有的“任务必须属于项目”检查。

**要求 Codex**：
1. 需求新增 R13，T0.1 新增“消息链接路由”一节：
   - 识别：复用 T3 shared 的识别逻辑，记录来源与版本；
   - 路由表：项目文件根内的文件 → 文件工作区打开并跳到行列；目录 → 文件树定位；`http(s)` → 内置浏览器新标签；其余协议拒绝；
   - 根外路径、不存在、无项目任务（浏览器要求任务属于项目）各自如何提示；
   - 修饰键行为：T3 用 Cmd/Ctrl+点击走外部编辑器，PDF 默认走浏览器预览。
2. 安全边界写清：点击是用户发起的打开动作，不等于授予 Agent 访问权；链接文本由模型生成，不能据此绕过文件根和浏览器访问规则。
3. 用例补：12 类样本（见 `probes/link-resolution.mjs`）加真实输出回放；文件已打开、未保存、被删除等状态下的联动。
4. 待用户决定：只有文件名的行内代码是否在“当前目录下确实存在该文件”时也做成链接（见 §7 D2）。

### C04｜高｜受管运行资源下载与方案 A 冲突，应删除

**依据**：RC2。T3 实际做法：`pnpm-lock.yaml` 第 307–314 行把 `@anthropic-ai/claude-agent-sdk-<平台>` 8 个原生包全部覆盖为 `-`（剔除），`ClaudeExecutable.ts` 解析用户配置的 `binaryPath`（默认 PATH 中的 `claude`），经 `pathToClaudeCodeExecutable` 传给 SDK。Codex 用本机 `codex app-server`。

**要求 Codex**：

### C06｜中｜“发现什么版本用什么版本”缺少按版本开关功能的设计

**现状**：M13 适配器锁定精确版本（`resources/agent-adapters/codex/1.5.0/adapter.json` 只认 `cliVersions: ["0.167.1"]`，Claude 1.3.0 只认 `2.1.322`）；任务启动代码里也有 `native.version==='0.167.1'` 的硬判断（`task-capability-launcher.ts` 中 Codex 插件 Skill 分支）。用户认为锁定不合理。

**T3 做法**：不锁本机程序版本。`model-manifest.json` 用 `adapter.claudeCode.minVersion`、`adapter.codex.minVersion` 标注模型所需的最低版本，版本不够时在选择器里提示升级；协议差异在适配器内按版本分支（OpenCode 1.x 和 2.x 两套运行方式）；未知事件保留为诊断，不中断。

**要求 Codex**：
1. 设计“能力按版本声明”：每项能力（原生子 Agent、steer、恢复、approvalsReviewer、skills/list 等）写最低版本，加启动后的能力探测；版本低于下限时只关掉这项能力并提示，不整体拒绝。

### C08｜中｜共用用户 Codex 配置的影响没有设计

**证据（V03、V08）**：Codex 订阅用户的 `CODEX_HOME` 默认是 `~/.codex`（`runner-adapters.ts:83`）。实测：
- 用户的 hooks（会话开始、工具前后、停止）在 WillYou 运行里全部执行；
- `-c mcp_servers={}` **无法清空**用户的 MCP（仍加载 9 个，含 computer-use、207 个工具的 rea、239 个工具的 codex_apps），只能逐个 `enabled=false` 再加 `--disable apps`；
- 用户配置 `approvals_reviewer=auto_review` 时，审批被自动审核子 Agent 接走，**客户端收不到请求，写操作被自动批准**；`thread/start.approvalsReviewer: 'user'` 可以逐线程收回，批准和拒绝都按预期生效。

**T3 做法**：直接使用用户的 `~/.codex`（可选影子目录：只隔离 auth，其余共享），**不禁用用户的 MCP、hooks、插件、Skill**；权限在每一轮 `turn/start` 显式下发（`CodexAdapterV2.ts` 的 `codexRuntimeModeTurnDefaults`：Supervised→`untrusted`+`user`+只读；自动接受编辑→`on-request`+`user`+工作区可写；Auto→`on-request`+`auto_review`；完全访问→`never`+`user`+完全访问）。

**用户决定（D3）**：按 T3 方式，且与 M13 已定规则一致：

| 配置来源 | 做法 |
| --- | --- |
| 订阅／原生登录（用户 `~/.codex`、`~/.claude`） | **沿用**用户的 MCP、hooks、插件、Skill；每轮显式覆盖审批策略、`approvalsReviewer`、沙箱、模型与推理强度；与 WillYou 业务 MCP 重名按 M13 冲突规则处理 |
| WillYou 托管的第三方供应商 | 隔离（沿用 M13：独立 `CLAUDE_CONFIG_DIR`／按次 `-c`） |
| 自动化验收 | 一律隔离配置，保证可复现 |

**要求 Codex**：
1. T0.1 写明上表及每个权限档位到各 Provider 参数的映射表（Claude：`permissionMode`／`canUseTool`；Codex：上述四档；ACP：Provider 声明的模式，不支持的档位按 T3 降级为需审批）。
2. 用 `probes/real-approval.mjs` 的场景做验收：继承 `auto_review` 的用户配置下，WillYou“需审批”档位仍收到审批请求。
3. 是否提供“关闭我的扩展”开关，原型阶段再定，不影响架构。

### C09｜中｜T3 已知坑在设计中缺失或不完整

逐条对照 T3 `docs/internals/adding-a-provider.md` 的 “Traps several providers hit”：

| T3 坑 | T0.1 现状 | 要求 |
| --- | --- | --- |
| Agent 登记这一轮之前收到停止，会被忽略或留下未保存的会话 | 未涉及 | 以原生“回合已开始”信号为准；补“发送后立即停止”的用例 |
| “默认模型”是占位值，不能当模型名发给 Provider；切回默认要真的切回去 | 未涉及 | 写入模型选择规则 |

| Provider 自己发起的后台工作、目标、子 Agent 在回合结束后还会产生结果 | 已覆盖（后台工作、唤醒） | 保持 |

| 符号链接的工作目录（macOS `/tmp`） | 零散提及 | 加用例 |

另外：
- Claude 被拒绝后可能反复重试直到回合上限（V08 中 DeepSeek 重试了 6 次）。拒绝要区分“拒绝本步”和“拒绝并停止本回合”（Claude SDK `interrupt: true`）。
