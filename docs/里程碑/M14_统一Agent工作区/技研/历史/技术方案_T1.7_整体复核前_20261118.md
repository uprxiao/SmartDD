## 1. 整体设计与实现依据

宿主维护逻辑任务、规范时间线、原生绑定、运行身份及业务授权；适配器只负责 Claude SDK、Codex app-server 或 ACP 的协议差异。一次任务可挂多个原生会话，切换时恢复目标原生会话并补交缺少的上下文。宿主 MCP 委派复用同一任务与运行服务；写入委派按目录分流——Git 项目用宿主管理的工作副本（§6.1），SVN／普通目录用方案 B（§6）。右侧文件／浏览器及 M13 业务服务继续复用。

本机程序由现有发现服务或用户显式路径提供。应用锁 SDK 库，不分发 SDK 自带的运行程序。旧任务不迁移、不恢复、不复制历史；新列表只展示新任务，旧数据原样保留。详细历史推导及原失败保存在[旧整稿](技术方案_T0.1_20261116.md)与[历史验证账](全局设计验证账_V0.3_20261116.md)，现行研究判定仅在[验证账](../全局设计验证账.md)维护。

`capability_runs.task_id` 现有 FK 指向单任务快照，不能支持多个绑定。结构升级将其改为基础 tasks 归属，新增绑定／能力会话关联及复合归属校验；旧行各字段和外键引用原值保留，新行必须有完整新关系。旧单任务快照表保留作旧数据，不进行原生历史转换。数据库迁移器保留版本守卫、校验和、备份、事务回滚及 `foreign_key_check`；新表以后仍正常升级，旧包读到高版本应拒绝启动，不承诺应用版本降级。

**副作用恢复次序（工作副本与目标）**：宿主每个外部副作用先落“意图”行（`intent_id` UUID、动作、预期父提交 `expected_parent`、执行前 HEAD）再执行，执行后写结果：①派出前自动提交——意图行→`git commit`（提交说明末尾加 trailer `WillYou-Intent: <intent_id>`，父提交必须等于 `expected_parent`）→`agent_commit_provenance`；重启时若意图在而无 provenance，在 `expected_parent..HEAD` 中按 trailer 精确查找：找到且父提交匹配则补记，找不到且 HEAD 仍为 `expected_parent`、工作区仍脏才重做，其余情况（HEAD 已被用户移动等）标“待核实”，不重做、不猜测（评审 RR09）。子任务结果提交同样带 trailer。②建工作副本——`agent_workspaces` preparing→`git worktree add`→ready；重启见 preparing 时用 `git worktree list` 核对路径与分支，存在则补置 ready，不重复创建。③子任务结果提交——provenance 意图→commit→记录；同①核对。④完成通知——只在 attempt 的 commit_range 落库后发送，`notified_at` 去重。⑤目标自动暂停／恢复——先写 `paused_reason`、目标修订（objective 与原生 updatedAt）再调原生接口；自动恢复只对同一目标修订且 `paused_reason=waiting_children` 生效，用户后来主动暂停、停止或清除的目标不被唤醒恢复；重启后以原生 `thread/goal/get` 为准校正，修订不一致时不恢复。工作副本在任务归档时保留到用户删除分支或删除任务；`wy_send` 需要原工作副本，子任务存在期间不清理；清理只删 `~/.willyou/worktrees/` 下且在 `agent_workspaces` 登记过（路径、分支、基准提交一致）的工作副本，先经 `git worktree remove` 解除登记，不删分支、不删该根外或未登记的目录；userData 中其他资源的清理边界不变。

删除／归档新任务先检查请求、后台、业务操作、子任务和被读产物；活动／未知引用保持保留。旧任务关联业务数据、原生文件及配置不进入本期删除流程。`pty_id` 改读运行身份的逐文件影响见[清理清单](../旧代码清理清单.md)，这与旧任务转换无关。

## 3. Driver、运行与公共接口

Driver 定义是不可变注册项；每次 attach 创建独立实例，持有流式缓冲、原生关联、工具映射和待回应回调。任务／编排层无品牌配对枚举。统一接口均验证 task、binding、run、generation 和宿主 caller（例外：宿主业务请求的批准按 §8.1 校验任务与当前授权，不要求发起 run 存活）；客户端不得自报 PID、nativeId、parentRun 或真人来源。

| Driver 方法 | 入参／出参 | 责任 |
| --- | --- | --- |
| discover／probe | 显式 binaryPath 或 M13 发现结果 → executable identity/version/capabilities | 记录 realpath、版本和探测；不安装、不自动换程序 |
| open／resume | 冻结 profile、cwd、权限、配置根、能力交付、可选 native 引用 → ChildProcess/connection 与确认身份事件 | Claude SDK 使用 pathToClaudeCodeExecutable 与 spawn 回调；Codex 启动本机 app-server；ACP initialize→session/new/load |
| startTurn／steer | 冻结 inputId、blocks、模型／推理／权限 → native turnStarted／accepted | 等原生开始信号后才确认；可选 steer 不支持时使用明确排队 |
| respond | requestId＋原生选项 ID／结构化回答 → 原生确认 | 保留问题、URL、表单和业务 source；不压成 boolean |
| interrupt／close | 精确运行／节点 → terminal evidence、后台与 owner 排空 | 发送即停止先置 cancelPending，原生 turnStarted 到达后立即 interrupt；关闭不冒充回合完成 |
| events／history | 原生流／已确认记录 → §4 规范事件／只读历史 | 未识别关键必需事件标协议不兼容，未知通知保留诊断 |

MCP、IPC 和输入框调用同一 TaskCommandService；副作用在事务外执行，调用前后重核 profile 修订、能力、工作目录和当前政策。幂等只保证宿主接受，不推断 Provider 对同一 ID 不重复执行。

### 3.1 IPC、草稿与容量

Electron 本地采用单一 taskSeq：先订阅并获确认，再读取一致快照和水位，随后补拉 `(afterSeq,throughSeq]`。重复忽略、缺号补拉，裁剪或游标超前则重取快照；窗口恢复／重连查询最新水位，解决尾通知丢失。页面切换取消旧订阅和旧请求，闭包绑定窗口／task／requestToken；不叠加数据库、视图、历史等多重 epoch。数据库替换关闭所有连接后重建订阅。分页使用稳定 ordinal＋revision 和不透明 cursor，页不能推进事件水位，旧 revision 不能覆盖新数据；删除标记压制迟到页。

初始限制复用 F16 的已验证边界：事件 32 KiB、预览 4 KiB、IPC 请求 1 MiB／响应 256 KiB、事件页 128 条且 256 KiB、历史页 100 项且 256 KiB、正文范围读取 128 KiB；每 run 归一队列 128 项或 16 MiB、宿主合计 64 MiB；renderer 每 task 2000 项且 8 MiB，最多 4 个任务且合计 32 MiB。超限正文转 artifact，关键请求不截断；存储失败停止确认并保留草稿，取消使用独立控制通道。流式合批初值 50 ms／32 KiB；这些是拒绝／恢复边界，不是 App 性能承诺。

## 5. Provider 切换、交接与输入

选择预检返回目标、配置／凭据来源修订、程序版本、能力及兼容身份；应用及派发前再次核对。首次目标新建 binding 并交全量摘要；兼容目标恢复原 native 会话，只补其 coverage 未包含的规范内容。配置根、账号、cwd 或必要能力不兼容时新建绑定并保留旧绑定；不复制旧任务原生历史。仅在父运行空闲、无在途发送／回应且业务准入允许时切换。子结果始终按父逻辑任务收回，不随当前 Provider 丢失。

交接保存 exact payload/ref、来源条目、覆盖水位、遗漏／截断理由及预算。输入、附件、Skill、历史与子结果都有 sourceKind；只有可信当前 UI 提交可取得真人来源证据，恢复或观察历史不会重建实时授权。交接文字最多 256 KiB，并受本轮输入和宿主说明占用后的剩余预算约束。先选最近的未覆盖条目，再按时间顺序发送。预算不足时记录较早端被省略的条目。单条超限或原文不可读时记录该条的具体原因。附件按实际二进制与目标能力计预算，原消息原文保留。

插话是可选能力：当前执行器／版本／模式须同时通过协议探测和真实模型接受验证；Codex 用匹配 expectedTurnId 的 turn/steer，Claude 用 SDK 仍开放的 AsyncIterable 输入流。宿主记录提交时回合／工具状态、原生接受和后续回答的关联；不能以写入 stdin 成功认定已接受。无证据或状态不匹配一律走排队，不自动改成新回合发送。真实验证及其局限见[二次复核实验](../实验/20261116_二次复核修订验证/README.md)。

投递状态只有 prepared、sent、accepted、not_sent、unknown。能证明没发出才允许重试；发送后断线／宿主崩溃且不能确认消费才 unknown；恢复先读原生记录及业务操作账，不自动复发 unknown。原生同一 clientId 的幂等差异保留在适配器能力中。

## 6. 委派、方案 B 与后台结果

宿主 MCP 暴露目录查询、创建、观察及取消；父 caller 从桥绑定取得，不接受模型指定 parent 身份。主／子目标来自已接入配置，接受时冻结修订，启动时重检。持久创建子任务、来源、队列及收据同事务；相同 requestKey 返回原收据，不新建第二子任务。结果修订写入一次，通知只带引用；父忙排队，父空闲观察／领取后再唤醒，旧 run token 不可读取新代次结果。

**方案 B 只用于 SVN 与普通目录中的写入委派**。三类目录中互不相关的独立任务都可在同目录并行，并保留各自的会话。Git 写入委派走 §6.1 工作副本，宿主在父任务排空后准备工作副本。同一 Git 根的宿主工作副本准备按序执行。只读子任务在所有目录类型都在主目录并行。方案 B 的队列键取授权根的 realpath／物理目录身份；别名合并，父子重叠的项目目录采用同一登记工作根，未知归属拒绝启动而非全盘扫描。写入资格由宿主权限／可信角色政策决定：只读档位且所有写入入口受限才为 read，其余为 write；模型自报“只读”无效。原生只读不约束外部 MCP，业务、插件和可写 Skill／shell 必须同时受只读政策约束；不能证明时按 write 排队。

只读运行请求写操作时先阻止该步执行，转为写入排队；等当前回合结束并排空后，取得目录槽才可执行。不能延后该工具的目标拒绝本步并提示在写入回合重试，不能沿用 read 资格执行。不可约束的用户扩展按 write 管理。

参与方案 B 的写入运行在同一根最多持有一个 write 槽，多个 read 可并行；读取结果需在写入前复核文件版本。**写入型委派固定为异步：wy_delegate 持久创建并立即返回 queued 收据，父继续当前回合；子等父回合自然结束并排空后才启动。** 父不得持槽在 MCP 调用中阻塞等待子结果。只读子在可信只读约束下可立即并行。本期不启用同步等待写子；旧同步探针只证明目标可调用，不作为方案 B 调度证据，因此本期没有对外承诺的同步 MCP 等待／默认超时预算。

写入槽释放必须同时满足：原生回合确定终结；无在途工具／原生子工作／后台进程；宿主业务租约排空；宿主冻结该 owner 的新输入和写业务准入。终态与排空是不同证据，失败终态也不自动证明进程已排空。三类适配器分别落实：

| 执行器 | 自然回合边界 | 排空与不能证明时的处理 |
| --- | --- | --- |
| Claude SDK | 匹配本次输入／session 的 result（success 或明确错误） | 逐个 tool_use/tool_result 对账；原生 Agent／后台任务终态与业务账清空；SDK 输入流不再接收新写输入。不能证明无后台时关闭本次 query，独立观察实际 ChildProcess 退出及登记后代／业务排空，后续 resume 原 session |
| Codex app-server | 匹配 threadId/turnId 的 turn/completed | item/started/completed 对账，commandExecution／MCP／原生子工具均无 pending；thread/status 的后台活动及宿主登记进程／业务清空；阻止新 turn/start。仍有 background 则保持槽；不可靠时关闭该 owner，确认实际进程及后代／业务排空后 resume 原 thread |
| ACP | 本次 session/prompt 的 stopReason 确定响应 | tool_call/update 的 terminal status 逐个对账，session 声明的后台节点及宿主业务清空，冻结新 prompt；无可核对后台协议时关闭准确 owner 并观察退出及排空，再按实际 resume/load 能力续跑；不支持恢复则明确提示限制，不静默换会话 |

首版优先采用已验证的 owner 退出后释放路径；存活 owner 交槽作为开发阶段优化，须补齐同样四个核对点的真实验证后才启用。上述“owner 存活时的自然回合释放”是待开发合同，**当前真实模型证据只验证更保守的 owner 退出后释放**；不把 native pause 或 `pausedNoWrites` 布尔值当证明。回合未结束、工具未排空、退出不明或业务仍在途时都继续占槽。父释放后子按 FIFO 启动；子结束也经同一边界排空；父收到 notification 后重新入队，取得槽才恢复原 native 会话并读取结果。新的父写输入与待启动子共享同一队列，不能插队占回槽。排队可取消；超时／失联保留占用事实，不自动放给下一个写者。

[W1/W2 真实模型实验](../实验/20261116_二次复核修订验证/README.md)覆盖 Codex 可写父→Claude 可写子及反向：同一 cwd、原生文件工具、queued 前后继续写入、turn 完成及实际 owner 退出、子派发、结果送回、原父身份恢复后读随机 child.txt。宿主顺序与原生记录分别留证；不是生产调度器或 App 验收。

**放行时的重读提示（用户 2026-11-16 确认，补充方案 B）**：队列放行后拿到写入权的运行，宿主把“上一位持有者在其捕获区间内改动的文件清单”（取自 §11 的每轮改动记录；无记录则注明“未知，请重新核对工作区”）写进它的启动或续跑说明，要求先重新读取这些文件再修改。该说明只是提示，不替代写入前的文件版本复核。 当前实现发出重读提示并指向每轮差异记录，逐项写入改动清单待实现，测试判据见 [A77](../../验收/历史/测试用例_A1.10_20261118.md#m14-a77-写入委派在非-git-项目的提示与重读)。

后台／原生子 Agent 生命周期独立于父回合，按 node 身份接收迟到结果；能力不足以定向停止时只提供停止所属 run。宿主子树取消撤销所有后代桥权限并观察各自排空；一个 Provider 的失败不终止无关配置。运行可记录不同 cwd；Git 项目工作副本见 §6.1，本期不自动管理 SVN 工作副本。

### 6.1 Git 工作副本委派、合并、目标与计划（需求 R02、R06；D4 用户修改）

**分流**：委派写入子任务时，宿主检测主任务目录是否位于 Git 仓库（`git rev-parse --show-toplevel`，并排除 SVN 工作副本内嵌套 `.git` 的误判）。是 Git：走工作副本；否则（SVN、普通目录、检测失败）按 §6 方案 B 串行。只读子任务一律在主目录并行。

**阶段边界（复核 AR09）**：Git 写入委派与方案 B 一样**异步**：`wy_delegate` 持久接受后立即返回 queued 收据，父继续当前回合；宿主在父回合自然结束且工具／后台／业务排空、冻结新写入后才执行下面的“创建”，不在 MCP 调用内等待，避免父等创建、创建等父。子任务结束同样以排空为准：子回合终结后核对其工具、后台进程与业务租约全部结束，以这一份排空证据同时驱动“子任务提交”、§11 的 after 捕获和完成通知；仍有后台写者时不提交、不通知，停止与失败走同一核对。

**路径与目录映射（复核 AR12）**：工作副本路径 `~/.willyou/worktrees/<项目段>/<分支>`，`<项目段>` = 项目名的英文简写（小写、仅 `[a-z0-9-]`，中文或空格转写／去除，空则用 `project`）＋`-`＋项目稳定 ID 的前 6 位（如 `smartdd-a1b2c3`），同名项目不会撞目录；路径不含空格。分别记录 `repoRoot`（`git rev-parse --show-toplevel`）、主任务 `cwd`、工作副本根 `wtRoot`；子任务 `cwd = wtRoot + relative(repoRoot, cwd)`（主任务从仓库子目录启动时，子任务落在工作副本中的同一子目录），文件授权根为 `wtRoot`，锁文件先在映射后的子 cwd 查找、再到 `wtRoot` 查找。

**创建（宿主执行，不接受模型提供路径，不绑定 Agent 用 shell 自建的工作副本）**：①父任务回合及后台业务排空后，宿主按仓库根真实路径协调同一个 Git 工作目录（包含子目录与路径别名，区分独立工作副本及嵌套仓库）。暂缓同一工作目录的新输入及新的宿主写入，新增消息保留在任务自己的输入队列，已有会话继续当前回合。宿主等待当前回合及已知后台工作结束、在途业务排空。仍能自行开回合的 Codex 目标等待其自然停止或用户暂停，宿主保留目标与会话。复验目录和分支后，工作区不干净则 `git add -A` 后提交，注明“可能包含同目录其他任务的改动”，忽略文件沿用 Git 配置。该提交是共用目录快照，完成的其他改动也可能进入；②`git worktree add -b <当前分支>_willyou_<slug> ~/.willyou/worktrees/<项目段>/<分支>（照 T3 `~/.t3/worktrees`，路径不含空格以保证行内绝对路径可按 T3 规则识别） <该提交>`，slug 由委派标题生成英文短语，重名加序号；detached HEAD 用短提交号代替分支名。工作副本建好立即恢复其他任务原会话的输入派发。父任务停止或子任务取消若发生在等待阶段，释放暂缓且不创建提交。③检测锁文件安装依赖（`pnpm-lock.yaml`→`pnpm install --frozen-lockfile`，`package-lock.json`→`npm ci`，`yarn.lock`→`yarn install --frozen-lockfile`；Maven／Gradle 跳过），有超时，结果写 `agent_workspaces.deps_result`，失败写入子任务启动说明；④子 run 的 cwd、沙箱可写根、差异捕获范围、右侧文件与差异视图均绑定该工作副本（需求 R01：进入子任务视图时右侧切到子工作目录）。各步按 §2 副作用恢复次序落库。子任务不得再派子任务（照 T3）。

**子任务提交（宿主执行）**：子 run 终结后，宿主在其工作副本 `git add -A` 并提交到子分支，说明 `willyou: <子任务标题>（子任务提交）`；无改动不提交；失败或取消同样提交以保留现场，但不进入合并通知。子 Agent 不写 `.git`，不受沙箱影响。每次提交记 `agent_commit_provenance`，按 attempt 记录提交区间。

**合并（主 Agent 执行，照档位，照 T3）**：完成通知（结果收据）附分支、基准提交、**本 attempt 新增**的提交列表与改动摘要、建议步骤（先提交当前改动，再 `git cherry-pick -x` 按顺序拣入；冲突逐文件解决、保留两边意图）及禁用命令清单。主 Agent 写 `.git` 的命令按任务档位：请求批准逐条用户批准；帮我批准（Codex on-request＋auto_review＋workspaceWrite）由 Codex 申请提升权限、自动审核批准，自动审核结论（`guardianWarning`）显示为系统提示；完全访问直接执行。**宿主事后核对**（主 Agent 本轮终结后）：①子提交已进入当前分支——是 HEAD 祖先、或补丁等价（`git cherry` 标 `-`）、或 HEAD 自基准以来有提交带 `-x` 写入的 “(cherry picked from commit <原提交>)” 记录，三者都不满足则为“待核实”（评审 RV01：不再接受“作者时间＋标题相同”）；②无 `CHERRY_PICK_HEAD`／`MERGE_HEAD`；③受影响文件无冲突标记；④当前分支与委派时一致。结果写 attempt 的 `merge_check_json`；不通过提醒主 Agent，连续 2 次仍不通过标“需要你处理”。宿主不执行 reset／checkout／clean。

**`wy_send`（照 T3 `t3_thread_send`，限本任务派出的子任务）**：子任务已完成→新建 attempt，在原 native 会话、原工作副本开新一轮；运行中→按执行器能力插话或排队；档位不能高于发送方。独立复核使用新的 `wy_delegate`。

**目标**：能力 `supportsNativeGoals` 由驱动声明，命令菜单只对支持的执行器列出 `/goal`。Codex 用 app-server `thread/goal/set|get|clear`，`/goal` 由宿主拦截不作为文字发送；状态 active／paused／blocked／usage_limited／budget_limited／complete 映射到 `agent_goals` 与目标条目（时长、宿主计数的轮次，不显示 token）。停止：若 active 先 `status: paused` 再 `turn/interrupt`（V14：只中断会留下 active）。Claude：`/goal` 作为文字发送，状态从回复文字识别（“Goal set:”“Goal active: …”“Goal cleared:”），确认文字不重复成消息；不支持暂停／继续，只提供清除；识别失败显示“状态未知”。

**目标与切换执行器（AR10，V17，用户 2026-11-17 决定）**：`agent_goals` 有该任务未清除、未完成的目标（active／paused／waiting_children）时，切换服务拒绝把绑定换到其他执行器或供应商配置，返回“先清除目标”；同执行器换模型照常在空闲边界生效。原因：Codex 目标 active 时宿主不发输入它也会自动续轮（V17 A：30 秒 2 轮），Claude 目标保存在会话中、恢复后任一消息都会继续追目标（V17 R1），两者都会让旧执行器与新绑定冲突或产生意外行为。目标在等子任务时同样锁定，保证子任务结果回来时在同一绑定自动续跑。清除目标（Codex `thread/goal/clear`、Claude `/goal clear`，V17 R2 已验证）后解除锁定。委派给其他执行器的子任务是独立节点，不受此限。

**目标与待唤醒子任务（评审 RV05，V16 实测）**：“待唤醒”指本任务存在已派出、完成后会唤醒主任务、尚未终结的子任务（含 SVN 排队中的写入子任务）。
- Codex：在 `turn/completed` 事件到达时（不能用轮询，V16 run1 轮询被毫秒级续轮抢先）若目标 active 且存在待唤醒子任务，立即 `thread/goal/set paused` 并记 `paused_reason=waiting_children`。暂停后、唤醒前到达的 `turn/started` 是没有所属 run 的孤立回合：照 T3（`CodexAdapterV2.ts` “Pause orphan goal turns so they cannot work without an owning run”）再次暂停并立即 `turn/interrupt`，确认其终态为 interrupted 且工具、后台与业务排空后，才释放写入资格或继续交槽；不能放任其执行（评审 RR02；V16 run3：孤立回合被中断，无命令／文件改动）。子任务结果作为新一轮输入送达时恢复 active。不处理时 Codex 会空跑数轮后自行置 blocked（V16 run1）。
- Claude：宿主给 SDK 注册 Stop 回调，目标 active 且存在待唤醒子任务时返回 `{continue: false}`，会话停止但目标保留；子任务结果以唤醒消息 resume 同一会话，目标继续（V16 B：6 秒停下，唤醒后完成）。不处理时 Claude 会用 shell 循环干等、不结束回合（V16 A），在 SVN 串行下会与排队的写入子任务互相等待。
- 用户主动停止、子任务失败或取消、子任务请求长时间等待用户，分别作为唤醒或保持等待的输入，按 E11 补测。

**计划**：不下发计划模式，不做入口。Claude `ExitPlanMode` 入参 `plan`（Markdown）生成 proposed_plan 条目；计划批准在**所有档位**都进入统一请求面板（批准并开始／继续修改／拒绝）。实现上宿主在 `canUseTool` 中把 `ExitPlanMode` 作为原生阻塞请求挂起，用户批准即放行、拒绝即拒绝；PreToolUse 回调作为第二道拦截（V18，仅在本机 Claude Code 2.1.326＋DeepSeek `deepseek-flash` 下验证，其他版本由启动预检确认：带 canUseTool 时 bypassPermissions 下 ExitPlanMode 仍经 canUseTool，挂起期间无写入，批准后同一回合实施；PreToolUse deny 同样有效）。**SDK 不传 canUseTool 时不提供 EnterPlanMode／ExitPlanMode／AskUserQuestion**，宿主必须始终传入。计划模式期间 Claude 临时改变权限模式，只读命令也可能经过 canUseTool，完全访问档宿主直接放行这类调用。仅当所用版本无法截获时（启动预检发现），该执行器在完全访问档以 `disallowedTools` 去掉两个计划工具并提示，不以原生自动通过记为通过。Codex 普通任务不产生计划条目。

### 7.3 插件操作的生效档位（2026-11-16 需求 R08 补记）

- **清单属性**：插件清单的写操作增加可选 `maxTier`（`ask`／`auto`／`full`，对应请求批准／帮我批准／完全访问），缺省 `full`。安装与升级时校验取值；安装确认页列出 `maxTier` 低于 `full` 的操作。WillYou 自带邮件插件的发送操作为 `ask`，其余不声明。

- **待技术验证**：Claude 同一会话每轮切换权限模式（SDK `setPermissionMode` 或每轮 query 选项）是否在恢复会话后生效，对应 Codex 已有的 V09；执行器自身对 MCP 工具调用的批准与 WillYou 插件审批不得对同一次调用重复询问（各档下核对 Codex `mcp` 工具审批与 Claude `canUseTool` 对 WillYou MCP 的放行方式）。

### 8.1 交互等待与执行时限分离（需求 R01，评审 RV02）

需求要求交互式任务的请求不设界面超时，但现有服务把“等待用户”和“执行有效期”绑在一起：`src/main/core/browser/access.ts` 申请即写 `expiresAt=now+60000` 并以 60 秒计时器自动拒绝；`src/main/core/applications/plugins/write-approvals.ts` 把确认有效期定为 `min(operation.deadline, now+60000)`，批准后执行前再次检查过期。执行器侧的 MCP 工具调用同样有超时（Codex `tool_timeout_sec`、Claude MCP 调用超时），宿主让 MCP 调用一直挂起会先被执行器判失败。改造合同：

| 对象 | 交互式任务 | 无人值守（M15） |
| --- | --- | --- |
| 等待用户 | 请求持久化后**不设等待时限**；MCP 工具调用不阻塞等待，立即返回 `{status:"awaiting_user", requestId, next:"批准后会通知你结果，先做别的"}`，Agent 继续其他工作 | 直接拒绝（插件写、发送邮件、跨任务网页授权） |
| 用户批准时 | 重新校验：任务仍存在且未被用户停止、请求未撤销、插件仍启用、任务当前档位与授权仍允许、业务账本行仍是该 operation、审阅内容 hash／displayReceipt 与当前一致、账号／连接未变；任一失效则请求退役并提示，不执行。**不要求发起它的 run／generation 仍存活**（发起来源只作记录），由宿主以任务身份执行，不依赖旧 owner 进程 | — |
| 执行时限 | 沿用原 60 秒等执行时限。一律从宿主授予本次业务执行资格起算。SVN／普通目录写入槽排队、Git 父任务排空、工作副本准备与依赖安装等等待都在计时前。等待时面板显示待宿主放行并可撤销批准，停止也会作废本次批准。放行后重新校验当前任务、内容与授权。浏览器授权批准后作用于该任务**当前**的运行（发起它的 run 可能已结束），有效期到该运行结束，停止／撤销即失效；批准时任务没有当前运行（owner 已退出且尚无后继 run，见下方“浏览器授权待绑定”）则先持久为待绑定，绑定时刻起算 | — |
| 结果送达 | 执行结果作为通知送达**任务**：发起绑定仍是当前绑定时，运行中插话或排队、空闲则唤醒；已切到其他执行器则送入当前绑定的下一轮输入并标明来源；不重放到旧 run。与委派结果同一投递路径 | — |
| 退役 | 用户停止任务、撤销授权、插件停用、内容或账号／连接变化时，挂起请求立即退役，迟到批准拒绝。**普通回合结束、owner 进程退出（含方案 B 交槽）、切换执行器、宿主重启都不退役**（重启后按持久记录恢复。未取得执行资格的批准需重新确认，已开始执行且结果未知则从账本核对） | — |

**浏览器授权待绑定（复核 1135 N01）**：只在实际 owner 已退出、且没有后继 run 时适用；普通回合结束而 owner 仍在（同一 run 可继续接收插话）不算无运行，仍直接作用于该 run。

1. 批准通过上表校验后，请求状态记为 `approved_pending_bind`（持久化，重启后恢复为同一状态），不写回已退出的发起 run，也不生成可用授权证据。
2. 唤醒沿用“结果送达”的同一投递路径：任务空闲则唤醒；SVN／普通目录串行下需等写入槽的，按 §6 调度排队，不为授权插队或另起唤醒。
3. 后继 run 登记成功后、首个回合开始前，重新核对任务未被停止、授权未撤销、目标页面仍存在且属于原授权范围、档位仍允许；全部通过才绑定到该 run（记录 `bound_run_id`），执行与授权有效期从绑定时刻起算，到该 run 结束。
4. 绑定前不向 Agent 声称已获得权限；送达给后继 run 的通知在绑定成功后才写“授权已可用”，绑定失败写明原因。
5. 绑定前用户停止任务或撤销授权，待绑定授权立即退役，后继 run 不获授权；目标页面已关闭等核对失败同样退役并提示用户。

`browser/access.ts` 的 `expiresAt`／计时器和 `write-approvals.ts` 的 `expiresAt` 需按此拆成“等待”与“执行”两段；改造范围属 M14 生产开发，不追改已发布的 M12／M13 版本。原生命令审批（Codex 服务端请求、Claude canUseTool）本身由执行器等待，宿主只需不设界面超时。验证见 E12。

**请求的生命周期分类（复核 AR05；上表为宿主业务请求的完整规则，下表与之一致）**：

| 请求类别 | 归属 | 本回合正常结束 | owner 进程退出（方案 B 交槽等） | 切换执行器 | 用户停止 | 宿主重启 |
| --- | --- | --- | --- | --- | --- | --- |
| 原生阻塞请求（命令／文件审批、Agent 提问） | 本回合（turn） | 随回合收口、退役 | 随回合退役 | 切换只在空闲边界发生，此时已无 | 退役，迟到回应拒绝 | 原生会话已断，退役 |
| 宿主业务请求（插件写、发邮件、跨任务网页授权，已返回 `awaiting_user`） | 任务＋发起绑定（task／binding），不归属回合 | **保留**，不等同拒绝 | **保留**；批准时按任务身份重新校验并由宿主执行，不依赖已退出的 run | 保留，仍按原发起绑定的授权与内容校验 | 退役（停止即撤销），迟到批准拒绝 | 按持久记录恢复为待处理 |
| 后台／子任务节点 | 自身 node | 独立存活 | 独立 | 独立 | 按停止范围处理 | 按记录核对 |

§9 各终态与回放所说的“收口请求”只指原生阻塞请求；宿主业务请求按上两表处理。**写入资格**：只有原生阻塞请求会阻止释放写入槽；已返回 awaiting_user 的宿主业务请求不占目录写入资格（否则方案 B 下会无限阻塞），它批准后的执行另取业务租约，租约在执行期间计入 §6 的“宿主业务租约排空”。

## 11. 每轮改动与差异查看（C16、D5）

Git 项目使用独立 GIT_INDEX_FILE，读取当前工作树建立 before／after tree，commit-tree 保存无分支提交，update-ref 写 `refs/willyou/turns/<turnId>/before|after`；不移动 HEAD、不写用户 index、不产生用户分支提交。SVN／普通目录用私有裸 Git 的 GIT_DIR＋工作副本 GIT_WORK_TREE＋私有索引，同样存隐藏引用。显式排除 `.svn`、`.git`、产品受保护路径及项目忽略项；二进制和超大差异只显示元数据／不可预览原因。

SVN／普通目录的委派写入 run 取得方案 B 槽后捕获 before，Git 工作副本中的子 run 在其工作副本内单独捕获，完成或停止并排空写入后捕获 after；未完成快照标 incomplete，不能用下一轮状态补造上一轮差异。区间内的独立任务／外部／用户写入只声明观察到的变化，不归责给模型。差异用树间比较，打开时重验授权根和快照身份；未保存编辑缓冲不被差异结果覆写。M9 `syncFileConflictDiff` 提供展示组件和既有限额，新增独立只读差异文档适配，不借原编辑器保存基线作回退。

[10 GiB 实测](../实验/20261116_复核修订验证/results/shadow-git-10gib.json)：20,481 文件、10,737,418,240 实际分配字节，首次 70.1361 秒、无改动 0.1835 秒、三文件增删改 0.1171 秒；影子库约 70.7 MB。样本为高可压缩的独特文本，每文件正常写入，非稀疏；SVN 仅 seed 已提交，其余未版本化。结果证明这一合成样本上增量可行，不证明企业全量已版本化／高熵二进制项目的性能。

初始上限采用实际验证规模：可捕获文件总量 10 GiB、最多 20,481 个内容文件；首次后台准备预算 120 秒、增量 5 秒，影子存储预算 1 GiB，始终预留至少 2 GiB 空闲磁盘。超过规模先提示未在验证范围内，不在 UI 线程递归扫描；计量在后台捕获中累计，超限／取消保留旧完整引用并标本轮不可用。高熵数据可能先触及存储预算，不能按文本压缩比预测容量。首次捕获未就绪时任务可继续，首轮差异明确缺失，下一空闲边界重新准备。用户自行扩大上限属于后续评审，不宣称当前支持更大规模。

保留引用和已打开差异读租约防止清理在读数据；按任务归档及保留政策清理本方隐藏引用／私有影子库，不执行 reset、checkout、revert 或 svn revert。界面没有回退按钮，IPC 没有回退命令。
