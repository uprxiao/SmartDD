## 钥匙串前置的处理

Codex 第 424 次定位到：保存 SMTP 连接时，主进程卡在 macOS 钥匙串授权。第 452 次弹出“找不到用于储存 SmartDD Key 的钥匙串”：测试把 HOME 指到隔离目录，那里没有钥匙串。用户点了“取消”，没有点“还原为默认”。

r2 在启动 App 前，给隔离 HOME 建一个测试专用的钥匙串并设为默认。启动前先只读核对过：钥匙串偏好跟随 `$HOME`，切换 HOME 后看不到用户的登录钥匙串；演练时测试条目没有进入用户钥匙串，用户默认钥匙串保持 `~/Library/Keychains/login.keychain-db`。驱动在每次运行时也会断言这一点。之后测试连接和保存连接在零点几秒内完成，没有任何系统对话框，不需要用户操作。

## 发现并修复的缺陷

- **M14-D06-74**：发送审批进行中选择“手动修改”，保存时报“草稿已被发送意图占用”，修改保存不了，而旧发送请求已被标为退役。原因是手动修改没有像“让 Agent 修改”那样先取消待执行的发送意图。修复 `e45f7b4ba`，单元测试红绿验证。
- **M14-D06-75**：已确认原型中，邮件被修改后卡片标“已修改”，产品只显示“第 N 版”。修复 `bc11c405c`：草稿超过第 1 版且不在编辑中时显示绿色“已修改”。界面测试红绿验证。

## 第 466 次：18 项判据全部通过

- 批准发送：邮件原文留在时间线，输入框位置只有操作；捕获服务收到的收件人、主题、正文与合成数据一致。
- 手动修改：发件账号只是标签不可改；未保存时“批准发送”不可选；保存后显示新内容，生成新修订、新审阅哈希与回执，旧审阅的批准被拒；发出的是修改后内容。
- 让 Agent 按我的说明修改：写说明后选择，宿主取消原发送意图并把说明交给 Agent；请求批准档下 Agent 的草稿改写本身先经一次插件写批准；随后以新修订再次请求发送，卡片标“已修改”；连续两次，每次都是新修订，旧修订的批准都被拒；最终发出第二次改写的内容。
- 拒绝：邮件不发送。
- 完全访问档位：发送邮件仍要询问，批准后发出。
- 捕获服务只收到 4 封预期邮件，没有多余投递。

收尾时 App 未在 20 秒内正常退出：最后一次发送后，宿主把结果通知交给 Agent，有两条通知仍在排队，驱动没等它们处理完就请求退出，随后强制清理了本轮 App。这不是 A41 的判据，记为驱动收尾问题。
