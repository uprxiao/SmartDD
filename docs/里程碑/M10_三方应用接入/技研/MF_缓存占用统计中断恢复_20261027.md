# MF · 缓存占用统计中断恢复

需求R1.6＋§12.21，M10-R05-07占用展示及R05-04／版本占用恢复边界；沿用2026-10-20及当前继续开发／测试授权。2026-10-27，`feature/0.0.2`，HEAD `f1f1728d68a8595e665d4833dff048189e63e0f8`加工作区。

## 原失败与原因

真实MC打包App新建私有userData，无秘密、外部邮箱或Agent。先正常查看缓存占用，再仅在该App对本次`cache/mail`执行实际`readdirSync`前暂停，外部只读核对一个`application.cache.status`管理读取及其UI C包租约已经持久化；SIGKILL本次宿主，重启并重新查看。新查看成功，原操作仍running、原租约仍active，明确的“原死进程读取必须释放”断言失败。现场为`/private/tmp/willyou-m10-cache-status-HBwd4o`；原冷副本另存本机，库hash留证，不归档DB。

这是产品缺陷M10-MF-01。普通读取恢复只处理`ui.*`及内部索引读取；MC新增的严格管理恢复只处理写语义的`application.cache.clear`。管理统计使用`application.cache.status`／read，两条路径都不接管，留下永久包占用；需要兼容包激活或数据库迁移时也会保守拒绝启动。真实新查看成功并不代表原占用已恢复。

## 实现边界

复用MC的严格管理身份和资源证明，增加`recoverApplicationCacheStatus`，内部共享同一核验函数，按明确action／semantics分别处理。状态读取只访问本机缓存、业务占用与版本清单，不发外部业务请求；此宿主退出后不再有继续消费C包的该操作。仅在原host UUID／PID／内核出生标识确认stopped，原操作、包／资源归属、空target及无项目／Task／run／job／parent与完整快照均匹配时释放该租约。

- 原running读取变为cancelled／CANCELED；原缓存清理仍为unknown／RESOURCE_RECOVERY_REQUIRED，不将部分写效果认定成功。
- running／unknown进程、历史不完整schema、非法scope／目标／数据API、外来C资源、嵌套资源占用及提交前记录变化均保留；内核探针在C锁及SQLite事务外，最后原子重验与提交。
- 已有终态保持原结果；不执行缓存删除、不重放原统计、不释放Agent或其他写操作，不替换邮件缓存自身的归属恢复。
- 接入`ApplicationService.recover`及`openManagedDatabase`的迁移／激活前恢复，继续原有MC清理恢复与普通读取恢复顺序；界面、原型、需求范围和数据schema均不变。

测试扩展原缓存清理／统计两类，分别核对死亡、活跃／未知、PID复用、完整证明、终态、竞争及事务回滚；受管启动覆盖两类操作的激活和迁移＋激活。当前8文件276项、完整类型、新MF包六原生及21组实际服务／Codex检查通过；原失败数据的旧宿主拒绝／新宿主恢复激活也已完成。实际新包及原红测升级结论由[验收记录](../验收/MF_缓存占用统计中断修复与新包复验_20261027.md)记录；保持各层级与真实边界。M10正式仍31/72，T17／T65等完整用例未因此关闭。
