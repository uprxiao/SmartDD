# Codex逐应用加载与恢复接线 · 2026-10-22 AU

依据M10 R1.6含12.21及已有开发授权，承接AT逐应用运行基础。本批把**Codex原包资源部分不可用**的处理接入真实TaskService／ManagedTaskCapabilities生产组合。仍在第5步，Claude对应主入口红测及进一步名称冲突隔离未完成，REVIEW-01不关闭。

## 实现

AgentLoadRequest新增仅宿主内部使用的applicationScope；只接受非legacy的Codex原S应用子集，空集、重复、外来应用或Claude输入拒绝。适配器先核对完整原S、原生身份与完整H清单，只为健康原应用和全部原标准Skill构造临时规划视图；纯CJS适配器1.0.0／1.1.0字节、原名字、路径、MCP键与存储S都不变。完整H条目仍逐一校验并明确启停；受管目录归属损坏、共享MCP冲突等不会被藏在部分范围里伪作可用。

sourceSkills可只读取本轮原应用，保留完整Skill目录、二进制附件／可执行位和全部原标准Skill。源文件读取时核对大小与哈希，并在每个应用读取后复核完整原包；不把复制期间变化的字节标为原sourceHash。

新建／恢复均逐应用检查原资源：部分健康且适配器支持时，为本轮源登记真实H投影引用，按原协调协议预留H消费者，再用AT的reserveScoped保护本轮来源、标准资源及实际投影的完整依赖闭包。完整原S和长期引用保留；排除应用不会在运行中因原hash修复而自动获得授权，下一次正常恢复再重新核验。本轮还保留原launcher必读的legacy-runtime引用，即使项目上下文MCP被关闭，也不因缩小应用范围丢失这项共享资源保护。

初始S提交仍核对完整应用选择、默认版本、标准Skill与连接身份；只将禅道pending门控限定为本轮实际准备的应用，并绑定完整选择摘要。恢复、arming和最终同步fork门控使用同一范围。实际连接切换不会误停仅注入Mail的运行；当前Mail停用立即拒绝后续调用，重新明确启用后同一健康能力可继续。所有应用都依赖的原runtime缺失时，保留普通原生Agent且不授予应用能力。

诊断原来用全S一次资源失败污染每个应用。本批保留整体原S问题，同时对Codex各应用核对其原来源、共享资源、标准Skill及所属H引用；禅道缺包不再把健康Mail资源标为不可用。诊断仍明确Skill发现／正文读取未验证，文件／参数不冒充真实原生读取。

## 验证与边界

冻结1997输入后的整轮18文件433项为431通过／2失败／0跳过（exit1）。新增切换夹具未还原配置操作所需的原禅道包，目标停止范围断言前被原包校验拒绝；仅修正这一前置，生产代码未改，定向复验1通过、91按名称未执行。按唯一完整用例名仅替换该失败项，**最新去重433项：432通过、1失败、0跳过**，并非单次全绿。修正后最终node／web类型exit0。新增13项最新全通过，包含在总数内，不叠加定向次数。保留的唯一失败是AT原始Claude新会话“禅道缺失但健康Mail仍应可调用”主入口红测；Codex同一原红测已通过。**本批仍非全绿。**

新增6项规划／投影检查使用真实安装的两个合成不可变包，第二包不冒充内置Mail业务。新增7项真实宿主服务组合使用原内置应用，覆盖旧S／原H路径保留的恢复、双向缺包、同hash修复不扩大当前范围、当前策略复核、禅道pending新建／恢复、arming后最终fork竞争、实际连接切换及共享runtime缺失、逐应用诊断。旧真实Mail Data API、跨Agent／发送来源与C/H保护回归一并执行。所有TestPtys均不fork原生Agent，只配对其自己已知的合成CLI／桥退出；原有真实OS PTY与原CJS MCP无害合成CLI层保留，**不是实际CC／Codex或打包App证据**。

首轮新增测试有两项失败：一项误写资源前缀application-package而实际原身份是app，修正夹具断言；另一项确为整体诊断污染健康Mail，修复生产代码。两轮定向原输出及修正脚本保留。扩大回归新增切换夹具还缺少配置操作必须的原包，现先恢复同hash资源并再次断言范围仍仅Mail，再执行实际切换；这是到达停止范围断言前的夹具前置错误，原输出／整轮源码与最终定向证据均保留；未修改产品预期、删除或标expected来消除原Claude红测。整轮冻结期间源码未变；随后只修正一项夹具前置，生产输入、原生文件和不可变适配资源未变并逐项核对。没有GUI、实际Agent会话、外部业务／发送、依赖或原生重建及M9操作；旧AF未知桥保持原占用。
