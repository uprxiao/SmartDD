# H恢复者连续中断与交接依据 · 2026-10-22 AQ

依据M10 R1.6含12.21、R10-19／20及T54／65／68／72，沿用正式开发授权，仍在第5步。本轮修复已在AP记录的恢复者交接窗口，不新增业务或发布。

## 原问题及最终行为

软件红测在AP生产代码上实际终止原发布子进程，再让恢复者更新H意图并阻塞于本次C协调进程。终止该恢复者后，下一恢复因H owner与C原计划不一致而拒绝，尚未进入第二次交接；原日志和1失败／8名称过滤未执行保留，未把它们计为通过。

恢复意图现保存可选的交接依据：原C计划的完整规范摘要及原owner。C已提交时要求同一owner、token和交接元数据；H先变而C尚未提交时必须精确锚定仍存在的原C计划。每个未完成交接的H恢复者与C登记持有者都须可核验停止，本宿主同操作另受active门控。原安装租约按实际C登记owner核对，不能用新H owner误判旧租约，也不能强行改签未知恢复者。

取得C协调锁后，在业务SQLite事务内重新核对原计划及状态、owner和租约／其他占用，再提交同一operationId。C记录改变时保留记录，不覆盖；携带交接依据却缺完整C原登记时，不按“从未登记的早期意图”重新创建。未知、无依据、坏hash、来源／目标或租约冲突仍保留并诊断。原S、native ID、包／Skill版本、名称、路径、来源字节及长期引用不替换；没有释放业务run或发送租约。

## 软件验证和故障边界

最终类型exit0，7文件按完整文件最新结果去重224项通过，新增11包含其中。首轮7文件222项全绿；之后仅增强handoff测试文件，生产和其余1985输入未变，整个11项文件及最终类型再次通过。最新账明确六份整文件来自首轮、一份来自复验，不冒称单次224项；原完整输出与哈希均归档。

新增实际子进程场景覆盖同一原操作在C登记前连续两次恢复者SIGKILL、恢复者完成C归属登记后再被SIGKILL。正例用真实会话登记构造非空长期引用，并核对原字节、同操作提交和安装租约结算。负例覆盖无交接依据、错完整计划hash／owner、变更计划、H／C任一未决owner未知及未知安装持有者，均核对原意图和C数据保留。完整C操作／目标资源／安装占用丢失的负例是明确的隔离故障注入；原H证明因此拒绝按未登记状态重建。

另以私有C门闩固定等待点，测试用直接SQLite写入模拟绕过协调协议的并发计划变更，恢复者必须在C内拒绝而保留注入后的数据及原catalog；这不是未修改环境的正常路径。所有latch／发布者都是本次新建的夹具进程，清理仅终止这些已知子进程。没有真实CC／Codex、模型、外部业务或GUI动作，也没有新App包。AP内核协调器、原生helper／SQLite／PTY和不可变适配器字节未改。最初驱动曾引用AP保留的R3红测作为启动门槛而在执行前被挡，修正为最终审定结果后才开始实际红测，单独记录，不混为产品失败。
