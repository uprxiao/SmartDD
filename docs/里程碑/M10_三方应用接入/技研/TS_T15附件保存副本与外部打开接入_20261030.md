# TS · T15 附件保存副本与外部打开接入

M10 R1.6＋§12.21，M10-R06-03、原 T15 第 5 步。2026-10-30 SG，范围内缺失功能补齐；未新增收发、分析或 M9 范围，未发布。当前仍 54/72 通过、剩余 18、75.00%。

现状：文字附件查看及全部附件保存已有真实结果；二进制附件仅元数据，外部打开入口未实现。不能继续把这一项只写成系统工具阻塞。

## 实现边界

- 在现有附件控件增加“保存并打开…”；沿原本机保存对话框／覆盖确认／受保护复制，成功后选择本机应用打开。取消、失败、unknown 均不打开。普通“保存附件”仍只保存。
- 已保存回执提供“打开已保存附件”，重启后仍可从原保存历史进入。用户明确选定的独立副本交给外部应用；Foxmail 来源及不可变草稿 blob 不交给外部编辑器。外部改动不回写原附件，不把打开回执描述为阅读／分析成功。
- 复用 M9 已有 native `applications`／`open-external` 的目录／文件／应用内核身份与 NSWorkspace 文件引用 URL，不用 shell.openPath／命令字符串，不在原始 MIME／cache 上打开。
- 主进程只接 projectId、原保存 operationId、本次列表 ID／应用 ID。重新校验原 M10 权限／附件修订和已保存副本的原 inode／hash／大小；原路径替换、文件变化、旧窗口、其他项目／过期／伪造列表拒绝。应用路径来自本次原生发现，前端不提供文件或应用路径。
- native 仅在本次请求带预期 revision 时补内容复核；已有 M9 请求语义保持。外部打开超时／未知不自动重试。可执行／安装器等非普通文档只允许保存，不借“打开附件”执行脚本或安装程序。
- 不新增私有自动清理副本池；保存位置由用户明确选择，沿用已验证复制恢复／覆盖／历史和材料分类，避免后台删除外部应用仍在使用的文件。
- 原型先同步合成保存／取消／失败／未知及应用选择／打开回执，保持不操作系统、不读取文件。沿用现有按钮、AppDialog、字体与主题 token；不是新视觉方向或全 T22 对照。

## 验证计划

1. 先记录现有 UI 无“保存并打开”入口的红测，再验证保存成功才进入打开、取消／覆盖／失败／unknown 不放行、显式应用选择、忙碌／关闭及失败恢复。
2. 后端覆盖保存回执状态、项目／窗口／目标权限、原 saved inode／hash、列表授权／过期、应用身份、普通文档类型边界及原生失败不重放；真实 native 错 revision 在分发前拒绝。
3. 适当软件／类型、新包原生检查后，在全新隔离 userData 使用真实 UI 选择并打开自建二进制文档；系统应用能读取时补其文档证据。保存夹具与真实系统保存分层记录，不用 I 层选择器冒充系统 UI；现有 TA 原生保存证据保留原包范围。
4. 核对原只读来源、草稿附件副本、保存回执、进程和数据库；T15 真实 Foxmail 对照等仍单独保留。该功能完成不等于整例或整个阶段完成。
