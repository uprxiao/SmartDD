## 实际落盘与预算

缓存仅位于由 `ResourceStore` 解析的规范U下：

```text
U/cache/mail/
  .willyou-mail-cache.json              # 本store归属与格式
  index.sqlite                         # 缓存表、持久时钟、对象、暂存、租约与记录
  index.sqlite-journal                 # SQLite事务期间可能存在
  objects/<sourceHash>/<contentHash>    # 来源内去重，内容不可变
  staging/<writeUUID>.part              # 先登记全额预约，再实际写字节
```

生产总预算固定为500,000,000字节，30×24小时未使用回收。独立缓存数据库使用DELETE日志、synchronous FULL／fullfsync、cache_spill OFF、内存临时存储及每个受管连接复核的max_page_count；主业务库和持久附件不迁进缓存。索引上限16 MiB，保守预留其4倍（67,108,864字节）容纳索引、回滚日志及标记，其余供全部来源对象和暂存共用。不靠journal_size_limit承诺日志硬上限，不运行VACUUM、ATTACH或磁盘临时索引；逐主键删除，保留回收所需页余量，索引不足明确拒绝扩张。

SQLite机制依据：[PRAGMA](https://www.sqlite.org/pragma.html)、[原子提交](https://www.sqlite.org/atomiccommit.html)、[临时与辅助文件](https://www.sqlite.org/tempfiles.html)。这些是引擎依据；容量、并发和中断结果以本轮实际量测为准。参考了本地Yoda的 `src/main/lib/keyed-ttl-single-flight-cache.ts` 的合并／TTL边界，未复制其代码；该内存实现不能代替持久预算与进程租约。

每次写入先在SQLite IMMEDIATE事务内检查持久预约和当前文件清单，登记对象／原暂存inode及全额字节。复制、fsync和完整内容校验在事务外；同卷rename不复制第二份内容，完成校验和发布后才返回ready。失败清理只操作原登记文件身份，实际未移除的文件继续占用预约；遇到活动对象占满空间，返回RESOURCE_BUSY，不删业务文件、不缩小邮件范围。

实际统计使用文件的st_size，包含索引、辅助文件、对象、暂存、标记，以及未知目录中的文件／链接本身；不跟随符号链接，不把链接目标纳入或删除。目录统计与受管命名空间变更共用预约事务，避免并发rename造成漏算；深度或文件数异常明确统计未完成。外部新增或替换的未知内容保留并阻止新增缓存；未知内容使目录超预算时仍返回实际数字和overBudget，不伪造为0。文件系统压缩、APFS块分配和目录元数据不等同这里的文件字节口径。

## 使用、清理和真实结束

LRU和30天期限使用持久UTC最后使用时间，刷新写入只以创建时刻作初始值，维护扫描不计使用。持久时钟下界防止回拨使刚使用项提前过期。清理每批至多50对象，重新选择当前最久未使用对象；活动读取租约保护原generation，移除文件后才释放对应字节。清理后索引保留，不把未缩小的SQLite文件报成已释放空间；无引用且为空的来源目录及记录同时回收。

同进程相同来源／摘要的put可合并，各等待者独立取消和记录使用；最后等待者取消只中止生产者后续步骤，已开始且忽略取消的复制／回调在实际结束前仍占预约。跨进程依靠同一缓存库的事务登记，不能各自使用一份完整预算。缓存记录捕获全部所需对象，直到其实际懒加载全部结束才释放租约；必要内容丢失或损坏会失效对应覆盖记录，不把缺失缓存解释成完整空结果。

会话记录由PID及原生微秒级启动身份定位，只探测本服务登记的PID。恢复只接管明确closed或内核证实原进程已退出的记录，running／unknown都保留。接管先在事务内更新归属，再在事务外检查原暂存内容；完整written／renamed内容按原hash发布，未完成副本清理后才释放预约。本宿主已实际结束但清理失败的写入也可再核对，活动生产者用独立登记保护。恢复缓存内容不会自动生成“查询完整”的记录。正常关闭等待实际生产者、读取及懒加载结束，再关闭缓存SQLite。事务仅在尚未进入回调时重试BUSY，避免提交受外部读锁阻塞后重做文件创建／rename；该边界使用真实SQLite读事务验证。

主进程惰性打开一个U缓存引擎。普通草稿操作不要求缓存或Foxmail可用；`mailCacheStatus`／`clearMailCache` 仅允许受信主窗口，通过独立管理动作记账，无项目／模型自报授权。清理不改变连接、项目启用或固定会话，活动读取继续保护；主服务关闭会等待缓存操作与原业务作用域共同结束。

## 已做验证与证据边界

本批覆盖单／双引擎、跨来源去重、真实文件LRU／TTL／时钟回拨、元数据容量、活动占用、缺失／损坏／来源覆盖失效、未知文件与链接、各等待者取消和服务关闭，以及受信RPC和草稿保留。真实容量测试尝试20来源各25 MiB（共524,288,000字节），对各写入／发布／删除阶段统计，核对总预算及实际释放。

另以本轮编译的内核身份助手和自有Electron Node子进程测试：活写预约不抢占、reserved中断、written／renamed恢复、实际读租约、unknown身份保留、两原生进程同时预约，以及SQLite热回滚。热回滚使用**仅测试的委托VFS扩展**：原VFS照常写入并同步，扩展只在第一次真实主库写入后暂停；核对热日志magic后SIGKILL本轮子进程，再验证原记录恢复。该故障注入作用点、临时门闩及身份在证据中标明，不冒充未修改环境。它不编入生产App，也不改变生产日志、同步或cache_spill配置。

保留首轮LRU测试时间夹具失败、热日志夹具误改已有预算、Apple头文件扩展入口链接错误及扩展类型错误；修复夹具和入口后复验，没有放宽LRU、预算、身份或业务保留要求。全量并发回归时实盘容量测试触发默认5秒框架超时（570／571通过），为该新fixture单独设置30秒上限并复验；产品工具及请求预算未改，原失败完整保留。最终条数、命令和构建结果由结构化证据及执行记录维护，不把局部重复运行相加。
