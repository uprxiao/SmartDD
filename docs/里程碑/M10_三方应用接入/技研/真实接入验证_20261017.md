## 2. 本地邮件怎么读、需要什么授权

本机实证路线为：**只读`messages.db`→把mailid作为精确的本地对象ID→匹配Mail目录下同名十进制`.mail`→标准MIME解析→WillYou自己的查询索引和受控引用。** 不需要再用邮箱密码登录服务器才能读取这些已落盘历史；SMTP认证与这条读取链独立。

本轮SQLite使用`mode=ro`与`query_only=ON`，只读源文件；临时自有索引在私有临时目录构建，重复导入4个样本不重复建记录，实验结束即清理。没有复用Foxmail ICU全文索引，没有对源库checkpoint、写标记、删除或修复。Foxmail原生收取是用户另行确认的客户端操作，不能把整轮概括成“没有任何外部写操作”。

正式App仍须验证用户选择来源、容器权限允许／拒绝／撤销及恢复。当前CLI可读不等于打包Electron已经取得权限；本轮不需要额外系统授权弹窗，也不需要读取Foxmail保存的密码。

### 现场发现及适配要求

- **64位身份**：native mailid不可作为不精确的JavaScript Number传输；适配器、JSON、对象引用及查询参数保留十进制字符串或精确64位类型。当前PoC用Python整数，没有丢精度。
- **大小并非等价字段**：3个样本索引size与源文件字节数不同；大小的业务含义未完全还原。下载／解析预算使用实际源字节数，不能仅因不相等就认定源损坏。
- **附件元数据可能不齐**：一封MIME有1个显式附件而附件表无对应行；另一封含2个带名称的内嵌资源，不能直接当成2个独立附件。以MIME结构和本地实际存在情况分别呈现，不把缓存行计数当完整清单。
- **主题有差异**：4封中3封源主题与索引一致，1封仅一个标点不同。保留来源和索引字段差异，不伪造完全一致；列表展示、检索与正文来源规则应在实现时明确。
- **更新至少有一个真实样本**：原有历史快照后，批准的测试邮件确实新增并可按Message-ID和native ID读回。它证明一次“新增邮件落盘后可读取”，没有验证移动、删除、半写入、升级或持续监听恢复。
- **缓存与源分开**：原始正文、附件、账号目录和源内容哈希不写入公开证据；实际业务缓存和清理规则仍待产品评审。

## 3. 禅道复用方式与边界

配置实际在`~/.codex/config/resolve-zentao-bug-round/bindings/ultrasafe-ais-ms.json`，而不是写在Skill正文：包含站点、预期账号、`credential_source=runtime`及环境变量名。初查当前环境变量为空、Homerail两类凭据表均0行；没有读取加密payload或密钥文件。认证输入由用户本轮补充，经隐藏TTY输入，只用于已确认站点；不提取浏览器Cookie／会话。

复用原`export-zentao-bugs`的Token、身份、Bug分页、详情、资源下载与完整性校验；Story在独立实验中补充`products/{id}/stories`和`stories/{id}`。原Skill保持不变，不启动旧SVN修复流程、不回写任何工单。

连接检查与全量本人清单必须分开。前者可快速核对身份和最小能力；后者可能跨产品、多页和较多历史数据，需要范围、进度、取消、缓存及失败恢复。不能把API返回200、某个产品为空、前几页未找到本人或旧探针ok=true等同本人列表完整。

原官方SDK的17条定义仍是静态候选；本轮增加的是明确目标上的真实v1／v2证据。SDK声明最低biz13.5的`/api.php/v2/my/bugs`与`/my/stories`已在目标13.0作可选实测，均返回403；没有据此分辨出版本／角色／接口权限的唯一原因，也不能解释为账号整体认证失败。通用`filters[0][field/operator/value/join/group]`筛选以不存在账号作负控，仍返回1条、`hasNext=true`，该编码没有证明能按账号过滤。不使用SQL绕过业务API。

### 指定Bug与全量范围必须分开验收

原导出器的全13产品扫描在600秒被实验预算中止，尚未完成清单，所以那一轮没有进入独立验证器。用户随后按请求提供三个样本ID；这不是完整页总数或完整ID集合。初次定向实验错误传入了`--verified-scope-count=3`，导致原工具依据调用方声明输出范围完整；**该范围结论已撤回**，原输入／结果留私有历史，公开[勘误](实验/real-readiness-20261017/zentao-scope-input-correction.json)说明原因。

随后使用未修改的原导出器`--resume`、不提供任何范围背书重跑。最终保留三条完整材料和三份逐条manifest；原验证器对字段、历史、资源、文件／校验和没有报错，但整体退出1，错误为`direct_ids_scope_evidence_missing`、`scope_marked_incomplete`、`export_marked_incomplete`和`global_manifest_reported_scope_errors`。这是预期保留的范围缺口，不能改写为“全部本人Bug导出通过”。

原始Bug、资源、日志在本机忽略目录`release/m10-research/live-verification-20261017/zentao-private-targeted/`及其父目录；公开报告只保留用户已提供的编号、字段名、布尔判断和计数。未将工单标题、正文、评论、文件名或账号入库，未操作流转。

### 正式接入前要解决的查询问题

1. 身份／可达性／最小能力检查不得隐式启动全历史归档；连接成功和本人列表已同步分别表达。
2. 固定产品／项目／执行的稳定ID和范围；不能从绑定项目的英文名“AIS”猜产品。当前13个产品未匹配该名称的实验保留为选择失败。
3. 先核实企业版13.0可用的本人查询方式及接口权限，再做分页、分支、负控和页面总数／完整ID集对照。若采用产品枚举回退，须有明确范围、预算、进度、取消、增量缓存和断点恢复；不能把本次600秒扫描原样放在每次页面刷新中。
4. 在自动发现通过前，应用应明确显示“不完整／同步中／查询不受支持”，不能把前三页未找到、403或筛选失效显示成“0个”。

## 4. 邮件收发分离与结果语义

读取适配器不必控制Foxmail发送：本次邮件由独立SMTP发送，Foxmail按现有POP3收取，随后本地适配器读回。该组合已经实证可行，能覆盖本地独有历史，也为Agent和M11提供独立发送能力。

连接设置需明确服务器、端口、认证账号、认证方式、传输模式及凭据引用。SMTP支持哪些模式以实际服务器为准；普通SMTP、STARTTLS、隐式TLS不是同一个开关。正式产品如何允许并提示当前未加密通道，仍需在连接规则中收口，不能静默更改用户邮件服务器或拒绝后误报密码错误。

本轮分别留证：EHLO可达→235认证接受→唯一草稿一次提交／服务器接受→Foxmail本地唯一收件记录。各阶段不能互相替代。本地投递成功不是其他收件人送达／已读证明；SMTP直发是否同步Foxmail“已发送”文件夹本轮未验证，不据文件夹是否出现判定发送结果。

收到测试授权前没有发信；首次自动审批拒绝“收取新邮件”后未执行该操作。用户明确确认删除对应服务器副本后才点击收取；初次120秒只读等待未观察到邮件的回执也保留，不覆盖成当时已经收到。
