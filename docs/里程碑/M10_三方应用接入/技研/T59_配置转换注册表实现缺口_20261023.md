# T59 配置转换注册表实现缺口 · HD

依据已确认R1.6技术方案§5.8、需求M10-R10-15/16、T59原八步。属于原授权范围内未落地实现，不能以此前开发出口结论或同schema1回归替代。

## 当前代码事实

- `host-application-registry.ts` 的HostProvider.configApiMajor类型固定1，构造器拒绝其他值；当前物理config_schema_version与provider.configApiMajor直接相等校验，物理schema与包视图契约尚未独立。
- `connection-service.ts` planConfigChange仅判断目标contract major1、identity1和authModes，没有选择／固定转换器实现hash，也没有执行等价转换校验。decodeRow仅允许当前单版本。
- `package-config-views.ts`只生成三个内置provider的schema1字段白名单，再校验旧包Schema；没有以provider/sourceSchema/targetAPI/identityContract/implementationHash注册转换器。
- `activation-preflight.ts`同样硬编码物理schema1及目标major1。因此“schema2当前配置→旧API1等价转换”和缺转换器的区分尚无完整生产路径。
- 技术方案要求的viewMajor/viewDigest/修订及不透明认证handle尚需与现有execution-context／SecretsStore统一核对，不能重新复制秘密或另建每版本连接。

## 下一项正式开发（顺序）

1. 复用现有HostApplicationRegistry及PackageConfigViews，独立物理schema版本与目标config API；建立受信静态转换注册表，键含provider、source schema、target major、identity major、实现hash。未注册／重复／未知枚举拒绝；转换是无外部权限的纯数据处理，输入输出严格校验，保留身份与认证语义。
2. 将当前三个provider的1→1现有字段视图接入注册表，保持既有行为；用明确的schema2隔离夹具验证等价转换和无法表达的新认证，不随意改变现有生产格式或账号。
3. 让调用解析、配置保存兼容计划和升级预检共用同一评估；plan含转换器hash／版本及当前修订，提交重核避免并发配置／引用／转换器变化。不得只在测试或孤立helper中实现。
4. 沿用当前认证执行器核对秘密及身份修订，不向renderer／Agent返回秘密或可复用handle；补失效、同身份修复恢复和新旧会话固定包断言。
5. 完成相关软件回归后构建，按T59原八步执行两版实际包组合，区分真实旧包、合成schema夹具、模型和业务边界。所有步骤完成前T59保持未通过。

T04界面焦点前置沿用EY登记，用户不在时不重复尝试。正式16/72（22.22%）不变；M10回到第5步补已确认范围的实现缺口，完成后接第6步验收。此记录不撤销已有16条通过事实或开发授权。
