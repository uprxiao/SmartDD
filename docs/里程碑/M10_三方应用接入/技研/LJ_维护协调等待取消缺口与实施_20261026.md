# LJ · 维护协调等待取消缺口与实施

2026-10-26，R1.6＋§12.21／R10-20，关联原T71步骤10–11、T65；沿用同范围已批准开发授权。本增量只补尚未进入删除的版本清理协调等待，不改变原包／引用／计划校验、已发生清理的恢复取消、安装／启动迁移门槛或正式用例范围。

## 已核实缺口与复用

`ApplicationVersionsPanel`提交清理后禁用关闭和取消。`ApplicationService.cleanupVersion → ApplicationVersionMaintenance.cleanup → ResourceGraphMaintenance.coordinate`没有传递取消信号；而最底层`withCoordinatorLock`已支持AbortSignal，并在进入动作前检查取消。图协调按H根顺序→C取得，初始只读提案还会短暂取得C，三处等待都须覆盖，不能只取消前端Promise。

已发生的清理由`cancelCleanup`按持久operation／plan恢复，语义不同；不得复用它伪称取消了尚未执行的等待，也不得在标记deleting之后直接中断物理清理。

## 实现约定

1. UI明确确认原版本／原plan后生成一次性waitToken；服务绑定原WebContents／发起窗口，建立短期等待记录。取消只命中本窗口本请求，重复取消幂等，另一窗口或迟到token不得取消别的工作。
2. 服务向版本维护和资源图协调传递AbortSignal及有界的剩余等待预算；C初步读取、每个H及最终C取得均沿用原门闩，不改锁顺序、不抢占原所有者。取消在进入最终动作前生效，释放本操作已取得的协调权，不删除包／引用／日志或终止Agent。
3. 最终协调动作开始即标记executing；此后“取消等待”返回未接受，仍执行原完整plan校验、意图、事务及恢复流程，不能将已执行操作写成未发生。原请求完成、窗口销毁和服务退出清理自己的等待记录；退出只中止尚未进入动作的等待。
4. UI区分“取消等待”和既有“保留版本，取消清理”。等待取消接受后，以原请求CANCELED收敛，说明原版本保留；失败／执行开始不得显示已取消。临时等待token及锁名不进入日常文案。独立原型先补同语义等待／取消，并保留完整准备成功后才换默认的规则。
5. 本增量不因此宣称所有安装／迁移／GC状态已齐。后续仍逐项核对原T71／T65及R10-20全部约定，包括跨实例、持久恢复与各Agent；不得缩减原72条。
