## 2. 优先复验请求

以下以公开的部署占位根 `{BASE}` 表示，不保存内网地址或认证值。所有动作均为 GET，只取本人指派列表。

### A. 网页同入口 JSON，适用于现场已使用 PATH_INFO 的部署

```text
{BASE}/my-work-bug-assignedTo-0-id_desc-0-20-1.json
{BASE}/my-work-story-assignedTo-0-id_desc-0-20-1.json
```

位置依次是 `mode / type / param / orderBy / recTotal / recPerPage / pageID`。下一页把最后一段改为 2。页面出现 `assignedTo--id_desc` 时，空段占 `param`，显式写 0 更便于复验。`recTotal=0` 是输入，不表示结果一定是 0；DAO 会重算总数。

PATH_INFO 的 [setParamsByPathInfo L2559](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/framework/base/router.class.php#L2559) 按分隔符顺序取参。因此仅在 `my-work-bug.json` 后拼 `?recPerPage=100&pageID=2`，不能假定 controller 已收到这两个值。**分页值应写进完整路径**，同时核对返回 pager。

旧页面 JSON 的 [parseJSON L687](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/framework/base/control.class.php#L687) 返回 `status / data / md5`，其中 `data` 本身是 JSON 字符串；正常需先解外层，再解 data。列表可能是按 id 作 key 的对象；应保留 ID 并转成数组，不能拿对象 key 的顺序当分页证据。不要把外层 HTTP 200、status=success 或输入 recTotal 当成完整性证明。

### B. API v2 通用 controller 路由，复用已有效 REST Token 的候选

```text
{BASE}/api.php/v2/my/work?mode=bug&type=assignedTo&param=0&orderBy=id_desc&recTotal=0&recPerPage=20&pageID=1
{BASE}/api.php/v2/my/work?mode=story&type=assignedTo&param=0&orderBy=id_desc&recTotal=0&recPerPage=20&pageID=1
```

[routeV2 L300](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/framework/api/router.class.php#L300) 使用第二路径段作为 controller 方法，`my/work` 保留网页原始入口语义。[setParams L689](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/framework/api/router.class.php#L689) 根据方法正式参数名读取 query。该 commit 的 `config/apiv2.php` 没有 my 专用映射；`my::bug/story` 均为单数方法，故 `/my/bugs`、`/my/stories` 不能当作这份基线中已存在的本人列表端点，403 也不能单凭状态码判定为“本人列表功能本身无权限”。

v2 使用 API control 的 `parseJSON`，正常结果是直接的 `status/bugs|stories/pager`，不同于 A 的双层 data。服务端仍检查账号权限、访问范围；候选不是新增权限、修改权限或绕过拒绝的办法。若正确路由仍明确拒绝，应留存错误类型并停止依赖该候选。

### C. 认证：先复用已有有效认证，必要时用官方旧会话流程

公开基线 [baseRouter::startSession L1230](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/framework/base/router.class.php#L1230) 会读取 `Token` 请求头并将值用作会话 ID；[tokensEntry::post](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/api/v1/entries/tokens.php#L49) 在登录后返回 `session_id()`。因此 A 的 `Token` 头复用具有公开源码候选依据，**不能取代目标部署的实际认证复验**；自定义会话处理、版本补丁等仍可能不同。父任务已反馈目标 A＋Token 实际返回登录页数据，不能按成功列表处理；B 通过既有 REST 认证取得业务列表。本子任务没有尝试 Bearer、Cookie 或 Token。

若 A 不能复用已有 REST Token，应按实际错误分类。官方 [PHP SDK login](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/sdk/php/zentao.php#L42) 的旧流程为：取得 `api-getSessionID.json` 返回的 sessionName/sessionID，向 `user-login.json` 提交已授权账号认证，随后用该 session Cookie 调 JSON 页面。凭据与会话只能在连接服务／临时进程内处理，研究文档和日志不落值。不能直接复制该旧 SDK 的关闭 TLS 校验配置；本文仅参考接口与解析行为。

`api.php` 不带 `/v1` 或 `/v2` 的入口另走 `checkEntry()` 应用集成校验，不能当作免认证替代入口。

## 3. 旧接口可复用部分与限制

| 公开实现 | 可复用知识 | 限制 |
| --- | --- | --- |
| 网页 controller JSON | 同入口查询、分页、字段与错误解析；可与页面 ID 集直接比较 | 附带用户字典等展示字段；账号／配置／企业扩展需现场确认；请求可能更新会话内筛选／列表状态 |
| API v2 通用路由 | 已有 Token、按正式参数名分页、直接 JSON；`/my/work` 可保持 work 入口 | 基线没有复数 my 方法映射；候选须验证实际路由、权限和响应格式 |
| REST v1 `bugsEntry::get` | 参数 `product/branch/status/order/limit/page`，返回 `page/total/limit/bugs`；按产品 browse 取得分页 | product 必填；不是跨产品本人专用列表，不能通过当前页本地 assignedTo 过滤声称全量完整 |
| REST v1 `storiesEntry::get` | `product/branch/status/type/order/limit/page`，返回 `page/total/limit/stories`（还附 requirements） | product 必填；默认 status=unclosed，与 my Story 查询的状态范围不同；研发需求要 `type=story`；该公开 GET 实现返回201，客户端不宜仅接受200 |
| `api::getModel` | 公开 model 方法名、参数与双层 JSON 包装，可解释旧 Skill 的调用经验 | [config/config.php L151](https://github.com/easysoft/zentaopms/blob/88d6de983014956235e3bf735d225106e38be551/config/config.php#L151) 默认关闭 apiGetModel；另有权限与全功能调用面。分页需要 server pager 对象，普通字符串参数不能直接构造它；本轮不要求开启，也不通过 SQL 弥补列表问题 |

## 4. 现场复验应记录的可判定结果

1. 固定同一账号、vision、列表筛选、排序、每页数量和时间窗口；记录页面可见总数、总页数及完整 ID 集。只有一页时仍核对 pager；多页时逐页收齐。
2. 对 A／B 分别记录实际状态码、成功／错误结构、当前账号识别结果、列表顶层 ID 集与 pager 的 `recTotal/recPerPage/pageID/pageTotal`。日志只保存必要结构或脱敏统计。
3. 逐页读取直到返回页码、已收集数和总数一致；检测页码被回退、重复 ID、页间数量变化及中途失败。不能用指定 ID 详情成功证明列表完整。
4. Bug 比较“my/work 指派给我”的状态边界；Story 只比 `story` 顶层行，附带子项不擅自当作额外本人条目计数。权限或对象可见性差异需解释。
5. 两种方式的 ID 集与网页相同、总数一致且无缺页，才可记为**该环境、该账号、该时刻的列表完整性通过**。公开代码静态分析、HTTP成功、取到几个对象或全历史扫描结束均不单独满足此项。
