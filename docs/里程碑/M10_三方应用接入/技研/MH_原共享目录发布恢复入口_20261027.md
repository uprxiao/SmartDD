# MH · 原共享目录发布恢复入口

依据R1.6＋§12.21、R10-19–20及原T54第10步，沿用开发／测试授权。2026-10-27，feature/0.0.2，HEAD `f1f1728d68a8595e665d4833dff048189e63e0f8`＋可恢复工作区。M10-MH-01在目录发布中断及兼容激活范围已修复并复验；正式仍31/72，M10仍验收中，未发布。[实际红绿、全部原失败与包](../验收/MH_T54目录发布中断与恢复_20261027.md)。

## 实际原因

真实MF包在原H第一个新目录rename后SIGKILL，重开后正式tasks.create仍失败“共享目录正在维护，暂不接受新消费者”。已有DiscoveryCatalog原操作恢复内核具备C账／所有者核验，但普通启动及任务准备未调用，且物理检查或降级guard先遇到半成品H。只把publish改成publishOrRecover不能覆盖已改选项目、旧完整来源、已发catalog／已提交C仍保留intent及物理核对之前的恢复。

首MH包接普通入口后，336软件／类型／六原生及两场实际中断绿测通过；但同一原红数据配兼容Mail1.0.5分发仍无法启动。先保存超时，再观察本次App原错误框参数且调用原弹窗，证明为“受管运行或在途操作尚未停妥”。激活idle检查先于任务服务初始化，因而原发布lease挡住到达恢复入口的路径。原DB／intent始终与冷副本hash一致，没有用手工解锁来消除症状。

## 原内容恢复及安全边界

增加`DiscoveryCatalog.recoverRecordedPublication`：

1. 用H短锁读取原intent，确认本storeId／U指纹，锁外核验原所有者内核出生身份必须stopped。活跃／unknown／外来U均保留原操作。
2. 只查询本U的ready／valid C应用包和标准Skill资源，候选上限4096；从原manifest完整树重建文件与可执行位。支持现代和旧格式标准Skill，验证C原所有权／hash；不把部分H字节当来源。
3. 每项必须重算得到原entry的完整nativeName／sourceHash／resourceId／projectionHash等同一身份，候选恰好一个。恢复原静态计划独立于当前项目选择，新的Task仍独立核验当前范围、连接、原生冲突和业务权限。
4. 复用已有`recover(originalOperationId, sources)`重新核验原C计划、lease、handoff、内核所有者、H基线及完整树；按原H→C短锁／SQLite事务边界原子完成，不通过删除journal／直接释放install lease冒充恢复。

ManagedTaskCapabilities启动在run／消费者恢复后调用；Codex任务准备在H物理检查／历史盘点前调用，取消继续传播，其余未解决状态沿用正常保护。

`openManagedDatabase`在schema核验／迁移完成之后、正常应用激活之前，对已记录canonical H及其hash做同一消费者／原发布恢复。宿主生命周期独占DB协调门闩不同于短C锁；原恢复仍按H→C，不在SQLite事务内等进程。此位置使用已知当前schema，不在未知旧schema上硬读现代表。个别原根不可信时记录未解决，原idle检查继续拒绝尚在的lease，不放宽升级、活进程或未知身份保护。既有pending激活有独立恢复协议，未改其规则。

无schema、UI、原型或分发资源变更。没有更改CLI正常read-only／never策略；外部harness仅增加失败PID元数据便于核对自己的进程。
