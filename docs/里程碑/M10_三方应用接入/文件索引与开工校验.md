| 层级 | 实际结果 | 明确限制 |
| --- | --- | --- |
| 本轮模型／合成 | 原型17项、合成邮件12项、假provider14项、临时SQLite8断言满足 | 不访问真实邮箱／禅道，不证明生产存储、迁移或业务适配成功 |
| 本轮本机协议元件 | 15项socket检查通过，含3个实际stdio子进程 | owner是Python替代实现；不是新业务Electron主进程的完整接线 |
| 本轮现有MCP／Codex | 9项观察（6基本行为＋3限制），1个实际旧工具研究测试通过 | 合成项目；无模型turn；未调用真实三方provider |

| 历史真实Foxmail | schema只读检查，3个完整MAIL结构可解析 | 结构统计不是正文／附件保真、索引关联或邮箱全量验收 |

| 正式业务验收 | 42条评审草案未按批准基线逐条执行 | 无真实发件／禅道流转、完整真实读取、已验收打包App或其他平台通过结论 |

旧测试、迭代失败和复验记录继续保留；研究断言、结构样本、原型观察、正式业务用例不相加成一个“总通过率”。

## 4. 开工前必须补齐的最小集合

1. **Foxmail真实读取验证**：获准最小样本的索引→源文件→正文／附件对照、稳定身份和有限变化检测；只保存匿名检查结果，不写源库。
2. **目标禅道只读认证验证**：身份、本人Bug／Story范围与分页、Bug详情、一个获准非空Story及历史／附件，记录实际schema和页面对照。现有“本人Story为0”不阻止选合法非空样本验证详情。
3. **业务收口**：发件后端／账号配置方式和测试目标、具体流转动作／审阅、首版平台及影响首版的缓存／清理／迁移规则。已认可的连接组织方式不重复询问。
4. **工程收口**：最小真实CLI→Electron桥接PoC，固定主进程输入输出、凭据／配置迁移和生命周期契约。完整崩溃／打包端到端按正式开发计划执行。
5. **形成可审阅基线**：同步需求、原型、技研、用例后记录评审；用户批准明确范围再进入正式开发。不擅自移出邮件发送／禅道流转来降低门槛。

各项判定标准与所需输入详见[报告§3](../../review/review-20261017-1559.md#3-修改建议与进入开工的条件)。缺验证是技术缺口，动作／发送方式等是业务决策，用户开发授权另列；三者分别处理。
