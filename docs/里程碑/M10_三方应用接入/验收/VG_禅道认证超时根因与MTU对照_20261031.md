# VG · 禅道认证超时根因与 MTU 对照

2026-10-31，接续用户“继续定位根因”的要求。基线仍为 R1.6＋§12.21，`feature/0.0.2`／`e355da862569f0adea67fb24a03706baf54c8313`，沿用[VF的8／60／120秒原失败](VF_UI首批续测与禅道认证超时诊断_20261031.md)。本轮只做传输诊断与认证／本人身份核验，没有 Bug／Story 业务读取或写入，没有修改生产源码、包或VPN配置。目标主机路由仅由用户按脚本临时修改并恢复，Agent另行只读核对。

**已确认根因：当前 VPN 网络路径与目标路由的MTU／MSS不匹配，形成大报文黑洞。** 相同地址、账号、认证请求在小报文传输下取得Token 201和本人身份200；随后用户执行唯一变量的路由实验：默认TCP选项保持15，只将该主机MTU1420→1200，静态大响应和API均恢复；恢复1420后同请求再次超时。这个对照确认了MTU配置的因果关系，具体丢包网关仍未知。路由已由脚本恢复并由Agent独立只读核对为1420，原App还没有在1200环境中复验，不宣称产品已修复。

正式仍 **64/72通过、7待收口、T45替代1**。I层认证成功不计 T09 列表、T10 详情、T22／T24／T57 或新增整例通过。

## 已观察到的事实

| 对照 | 实际结果与含义 |
| --- | --- |
| 目标路由 | `192.168.106.185` 走 `utun5`，接口及路由 MTU 1420；系统 HTTP／HTTPS／SOCKS 代理为本机7897，对192.168/16有例外。没有改这些设置 |
| 发送阶段 | 匿名原始TCP请求约80–90ms建立连接，随后小请求完整送出；默认连接失败时发送缓冲最终为0，说明不是应用一直没把请求交出去 |
| 同站普通入口 | GET首页及空JSON POST到index.php约0.26秒返回302；因此并非全部POST都不通，也不是只要VPN就一律等待数分钟 |
| 同一个登录页 | 默认HEAD约340ms返回200；默认GET超时；私有socket的TCP_NOOPT对照则完整收到17171字节，约677ms完成 |
| API只读身份入口 | 默认GET `/biz/api.php/v1/user`超时；TCP_NOOPT后1288ms收到正确的401 JSON。无认证401是API有响应的证据，不是认证通过 |
| 单独关闭ECN | 仍保留时间戳／SACK／窗口缩放，TCP选项从15变7；登录页及身份入口仍超时。不能把全关闭选项的成功归因于ECN一项 |
| 同一静态文件、默认TCP选项 | `/biz/favicon.ico`支持Range，文件117137字节。返回256／512／768／800／820／821／832／840／841／848／864字节均收到206及准确长度；896／900／901／904／928／1024／1280／2048字节样本超时。未把body长度当作IP MTU数值 |
| 前段缺失而尾段可达 | 默认1280字节样本收到242字节、全部为out-of-order；2048字节样本收到1010字节、全部为out-of-order。应用等待的是缺失的字节流开头，因此看不到HTTP状态／响应首字节 |
| MTU唯一变量正反对照 | 用户在本机管理员终端执行r2脚本，TCP选项始终15；MTU1200／maxseg1148时，2048字节Range以206完整收到，466ms完成，user API以401在325ms返回；恢复1420／maxseg1368后，同Range在5003ms超时。Agent随后独立只读确认目标路由恢复1420 |

Range对照保持同一地址、资源及默认TCP配置，仅改变响应长度；它把“某一个API业务处理慢”进一步排除，支持报文大小引起的传输失败。私有socket采用TCP_NOOPT后，完整网页和真实认证均可达，说明不是HTTP响应整体长度不能超过某个值，而是分段后的报文大小有影响。

上述特征符合[PMTUD黑洞的标准描述](https://www.rfc-editor.org/rfc/rfc2923.txt)：握手或小交换可用，较大报文消失直至超时。原先仅为机制推断，现由单变量MTU正反实验确认该配置导致故障。**没有双端抓包或网关日志，仍不能断言某个具体VPN客户端／网关、ICMP过滤规则或物理链路就是丢包点，也未测得精确路径MTU；1200是已验证可用值，不等于精确上限。**

## 真实认证成功的边界

使用会话中已授权的同一账号／密码，JSON结构、路径和HTTP认证方式保持；仅新建socket使用TCP_NOOPT。密码经getpass隐藏stdin输入，未进入命令参数、脚本、日志或证据；Token只在内存中使用，结束即清除，没有保存连接或复制浏览器会话。

| 请求 | 状态 | 实际耗时 | 验证内容 |
| --- | --- | --- | --- |
| POST `/biz/api.php/v1/tokens` | 201 | 1245ms | 收到非空Token；不保存其内容 |
| GET `/biz/api.php/v1/user` | 200 | 615ms | 当前profile.account与用户提供账号一致；返回1736字节 |

超时仍为8秒、重试0；两个网络调用合计约1.86秒。它证明当前凭据及REST API在该传输条件下可用，不是未修改环境的App端到端验收。[认证与身份脱敏结果](证据/continuation-vg-20261031/small-packet-auth-result.json)。

## 无效或未解锁的实验同样保留

- 在本机macOS上，连接前把TCP_MAXSEG设为1100被EINVAL拒绝；设为480虽然接受，连接建立后实际maxseg又为1368，不能把该轮失败解释为“小MSS也无效”。[相关结果](证据/continuation-vg-20261031/response-path-result.json)。[Apple实现](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/netinet/tcp_usrreq.c)和本机SDK用于核对选项约束，不冒称取得本机完整内核源码。
- SO_RCVBUF设为512后，实际TCP接收窗口仍为31464，未成功限制首个响应报文；不作为反证。强制走现有本机HTTP代理返回502，未解锁路径。[逐socket对照](证据/continuation-vg-20261031/tcp-path-result.json)。
- 本机管理员授权预检 `sudo -n /usr/bin/true` 返回 `sudo: a password is required`。这是macOS管理员凭据缺失，不是自动审批拒绝；没有尝试或复用禅道密码作为系统密码。随后由用户在其终端执行临时路由实验，工具侧再次检查仍无法复用该终端的sudo授权；Agent没有另行改动路由。
- 准备系统命令后核对到自带Python3.9.6未导出TCP_CONNECTION_INFO常量名，已用本机SDK的0x106补兼容并标记r2。当前脚本和实际执行输入应按哈希区分；若用户运行过r1，其探针会失败并进入原值恢复，不据此判断MTU实验无效。
