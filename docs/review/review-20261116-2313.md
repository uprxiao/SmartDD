# Review Report

**M14 需求、设计、原型、用例与技术研究整体评审**  
评审时间：2026-11-16；基线：`feature/0.1.6` / `7c4ed737dfc03cb9b2b4509de996cdaa1af6f560`＋本机未提交文件。场景：**文档＋原型代码一致性审查**，并检查拟复用的生产服务约束。输入 SHA 见[基线清单](evidence-20261116-2313/input-baseline.json)。

## 1. 摘要

当前材料有完整的设计主线，原有切换、基础委派、消息链接、目录串行等研究证据仍可按原范围使用。**但本轮新增的 Git 工作副本、目标持续运行、插件权限与统一请求流程尚未形成一致、可直接开发的基线。建议先关闭本报告的高／中优先级问题，再做评审定稿。** 发现 20 项：高 2、中 12、低 6；是 20 个可分别关闭的问题，不把测试数或历史坏链接次数当成问题完成数。

特别需要先处理：合并核对存在真实假阳性；“请求一直等待”与被复用服务的 60 秒有效期冲突；用例生成器会删除新增用例；新研究部分的“已通过”范围大于实际实验。原型纯模型测试通过，不能消除这些问题。

**本次只写报告与隔离验证证据，没有修改需求、原型、用例、研究脚本或生产代码。** 以最新需求补记为当前产品决定：D4 已改为 Git 写子用 worktree，SVN／普通目录仍串行；插件写操作按最新档位规则执行。不得按旧复核报告把这些用户决定改回去。前三轮复核的“关闭”仅适用于当时基线，不自动覆盖本轮新增范围。

## 2. 问题清单

优先级：高／中用于已证实的不一致或错误；缺说明、待补证和资料整理列低。原型问题指可操作设计样本，与尚未开发的产品缺陷分开。

### 高

### RV01 合并核对会把未合入的代码判为“核对通过”

[技术方案](../里程碑/M14_统一Agent工作区/技研/技术方案.md) L174–175、[A67](../里程碑/M14_统一Agent工作区/验收/测试用例.md) L608 接受“作者时间＋标题相同”作为子提交已合入的充分条件；[merge-agents.mjs](../里程碑/M14_统一Agent工作区/技研/复核_20261116/probes/merge-agents.mjs) L35–44 实际如此实现。

**已用原函数的精确代码在隔离 Git 仓库复现假阳性**：子分支新增 `important.txt`，主分支仅提交 `unrelated.txt`，故意同标题、同作者时间。子提交不是 HEAD 祖先，`git cherry` 为 `+`，子文件不存在，但 `missingChildCommits()` 返回空列表；其他核对条件也都是干净／无冲突／分支未变。结果见[反例回执](evidence-20261116-2313/merge-false-positive.json)。这会让“宿主核对通过”丢失实际意义。

### RV02 “请求一直等待”与现有插件／浏览器服务的硬有效期冲突，技术方案没有迁移合同

[需求](../里程碑/M14_统一Agent工作区/需求.md) L25、L31 与 [A11/A37](../里程碑/M14_统一Agent工作区/验收/测试用例.md) L115–116、L343–344 要求交互式任务一直等待，包含插件审批和跨任务网页授权。拟复用的 [browser/access.ts](../../src/main/core/browser/access.ts) L47、L68 仍有 60 秒到期与自动拒绝；[plugins/write-approvals.ts](../../src/main/core/applications/plugins/write-approvals.ts) L34–42 把批准有效期限制为 `min(operation.deadline, now+60000)`，批准后还会再次检查。

技术方案 §7.3 只改档位，§8 仍描述复用服务，没有说明如何将**等待用户的时限**与**执行、授权证据、业务 operation 的时限**分开。只去掉倒计时或保留请求面板，61 秒后照样可能无法批准。这是待实现设计与现有服务合同的冲突，不是要求现在修改已发布 M12/M13。

### RV05 目标等待子任务的合同、执行器差异与研究判定没有对齐

同时 E11⑤写“通过（V14）”，但 [goal-probe.mjs](../里程碑/M14_统一Agent工作区/技研/复核_20261116/probes/goal-probe.mjs) 没有创建子任务、回收结果或执行等待唤醒；只测目标本身的设置／暂停／继续／中断／清除。A70 步骤仅列 Codex，预期却另要求 Claude 不空转。当前不足以对两个执行器共同承诺自动联动，尤其是 SVN 串行写入时。另外，E11⑤写“通过（V14）”，但 `goal-probe.mjs` 没有派子任务或消费子结果，只验证目标设置／暂停／继续／中断／清除；不能据此把等待子任务的自动联动也归为通过。

技术方案 §4 的 `todo_list` 要求 TaskCreate/TaskUpdate 按 taskId 聚成一张清单，§6.1 要求目标状态进入界面。[timeline.mjs](../里程碑/M14_统一Agent工作区/技研/实验/20261116_复核修订验证/timeline.mjs) L10–12 只是把 Task* 工具改名为 `todo_list`，条目 ID 仍是每次 tool_use ID；没有 TaskCreate 结果与 taskId 的关联，也没有目标更新投影。

本次把 V10 **真实提取的 9 个 tool_use 片段**包进明确标注的合成 SDK 信封回放，得到 9 个独立 todo 条目，不是一张含 3 项的清单；V10 归档中的 TaskCreate 入参本身还没有 taskId，需要补结果关联证据。直接回放 V14 原生目标通知，10 条中 9 条 `thread/goal/updated` 为 unmapped，clear 只算诊断。见[定向回放](evidence-20261116-2313/new-recordings-replay.json)。旧回放与原型 25 项测试未覆盖这些新转换要求。

### RV07 子任务虽标工作副本，文件／链接／差异仍使用主任务的目录和身份

[技术方案](../里程碑/M14_统一Agent工作区/技研/技术方案.md) L162 要求子 run 的 cwd、沙箱、差异归属该 worktree。但 [M14TaskArea.jsx](../../prototypes/m6-codex/src/M14TaskArea.jsx) L353–354、L373–379 始终用父级 `projectRoot`；打开子任务 L412–424 仅换中间时间线，没有把子 cwd/task 身份交给右侧。 [App.jsx](../../prototypes/m6-codex/src/App.jsx) L497–499、L532 的文件打开请求和 FileWorkspace 仍绑定主 task／cwd。

因此在子任务里查看 `tests/release/arch.test.mjs` 时，原型展示的是主目录同名文件，不能评审尚未合入的子成果；切换子任务后的 dirty 缓冲、差异范围也无法按工作副本验证。这里不是要求原型读取真实磁盘，而是合成状态也应明确区分两个根和同名文件。

### RV08 任务内的权限菜单没有首次完全访问确认，也没有按执行器过滤档位

[A12](../里程碑/M14_统一Agent工作区/验收/测试用例.md) L125–126 要求首次完全访问先确认，取消不改档位；Claude 不提供“帮我批准”。但 [M14TaskArea.jsx](../../prototypes/m6-codex/src/M14TaskArea.jsx) L311–312 对所有 AGENTS 显示整个 `PERMISSIONS`，点击直接 `setPermission(p)`，并未调用 [App.jsx](../../prototypes/m6-codex/src/App.jsx) L315 的 `choosePermission`／确认框路径。该确认框目前只经首页旧控制器触发。

这是**任务页**与**首页**两个权限控制器不一致；P0.12 确认框截图不能证明任务内首次选择也会确认。任务内 Claude 实际还能选“帮我批准”。

### RV09 选择器／草稿／扩展开关没有按任务统一归属，运行中切换会误用未来目标能力

[M14HomeModelPicker](../../prototypes/m6-codex/src/M14TaskArea.jsx) L454–462 只保存内部 `sel`，没有向首页 `profile`／`createTask()` 返回选择；[App.jsx](../../prototypes/m6-codex/src/App.jsx) L402–411 创建任务仍读旧 M13 profile。任务页又在 L358 硬编码回 Claude 默认模型，不能验证“首页选择的目标实际用于新任务”。

任务内 `Composer` 的 text 仅局部 state，App 以 task.id 为 key 重新挂载后丢失；`EXT` 则相反，是按智能体 ID 保存的模块全局对象（L205–210），任务 A 的“本任务关闭扩展”会影响任务 B 的同智能体展示。另 L317 运行中切换立即改 `sel`，而排队“立即发送”在 L287 按新 `a.steer` 判断；生效点却声明为本轮结束后，当前轮与下一轮目标混用。

### RV10 附件只显示成卡片，没有随新任务／排队消息一起冻结

[需求](../里程碑/M14_统一Agent工作区/需求.md) L30 要求首页／任务内粘贴，R04 要求输入、附件来源和预算一起投递。但首页 `m14HomeChips` 不进入 `createTask()`；任务内 [Composer](../../prototypes/m6-codex/src/M14TaskArea.jsx) L274–279 排队仅保存 `{id,text,time}`，不保存 chips，也不在排队后将该批附件归入队列消息。

带文本和附件排队后，附件仍留在当前输入框，队列气泡只有文字，后续编辑／立即发送也没有附件。现在无法验证附件属于哪一条输入，以及准备中／失败附件能否随发送处理。此项只要求合成 payload 与 UI 状态闭合，不要求原型接真实模型。

### RV11 移除“拒绝并停止”后，请求面板没有对应的停止入口；子任务请求也不完整

[需求](../里程碑/M14_统一Agent工作区/需求.md) L31 指定停止用停止键；[A11](../里程碑/M14_统一Agent工作区/验收/测试用例.md) 要求统一面板和数字键。在 [Composer](../../prototypes/m6-codex/src/M14TaskArea.jsx) L314–322，`req` 分支只显示确认／提交，停止键在另一分支，`statusLine()` 恒为 null。[静态 React 渲染](evidence-20261116-2313/prototype-static-render.json)也确认 approval/question/business/plan 没有停止按钮；计划页保存截图同样如此。

此外 L447–451 的 `ChildRequest` 没有输入框、数字键或 Enter 提交处理，却复用写着这些提示的 RequestPanel。子任务页无法按统一合同附拒绝原因。不能以跳回主任务的操作代替子任务页宣称支持的同一面板。

### RV12 邮件进入手动修改后仍能批准旧请求，缺少“保存后再批准”的状态门槛

[需求](../里程碑/M14_统一Agent工作区/需求.md) L25、[A41](../里程碑/M14_统一Agent工作区/验收/测试用例.md) L383–384 要求手动修改、保存，再确认。 [M14Extras.jsx](../../prototypes/m6-codex/src/M14Extras.jsx) L34–45 把编辑中 draft 留在卡片局部 state；[M14TaskArea.jsx](../../prototypes/m6-codex/src/M14TaskArea.jsx) L393–401 没有根据 `mail.editing` 禁用“批准发送”。进入编辑后仍可在请求面板选批准，随后请求和业务卡会被 resolved 分支移除。

这是“编辑中／已保存待复审／已批准”没有区分的界面不一致。保存后的批准也应关联新 revision／内容摘要，旧批准选项不能继续指向旧审阅。

### RV13 目标“清除”只提示成功，不改变条目，与 A69 的可判定预期相反

[A69](../里程碑/M14_统一Agent工作区/验收/测试用例.md) L628 要求清除后条目消失；[GoalRow](../../prototypes/m6-codex/src/M14Extras.jsx) L8–29 只有暂停／继续修改局部 `st`，“清除”仅 `onToast('目标已清除')`。目标仍显示原状态，且停止键只是外层 toast，不会演示 Codex 停止后目标已暂停。

合成原型可以不调用真实目标接口，但应能切换到清除／暂停后的可见状态，供评审确认。当前截图和纯模型测试只验证存在目标行，不验证这些按钮结果。

### RV14 命令能力门槛和压缩显示仍违反最新界面决定

[需求](../里程碑/M14_统一Agent工作区/需求.md) L27、L46 规定 `/compact` 仅执行器公布时出现，`/goal` 仅已支持时出现，不支持手输要提示；压缩只显示分隔／进行中，去掉主动上下文用量展示。

[M14Extras.jsx](../../prototypes/m6-codex/src/M14Extras.jsx) L140–158 的两套命令列表都固定返回 `/goal`、`/compact`，不接收执行器能力；Composer 对 `/goal` 没有专门的不支持分支。Codex 目标状态的演示页又默认选中 Claude。`CompactionRow` L79 与 [m14-model.mjs](../../prototypes/m6-codex/src/m14-model.mjs) 的 compaction 数据仍展示“9.6 万 tokens → 1.2 万”。这与当前决定及“只显示支持的命令”的原型文案不符。

### 低

### RV15 新补记应在定稿前合并，多个“现行唯一”入口仍保留失效断言

需求 L9/L86 仍说首期不做 worktree、Git/SVN 同规则；最新 L40–48 已改。技术方案 §1/§6/§11 与新增 §6.1 也没有分清 Git 与非 Git 路径。[验证账](../里程碑/M14_统一Agent工作区/技研/全局设计验证账.md) Q35 仍是 worktree 范围外；A35 的理由也如此。原型说明 §0.1、§0.2、§2 仍把悬停时间、拒绝并停止、usage 等列作现行，后面的修订又撤销；[原型 AGENTS](../../prototypes/m6-codex/AGENTS.md) 顶部仍概括“写子等父结束”。

根规则允许迭代中补记，因此**补记本身不是产品缺陷，也不应撤回最新用户决定**。但当前“正文只维护现行合同”“D1–D5 不变”等表述不准确，交付开发前必须合并成新的需求／方案主修订，并限定旧研究适用范围。

### RV16 worktree、反复打回和目标新增了持久状态，但数据／恢复合同仍停在旧模型

技术方案 §2 只有旧 `agent_delegations` 和目录队列，没有落实 §6.1 要“登记”的 worktree／基准提交／宿主提交／合并结果／目标状态；§3 的公共 API 也没补 wy_send 与目标命令。未规定“自动提交后崩溃”“worktree 已建但记录未落库”“子结果通知前后重启”的恢复次序。

打回原 worktree 后，下一次通知应区分已合入提交与本次新增提交；否则旧通知、旧核对和新成果可能串代。工作副本需保留以支持 wy_send，但任务归档／删除后的保留和清理条件也未定义。此为设计缺项，不宣称产品已实现有缺陷。

### RV17 “到点自动继续”的行为已入需求／原型，技术状态机和用例尚未覆盖

需求 L27 与 Composer L300 已提供用户选择，但技术方案 §9、A60 仍只有额度错误后的手动继续，没有自动继续的持久意图、定时触发条件和取消规则。重启、切换执行器／账号、用户停止目标、重置时间未知或更新、再次限流时如何处理均未定义；不能把它等同“自动重发上次输入”。

### RV18 完全访问下的计划审批没有固定通过标准；扩展关闭的关键能力仍待研究

A71 的预期对完全访问仅写“实际行为如实记录（研究未验证）”，但需求计划流程要求“批准并开始／继续修改／拒绝”，E11⑧也未完成。仅记录原生自动通过不能算整条业务验收通过，应明确是否必须由宿主截获计划审批以及不支持时的能力出口。
