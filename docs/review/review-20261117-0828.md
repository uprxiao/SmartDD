## 2. 问题清单

### RR04 · 中 · 文件与差异隔离已修，子任务绝对路径识别和完整路径复制仍不正确

**已修部分**：消息路由增加 `ctxRoot`，差异改为按主／子身份保存，子目录的 `savedSeed` 也有独立根身份；不再复述上轮“整个差异面板未切根”的结论。

**剩余问题**：

- [M14TaskArea.jsx](../../prototypes/m6-codex/src/M14TaskArea.jsx)第 409–410 行把子工作根写为 `~/Library/Application Support/...`，`Inline` 又把原消息中的 `/workspace/SmartDD` 直接替换成该显示路径后再识别。实际 `inlineSegments`／`classifyToken` 不接受这种带 `~` 和空格的行内代码路径。上轮要求的子任务绝对路径边界仍未覆盖。
- **本次实际函数结果**：消息 `` `/workspace/SmartDD/scripts/build.mjs:1` `` 在子视图替换后变成 `` `~/Library/Application Support/.../scripts/build.mjs:1` ``，被识别为 `code`，没有生成链接。相对路径 `scripts/build.mjs:1` 则能路由成功；所以“同名文件打开成功”不能证明这一分支已修。
- 同文件第 401 行的完整路径复制仍拼接父 `projectRoot`。在子视图复制 `scripts/build.mjs`，实际提示为 `已复制：/workspace/SmartDD/scripts/build.mjs`，指向父目录。

**证据**：[focused-recheck.json](evidence-20261117-0828/focused-recheck.json) 的 `childInlineLink`、`childCopy`，使用实际识别函数和原样提取的复制处理函数；不是浏览器点击结论。

### RR05 · 中 · 任务内状态已保存，首页选择与创建快照仍有两个来源

**已修部分**：`TASK_STATE` 已保存任务内模型、权限和附件，首页权限列表使用 M14 所选执行器，任务创建也传入 `initialPermission`；这些修改成立。

**剩余问题**：

- [App.jsx](../../prototypes/m6-codex/src/App.jsx)第 409–415 行的启动预检、`profile`、`runner`、`agentSnapshot` 仍读取旧 `profile`，M14 新选择仅写入 `m14Sel`；权限快照却已按新的 `m13Tool` 生成。同一个新任务内的执行器身份和权限参数仍可能相反。
- **本次执行原 `createTask` 闭包**：旧 profile 为 Claude，首页 M14 改为 Codex、档位选“帮我批准”，创建结果同时包含 `m14Sel.agent='cx-ds'`、`runner='claude'`、`agent.tool='claude'` 和 Codex 的 `--approve-for-me`。这不是只剩隐藏冗余字段：[M13TaskDialogs.jsx](../../prototypes/m6-codex/src/M13TaskDialogs.jsx)第 23、39 行仍读取这些旧快照。
- [M14HomeModelPicker](../../prototypes/m6-codex/src/M14TaskArea.jsx)第 489 行每次挂载仍从 Claude 默认值初始化，App 不向它传回 `m14HomeSel`。首页选 Codex→创建任务→再次新建，选择器会显示 Claude，而 App 保留上次 Codex 的选择与权限目标。首页展示和新任务数据又会失配。

**证据**：[focused-recheck.json](evidence-20261117-0828/focused-recheck.json) 的 `homeCreate`、`createSource`。它保留原创建函数并调用实际 M13 快照／权限 helper，外围仅提供合成状态与记录 setter；生命周期分支另由源码核对，未声称本轮浏览器复现。

### RR06 · 中 · 附件拦截只接入任务 Composer，首页仍可发送准备中的附件

**已修部分**：任务 Composer 对 preparing／failed 已拦截，文字与附件均保留；本轮验证了空闲／运行中两种状态及就绪后的正例，共 6 组，均符合预期。

**剩余问题**：

- 首页走 [ReferenceHome.jsx](../../prototypes/m6-codex/src/ReferenceHome.jsx)第 21、33 行→App `createTask`，没有复用 Composer 的检查；首页的 `preparing` 是任务准备演示状态，并不读取 `m14HomeChips`。
- [pasteToChips](../../prototypes/m6-codex/src/M14Extras.jsx)第 185–194 行在粘贴后有 900ms 的 preparing 状态，此时首页“启动任务”和 ⌘Enter 都能进入 `createTask`。
- **本次原创建函数结果**：preparing 附件仍创建了任务，清空文字和首页附件，把带 preparing 的 chips 冻结进第一条消息。稍后的准备回调只更新已被清空的首页 chips，不能补齐已冻结输入。失败附件的合成输入也同样未被拦截。

**证据**：[closed-items.json](evidence-20261117-0828/closed-items.json) 证明任务内已修；[focused-recheck.json](evidence-20261117-0828/focused-recheck.json) 的 `homeCreate` 证明首页未修。原 RV10、A75 明确同时覆盖首页和任务内，这不是新增需求。

### RR07 · 中 · 停止已能移除请求，但任务状态仍等待，子任务甚至变成“继续工作”

**已修部分**：四类主请求均有停止键，`stopped` 会移除请求并显示停止记录；数字键和 Enter 的组合输入守卫也已补。当前不能再沿用“主请求没有停止键”的上轮结论。

**证据**：[focused-recheck.json](evidence-20261117-0828/focused-recheck.json) 的 `childStop`、上述已存截图和[本轮 SSR](evidence-20261117-0828/prototype-static-render.json)。SSR 仅证明停止入口存在；子停止结果为代码级合成探针，未当作真实 Agent 运行结果。
