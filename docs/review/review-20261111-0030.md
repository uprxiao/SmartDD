# Review Report

## 摘要

2026-11-11，审核 M13 原型 **P0.3**，依据需求 **R0.3（含补记）**、技术方案 **T1.0 草案**；原型提交 `663dc80d2`，分支 `feature/0.1.4`。已知用户认可该版原型的记录继续保留，本报告补充其业务一致性问题，不撤销已有认可，也不代表正式开发授权。

目录／详情的布局方向可以沿用，但目前还不能把“全部业务流程已闭环、可直接照原型实现”作为结论。发现 **9 项一致性问题（高 2、中 7）**，另有 **2 项待补设计（低）**。优先修正首页运行配置衔接、已有应用能力边界、连接与生命周期，再补项目选用和配置异常状态；无需推倒重做外观。

本次只审查并新增本报告及[证据摘要](review-20261111-0030-evidence.json)，未修改原型、生产代码或他人文档，未提交或推送。

## 问题清单

### P01 · 高：M13 运行配置与真实首页不是同一份数据，离开区域还会重置修改

- **依据**：[需求 §5.3](../里程碑/M13_应用Skill与MCP插件化重构/需求.md)明确保存 CodeAgent＋Provider＋模型配置后，在首页选择并启动。
- **实际**：`M13Workspace.jsx:28–34` 将插件、能力、Provider 和运行配置保存在组件自己的 state；`App.jsx:430` 仅在 `isM13` 时挂载该组件。首页 `App.jsx:435` 使用的是另一份 `profiles`，没有接收 M13 的 `configs`。AI 页的“首页显示效果”只是不可交互的展示块（`M13Workspace.jsx:239`）。
- **可复核路径**：新建并保存一项命名配置 → 返回工作台 → 打开首页配置选择器 → 再回 M13。源码可确定首页不会获得新配置；离开 M13 后组件卸载，再进入会按初始常量重建，刚才的配置／插件／纳管修改丢失。
- **影响**：核心配置流程不能跨页面评审。“只存内存”允许刷新后重置，不应造成同一次页面会话中正常导航即丢失。
- **证据层级**：组件数据流静态核对；本轮没有完成该完整 UI 序列，不能写作实机复现通过。

### P02 · 高：已有应用的读写边界被原型改写，并已传入测试用例

- **实际一**：`m13-model.mjs:23` 为禅道增加“添加 Bug 备注／写入”。但[补验 A5](../里程碑/M13_应用Skill与MCP插件化重构/技研/补验A5_插件声明与设计_20261110.md)列明现有三个能力全部 `zentao.read/read/safe-read`；生产 `src/main/core/applications/modules/zentao/index.ts:15–18` 与之相符。当前要求是迁移并保留原有能力，没有新增禅道写操作的需求决定。
- **传播**：[测试用例 M13-T014](../里程碑/M13_应用Skill与MCP插件化重构/验收/测试用例.md)把“添加备注（写入确认）”写成了“M10 已验收的主流程”，这不是现有代码及 A5 记录支持的事实。
- **实际二**：`m13-model.mjs:15` 把浏览器“打开页面”标为“读取”；`M13Workspace.jsx:118` 又解释为“只读取数据”。导航会改变任务当前页面，不应由概括性卡片重新定义为纯观察操作。应对应已有 M12 命令的正式读写分类。
- **影响**：用户可能在错误的能力／权限边界上确认设计，后续开发及测试又照此新增行为。这里是**原型与用例的设计错误**，不是声称当前原型已能向真实禅道写数据。

### P03 · 中：连接表单并非按插件声明渲染，保存也没有回写原型数据

- `M13Workspace.jsx:112` 允许邮件进入“管理”；但公共 `ConnectionDialog`（`:162–169`）对所有插件都固定显示禅道地址、账号、密码，连接成功固定为“可读取 Bug 与研发需求”。邮件因此会显示禅道配置及测试结果。
- 禅道现有配置还支持 Token／密码两种认证（生产 `modules/zentao/index.ts:25–33`）；原型只有密码字段，缺少认证方式。
- `:69` 的保存回调只是关闭弹窗并提示保存，没有读取输入值，也没有更新 `plugins.connections`。修改连接名称后关闭再打开，会恢复原值。
- **矛盾**：原型说明称其为“插件声明的表单”，需求要求保留既有连接及认证能力。可以使用合成连接测试，但表单和保存后的内存状态应真实反映所选插件。

### P04 · 中：“卸载保留数据”与实际重装状态相反，附带能力也没有联动

- 卸载弹窗 `M13Workspace.jsx:156` 承诺“保留私有数据目录、连接与项目授权，重新安装后恢复”。但 `:68` 两个卸载分支都只从 `plugins` 删除插件，`keep` 仅影响提示文字，没有保留区。
- 随后重装在 `:67` 一律创建 `projects:[]、connections:[]`。对既有禅道，按该表达式核对，连接数从 1 变为 0，项目数从 2 变为 0；[证据摘要](review-20261111-0030-evidence.json)明确标为表达式复核，未冒充 UI 重装或真实持久化实验。
- 独立 `caps` 中的 `s-zentao` 不随卸载／版本更新变化，仍显示“随禅道插件管理／禅道插件 1.0.0”。插件状态和能力状态不是同一来源。
- **影响**：生命周期两种选择无法评审出真正差异；与[技术方案所引用的 A5 生命周期](../里程碑/M13_应用Skill与MCP插件化重构/技研/补验A5_插件声明与设计_20261110.md)不一致。

### P05 · 中：新插件无法进入项目选用链路

- `M13Workspace.jsx:121` 显示“到项目资源页启用后，该项目的任务才会加载它”，但只有静态项目名称，没有项目选择、绑定连接或跳转动作。
- `App.jsx:462` 的项目应用页仍使用旧 `integration.data/APP_DEFINITIONS`，没有 M13 新安装的插件列表；新插件又只存于 M13 局部 state。
- **可复核路径**：安装 Demo Tracker → 查看“尚未在任何项目中启用” → 进入已有项目应用页；该页没有新插件的数据来源。
- **矛盾**：不是要求新增项目管理体系，而是应复用既有体系打通“安装 → 项目选用／授权 → 任务使用”。目前提示指向的目的地无法完成提示中的动作。

### P06 · 中：预设 Provider 永远不可选，删除后不能重新接入

- `M13Workspace.jsx:310` 对 Magpie／DeepSeek 无条件设置 `className='... disabled'` 和 `<input disabled>`；`has(id)` 只决定显示“已接入”还是说明文字，未控制是否禁用。
- Provider 详情允许删除（`:284`、`:72`）。删除 DeepSeek 后再接入，它仍为禁用项；用户只能走自定义服务，无法使用需求指定的预设接入流程。
- 原型说明说“已接入则不可选”，与实际“始终不可选”不一致。初始即内置成功记录，也不能替代首次接入及删除后恢复的设计。

### P07 · 中：更换 Provider 会保留上一家服务的 Claude 档位模型

- 初始 `rc-cc-ds` 有 `tiers`（`m13-model.mjs:123`）。`RunConfigDialog` 的保存表达式（`M13Workspace.jsx:266`）先展开 `initial`，只替换工具、Provider、默认模型等字段，没有重建或校验 `tiers`。
- 将该配置改成 Magpie、默认模型选 `gpt-5.5`，保存对象仍含 `opus/sonnet=deepseek-v4-pro、haiku=deepseek-v4-flash`，不属于该原型 Magpie 的模型目录。已用原保存表达式和合成数据独立核对，见证据摘要。
- 页面 `:272` 声称这些档位都映射到所选 Provider，且“可在高级设置中调整”；但高级设置没有档位选择器。
- **影响**：与技术方案“所有档位及子 Agent 只用该 Provider 允许的模型”相反。即使正式运行适配尚未实现，原型保存后的配置也应自洽。

### P08 · 中：高级设置可输入却不保存，旧高级配置又被限制成只能改名

- `M13Workspace.jsx:275` 的环境变量、启动参数没有 state／FormData 读取；`:266` 保存对象也没有这些字段，重开即丢失。
- 旧配置分支 `:268、:277` 只允许修改名称。原型说明据此写成“迁移来的高级配置只能改名”，但需求 §5.3 保留高级参数能力，技术方案 RunConfig 实体也包含高级参数／变量，没有把旧高级配置降为只读的决定。
- **影响**：用户需要的代理、启动参数等配置没有可用维护路径；迁移后继续可运行不等于以后只能改名。若这是产品范围调整，应先明确决定并同步需求，不能由原型单方面限制。

### P09 · 中：同一个 MCP 取消后重新纳管，配置状态改变而说明未变

- 初始 GitHub MCP 的 Codex 目标为 `onrun`，说明为启动时 `-c mcp_servers.github` 注入（`m13-model.mjs:67–68`）。
- 实际执行原函数 `manage(unmanage(github))` 后，目标变成 `configured`，位置说明仍是运行时注入。原因是 `:96` 只按项目／用户作用域判定状态，没有区分 MCP 与 Skill；用户级 MCP 落入“已配置”。
- 技术方案 §4.3 明确**所有已纳管 MCP 均按次注入，不写目标全局配置**；原型前后不应改变这个状态含义。
- 现有 `tests/m13-model.test.mjs` 的“取消纳管”测试恰好把 `configured` 写成预期，因此测试通过不能证明业务规则正确。

### P10 · 低：禅道声明式业务界面仍缺少迁移后完整流程的原型设计

- 目前只有静态 Bug 表格（`M13Workspace.jsx:122`），无行点击／详情、研发需求页签、刷新、分页、部分失败、正文／历史、附件及“插入终端”。这些都是 A5 逐项列出的现有面板要素。
- 旧 M10 页面保留是正确的，但它仍走旧状态与专用实现，不能据此证明新外部插件的声明式界面已经覆盖这些入口。
- 这是待补设计，不要求原型调用真实接口或实现生产渲染器；应通过合成数据把上述界面及失败状态画全，并与 P1 通用渲染验收对应。

### P11 · 低：异常与配置维护状态尚不完整，不能用成功提示代替设计

- 自定义 Provider 的最小确认固定返回两个协议成功（`M13Workspace.jsx:300、:318`），没有“模型列表能读但工具调用失败／仅一个协议通过”的界面；详情“更换 Key／刷新模型”仅 toast（`:287`），可用性测试结果仅存在弹窗局部 state（`:281、:288`），关闭即消失。需要补真实服务失败时的交互方案，可继续用合成结果。
- 本机工具自定义路径“检测并保存”不读取输入值（`:74`），也没有无工具／不可执行／检测失败状态；工具页说“模型连接在运行配置中测试”，配置弹窗却没有测试动作。
- 自动纳管开关只是布尔状态，重新扫描只显示计时完成（`:187、:190`），没有演示新发现自动纳管与冲突停下的完整过程。
- 能力页展示来源／已配置／运行时注入，但没有运行中会话“尚未加载、需恢复后生效、已加载、实际调用已验证”的关联状态。需求要求这些事实分开判断，不能让绿色配置状态代替会话可用结论。
- 可在正式用例中验证实际行为，但交互、失败恢复和状态表达应在原型阶段先补齐。

## 风险／待确认点

1. **已明确的剩余视觉项继续保留**：禅道图标为已声明的占位资源；正式版须使用可追溯官方资源。当前没有新增意见要求改变邮件／浏览器自有图标。深色、菜单、悬停、对话框和键盘遍历不能以部分几何测量宣布完全一致。
2. 现行“原型只用内存、不接真实服务”的边界合理。本报告要求补的是合成业务流程和一致状态，不要求原型接真实钥匙串、安装 CLI、扫描真实用户目录或执行外部写操作。
3. 用户原型认可记录有效；P02 的未经确认能力扩展应直接恢复既定只读边界。只有确实希望新增禅道写能力、限制旧高级配置等产品变更时才需另行决策，不能默认采用原型中的变更。
4. 真实签名 Electron 插件隔离、迁移、版本固定、权限与账本是正式开发 P1 验证范围，本报告没有替代或提前宣布通过。
5. **可能未穷尽**：本轮全面阅读 M13 组件／模型／样式／图标及相关需求方案，但受可交互浏览器工具限制，未完成每个弹层、键盘、长文本和全部异常组合的独立 UI 复验。具体证据范围已逐项区分，不能将静态核对当成实机结果。
