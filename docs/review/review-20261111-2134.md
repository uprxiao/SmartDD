## 2. 问题清单

### 中：K01 更换已有供应商 Key 时没有增加身份修订号，旧任务恢复仍不提示

**规则依据**：

- [技术方案](../里程碑/M13_应用Skill与MCP插件化重构/技研/技术方案.md)§2 Provider：地址、协议变化或已有 Key 被替换时，身份修订号加 1；首次填写 Key、刷新模型和改名不加。
- 同方案 §3.4 与需求 5.3：修订号变化时，恢复必须提示原来源与新来源，不预选，用户重新选择后才可继续。
- T064 已加入“供应商地址或 Key 被替换”的验收预期。

**位置与根因**：

- `prototypes/m6-codex/src/M13CodeAgent.jsx:323`：供应商详情的“更换”→“保存”只更新 `key`、`needKey`，没有更新 `rev`。
- `src/m13-model.mjs` 的 `agentSnapshot`／`identityChange` 已比较 `providerRev` 与 `p.rev`，但实际保存入口不增加它，前后都仍是默认的 0，判断结果是“身份未变”。
- `tests/m13-review-2119.test.mjs` 的修订号测试手动构造 `rev + 1`，证明比较函数有效，却没有验证“保存已有 Key → 修订号增加”这一步。
- 原型说明 P0.19 变更表写“原型无编辑地址／Key 的入口，仅单测覆盖”，其中 **没有 Key 编辑入口的说法不准确**：供应商详情确实有“更换”按钮，之前补 Key 的流程也使用同一个编辑区。

**实测步骤与结果**：

1. 用 Claude Code · DeepSeek 新建合成任务，再停止。
2. 打开 DeepSeek 供应商详情，原 Key 脱敏后四位为 `3f9a`；点“更换”，填写虚构测试 Key 并保存，页面后四位变为 `5678`。
3. 回旧任务打开恢复：没有身份变化提示，仍预选 `rc-cc-ds`，标“原智能体”，“恢复任务”可直接点。

**预期**：此次替换已有 Key 应增加身份修订号，使旧快照不再匹配；恢复应出现“DeepSeek → DeepSeek（地址或 Key 已修改）”之类的提示，并先要求重新选择。

这次只在合成原型中操作虚构 Key，没有调用真实模型，不能据此声称发生了真实凭据泄漏。问题是恢复确认规则仍漏掉已承诺覆盖的实际入口。

证据：[Key 保存后的页面](evidence/m13-20261111-2134/key-updated.png)、[仍直接可恢复的弹窗](evidence/m13-20261111-2134/key-change-resume.png)、[原始结果](evidence/m13-20261111-2134/key-change-review.json)、[独立驱动](evidence/m13-20261111-2134/key-change-review.mjs)。

## 3. 修改建议

1. 把供应商身份相关修改归到统一的状态更新逻辑：**替换已有 Key** 时连同非敏感修订号一并更新；首次补 Key 不增加，改名／刷新模型不增加。正式实现由主进程维护，不能只在界面增加数字。
2. 保留已修好的 `identityChange` 与重新选择流程，接通保存入口即可，不需要重新设计恢复弹窗。
3. 增加从“已有 Key 的供应商详情 → 更换 → 保存 → 恢复旧任务”的回归；同时保留“首次补 Key 可启动、不误判身份变化”的对照。测试应操作真正的保存处理逻辑，不能只手动构造一个增加过的 `rev`。
4. 更正原型说明里“没有 Key 编辑入口”的描述；T064 的现行预期本身正确，无需改成迁就当前实现的结果。
