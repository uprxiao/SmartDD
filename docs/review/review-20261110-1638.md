# Review Report

## 摘要

本次复核 M13 R0.3 补记、T1.0 草案、A1–A5 文档、实验脚本和归档结果。补验明显推进了研究：官方 DeepSeek 直连、审批矩阵、声明式禅道草案和 P1 门槛都有新增依据，唯一技术方案已建立。**但“R01–R11 全部关闭、五组补验全部完成”仍不能成立。**本轮增加了五个可复现反例：项目配置可改发 Provider Key、项目级 Skill 跨项目可见、MCP 自有 Key 被过滤、缺变量仍生成配置、合法 TOML 被错误还原；另有设计口径与证据不一致。

时间：2026-11-10，分支 `feature/0.1.4`，工作区未提交。场景：文档＋实验代码／证据一致性审查。核对 A1–A5 全部 **46 个清单文件**，哈希均匹配、无漏项。新增 CLI 探针使用 Node 22.23.1、Claude Code 2.1.321、Codex 0.166.0，临时 HOME／配置、诱饵 Key、本机假模型和拒绝外网的记录代理；不使用真实订阅、真实 Key 或真实模型，不打开日常 App。只新增本审核与证据，不修改生产代码、需求或原实验。

## 问题清单

### 高：F01　只校验独立配置目录，仍会把 Provider Key 发往项目指定的另一端点

- [T1.0 第 35–40 行](../里程碑/M13_应用Skill与MCP插件化重构/技研/技术方案.md)采用每 RunConfig 一个独立目录，只明确检查该目录的 `settings.json`，并为任务项目写入信任。A3 负例检查了目录残留 env、apiKeyHelper 和 `--settings`，没有覆盖项目 settings。
- 本轮新建干净独立目录，注入模拟端点 A 与诱饵 Key A；只在项目 `.claude/settings.json` 写 `env.ANTHROPIC_BASE_URL=B`，没有写项目 Key。实际 Claude 向 **B 发送 Key A**，A 零请求，CLI 退出 0。项目同时指定 Key B 时也能覆盖注入结果。
- 这直接违反所选 Provider 的端点／身份隔离。清除 shell 变量、检查 `CLAUDE_CONFIG_DIR` 不足以保护认证；无外部代理日志也不能发现这种发往另一允许本机端点的错误。
- 建议：明确全部有效配置源与优先级，覆盖项目 settings、local settings、启动参数及会影响认证的 helper；按 CLI 支持的配置来源控制或严格拒绝冲突，让 WillYou 选中的端点与认证不可被静默覆盖。不要为了 headersHelper 无条件信任项目全部配置／钩子。补“只改 BASE_URL、不改 Key”的反例。
- 证据：[仅改地址后的原始探针输出](证据/M13-20261110-1638/project-credential-probe.mjs.stdout)、[同时改地址／Key 的对照](证据/M13-20261110-1638/project-settings-probe.mjs.stdout)。均为合成令牌，无真实泄露。

### 高：F02　每 RunConfig 共用 Skill 根，会扩大项目级 Skill 的作用域

- T1.0 第 35 行规定 Claude 独立目录按 **RunConfig** 分配；[第 75 行](../里程碑/M13_应用Skill与MCP插件化重构/技研/技术方案.md)将第三方配置的 Skill 统一链接到 `$CLAUDE_CONFIG_DIR/skills`，没有区分用户级和项目级。与[需求第 158 行](../里程碑/M13_应用Skill与MCP插件化重构/需求.md)“项目级安装不自动扩成全局授权”不一致。
- 本轮在项目 A 创建 `sk-project-a-private`，按方案链接到配置根；随后在另一项目、同一配置根启动 Claude，模拟模型请求已包含该 Skill。**加载成功本身正是越作用域的证据。**这并不等于宿主的项目资源授权被绕过，但项目专有指令和资源入口已对其他项目暴露。
- 建议：用户级能力才放共用根；项目级能力按 task／project 投影到本次运行的插件目录或其他已验证隔离落点。不能在共用目录里启动前轮流替换链接来解决，因为同一 RunConfig 可在两个项目并发。补 A/B 同时运行、取消纳管、切换项目和恢复的作用域用例。
- 证据：[跨项目可见结果](证据/M13-20261110-1638/skill-scope-probe.mjs.stdout)、[执行驱动](证据/M13-20261110-1638/skill-scope-probe.mjs)。

### 中：F03　MCP 包装先 set 后 unset，会删除 MCP 自己明确配置的同名 Key

- [包装脚本第 17、20 行](../里程碑/M13_应用Skill与MCP插件化重构/技研/实验/A1_MCP语义与策略_20261110/wy-mcp-launch.sh)先映射 MCP 的环境变量，再按模型变量名清除。
- 反例：模型使用 `ANTHROPIC_API_KEY=decoy-model-key`；MCP 自己也需要名为 `ANTHROPIC_API_KEY` 的独立 Key，通过 `--set ANTHROPIC_API_KEY=WY_MCPV_1` 传入 `decoy-mcp-key`。随后 `--unset ANTHROPIC_API_KEY` 把它一起删掉，子进程读到 null，包装退出 0。
- 与 A1“过滤模型凭据，同时 MCP 自身凭据正常到达”的结论不符；原测试的 MCP `API_KEY` 与模型变量名不同，未覆盖碰撞。
- 建议：先清除继承的模型／宿主凭据，再注入该 MCP 明确授权的自有变量；区分变量来源，保留私有槽直到参数／映射完成，最后清理私有槽。不能把“同名”当作“同一个秘密”。
- 证据：[包装反例](证据/M13-20261110-1638/wrapper-result.json)、[准确输入与执行方法](证据/M13-20261110-1638/复核方法.json)。

### 中：F04　缺变量时只记录问题，仍会生成可注入的 MCP 配置

- [a1.mjs 第 56–63 行](../里程碑/M13_应用Skill与MCP插件化重构/技研/实验/A1_MCP语义与策略_20261110/a1.mjs)在变量求值失败后，只 `continue` 当前 env／args／header 项，仍把整个服务器写入目标配置。
- 本轮复用原 `emit`，输入 MCP `API_KEY=${NOT_SET}`。两方向都返回“缺少变量”，**同时仍生成该 MCP 的可执行启动配置**；不是“不注入”。原 M3 只检查 problems，未检查目标服务器不存在。
- 缺少参数时还可能产生参数位移；缺凭据时有落回服务器自身其他认证来源的风险。这里验证的是实验生成器错误，尚非已发布 WillYou 缺陷。
- 建议：以服务器为单位完整求值并验证，任一必需变量缺失则该服务器不进入配置，清理其临时槽；其他正常服务器可以继续。断言目标服务器缺席、启动次数及执行次数均为零。
- 证据：[两侧实际生成结果](证据/M13-20261110-1638/missing-variable-result.json)、[纯逻辑探针](证据/M13-20261110-1638/missing-variable-probe.mjs)。

### 中：F05　全局模型还原会误删合法 TOML，G1–G6 不能证明配置安全

- [a3b.mjs 第 18 行](../里程碑/M13_应用Skill与MCP插件化重构/技研/实验/A3_AI隔离与恢复_20261110/a3b.mjs)只识别整行双引号赋值；合法 TOML 单引号字符串、行尾注释不匹配。
- 本轮输入 `model = 'user-default' # valid TOML`，readTop 将原模型当作不存在；模拟本次会话写入模型后执行还原，函数返回 ok，却直接删除 `model` 行。违反 T1.0“只还原原值，不破坏用户配置”的设计目标。
- 建议：复用 TOML 解析器／支持保留格式的定点编辑器，保存原键存在性、值与对应语法范围；不支持的格式宁可拒绝还原。补注释、单双引号、转义、顶层键顺序、外部并发写入。当前比较交换只是纯字符串函数的检查，落盘阶段的并发与原子更新仍要设计，不能据 G1–G6 宣称完整文件 CAS 已实现。
- 证据：[还原结果](证据/M13-20261110-1638/restore-result.json)、[原函数与新增输入](证据/M13-20261110-1638/restore-probe.mjs)。未读取或改写真实 Codex 配置。

### 中：F06　敏感 URL 的处理与“不落明文”的需求仍冲突

- [需求第 70 行](../里程碑/M13_应用Skill与MCP插件化重构/需求.md)要求 env、headers、URL 的敏感值加密或引用，启动注入、不落明文。

### 中：F07　部分补验的归档结果仍是失败／不一致，不能统称已修正通过

- **A1 literal header**：[a1-result.json](../里程碑/M13_应用Skill与MCP插件化重构/技研/实验/A1_MCP语义与策略_20261110/a1-result.json)里 `M1c` 的原生 `X-Lit` 是 `${SRC}`，`M1d` 的转换结果仍是 `SRCVAL`；执行驱动没有接入 `headersHelper` 分支。目录虽有 `hh.sh`，但当前清单没有对应 helper 修正后重跑的结果。文档声称修正后保留字面量，当前归档无法独立验证。
- **A2 timeout**：[a2b-result-dedup.json](../里程碑/M13_应用Skill与MCP插件化重构/技研/实验/A2_Skill生命周期_20261110/a2b-result-dedup.json)中 Claude v1／v2 两种落点共四个运行仍退出 143；说明也承认模拟模型循环后超时。已有 `Launching skill`、v1／v2 与脚本输出足以证明局部能力，但“去重结果”不是修好驱动后的绿测，不能据此宣称完整运行闭环通过。
- **A3 requestedModel**：归档 a3-result 的 assistant 摘要没保留 requestedModel，驱动只附加“全文含某个字符串”的布尔值。该字符串也可能来自其他记录，不能独立证明所设计的解析路径与筛选规则；API 事实可继续采用，但解析器还需最小可复判夹具。
- **A4 background**：原 bg.mjs 只打印结果，且零外连组同时关闭 apps、remote_plugin、plugins、analytics、feedback，不是方案中的两个参数单独对照。本轮已补跑**精确方案参数**与完整参数组，两者在临时空 CODEX_HOME 下均无记录代理外连，故此疑点在该边界可关闭；不扩大为含日常全局 MCP、应用配置的所有环境均无外连。
- 建议：只补 helper 的一条最终对照、四个 Claude 正常收尾、最小原生历史 fixture＋实际模型解析断言；保存旧红和新绿。不要重跑已有效的官方真实请求。继续区分“实验发现已记入方案”与“修复实现和最终证据已通过”。

### 低：F08　通用协议探测不宜用 HTTP 状态码直接定性“兼容且不计费”

- T1.0 第 46 行以 400／422 判支持、404 判不支持、401／403 判 Key 无效。A4 在 DeepSeek 的结果成立，但通用网关／反向代理的默认错误页、统一路由返回或权限限制也会出现同样状态；有端点不等于满足流式及工具契约，403 也未必是 Key 错误。
- 建议：探测结果先标“候选协议／待验证”，结合结构化错误和已知预设契约；最终兼容性由最小流式／工具调用确认。“空请求在本轮 DeepSeek 未形成模型调用”可以记录，不应扩展为任意第三方服务的收费保证。此项是设计完善，不是已复现的 DeepSeek 故障。

### 低：F09　Codex 项目链接方案可用，但 exclude 不是隔离或零改动保证

- `.git/info/exclude` 只控制未跟踪文件的状态显示，不阻止其他终端加载 Skill，也不会忽略已跟踪文件。worktree／submodule 的 `.git` 可能是文件，非 Git 项目也无该路径。
- 建议按 Git 返回的真实 exclude 路径处理，仅排除本方生成的具体链接与标记，不整段隐藏用户已有 Skill；已有文件／已跟踪路径冲突时停止覆盖；记录所有权，取消纳管只清理本方仍未被用户替换的产物，非 Git 项目正常工作。以上属于该工程选择的实现条件，不能只做一次 append 就声称“不污染仓库”。
- `--disable plugins` 的代价也应明确：原生 Codex 插件能力若需要 WillYou 代投影，须列出发现／归属／兼容边界，不能静默消失。现方案尚未给出对应完整用例。

## 修改建议

只做聚焦修改和对应复验：

1. **AI 隔离**：修正全部配置源的认证优先级（F01），新增“只改项目地址”负例；将用户级／项目级 Skill 分开投影（F02），以同 RunConfig 两项目并发验证。
2. **MCP**：纠正先清继承秘密、再注入 MCP 自有凭据的顺序（F03）；整服务器求值失败即不生成（F04）；敏感 URL 与需求对齐（F06）。补 literal header helper 绿测，不重跑整个 A1。
3. **配置还原**：替换简易 TOML 正则，补合法语法及真实落盘的并发保护（F05）。
4. **证据**：补 F07 指出的具体缺项，保留红测。修正阶段“全部完成”的表述，关闭到证据支持的粒度。
5. **原型可继续准备**：F08／F09 并入设计与用例，不需要因此重做已有研究；F01／F02／MCP 约束需在受影响页面定稿前同步。正式开发仍按用户评审授权推进，P1 不提前宣称完成。

对两项待评审工程选择：

- **Claude `--permission-mode default`：建议采用。** 已有终端允许／拒绝证据，能避开第三方 Provider 的 auto classifier 不可用；它仍是询问，不等于预先自动批准。应按第三方配置明确注入，保留逐工具限制与用户批准策略。
- **Codex 项目级 Skill→项目 `.agents/skills`：有条件合理。** 可作为已验证固定扫描根下的落点，按 F09 做所有权、冲突、worktree 和清理；该选择不解决 F02 的 Claude 跨项目问题，也不隔离同项目的其他 CLI。
