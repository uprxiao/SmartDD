## 3. 新发现的问题

### T1（中，缺陷，直接修）：裸写的文件名被识别成网页链接

- 代码：`agent-task-view.tsx:38` 用 `new MarkdownIt({ linkify: true })` 渲染回答。linkify 默认会模糊匹配不带协议的地址，于是 `CHANGELOG.md`、`main.py`、`deploy.sh` 这类文件名被当成域名（`.md`、`.py`、`.sh` 恰好都是国家域名后缀）。
- 试验结果：
  - `见 CHANGELOG.md 和 main.py、deploy.sh` 渲染成 `http://CHANGELOG.md`、`http://main.py`、`http://deploy.sh` 三个链接。
  - 关闭模糊匹配（`fuzzyLink:false`）后，三个文件名都恢复为纯文本，`https://` 开头的网址仍然是链接。
- 影响：需求第 133 行规定“只有文件名的行内代码不做链接”，用例 A57 也要求“只有文件名保持纯文本”。现在这些文件名显示为蓝色可点击的链接，点开会作为网页在内置浏览器中打开 `http://main.py`。新截图 `links` 里的 `CHANGELOG.md` 就是这样。
- 参考：T3 Code 用 remark-gfm 渲染 Markdown，只自动识别带协议的网址和 `www.` 开头的网址，不会把裸文件名当成链接。
- 修改：关闭 linkify 的模糊匹配，按 T3 Code 的 GFM 规则，只自动识别带协议和 `www.` 开头的网址。注意：只设 `fuzzyLink:false` 会把 `www.` 开头的网址也一并关掉（试验中 `www.example.com` 不再是链接），要和 GFM 一致，需要另加一条 `www.` 规则。补一条渲染端测试，覆盖 `CHANGELOG.md`、`main.py` 保持纯文本，`https://` 和 `www.` 开头的网址仍是链接。
