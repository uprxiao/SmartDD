## 2. 问题清单

### 中优先级

### X01：判定器只检查包含 red，否定答案也会判通过

类型：测试误报通过。代码：[attach-judge.mjs 第 13 行](evidence-20261118-0049-fix/driver/attach-judge.mjs#L13)。

回执要求“没有回答、回答不是 Red 都失败”，驱动提示也要求只回答一个英文单词。实际使用 `/\bred\b/i`，判断的是包含单词 red，并没有判断回答是否为 Red。

将已保存的成功结果仅替换答案，其他条件不变：

- `Not red` → 判通过。
- `The image is white, not red.` → 判通过。

这不是模型输出的真实新失败，而是对判定器的受控反例，证明“答非 Red 必失败”仍未落实。原 13 组只覆盖了 `White`，没有覆盖含 red 的错误／否定答案。

证据：[C02、C03](evidence-20261118-0101/driver-boundary-observations.json)。建议对归一后的完整回答做匹配，例如去掉允许的首尾空白后要求整串为 Red（大小写可忽略）；若要允许末尾标点，明确允许范围，不能退回包含匹配。

### X02：等待和“已完成”没有绑定本次回合，会同时造成假超时和假通过

类型：测试时序与终态归属错误。代码：[发送后才读取回答数](evidence-20261118-0049-fix/driver/m14p2-driver-attach-v2.mjs#L90)、[等待及完成状态判断](evidence-20261118-0049-fix/driver/m14p2-driver-attach-v2.mjs#L93)。

**快回复被误判超时。** 驱动点击发送后会暂停 200 ms，再等待卡片清空，然后才读取 `before`。如果第二条回复此时已出现，`before` 已是 2，后面却要求回答数大于 2。这条只应有两次回答的流程即使已经完成，也会等待不存在的第三条回答并报超时。

本轮执行真实等待代码片段：慢路径先读到 1，之后第二条 Red 到达，判通过；快路径开始时已有 `OK`、`Red` 两条完成回答，却生成 `length>2` 并报超时。证据：[C05 对照、C06 反例](evidence-20261118-0101/driver-boundary-observations.json)、[提取的等待代码](evidence-20261118-0101/reply-wait.fragment.txt)。有界替身对稳定完成 DOM 检查 5 次；这不是声称真实模型本轮出现过 200 ms 回复。

**本轮失败借用了上一轮“已完成”。** `turnFinished` 判断整个任务页包含“已完成”，而首轮 OK 的完成尾注一直留在时间线中。如果第二轮已输出 Red 随后失败，停止键消失，任务页仍有首轮“已完成”，这时当前代码仍把第二轮当成完成。

本轮执行真实终态读取代码：首轮 completed，第二轮 Red 后尾注为“失败”，计算出的 `turnFinished` 仍为 true，判定器给出 passed。证据：[C07](evidence-20261118-0101/driver-boundary-observations.json)、[提取的终态代码](evidence-20261118-0101/reply-status.fragment.txt)。DOM 使用真实界面已有的 `.agent-assistant`、`.agent-md`、`.agent-turn-footer.failed` 结构；没有改产品状态或 App。

建议在发送动作前固定基线，并识别本次提交对应的消息／回合，再核对该回合的实际终态。既要接受发送后立即出现的正确回复，也要拒绝本轮 failed／interrupted／unknown；不能从历史任意一轮的完成尾注推断本轮成功。可以结合只读快照／DB 的 turnId 与终态核对，输入、发送仍通过真实 UI。
