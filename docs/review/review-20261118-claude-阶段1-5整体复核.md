## 3. 问题

### G1（高，需确认规则）：项目下只要有新任务区的任务，删除项目就会失败

- 代码：`tasks.project_id` 对 `projects` 是 `ON DELETE CASCADE`（`src/main/db/schema.ts`），而 `drizzle/0037_agent_workspace.sql` 中 `agent_tasks.task_id` 对 `tasks` 是 `ON DELETE RESTRICT`。删除项目时，级联删除 `tasks` 行会被 `agent_tasks` 挡住，整个事务回滚。
- 实测（[复现](evidence-20261118-claude-phase1-5/probe-delete.test.ts.txt)、[观察值](evidence-20261118-claude-phase1-5/delete-probe.json)）：建项目和一个 M14 任务后调用 `ProjectService.deleteProject`，报 `FOREIGN KEY constraint failed`，项目仍在。
- 相关：删除前的“有任务正在运行”检查（`projects/controller.ts` 的 `runningTasks`）只统计旧终端任务（`tasks.runningInProject`），不统计 M14 任务。
- 影响：开启新任务区后，用过的项目都删不掉，界面只显示外键错误。需求与技术方案没有写删除项目时 M14 任务如何处理。
- 参考（2026-11-18 调研）：
  - T3 Code（本地 `t3code` `fe59fa44d0`）删除项目时连同全部线程（含已归档）一起删除，不可撤销；确认框列出线程数，并写明执行器自己的会话保留、磁盘文件不动；工作副本不删。
  - Codex App 的“移除项目”只删项目信息，聊天保留。Codex 的项目只是文件夹；WillYou 的项目还带数据库、服务器、应用选择、规则、插件等配置，任务离开项目后会缺少这些配置，因此不采用 Codex 的做法。
  - 想保留记录时，用现有的“归档项目”。
- **用户决定（2026-11-18）：删除项目时一并删除该项目的全部 M14 任务（含已归档），不可恢复；有未收口的任务时拒绝删除；确认框必须写清删除和保留的内容。**
  - 一并删除（都是 WillYou 自己的数据）：任务、事件、条目、请求、委派、差异记录；附件副本；本方快照（Git 仓库里的 `refs/willyou/turns/*` 隐藏引用、SVN／普通目录的私有影子库）。目录不在或不可访问时跳过清理，不阻止删除。
  - 保留：代码目录；子任务的 Git 工作副本目录和分支（可能有未合并的改动，与 R06 一致）；Codex／Claude 的原生会话文件；M13 应用调用记录（按现有规则显示“已删除项目”）。
  - 拒绝删除：有任务正在运行（回合中或后台命令）、有待批准的请求、子任务未交回结果，或 Git 工作副本正在准备。提示写明具体任务和处理方法。不采用 T3 Code 的自动取消，以免业务操作（如发送邮件）结果不明。`runningTasks` 要把这些 M14 任务算进去。
  - 确认框（替换现有的“只删除 WillYou 中的记录……”）写明：将删除的 Agent 任务数（含已归档）；对话和差异记录会从 WillYou 删除，无法恢复；代码目录、子任务工作副本（列出路径）和 Codex／Claude 自己的会话文件不会删除；想保留记录请改用“归档项目”。原有的“同时删除已加密保存的密码”选项不变。
  - 补测试：删除带 M14 任务（含已归档任务、父子委派、差异记录、业务请求、附件）的项目成功，相应记录、快照引用、附件都已删除，工作副本目录仍在；有运行中、待批准或子任务未收口的任务时拒绝删除，项目和任务都保持不变；确认框文案（含任务数和工作副本路径）有界面测试。

### G2（中，需确认保留规则）：差异快照、私有影子库和附件副本都没有清理

- 代码：
  - `turn-diffs.ts` 的 `releaseArchived` 没有任何调用方；`agent_turn_changes.retained_until` 列在迁移中建了，代码里没有读写。
  - 归档只调用 `diffs.archive`，它只检查是否在读写，不释放引用。
  - 技术方案 §11 写的是“按任务归档及保留政策清理本方隐藏引用／私有影子库”，实际没有落地。
- 影响：
  - **Git 项目**：每一轮在用户仓库写入 `refs/willyou/turns/<turnId>/before|after` 两个隐藏引用，以及工作区文件的对象（未提交、未被忽略的文件也在内）。永不释放，`git gc` 也不会回收，仓库会随使用持续变大。
  - **SVN／普通目录**：每个目录的私有影子库上限 1 GiB，没有回收。到达上限后，这个目录以后每一轮的差异都会报“影子库达到 1 GiB 存储预算”，变成永久不完整。
  - **附件**：`userData/agent-attachments` 下准备后没发送的副本和冻结副本都不清理。
- 相关缺陷：差异列表 `list` 只返回最近 50 轮（`LIMIT 50`）。点击时间线里更早一轮的改动卡片时，`workspace-panels.tsx` 在列表中找不到这一轮，就退回显示最新一轮的差异。
- 参考（2026-11-18 调研，本地 `t3code` `fe59fa44d0`）：
  - 只给 Git 仓库拍快照（隐藏引用 `refs/t3/checkpoints/...`），非 Git 目录不显示差异；每个线程不设轮数上限。
  - 归档的线程保留快照和附件。线程删除后，由 `storageCleanup.ts` 的后台清理（每小时一次，也可手动触发）删除它的引用。清理依据删除标记判断归属，不会因为“本数据库里没有记录”就删除引用，因为同一仓库可能还被其他数据目录使用。
  - 回退到某一轮时，清掉之后各轮的引用。不在用户仓库执行 `git gc`。
  - 附件：线程删除时删；排队消息被编辑时去掉的附件删；准备后 24 小时未发送的删；上传一半的 1 小时后删。
- **用户决定（2026-11-18）：除下面两点外，沿用 T3 Code 的规则。① SVN／普通目录按需求 R09 保留差异，补充空间回收规则；② 本期不增加“删除单个任务”，Git 快照只在删除项目时清理。** 具体规则：
  1. **查看**：差异列表能翻到全部轮次，不再只显示最近 50 轮；点击任一轮的改动卡片，显示的就是那一轮；快照已被回收的轮次显示“快照已清理（空间回收）”。
  2. **Git 项目**：进行中和已归档的任务都保留全部快照，不设轮数上限。删除项目时，删除这个项目全部任务的 `refs/willyou/turns/*` 隐藏引用。只删引用，不在用户仓库执行 `git gc`。
  3. **SVN／普通目录**（私有影子库，每个目录 1 GiB）：
     - 平时保留；删除项目时释放这个项目各任务的快照，如果该目录的影子库已经没有其他任务在用，就整个删除。
     - 捕获前影子库接近上限时，先回收已归档任务的快照，再回收进行中任务最旧的轮次，然后清理影子库（`prune`）。
     - 回收后仍然超限，才把本轮标为“影子库空间已满”并说明原因。
     - 有读租约（正在查看）的轮次不回收。
  4. **附件**：任务还在就保留（包括已归档）。删除项目时一起删。从草稿移除的附件、被取消的输入，副本立即删除。准备后 24 小时没被任何草稿或输入用到的，也删除（包括崩溃后的残留）。
  5. **重试与归属**：
     - 删除时清不掉的快照（目录不在、仓库被占用等）记进“待清理”表，后台在启动时和每隔一段时间重试；表为空时不做任何操作。
     - 只删除 WillYou 自己写过并有登记的引用或快照，不按前缀批量删除，因为开发版和正式版可能使用同一个仓库。
     - 清理和捕获使用同一把目录锁。
  6. **不做**：归档时不清理；不按时间保留，`retained_until` 不再使用（迁移可保留该列，代码不读写）；本期不增加删除单个任务。
- 已知限制（用户接受）：长期使用的 Git 项目，`.git` 会随轮次慢慢变大，直到删除项目才回收。变大主要来自没被 `.gitignore` 忽略、又每轮都在变的大文件。
- 补测试：
  - 删除项目后，Git 隐藏引用、影子库快照和附件都被删除，工作副本仍在；清理失败的进入“待清理”表，并在下次重试时成功。
  - 归档任务的快照和附件保留。
  - 第 51 轮之前的改动卡片能打开对应轮次。
  - 影子库达到上限时，先回收已归档任务的快照、再回收最旧轮次，之后能继续捕获；正在查看的轮次不被回收。
  - 附件从草稿移除、输入取消后立即删除；超过 24 小时未引用的副本被删除。
  - 仓库中不属于本库登记的 `refs/willyou/*` 引用不被删除。

### G3（中，已确认改为方案 C）：Git 工作副本准备时的等待没有界面提示，遇到进行中的 Codex 目标会无限期等下去

- 代码：`delegation-service.ts` 的 `waitForGitBoundary` 循环等待，条件包括同一工作目录里 Codex 任务的目标处于 `active`（`agent-run-service.ts` 的 `workspaceTasks`），没有上限。等待期间 `workspaceWaiting` 让同目录其他任务的新输入都排队。
- 界面：`grep` 渲染端，没有任何地方显示这一状态。
  - 父任务显示“进行中”，子任务显示排队。
  - 其他任务发出的消息显示“排队”，但看不到原因。
  - 插话和命令只在 toast 里提示“Git 工作副本正在准备，请稍后”。
- 影响：
  - 同一仓库里有一个任务开着 Codex 目标时，再派 Git 写入子任务，父任务、子任务以及同目录其他任务的新输入都会停住，直到那个目标完成或被暂停，可能是几十分钟甚至更久。用户不知道在等什么，也不知道怎么解除。
  - 等待条件里的 `nativeNodes` 来自 Claude 的 `task_started`／`task_notification`。按 Claude Code 的消息格式，后台 Bash（如 `pnpm dev`）也会产生这类消息，此时会一直等到用户停止命令（未实测）。
  - 另一个任务在等用户批准时，它的回合一直在进行中，也会一直等。
- 根因：需求 R06 规定派出 Git 写入子任务前要自动提交主目录改动；R1 又规定提交前要等其他任务的回合结束。等待就是从这两条来的。
- 参考（2026-11-18 调研）：
  - T3 Code：从已提交的 base ref 建工作副本，不带未提交的改动，不自动提交，也不等其他线程（`ThreadLaunchService.ts`）；子 Agent 与父线程共用目录。
  - Codex App：由用户手动把聊天移到工作副本，用 `git stash` 搬走未提交的改动，只检查被搬的这个聊天是否在运行，不等其他聊天，也不自动提交。
- 场景分析（与用户讨论确认）：
  - 子任务需要看到父任务未提交改动的场景：审查未提交的设计或代码、接着父任务的改动继续写、检查当前改动（测试、构建、lint）、审查后直接修改。
  - 只有“并行开发互不相关的功能”不需要。
  - 只读子任务虽然在主目录运行，但只有能证明只读的配置才算只读：目前只有 `trustedRead`，即 Codex 接第三方供应商。Claude Code 和订阅登录的 Codex 都按写入处理，要进工作副本，看不到未提交的设计。
- **用户决定（2026-11-18）：Git 写入委派改为方案 C，同日 R1 的决定作废。**
  1. **两种模式，由父 Agent 选择**：`wy_delegate` 增加参数，取值为共用目录或独立工作副本，工具说明写清两者的区别和适用场景。未选时默认共用目录。用户可以用自然语言指定。任务关系卡和子任务卡片上标明所用模式。
  2. **共用目录（默认）**：子任务和父任务在同一目录，按现有方案 B 串行，与 SVN／普通目录相同：父任务这一轮结束后子任务开始，子任务结束后父任务重新取得写入权。子任务结束时宿主**不提交**，改动留在目录中。`childInput` 里的“完成后由宿主提交”只在独立工作副本模式下使用，共用目录改为说明改动保留在目录、不提交。`wy_send` 继续沿用原子任务的会话，支持审查、修改、再审查的多轮循环。
  3. **独立工作副本**：由宿主从父任务当前提交（HEAD）创建，不带未提交的改动。委派回执和子任务启动说明写明所基于的提交；主目录有未提交文件时，回执写明“主目录有 N 个未提交文件，没有带进子任务”。工具说明提示“需要子任务基于你的改动时，先提交你改过的文件”。子任务结束时宿主提交到子分支，由主 Agent 合并（沿用现有合并核对）。路径、分支命名和依赖安装不变。
  4. **删除**：派出前的自动提交（`auto_before_delegate` 及其意图／提交来源记录）、`waitForGitBoundary`、`sharedGitPreparations` 和对应的输入闸门（`workspaceWaiting`／`WorkspacePreparationPending`）、提交说明里的“可能包含同目录其他任务的改动”。`git worktree add` 按根串行的锁可以保留。
  5. **不变**：只读子任务继续在主目录并行；独立任务继续并行；SVN／普通目录仍按方案 B。
  6. 同步：需求 R06、R09 已改，见需求 2026-11-18 勘误。原型、技术方案、用例的修改见第 6 节（6.2 中的 G3 行、6.3 中的 §2/§3/§6/§6.1/§9、6.4 中的 A30–A32/A66–A68/A70/A74/A77 以及新增的 A80–A85）。R1 的回归测试改为验证不再自动提交、也不再等待。
  7. 补测试：
     - 未选模式时，在 Git 项目里派写入子任务，子任务和父任务共用目录、能读到父任务未提交的文件、按方案 B 串行，结束后宿主不提交。
     - 独立工作副本模式：从 HEAD 创建、不含未提交的改动，主目录不出现自动提交；主目录有未提交文件时回执带提示。
     - 同一仓库里另一个任务开着 Codex 目标或回合正在进行时，派两种模式的子任务都会立即开始准备，那个任务的输入不受影响。
     - 用 `wy_send` 让同一个共用目录子任务做第二轮审查时，沿用原会话，仍然串行。

### G4（低，直接修）：新建任务时，主进程直接采用渲染进程传入的工作目录

- 代码：`controller.ts` 的 `agentTasks.create` 把 `req.cwd` 原样交给 `AgentTaskService.create` 写入 `tasks.cwd`，没有核对它是否是 `dirId` 对应的项目目录，也没有核对 `dirId` 是否属于 `projectId`。旧任务流程（`tasks/task-service.ts`）和同一文件里的 `openHomeTerminal` 都是按 `dirId`＋`projectId` 从 `project_dirs` 取路径。
- 影响：目前只有首页一处调用，传入的是正确路径，没有用户可见问题。但任务工作目录决定 Agent 的运行目录、写入队列的目录身份和链接授权根，这条边界应由主进程保证。
- 修改：RPC 创建时要求 `projectId`、`dirId`，按 `openHomeTerminal` 的写法查询 `project_dirs JOIN projects`（未归档），用查到的 `realpath` 作为 `cwd`，忽略渲染进程传入的 `cwd`。内部创建子任务的路径不受影响。补测试：`cwd` 与 `dirId` 不符、`dirId` 不属于该项目、项目已归档，三种情况分别拒绝或纠正。

### G5（中，讨论 G1 时补充发现，已确认）：侧栏归档区列的是旧终端任务，新任务归档后在界面上找不到

- 代码：
  - `sidebar-projects.tsx` 底部的“未关联项目”和“已归档任务（N）”两个分组读取旧任务的 `tasksStore`（`rpc.tasks.list`），没有判断 `agentTasksStore.enabled`。新任务区模式下，这里仍列出旧终端任务；点开进入旧终端任务页（`sidebar-tasks.tsx` 的 `TaskRow`），右键菜单是旧任务的重命名、归档和取消归档。这违反 R10 的“侧栏及任何入口都不再列出旧终端任务，也不设旧任务分组或只读查看页”。

**A78 删除项目（G1）**
- 关联：R10“删除项目”；原型中的项目删除确认框和拒绝状态。层级：U＋I＋A。
- 数据：P1 中准备一个项目，含进行中和已归档的新任务、一对父子委派（其中一个独立工作副本）、差异记录、业务请求记录和附件；另准备一个有运行中任务的项目，和一个有待批准请求的项目。
- 步骤：通过界面打开删除确认框，核对文案后确认删除；对另外两个项目重复操作。
- 预期：
  - 确认框显示任务数（含已归档）、不可恢复、保留路径和“改用归档项目”的提示。

**A79 已归档任务：设置页、只读查看、恢复、撤销（G5）**
- 关联：R10“新任务的归档与恢复”；原型中的设置页“已归档任务”、只读视图和归档提示。层级：U＋I＋A。
- 步骤：
  1. 归档一个任务后立即点“撤销”。
  2. 再次归档，到设置页查看列表。
  3. 点开该任务只读查看，尝试发送、插话、切换、委派。
  4. 点“恢复”，然后发一条消息。
  5. 归档一个有已完成子任务的父任务，然后恢复。
  6. 单独归档一个子任务，然后恢复。
- 预期：
  - 撤销后任务回到原位置。
  - 设置页按项目分组列出已归档任务，没有删除按钮。
  - 只读视图能看到完整时间线和差异，所有写入操作都被拒绝。
  - 恢复后任务回到原项目下面，发消息时沿用原来的原生会话。
  - 父子任务一起归档、一起恢复；单独归档的子任务恢复后回到父任务下面。
  - 侧栏始终没有旧任务分组。

**A80 至 A85：多 Agent 协作场景（G3，用户 2026-11-18 讨论确认）**

公共设置：
- 层级 U＋I＋R＋A。宿主路由、串行和提交用确定性夹具做 U＋I；“Agent 按自然语言选对模式、用 `wy_send` 往返”用真实模型做 R；模式标识、任务关系卡和差异归属用打包 App 做 A。
- 父子执行器至少覆盖两组：父 Claude（C1）派子 Codex（X1），以及反过来。共用目录类场景（A81 至 A84）除 P1 Git 外，再选 P2 SVN 或 P3 普通目录中的一种各跑一次。
- 每条都核对：用户分支上没有出现宿主的自动提交（共用目录模式下子任务结束也不提交）；同一仓库里另一个独立任务正在进行回合时，不受影响。
- 判定方法：在父任务未提交的文件里放一个唯一标记（比如在设计文档里写一个独有的词或版本号），用它来证明子任务看到的是未提交的内容，而不是 HEAD。

| 用例 | 场景 | 步骤要点 | 明确预期 |
| --- | --- | --- | --- |
| A80 | ① 并行开发互不相关的功能 | 主目录有与子任务无关的未提交文件。用户对父 Agent 说“开两个独立工作副本并行做功能 X 和 Y”，父任务同时继续修改主目录；子任务完成后由父 Agent 合并 | 两个子任务都在独立工作副本里，从 HEAD 创建，不含主目录的未提交文件；回执提示未带入的文件数；与父任务并行；主分支 `git log` 在合并前没有宿主提交；子分支各有宿主提交；合并按 A67 核对通过；任务关系卡显示“工作副本 · 分支” |
| A81 | ② 审查未提交的设计 | 父任务写好设计文档但不提交，派两个审查子任务：一个用 X1（不可信只读，按写入处理），一个用 X2（可信只读） | 两个子任务的审查意见都引用了唯一标记。X1 走共用目录，在父任务这一轮结束后才开始；X2 是只读子任务，在主目录与父任务并行。都没有产生提交 |
| A82 | ③ 接着半成品继续写 | 父任务新建一个接口文件但不提交，里面有唯一的符号名；派子任务“基于这个接口实现模块” | 子任务的代码使用了这个符号；在主目录里类型检查或构建通过；子任务结束后宿主不提交；父任务恢复时收到重读提示，并列出子任务改过的文件 |
| A83 | ④ 检查当前改动 | 父任务做一个未提交的修改，让某个测试从通过变成失败（或反过来）；派子任务“跑测试并报告结果” | 子任务报告的测试结果与未提交的状态一致，与 HEAD 上的结果相反，证明它测的是当前代码；没有产生提交 |
| A84 | ⑤ 审查后直接修改 | 父任务的设计文档不提交，派子任务“审查并直接修正问题” | 修改直接出现在主目录；差异归到子任务的那个区间；父任务恢复时收到重读提示和文件清单；没有产生提交 |
| A85 | 设计、多轮审查、再开发（用户的实际工作流） | ① 父任务 A（C1）写设计，不提交；派 B（X1，共用目录）审查。② B 的结果送回后，A 修改，用 `wy_send` 让同一个 B 再审，重复到第 3 轮 B 回复“没有问题”。③ A 派 C 开发：先用共用目录；再做一个分支，A 不提交设计就要求 C 用独立工作副本，看到回执提示后先提交设计再重新派出 | B 的每一轮都沿用原会话，并引用前几轮的意见；每轮 A 和 B 交替写入，从不同时写；共用目录的 C 能直接读到设计；独立工作副本分支在 A 未提交时，回执明确提示“主目录有 N 个未提交文件，没有带进子任务”，A 提交后重新派出的 C 能读到设计；整个过程中，宿主只在工作副本模式下往子分支提交 |

补充一条负向检查，可以并入 A80 或 A85：父 Agent 没有指定模式时，默认是共用目录；用户用自然语言要求“开独立工作副本”时，Agent 会传入独立工作副本的参数（R 层）。
