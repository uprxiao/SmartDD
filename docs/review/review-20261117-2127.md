## 2. 问题清单

### 高优先级

### FR01：旧运行退出会撤销用户后来发出的停止，自动发送队列

关联 NR04；阶段 2；违反 R01／R02 的停止语义及技术方案 §9。

代码：[退出订阅](../../src/main/core/agent/agent-task-service.ts#L70)、[等待旧运行退出](../../src/main/core/agent/agent-task-service.ts#L253)、[停止](../../src/main/core/agent/agent-task-service.ts#L271)。

`blockedByClosing` 只记 taskId。收到 `run.ended` 时直接删除 `paused`，没有判断等待退出之后是否又发生了用户停止。

反例顺序：首轮完成 → 运行发出 `unusable`，但进程尚未退出 → 新输入保留并等待退出 → 显式调用停止 → 旧运行退出。结果新建了第二个执行器实例，排队输入从 `accepted` 变成 `started`，任务重新显示 `working`。这是服务层顺序注入验证；也覆盖停止请求已从尚未刷新的界面发出、稍后才到达服务的情况，不声称已完成该顺序的真实 UI 复验。

证据：[F02](evidence-20261117-2127/new-core.test.ts#L95)、[观察值 F02](evidence-20261117-2127/new-core-observations.json)。旧进程真实退出前保留占用的修复应保留；只允许自动解除“等待该运行退出”这一原因，不能解除后来新增的用户停止。可复用现有 `stopSeq` 核对自动恢复资格。

### 中优先级

### FR02：整体容量仍未守住，中文正文范围也按字符而非字节切分

关联 NR06；阶段 2；与技术方案 §3.1、A45 的明确容量合同不一致。

代码：[预览与范围读取](../../src/main/core/agent/agent-task-service.ts#L29)、[快照](../../src/main/core/agent/agent-task-service.ts#L331)、[事件页](../../src/main/core/agent/agent-store.ts#L377)、[即时通知](../../src/main/core/agent/agent-store.ts#L38)。

快照只给 `items` 分配剩余预算；`requests`、`draft` 等基础部分可以先超过预算，随后仍至少加入 16 KiB 的条目预算。`rangeOf` 的 `128 * 1024` 实际限制 UTF-16 字符数；事件分页只限条数，即时事件则直接转发尚未有界化的原始 payload。

| 反例 | 实测结果 | 合同上限 |
| --- | --- | --- |
| F01a：同轮 3 个各 90 KiB 的待处理计划 | 快照 278,881 bytes | 响应 262,144 bytes |
| F01b：合法的 255 KiB 草稿＋20 KiB 用户消息 | 快照 282,708 bytes | 响应 262,144 bytes |
| F01c：中文请求正文第一段 | chunk 393,180 bytes；响应 393,225 bytes | 正文段 131,072 bytes；响应 262,144 bytes |
| F01d：20 条各约 20 KiB 的事件 | 事件页 413,783 bytes | 事件页 262,144 bytes |
| F01e：40 KiB 计划的即时通知 | payload 41,311 bytes | 事件 32,768 bytes |

证据：[F01a–c](evidence-20261117-2127/new-core.test.ts#L70)、[F01d–e](evidence-20261117-2127/new-core.test.ts#L152)、[观察值](evidence-20261117-2127/new-core-observations.json)。当前 `wiring` 将订阅事件原样交给 Electron 事件出口，因此 F01e 不是只观察到一个不会出进程的内部大对象。

应按最终序列化后的整份响应／事件计预算，所有字段都纳入；需要引用或分页时保留可恢复的全文与明确状态，不能靠丢弃草稿或关键请求内容解决。范围游标与 chunk 必须按真实字节合同实现，并处理中文、emoji 和 JSON 转义开销。

### FR03：Codex 恢复原生默认时省略 model，实际继续沿用上次显式模型

关联 NR05；阶段 2 的模型选择接口；违反 R03“默认模型是选择状态、恢复执行器默认”的合同。

代码：[默认值解析与派发](../../src/main/core/agent/agent-task-service.ts#L175)、[Codex 打开响应](../../src/main/core/agent/drivers/codex-app-server.ts#L66)、[turn/start](../../src/main/core/agent/drivers/codex-app-server.ts#L87)。

托管供应商有明确 `launch.model` 时，本轮修复有效；原生登录的默认解析可以为空。此时“恢复默认”传到驱动的是 `undefined`，驱动省略 `model`。Codex 的模型覆盖会延续到后续回合，省略字段并不恢复默认。

本机 Codex 0.169.0 生成的[原生协议](evidence-20261117-2127/Codex-0.169.0-TurnStartParams.txt)明确写模型覆盖适用于本轮及后续轮次；[线程打开响应](evidence-20261117-2127/Codex-0.169.0-ThreadStartResponse.txt)有解析后的 `model`，当前驱动只读取 threadId。

按该协议构造的有状态对端得到：选择 `默认 → explicit-other → 默认`，原生有效模型却是 `native-default → explicit-other → explicit-other`。这是实际服务／驱动的协议替身验证，没有宣称进行了真实模型调用。证据：[F03](evidence-20261117-2127/new-core.test.ts#L106)、[观察值 F03](evidence-20261117-2127/new-core-observations.json)。

需要可靠解析并保存默认选择，或采用已验证的重开／恢复路径显式恢复；不能把空字段当作重置。初次打开时用户指定的模型也不能反过来被记录成“执行器默认”。

### FR04：长用户消息、计划和工作正文缺少全文入口；复制计划只复制预览

关联 NR06；阶段 2；违反 R01 的完整时间线、计划复制／下载及 A45 的恢复要求。

代码：[服务预览](../../src/main/core/agent/agent-task-service.ts#L37)、[条目渲染与计划操作](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L64)、[工作过程正文](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L100)。

超过 24 KiB 的 payload 会变成截短预览。界面仅给 `assistant_message` 添加 `FullBody`；`user_message`、`proposed_plan` 及工作过程正文仍直接使用预览。计划的“复制”“下载”同样直接读取 `p.plan`，没有先取得全文。

组件反例使用约 30 KiB 的消息／计划：尾部不可见，找不到全文入口；实际点击“复制”只写入 **4,000 个字符**，原计划为 **30,742 个字符**。预览中的 `truncated` 标记也没有在这些行提示用户。证据：[F06a–b](evidence-20261117-2127/new-ui.test.tsx#L47)、[真实按钮交互 F06c](evidence-20261117-2127/new-ui.test.tsx#L87)、[观察值](evidence-20261117-2127/new-ui-observations.json)。下载截短的判断来自按钮使用同一 `p.plan` 的源码，本轮没有另做系统下载验收。

应让所有被预览的条目能读取其相应全文；复制／下载取得完整 plan 后才能完成，失败应明确提示。不能只把当前只提取 `.text` 的 `FullBody` 原样加到计划上。

### FR05：初始化竞态仍会漏载已保存草稿，或清掉用户刚粘贴的附件

关联 NR07；阶段 2；违反 R01 的按任务草稿保存恢复和技术方案 §3.1。

代码：[reload](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L240)、[初始化快照](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L260)、[附件编辑](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L317)。

有两条遗漏：

- 更新的快照先返回时，`reload` 只更新 `snap`，不初始化草稿与 `draftRev`；旧初始化快照随后被水位检查丢弃。反例中服务端已有 `saved server draft`、revision 7，用户没有编辑，编辑器最终仍为空。
- `editedRef` 只在文字 `onChange` 中设置。用户先粘贴附件，随后同水位初始化快照返回时，仍被视为未编辑，`setChips(saved)` 会清空新附件。菜单插入、移除附件也需要纳入本地编辑判定。

证据：[F07a–b](evidence-20261117-2127/new-ui.test.tsx#L61)、[观察值](evidence-20261117-2127/new-ui-observations.json)。旧反例“用户已经输入文字后，旧水位不能覆盖”现在通过，但不覆盖这两条路径。

应由首份被采纳的最新快照完成一次草稿／修订初始化；所有本地输入编辑共用保护，后来的快照不能覆盖本地修改。

### FR06：模型／档位修订变化后，同一已接受输入的重试拿不到原收据

NR01 的覆盖图片原问题可关闭；本项是幂等接口的另一处边界。阶段 2；与技术方案 §5、`acceptTurn` 的重复提交合同不一致。

代码：[submit 前置校验](../../src/main/core/agent/agent-task-service.ts#L115)。

虽然幂等查询已经移到冻结之前，但仍位于 `expectedSelectionRevision` 检查之后。反例先用修订 1 接受输入，再修改模型到修订 2，然后重发原请求：返回“模型或权限已变化，请确认后再发送”，没有返回已经接受的 turnId。该请求本来只需要查询上次投递收据，不是按旧权限开始一次新执行。

证据：[F04](evidence-20261117-2127/new-core.test.ts#L125)、[观察值 F04](evidence-20261117-2127/new-core-observations.json)。这是原请求重传的服务合同验证，不声称当前组件一定会重复使用旧修订；当前组件重试可能读取到更新的修订，不能代替接口自身的幂等保证。

应保留任务身份和访问校验，随后先按 taskId＋clientInputId 返回现有收据；只有真正的新输入才检查当前选择修订并冻结附件。

### FR07：同一目标命令轮次中，兼容文字仍能覆盖已到达的 active_goal 原生事实

关联 NR13；阶段 2；与“原生目标事实为准”及本轮回执“SDK active_goal 仍优先”的说法不一致。

代码：[active_goal 分支](../../src/main/core/agent/drivers/claude-sdk.ts#L150)、[文字确认分支](../../src/main/core/agent/drivers/claude-sdk.ts#L159)。

限制到 `/goal` 命令轮次及首段回复，已经修好普通回答误触发目标的问题；但收到 `active_goal` 后没有取消或降级 `goalCommandTurn` 的兼容解析。顺序注入：宿主发送 `/goal` → SDK 原生事实设为 `native canonical target` → 首条兼容文字为 `Goal set: other target`。最终目标被改成 `other target`。

证据：[F05](evidence-20261117-2127/new-core.test.ts#L134)、[观察值 F05](evidence-20261117-2127/new-core-observations.json)。这是冲突事件顺序的驱动验证，未以真实模型复现该冲突，不将它描述为常规成功流已经发生。

文字确认只能作没有结构化事实时的后备；同轮已得到结构化事实就不能再让兼容文字覆盖，较晚的结构化事实仍应更新状态。保留现有 CLI 兼容路径，不改用户确认的目标规则。

### FR08：审批 reviewer 能力门禁只覆盖普通发送，/review 仍能绕过

关联 NR09 的能力门禁部分；阶段 1、2；违反 R11、技术方案 §7.1／§7.2 的能力与档位保证。

代码：[普通发送的门禁](../../src/main/core/agent/agent-task-service.ts#L241)、[命令入口](../../src/main/core/agent/agent-task-service.ts#L184)。

普通 `pump` 在请求批准／帮我批准下检查 `approvalsReviewer`。`command('review')` 则直接 `ensureRun → runs.command`，没有同一检查。

反例使用当前能力表允许基础运行、但 reviewer 不可用的 Codex 0.167.1：普通发送已正确拒绝；同样的 `ask` 任务执行 `/review`，却实际调用了驱动的 review 命令并返回成功。证据：[F08](evidence-20261117-2127/new-core.test.ts#L142)、[观察值 F08](evidence-20261117-2127/new-core-observations.json)。没有据此声称真实旧版发生了未批准写入；已证明的是宿主没有执行自己声明的能力门禁。

应把会开始原生工作的入口纳入一致的档位／能力预检，不能仅修普通文字发送。对 native review／compact 等入口同时核对当前选择的生效方式，避免借用旧运行配置；本轮具体红测是 reviewer 缺失仍启动 review。
