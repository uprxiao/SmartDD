## 2. 问题清单

### RF01 · 中 · 目标状态没有按任务隔离，清除 A 会解锁 B（关联 AR10）

- **位置**：[M14Extras.jsx][EXTRAS] 第 9–17 行。`GOAL_STATE` 是全局对象，键为 `e.agent + ':' + e.objective`；没有 taskId、bindingId 或目标身份／修订。`goalLock(scenario)` 与 `GoalRow` 都读取这个键。
- **反例**：准备两个不同 taskId、不同 goal id 的任务 A/B，执行器相同、目标文字相同，初始都 active。调用 A 的实际“清除”处理函数后，A/B 的 `goalLock` 同时变成 null；B 模型选择器中其他执行器的禁用数量变为 **0**。B 的目标并未被用户清除。
- **影响**：切换限制本身在单任务正常，但普通的“两个任务设同一目标”就能使另一任务错误解除锁定；重新进入 B 时还会把目标显示成已清除。不能只用单个演示任务“置灰 4 个／清除后 0 个”证明隔离正确。
- **证据**：[真实组件处理函数结果](evidence-20261117-1101/cross-artifact-probes.json)，`goals-across-tasks`；[合同断言](evidence-20261117-1101/recheck-assertions.json)，`clearing-A-keeps-B-locked` 失败。此为合成原型缺陷，不宣称生产目标接口已实现或发生跨任务修改。
- **建议**：目标状态归属具体 task／binding／目标身份与修订，向 GoalRow、goalLock 及锁定视图传递同一份状态。新增 A14/A69 的双任务同文目标反例，保留“同执行器换模型允许、委派不受限”的决定。

### RF02 · 中 · Codex 请求批准的研究合同仍是旧参数（关联 AR01）

- **位置**：[runtime-contract.mjs][RUNTIME] 第 11–16 行：`ask` 仍为 `untrusted + user + readOnly`，同时保留 `edits` 入口；但[现行方案 §7.2][T]、R08 和首页快照已经改成用户确认的 `on-request + user + workspaceWrite`，产品只留三档。
- **实测**：调用当前导出的 `turnParams({permission:'ask'}, [], {})`，得到 `approvalPolicy:'untrusted'`、`sandboxPolicy.type:'readOnly'`。原型两个入口的菜单与快照已经一致，**没有再发现上一轮的首页／任务页列表差异**；剩余问题在仍被现行验证链引用的研究函数与测试。
- **影响**：当前 `runtime-contract.test.mjs` 仍可全部通过，因为其权限断言主要检查 reviewer，没有核对完整的当前档位合同。后续不能把这组通过结果当成 T1.3 新参数已验证。
- **证据**：[`research-permission-params`](evidence-20261117-1101/cross-artifact-probes.json)；[现行政策断言](evidence-20261117-1101/recheck-assertions.json)，`research-ask-agrees-with-T1.3` 失败。
- **建议**：同步现行候选代码和断言；旧的参数／录制作为旧输入的历史事实保留。明确任何内部 `edits` 能力的适用范围，不把它继续列作现行产品档位。后续真实审批验证须选择会触发提升权限的操作，不能把工作区内本来允许的编辑误当成“应该弹审批”。

### RF03 · 中 · 新请求分类表仍与旧主表、数据／接口合同冲突（关联 AR05）

- **已改对**：[方案 §8.1][T] 第 274–278 行的新分类表明确：返回 awaiting_user 的宿主业务请求归 task／发起 binding，普通回合结束、owner 退出和切换时保留；结果送任务的新一轮。A60 也已区分原生阻塞请求和宿主业务请求。
- **仍相反的规则**：同节第 263、265、266 行的原主表仍要求“原 run／generation 有效”“结果送回原 run”“run 失效立即退役”；§2 `agent_requests` 仍以完整 run／generation scope 作统一归属，§3 又统一要求验证这组运行身份。需求 R02 仍写“待处理请求未排空前不释放写入资格”；§9 末尾还保留“四种终态下所有请求终结”的总括句。验证计划 E12 也仍把 run 失效统一写成退役。
- **具体冲突**：请求已返回 awaiting_user，父回合完成、owner 因方案 B 交槽退出，再批准。按新增表必须保留并由宿主执行；按原表／通用运行校验必须退役。当前文档仍能导出两种相反实现。
- **建议**：把新增分类真正合并进现行主表、R02 的排空边界、请求字段／回应契约及 E12。区分不可变的“发起 run 来源记录”与批准后执行所需的当前授权／执行身份；保留对用户停止、撤销、内容／账号变化和旧原生回应的拒绝。不要通过省略认证来实现跨 run 保留，也不要要求旧 owner 一直活着。
- **关闭边界**：先完成设计与生成用例的一致性，明确普通结束／退出／切换／用户停止／重启的判据；E12 服务改造和真实 App 仍可如实未执行。本项没有要求现在接入生产代码。
