## 1. 评审结论

**方案方向可行，目标与改造范围覆盖较完整；当前可指导技术预研和需求评审，尚不足以作为全面生产开发的规格基线。建议补齐详细设计后再次评审。**

R0.1 有 17 个章节、16 项需求、6 组兼容实验和 17 组验收场景，已覆盖统一 UI、双 Agent、配置、能力、历史、授权及迁移等主要问题。其主要不足在于关键内容仍为“需要验证、建议增加、具体待定”，尚未形成开发者可以共同遵循的字段、状态、时序及失败处理契约。

本次归纳 **8 项需收口问题：5 项高优先级、3 项中优先级**。“高优先级”表示在对应模块正式开发设计前应明确，不表示现有应用已被证实存在同等严重的运行缺陷，也不与 M13 的“P1 门槛”阶段混用。

| 使用目的 | 当前能否支持 | 依据 |
| --- | --- | --- |
| 说明用户目标、改造价值及主要影响范围 | 可以 | 目标、现状、模块与兼容边界已具备 |
| 安排隔离的兼容实验和技术调研 | 可以，需补实验输入与判据 | 已列 A1–A6，尚未指定版本组合与可执行判据 |
| 直接拆给多个开发者实现并集成 | 不充分 | 公共契约、状态权威、存储与生命周期尚未定案 |
| 证明旧功能不会回归 | 不可以 | 尚无逐条兼容清单、权威用例映射或执行证据 |
| 批准默认入口切换或正式发布 | 不可以 | 关键实验、原型、正式用例与验收均未完成 |

## 3. 具体发现与补齐要求

### RV-01［高］能力生效规则需要按对象定案

**依据。** 原稿 §7.3 将“能力选择、冻结版本、项目启停”合并描述，第 302 行还提出按适配器能力决定实时刷新或恢复后生效。但现行 [M13 需求](../里程碑/M13_应用Skill与MCP插件化重构/需求.md)已有不同对象的明确规则：

- 第 135、149 行：经宿主转发的插件调用在更新后使用新版本，在途调用按旧版完成。
- 第 148–150 行：新建／恢复加载最新状态；运行中的 Skill／MCP 保持启动时状态；切换连接时运行中任务继续使用原连接。
- 第 207 行：独立纳管的 Skill／MCP 不提供逐项目启停，项目自带能力仍限定在来源项目。

**影响。** 如果开发者统一采用“可热加载就刷新”或“整个运行固定全部版本”，均可能偏离既定规则。原稿虽然引用 M13，但缺少对应对象的映射，不能把规则选择交给适配器。

**需要补齐。** 增加“插件包、在途调用、Skill、MCP、连接、项目权限”生效矩阵。逐项明确创建、恢复、运行中启停、更新、卸载和切换连接的结果；适配器能力只决定如何实现，不改变产品规则。明确本次承接已交付行为还是 M13 最终规则，以及未实施部分的阶段分工。

**收口证据。** 至少覆盖运行中更新／停用插件、运行中变更 Skill／MCP、切换连接和恢复任务，验证各对象按不同规则生效。

### RV-02［高］真实进程与能力运行身份尚未接通

**依据。** 原稿明确不能伪造 ptyId，方向正确；但现有运行体系的依赖深于终端 UI：

- [TaskCapabilityLaunch](../../src/main/core/tasks/capability-lifecycle.ts)要求 `beforeSpawn`、`spawned(pid)`、`exited`、`stop` 等回执。
- [任务启动](../../src/main/core/tasks/task-service.ts)在约第 598–600 行检查预留 ptyId 并交付真实 PID。
- [运行登记](../../src/main/core/applications/run-registry.ts)约第 333–368 行要求先登记启动窗口、再绑定 PID 与启动身份，CLI 退出会触发运行撤销；第 401 行的输入上下文仍按 taskId／ptyId 查询。
- [能力启动器](../../src/main/core/applications/task-capability-launcher.ts)第 336–340 行在这些回执中启用观察与清理。

**影响。** 只用 runId 替换界面中的 ptyId，会留下未激活运行、未登记的 Agent 进程或不能释放的资源占用；SDK 回复完成、连接关闭与真实进程退出也不能互相替代。

**需要补齐。** 为每种运行方式写出具体时序：预约资源 → 登记启动窗口 → 启动真实进程 → 绑定身份 → 激活能力 → 绑定原生会话 → 开始回合 → 中断／关闭 → 收到退出回执 → 撤销与释放。明确：

1. Claude SDK 的真实子进程由哪个宿主入口捕获，如何在锁定版本中取得启动与退出回执。
2. Codex 去掉 TUI 后，app-server 如何成为实际运行所有者，原 CLI 记录及后端记录如何调整。
3. 正常回合结束、后台子任务仍运行、进程退出、连接中断、应用退出各自处理什么。
4. 启动取消、启动后登记失败与身份未知时，何时保留占用，何时允许释放。
5. CLI 与聊天模式如何共同实现可信运行上下文，哪些旧接口迁移、哪些保留。

**收口证据。** 覆盖准备期取消、进程先退出后附着、附着失败、连接中断但进程仍在、重复关闭及退出后资源清理；不能通过弱化原所有权校验让新路径通过。

### RV-03［高］需要分别设计三条审批／授权链路

**依据。** 原稿 §8.2 已识别真实用户输入风险，但尚未定义新凭据的生成与消费接口。当前代码存在不同机制：

- [NativeUserInputs](../../src/main/core/applications/native-user-inputs.ts)第 8–11 行只声明终端／启动参数两类运输；保留及最新性判定还依赖内存编辑器和输入序号。
- [NativeUserMessages](../../src/main/core/applications/native-user-messages.ts)将宿主凭据与原生消息及版本能力对应。
- [邮件授权](../../src/main/core/applications/mail-user-authorizations.ts)核对输入序号、运行、连接与策略等信息。
- [插件写审批](../../src/main/core/applications/plugins/write-approvals.ts)有自己的待处理请求、审阅回执、内容哈希及过期规则，仍使用终端目标。
- M13 第 323 行规定：完全访问仅影响 Agent 内置工具；插件写操作仍由宿主审批。

**影响。** 一个通用的“批准”按钮不能替代全部链路。仅记录聊天消息无法证明模型实际接收到用户原话；仅响应 SDK 许可也不能替代宿主对插件或邮件的审批。

**需要补齐。** 分别定义：

| 链路 | 要明确的契约 |
| --- | --- |
| Agent 原生工具审批 | 原生请求类型、可用决策、回调／协议响应、原生已解决事件、超时与取消 |
| 宿主插件／业务操作审批 | 沿用哪个服务、如何把终端目标改为运行目标、审阅回执与内容版本如何绑定 |
| 用户原话驱动业务授权 | 原文、投递上下文、实际发送内容、原生接收证据和输入序号如何关联 |

区分“已保存、开始提交、原生接收已确认、结果未知”，明确在哪个阶段生成何种凭据。恢复历史、系统补充和工具输出不生成用户操作权限；完全访问模式不能取消宿主既定审批。

**收口证据。** 同样文本重复提交、上下文追加改变发送内容、拒绝插件操作、完全访问下的插件写入、重载 UI 后过期审批、旧历史被导入后尝试授权，均有可判定结果。

### RV-04［高］公共接口、消息协议和存储约束仍缺规格

**依据。** 原稿第 208 行的接口是职责示意，相关输入输出类型未定义；§9.2 只有事件种类，§9.3 只有数据类别，§9.4 提出幂等但没有数据库约束或处理时序。当前 [任务 RPC](../../src/main/core/tasks/controller.ts)主要提供创建／打开等操作，[TaskView](../../src/shared/tasks.ts)也仍以 ptyId 表示运行信息。

**影响。** 前后端可能对“提交成功”“回合完成”“消息增量”的含义各自理解。若先调用执行再订阅事件，可能漏掉快速返回；若同时追加文本增量和完整回复，可能产生重复内容。没有持久化唯一约束时，重启后的重试也无法由内存 Map 保障。

**需要补齐。** 在正式技术方案中提供以下共同契约：

1. 发送、停止、关闭、审批、历史分页、快照订阅等 IPC 的请求／响应 Schema、错误码及可信发送者检查。
2. 带区分字段的事件与内容块类型；哪些字段必填，哪些事件允许没有 turnId／itemId。
3. 原生请求 ID 与宿主请求 ID 的映射、范围及有效期。
4. 客户端先取快照还是先订阅、游标如何交接、漏号如何补取、重复及过期事件如何处理。
5. 文本增量、完整消息、工具项目和历史导入的合并与去重规则。
6. 最小表结构、主外键、索引、消息提交唯一约束、格式版本及删除／保留规则。
7. 提交记录与派发过程的持久化边界；进程退出后“确定未提交／可能已提交／已确认”如何恢复。

**收口证据。** 同一提交在客户端重载、主进程重启和确认回包丢失后不盲目重复派发；快速结果不丢事件；重放事件和导入历史不重复显示消息。

### RV-05［高］旧会话恢复需要完整决策矩阵

**依据。** 原稿 §10 主要按“历史是否可读、是否验证恢复”分类，§6.1 强调相同配置根。但 [M13 需求第 328–329 行](../里程碑/M13_应用Skill与MCP插件化重构/需求.md)还要求：

- 供应商地址、Key 或登录来源变化后显式重新选择，不静默换来源。
- 允许按规则选择同一 Agent 的另一智能体，并携带旧会话；携带失败不能用新会话代替。
- 恢复最后实际使用的模型，不在新选择允许列表时才按规则提示后使用默认模型。
- 恢复时加载最新插件与连接，保留创建时的权限档位。

当前 [TaskService.openOnce](../../src/main/core/tasks/task-service.ts)约第 272–274 行仍沿用原配置根，是当前实现与 M13 目标需要明确分工的例子。笼统要求“原配置根不变”不足以覆盖跨配置目录恢复。

**影响。** 最常见的改 Key、改供应商地址、删智能体、更换默认模型、配置根迁移，都需要开发者自行补业务规则，存在丢上下文或错用账号／模型的风险。

**需要补齐。** 增加恢复决策表，输入至少包括原智能体是否存在、来源身份修订、目标 Agent、原／目标配置根、历史状态、最后模型、当前允许模型、原权限、当前能力和资源占用。逐项输出：允许恢复、需确认、需复制历史、仅可查看或拒绝，并明确数据库与文件操作顺序、目标同名文件冲突及失败后的回滚。

同时明确本次是否负责落实尚未实施的 M13 恢复能力；如果由 M13 先完成，本方案应以其实现为前置，避免扩入未安排范围。

**收口证据。** 原 Key 被替换、默认模型改变、最后模型被取消勾选、同一 Agent 跨配置目录、目标历史同名、复制中断及两个入口竞争恢复，分别有确定结果。

### RV-06［中］兼容矩阵与配置专项实验尚未落地

**依据。** 原稿阶段 A 正确列出了待验证事项，但未给出具体候选 SDK 版本、CLI 版本、平台、登录类型、供应商及能力组合。当前 Codex 私有服务路径固定约束与最新官方文档之间也存在版本差距。

Claude 的项目 settings 隔离、CLAUDE.md、Skill／MCP 加载组合是原稿已识别的关键未决项。官方参考将设置来源与指令加载关联，实际行为仍须按锁定版本实验确认。[Claude SDK TypeScript 参考](https://code.claude.com/docs/en/agent-sdk/typescript)

**影响。** 无法明确“首批支持 Claude／Codex”具体包含哪些配置，也不能确定兼容入口只是临时安排还是某些配置长期必须保留的路径。

**需要补齐。** 建立矩阵：平台／架构、SDK、原生程序、认证来源、供应商协议、模型、配置根、设置加载、工具、审批、图片、能力交付、恢复。每项标注代码已实现、实验已验证、待实验或不支持，并附证据。不要用“可读凭据文件”代表认证方式必然适用于该程序化入口。[Claude SDK 认证与使用说明](https://code.claude.com/docs/en/agent-sdk/overview)

作为实验方案，需要先补候选版本、输入夹具、前置条件和通过／失败判据；作为正式开发基线，需要得到关键行的实际结果。两者不能混写。

### RV-07［中］失败、模式切换及回退需要状态决策表

**依据。** 原稿提出“停止生成”“关闭会话”“结果待确认”“兼容入口”“功能开关回退”，但未定义每种状态允许哪些操作。

例如：正在等待原生批准时点击停止，原请求何时过期；聊天提交可能已送达时能否切 CLI；UI 重载与主进程重启分别怎样处理；关闭聊天开关是否影响正在运行的任务；由新聊天模式产生的会话能否反向用 CLI 继续，均需定案。

**影响。** 不同失败阶段可能被统一解释为“重试”或“切终端”，造成双实例、重复输入或未确认的旧请求继续有效。

**需要补齐。** 对“准备中、提交中、执行中、等待批准、取消中、结果未知、进程退出、运行关闭”建立操作矩阵，逐项给出状态转换、用户文案、可用按钮、原生动作、持久化动作和允许重试条件。确认模式切换前需要核验原实例已结束，并在应用版本回退时规定数据库兼容与新数据保留方式。

**收口证据。** 断连、停止无回执、关闭期间再次打开、原生响应迟到、开关关闭时仍有运行、聊天会话反向恢复到 CLI，都有明确判据。

### RV-08［中］验收、UI 与性能描述尚不足以交付判断

**依据。** 原稿 §13 已说明 V01–V17 是场景组，当前没有前置、输入、步骤、明确预期及既有权威用例映射。§4 定义了区域，但排队／中途引导、模型与权限切换、审批堆叠、滚动锚点、草稿切换及快捷命令仍有选择空间；“有界缓冲”“长历史可用”也缺少量化条件。

**影响。** 开发者可以实现出不同但都声称符合原稿的交互；测试方无法客观判断何时全部完成，或哪些旧功能已通过回归。

**需要补齐。**

1. 将需求映射到页面状态与逐条正式用例，列出实际前置、输入、步骤和可判定结果。
2. 以当前已交付用例建立兼容清单，区分直接复用、调用接口改变需补测、尚未交付及本次不适用。
3. 定案常用 CLI 命令迁移表，以及输入／停止／审批／历史等页面状态；用户决定项和可由实现方确定的细节分别列明。
4. 约定长历史、长工具输出、并发任务等测试规模，定义分页大小、输出上限、缓冲上限及交互性能指标；新指标须标为拟议目标，不能冒充实测结果。
5. 将阶段 C–E 拆成有依赖、交付物、验证文件和完成条件的工作包，优先确定公共契约后实现界面。

## 4. 补充的实现注意事项

以下用于补充详细技术方案，不单独增加发现数量：

- **现有 Codex 控制客户端适用短期控制流。** [codex-private-server.ts](../../src/main/core/applications/codex-private-server.ts)第 124–139 行拒绝交互请求，并对连接累计响应设置 8 MiB 预算。新增聊天客户端应重新定义单帧、工具输出及缓冲限制；若直接复用这段累计预算接收全部流式内容，长会话可能被终止。原稿已有“不能直接当完整聊天客户端”的提醒，详细方案应把这些具体边界列出。
- **Agent 原生请求并非只有二选一批准。** Codex 官方协议区分命令、文件、权限、用户提问及 MCP elicitation 等请求；实际接入以固定版本支持的类型为准，客户端不能将所有响应都压缩为布尔值。[app-server 请求与审批](https://learn.chatgpt.com/docs/app-server)
- **流式文本与最终文本需合并。** 保存完整回复时要更新同一稳定项目，避免把最终消息再次作为新回复追加。
- **消息持久化增加数据处理范围。** 需规定显示用正文、工具输出、脱敏诊断、附件引用与原始载体分别保存哪些内容、保留多久、如何随任务删除；不把含运行环境或凭据的诊断直接作为聊天历史落库。
- **T3 的本地链接依赖同级目录。** 原稿中的参考在当前机器有效；若文档用于其他机器或交接，应补可追溯的仓库／提交来源，或明确这是本地参考。
