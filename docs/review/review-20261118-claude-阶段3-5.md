## 1. 结论

发现 4 项问题：1 项高（涉及产品规则，需要用户确认）、2 项中、1 项低（需确认）。P1、P2 已用最小复现测试实测确认，P4 是 M13 全量回归里的真实失败，P3 由代码路径推出、未单独复现。交接中“M13 回归 400 项通过”只覆盖 7 个文件，M13 应用模块全量回归有 3 项真实失败。其余已读部分没有发现需要阻塞的问题。前几轮复核修好的保护在阶段 3–5 中都还在。

## 2. 问题

### P1（高，需用户确认）：同一 Git 仓库里的独立任务也被写入队列串行，与技术方案 §6 不一致

- 代码：每个任务派发前都要经过 `DelegationService.beforeDispatch`（`delegation-service.ts`）的目录写入队列，没有区分 Git、SVN 和普通目录，也不区分是否属于委派。空闲的持有者在别的任务排队时会被关闭（`work()` 中 “ordinary idle owner … yields when another writer actually queues”）。
- 合同：技术方案 §6 写明“**方案 B 只用于 SVN 与普通目录**；Git 项目的写入委派走 §6.1 工作副本”。需求 R06 也只在 SVN／普通目录一节规定“同一规范目录同时最多一个写入型 Agent”。
- 实测（[复现](evidence-20261118-claude-phase3-5/probe-git-serial.test.ts.txt)、[观察值](evidence-20261118-claude-phase3-5/probe-git-serial.json)）：同一 Git 仓库建两个独立任务，第一个任务回合进行中时，第二个任务的输入一直停在 `accepted`；第一个任务回合结束后，它的运行被关闭（`firstRunAfterTurnEnd: closed`），第二个任务才开始。
- 影响：日常在同一项目里同时开两个任务会互相排队，每次交替都要关闭并恢复会话；在 M14 之前，同项目的多个任务可以并行。
- 需要用户确认的产品规则：①Git 项目的独立任务是否应当并行（按技术方案字面即应并行）；②SVN／普通目录里**互不相关**的两个独立任务是否也要串行（需求只对委派写明了方案 B）。确认后再改代码与对应用例。

### P2（中）：交接内容超出预算时丢掉的是最近的历史；预算上限也小于方案

- 代码：`handoff.ts` 的 `prepare` 按 `ordinal` 从旧到新装入，装满就把后面的条目列为遗漏；上限写为 `Math.min(budget, 128 * 1024)`。
- 合同：技术方案 §5 交接“文字初值 256 KiB”“不足返回部分覆盖”。没有规定保留哪一端，但切换执行器时最近的对话最关键。
- 实测（[复现](evidence-20261118-claude-phase3-5/probe-handoff.test.ts.txt)、[观察值](evidence-20261118-claude-phase3-5/probe-handoff.json)）：在 A 上进行 30 轮（每轮回答约 8 KiB）后切到 B，B 收到的交接只包含第 0–14 轮，**最近的第 15–29 轮全部列为遗漏**（`newestIncluded: false`，交接 130,302 字节）。
- 建议：从新往旧选取、按时间顺序输出，保证最近的上下文优先进入；上限按方案改为 256 KiB（同时受本轮输入剩余预算约束）；遗漏说明写清缺的是较早的部分。

### P3（低，需确认）：业务批准后的 60 秒执行时限把排队等写入槽的时间也算进去

- 代码：`host-business-requests.ts` 的 `executeOwned` 先建立 `AbortSignal.timeout(60s)`，再调用 `acquire`（`wiring.ts` 中为 `delegations.acquireBusiness`，循环等待目录写入槽，信号中止即放弃），之后才执行。超时后请求被退役，提示“本次业务未执行”。
- 合同：技术方案 §8.1 写“执行时限……从批准时刻起算”，字面上与代码一致；但同一节也写“需等写入槽的，按 §6 调度排队”。
- 影响：与 P1 叠加时，用户批准了一封邮件发送，如果同项目另一个任务正在跑一个超过 60 秒的回合，批准会被退役，需要重新发起。这一项由代码路径推出，没有单独复现。
- 建议：先随 P1 确认规则；如果排队属于“等待”而不是“执行”，执行时限应从取得写入槽开始计算。
