## 2. 问题清单

### 高优先级

### SR01：停止保护仍漏掉两个异步窗口，停止后会开始执行新输入

关联 FR01／FR03；阶段 2；违反 R01／R02 的停止与队列语义。

代码：[停止序号与退出恢复](../../src/main/core/agent/agent-task-service.ts#L87)、[默认模型查询及派发](../../src/main/core/agent/agent-task-service.ts#L270)、[记录等待退出原因](../../src/main/core/agent/agent-task-service.ts#L286)。

两条实际复现路径：

1. **Q01a：在默认模型查询期间按停止。** `stoppedSince()` 检查之后新增了 `await resolveDefaultModel()`，返回后没有再次检查便派发输入。反例使用实际 Codex 驱动与有状态协议对端：先恢复旧线程并使用显式模型，再选默认，在 `config/read` 等待期间停止。查询返回后仍发出了第三次 `turn/start`，随后才中断它。第三条输入最终显示 `interrupted`，但“先开始再中断”不能满足停止后不再派发的合同。
2. **Q01b：在启动解析期间按停止，稍后才登记等待旧进程退出。** catch 中记录的是当下 `stopSeq`，已经包含用户刚发出的停止；旧进程退出时两者相等，用户停止仍被解除。反例最终新开了第二个实例，排队输入从 `accepted` 变为 `started`。

证据：[Q01a／b](evidence-20261117-2251/boundary-core.test.ts#L70)、[观察值](evidence-20261117-2251/boundary-core-observations.json)。这些是服务／驱动的受控顺序验证，未声称完成真实 App 中这两个竞态的复验。

需要在最终派发前重新核对停止资格，覆盖默认模型等所有异步前置；等待退出的恢复资格应绑定本次尝试开始时的停止序号，不能在已发生停止之后重新取得自动恢复资格。保留“未停止时退出后自动恢复”和“真实退出前不释放占用”的正常路径。

### SR02：合法输入长度的草稿保存返回成功，原文却已被不可逆截断

关联 FR02 的“不丢草稿”声明；阶段 2；违反 R01 草稿持久化、A43／A45 的保存与失败合同。

代码：[saveDraft](../../src/main/core/agent/agent-store.ts#L230)、[boundedJson](../../src/main/core/agent/agent-store.ts#L14)、[draftBody](../../src/main/core/agent/agent-task-service.ts#L431)、[草稿加载](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L262)。

分段读取只解决了传输大小，存储仍调用 `boundedJson(draft, 256 * 1024)`。超过序列化限额时，数据库只保存 `truncated/bytes/sha256/head`，随后仍返回 `{ok:true, revision:1}`。后续再分段读取，也只能读到这个截断对象，已经没有原文。

| 合法输入 | 最终草稿 JSON | 实际保存／读回 |
| --- | --- | --- |
| 256 KiB 普通文字 | 262,155 bytes | 返回成功；原 text 字段丢失 |
| 130 KiB 引号文字 | 266,251 bytes | 返回成功；原 text 字段丢失 |

两条原始文字均不超过当前输入的 256 KiB 上限，完整请求也低于 1 MiB；第二条说明并非只差一个 JSON 字段开销，转义会让较短输入触发。

证据：[Q04 两例](evidence-20261117-2251/boundary-core.test.ts#L134)、[服务观察值](evidence-20261117-2251/boundary-core-observations.json)。组件再用相同形状的已截断对象复验：重新打开后编辑器为空，且没有错误提示，见 [Q04ui](evidence-20261117-2251/boundary-ui.test.tsx#L45)、[组件观察值](evidence-20261117-2251/boundary-ui-observations.json)。这是存储／组件分层验证，不冒充打包 App 操作。

草稿应完整保存或在写入前明确拒绝并保留原记录和本地编辑，不能将截断写入当作成功。应按完整 JSON 与转义开销协调输入和存储预算；加载已有不完整记录也不能当作空草稿成功处理。

### 中优先级

### SR03：默认选择下恢复旧线程时，跳过默认模型查询，继续使用旧覆盖

关联 FR03；阶段 2 的恢复与模型合同；违反 R03 的“默认选择必须恢复执行器默认”。

代码：[恢复运行时初始化 sentModel](../../src/main/core/agent/agent-run-service.ts#L79)、[仅在 sentModel 时解析默认](../../src/main/core/agent/agent-task-service.ts#L275)、[恢复响应不作默认](../../src/main/core/agent/drivers/codex-app-server.ts#L77)。

恢复旧线程本身就可能带有先前的模型覆盖，但 `sentModel` 只有在本次恢复传入了 `input.model` 时才为真。当用户已选择默认，恢复参数没有模型，`defaultModel` 和 `sentModel` 同时为空／假，`pump` 就不查询默认，也不进入“查不到必须明确选择”的拒绝分支，直接省略 model 派发。

反例实际执行 **默认 A → 显式 B → 关闭运行 → 清除显式选择 → 恢复同一绑定**：第三轮仍是 B，`config/read`／`model/list` 查询次数为 0。默认可查到和不可查到两种情况都错误派发。证据：[Q02 两例](evidence-20261117-2251/boundary-core.test.ts#L114)、[观察值](evidence-20261117-2251/boundary-core-observations.json)。

另用本机原生 Codex 作独立核对：配置默认为 `gpt-5.1-codex`；一轮显式 `explicit-other` 的本地合成失败后，重开进程、无模型覆盖地恢复旧线程，响应模型仍为 `explicit-other`，而 `config/read` 返回的默认仍是 `gpt-5.1-codex`。见[原生结果](evidence-20261117-2251/native-resume-observations.json)、[探针源码](evidence-20261117-2251/native-resume-probe.mjs)。因此协议替身的“恢复保留旧覆盖”不是凭空假设。

应将恢复线程的模型覆盖视作需要核对的既有状态；默认选择下先可靠解析默认，查不到就按回执所述阻止派发并给出原因，不能用“本次运行是否发过显式模型”代替判断。现有正式测试标题虽写“恢复的线程”，服务测试实际上是在同一个替身实例里先发显式模型再清除，未覆盖关闭后恢复时选择已经为空的路径。

### SR04：请求预览本身没有合计预算，快照仍会超出 256 KiB

关联 FR02；阶段 2；违反技术方案 §3.1、A45 的整体响应上限。

代码：[请求预算](../../src/main/core/agent/agent-task-service.ts#L370)、[最终快照收缩](../../src/main/core/agent/agent-task-service.ts#L387)。

完整请求放不下后改成预览，但每个预览仍无条件加入，累计超限也继续追加。最后的 while 只删除 `items`，基础部分已经超限时无法收口。

容量注入使用 40 个分别约 90 KiB、内容含中文的合法命令审批请求。单条均低于 1 MiB；合计正文约 3.6 MiB。快照达到 **347,049 bytes**，超过 262,144 bytes；`items` 已经为空，却仍返回超限响应，`hasOlder:true`。证据：[Q03](evidence-20261117-2251/boundary-core.test.ts#L126)、[观察值](evidence-20261117-2251/boundary-core-observations.json)。这是容量边界注入，不声称真实模型已产生该批请求。

请求预览及其他基础字段也必须纳入整体预算；可采用可分页的请求摘要／正文引用，保留所有待处理项的可访问路径。不能靠丢弃待处理请求或时间线而仍返回超限对象。上轮三条大请求、草稿、中文分段和事件边界已通过，问题是“所有请求的预览合计”仍未守界。

### SR05：展开全文后的缓存不随条目 revision 更新，待办状态永久停在旧值

关联 FR04 新增全文读取；阶段 2；违反 R01／R02、A44／A76 的修订与待办进度合同。

代码：[useFullPayload](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L73)、[待办渲染](../../src/renderer/features/agent-tasks/agent-task-view.tsx#L99)、[同一 todo 条目持续更新](../../src/main/core/agent/timeline.ts#L40)。

`full` 一旦读取成功，就始终优先于 `item.payload`；itemId／revision 变化时不会清理或重新验证缓存。Claude 的多次 TaskCreate／TaskUpdate 本来就会更新同一个 todo 条目，因此并非所有展开后的条目都是不可变历史。

组件反例：50 项长待办先展开全文；随后收到 revision 2 的快照，第一项已为 completed。界面已采用新快照（标题同步更新），待办行却仍为 `agent-todo-row pending`，正文只读取过一次。证据：[Q05](evidence-20261117-2251/boundary-ui.test.tsx#L54)、[组件观察值](evidence-20261117-2251/boundary-ui-observations.json)。

全文缓存需要按任务、条目及修订维护有效性；修订推进后采用新预览／重取全文，旧的异步读取结果也不能写回覆盖新修订。计划复制等操作同样不能复用已经失效的旧全文。
