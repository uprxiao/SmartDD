## 2. 本轮问题清单

### N01 · 低 · 浏览器授权获批时没有活跃 run 的承接方式还需明确

**位置**：[技术方案 §8.1](../里程碑/M14_统一Agent工作区/技研/技术方案.md)第 264–278 行、[用例 A37](../里程碑/M14_统一Agent工作区/验收/测试用例.md)、[验证计划 E12](../里程碑/M14_统一Agent工作区/技研/兼容验证计划.md)。目前已允许 owner 退出后保留宿主业务请求，但浏览器授权的落点写的是“任务当前的运行，有效期到该运行结束”。

存在合法场景：SVN 方案 B 中父 owner 已退出并交槽，父任务尚未创建新 run，用户此时批准此前的跨任务浏览器授权。**这里指实际 owner 已退出且没有后继 run，不能仅凭普通回合结束就判定没有 run。** 方案没有说明授权此时进入何种状态、何时绑定以及何时开始其运行有效期。现有浏览器服务本身需要真实有效的 run 身份（[access.ts](../../src/main/core/browser/access.ts) 第 26–48、55–64 行）；它待 E12 改造这一事实不是当前产品缺陷，但新合同仍需覆盖这个空档。

**建议**：明确一种实现路径，例如无 run 时持久保存“已批准，待绑定运行”；下一次真实运行登记成功后重新核对任务、授权、目标页面和停止／撤销状态，再绑定明确的 run。或者由宿主按调度规则唤醒后绑定。两者都应避免把授权写回已退出的 origin run，或在尚未绑定时提示 Agent 已获得可用权限。

**关闭条件**：§8.1、A37/E12 增加“无当前 run 时批准→后继 run 登记→授权可用”和“绑定前用户停止／撤销→后继 run 不获授权”两组状态与预期。此项是设计完整性补充，不是已复现的运行故障；不重新打开上轮已经消除的请求分类冲突，也不要求本轮完成 E12 服务改造。
