## 2. 问题清单

### B01〔中〕两份有效 manifest 示例违反自身的工具版本校验规则

**证据：**[架构设计](../里程碑/M11_应用接入标准化/技研/架构设计.md)第 92、103 行：`zentao.object.list` 的 `contractMajor` 为 `1`，降级工具却为 `smartdd_zentao_object_list_v2`；第 117、124 行：`mail.send.execute` 同样声明 `contractMajor: 1`，主工具为 `smartdd_mail_send_execute_v2`。第 130 行明确规定工具名 `_v<N>` 必须等于能力的 `contractMajor`，第 193 行又要求新结果契约使用新主版本。

**影响：**按本文规则实现的解析器会拒绝两份正例；若照抄示例放宽校验，就会混淆旧 v1 和新 v2 契约。上一轮 A10 的“双主入口”冲突已经修复，但示例仍不能作为有效正例直接使用。

**复核：**本轮直接解析文内两段 JSON，分别提取主／降级 MCP 工具后缀，两项检查均为 `contractMajor=1, suffix=2, pass=false`。这不是对尚未实现的生产解析器报缺陷。

### B02〔中〕R14 允许的手动确认范围与 §2.5、架构和 T18 不一致

**证据：**[需求](../里程碑/M11_应用接入标准化/需求.md)第 98 行 R14 写“邮箱且与 SMTP 一致时自动确认，**否则**（含只配 SMTP）由用户……确认”。“否则”包含“目录是邮箱，但与 SMTP 不一致”。同文第 69 行 §2.5 的已确认决定，以及[架构设计](../里程碑/M11_应用接入标准化/技研/架构设计.md)第 295–296 行，仅允许“没有 Foxmail”或“目录名不是邮箱”时手动确认；[T18](../里程碑/M11_应用接入标准化/验收/测试用例.md)第 42 行要求“为邮箱但不一致”时拒绝。

**影响：**按唯一需求账 R14 开发可能允许用户覆盖邮箱不匹配，按 T18 验收却必须拒绝。这涉及发送前的身份判断，不能留给实现者自行选择。

只配 SMTP 时经用户确认后发送的分支已经补齐；本项仅要求消除“有效邮箱不匹配”分支的歧义。

### B03〔中〕邮件迁移矩阵把不存在的 v1 `write` 当成现有工具，并遗漏现有工具的对应关系

**证据：**[架构设计](../里程碑/M11_应用接入标准化/技研/架构设计.md)第 275 行标为“源码”并列出现有 `write` 工具，第 279 行表头称“对应 v1 工具”，第 284–286 行将创建／修改／复制／回复／附件导入统一标为 `write`，第 289 行又承诺保留“v1 的 `write`”语义。

实际工具定义在 [definitions.mjs](../../resources/applications/definitions.mjs)第 78–92 行：当前邮件有 14 个粒度明确的工具，包括 `draft_get`、`draft_create`、`draft_update`、`draft_copy`、`reply_create`、`attach_import`、`send_prepare`、`send_get`、`send_cancel`，**没有 `smartdd_mail_write_v1`**。[当前邮件 Skill](../../resources/applications/mail/1.0.4/skills/work-assistant/SKILL.md)第 18–28 行也使用这些独立工具。

**影响：**该矩阵目前无法逐条指导“v1 工具 → 新能力 → 必需／条件槽”的迁移，尤其未说明 `draft_get`、`send_prepare`、`send_get`、`send_cancel` 的对应项。后两者关系到 unknown 结果查询和停止等待，不能根据一个虚构的聚合工具验证迁移完整性。[需求 R06、R13](../里程碑/M11_应用接入标准化/需求.md)要求保持现有草稿与发送行为。

允许将“write”用作写操作类别，但须明确它是类别，并另给真实工具的完整映射；本项不是要求禁止能力分类或禁止 v2 合理拆分。

### B04〔低〕实施表需说明运行计划的共同前置和跨步骤验收时点

**证据：**[架构设计](../里程碑/M11_应用接入标准化/技研/架构设计.md)第 181 行 Agent 调用身份要求 `RunPlanRef`，第 191 行按运行计划解析能力，第 344–358 行规定每次运行固定计划并由服务端执行允许表。但第 421 行 S4 已迁移邮件 v2，运行计划却安排在后面的 S5（第 422 行），S4 未列出这一前置。S5 的完成判据引用 T01／T02，而这些用例需要 S6 才迁移的禅道 CLI 包。

**影响：**不影响整体分层成立，但实施者可能在早期步骤临时绕过共同计划，或把夹具测试完成误写为整条真实用例通过。第 433 行已要求生产输入变化后重新打包，这条正确规则应保留。

此项按“缺少实施说明”列低优先级，不据此断言产品已发生安全缺陷。
