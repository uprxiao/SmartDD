# Review Report

## 摘要

2026-11-11 复核 **M13 原型 P0.15**。依据为当前需求 R0.3（**包括 2026-11-11 补记 1–5，较新的用户决定优先**）、技术方案 T1.0 与验收用例初稿；代码为 `feature/0.1.4`、HEAD `2bea3b984` 加未提交修改。[源码与文档哈希](review-20261111-1500-evidence/baseline.json)标识本轮实际文件，不能只用 HEAD 复现本轮版本。

上轮原型错误已有实质修正，可以沿用当前视觉与页面方向；但尚有 **9 项一致性问题（高 1、中 8）**，不宜将“全部业务流程已闭环、可以直接按原型开发”作为结论。重点是任务启动／恢复没有接完新智能体数据、多模型与导入导出不一致，以及新增真实 SMG 测试的判定和超时不完整。本轮只审核并新增报告／证据，未改原型和生产实现，未提交／推送。

## 问题清单

### N01 · 高：首页接通了新列表，但启动、终端与恢复仍走旧配置

**证据**：`prototypes/m6-codex/src/App.jsx:287–292、373–378、452、510–512`；`TerminalPreview` 在同文件约 114、121 行显示运行器与配置名称。

- `useM13State` 已上移到 App，首页通过 `homeAgents` 共用新智能体列表；上轮“切页面丢失全部修改”已解决。
- 但 `m13Profiles` 只映射 `id/name/runner/isDefault`，创建任务只记录这几个字段，没有所选 Provider、默认模型、多选模型及配置快照。
- 新任务进入终端时，仍从旧 `profiles` 查新 `rc-*` ID，查不到就回退显示 **Claude Code／CC-work**。例如首页选“Codex · DeepSeek”，任务对象虽记 `runner:codex`，演示终端却会按默认 Claude 配置显示。
- “恢复任务”和“任务配置”弹窗仍列旧 `profiles`，任务信息也仍从旧数据取配置名称；不能选择本轮智能体，不能按原 Provider／模型恢复。会话插件按钮和运行快照同样仍取旧 `integration.data`。

**影响**：用户能选择和保存智能体，但不能在原型中核对“用的究竟是哪一组工具＋供应商＋模型”及恢复结果。这里要求的是合成任务也保持身份一致，不要求原型启动真实 CLI。

**最小建议**：共用任务配置解析与快照模型，首页、演示终端、任务信息、恢复、任务配置及插件预览全部读同一来源；补一条“选 Codex·供应商 → 建任务 → 停止 → 恢复”的原型回归。

### N02 · 中：Claude 档位仍保留旧映射，而且失败模型可以留在保存数据中

**证据**：`M13CodeAgent.jsx:103–119`；`m13-model.mjs:191–195、203`；需求补记 5、技术方案 §3.7、用例 T090。

- 最新决定为 **五个档位一律等于默认模型**，不再提供独立档位设置。
- 保存仍调用 `rebuildTiers(provider, model, initial.tiers)`；该函数保留同一供应商内仍可用的旧档位。现有 Claude·DeepSeek 的 Haiku、small-fast 因此仍是 Flash，默认模型却是 Pro。直接编辑后保存也不会统一。原函数反例见[探针结果](review-20261111-1500-evidence/probes.json)。
- 模型测试失败后，`options` 会隐藏失败模型，但没有移除 `picked` 或改选 `model`。`ready` 只检查 `picked.includes(model)`，不检查这些 ID 仍属于 `options`，所以“默认模型已被隐藏但仍可保存”的路径存在。`ready` 也未校验工具当前已安装。

**最小建议**：保存时统一按默认模型生成全部档位；供应商／可用性变化后同步清理选择并重新校验默认模型、工具安装状态。T090 须断言五个值均等于默认值；现有“都属于供应商”断言不足以覆盖最新规则。

### N03 · 中：导出会丢多选模型，重复导入会产生重名

**证据**：`m13-model.mjs:400–415`，`M13AgentSettings.jsx:63–66`。

- `buildExport` 没有导出 RunConfig 的 `models`，Provider 也没有保留 `recommended/endpoints`。实际取当前 Claude·DeepSeek 导出，原来勾选 Pro＋Flash，文件里只剩默认 `model:Pro`；导回后 `agentModels` 只能恢复一个模型。
- 对多端点的自定义 Provider，只有单一 `url` 和协议名称也不足以重建原来各协议的地址。不能把“导出配置、别人导入后使用”当成已闭环。
- `importPreview` 对重名只追加一次“（导入）”，不检查该名字已经存在，也不在本批分配名称后更新集合。连续导入现有示例两次，第二次再次产生 **Codex · DeepSeek（导入）**。供应商名称有同样问题。
- 最新规则允许导入时建立新 Provider 实体以避免组合冲突；这不等于允许最终智能体重名。不能把规则改回禁止导入重复来源来掩盖问题。

**最小建议**：补完整 round-trip Schema，至少保留模型列表及每协议端点；名称分配在现有和本批集合中循环避重。加多模型／双端点导出后导入、同文件连续导入两次的回归。

### N04 · 中：工具消失后，列表“默认项”与首页实际默认不一致

**证据**：`M13AgentSettings.jsx:28–44`；`m13-model.mjs:257–284`；`App.jsx:292`。

- 把 Codex·DeepSeek 设为默认，再切到“没有安装 Codex”场景，检测只改 `tools.installed`，没有交接或清除默认。
- 首页把这个默认项过滤掉，回退选择列表中第一项；设置页却仍把不可用 Codex 标为默认、固定第一，并禁用它的首页开关。本轮模型反例中首页剩下三项，但全部 `default:false`。
- `nextDefault` 也不接收工具状态，退出登录／删除供应商时可能将默认交给已被首页排除的工具配置。新建第一项时也没有统一的默认整理入口。

**最小建议**：按同一“首页可选集合”处理所有交接，明确工具丢失时的规则；没有可选项时展示空态。当前“默认必须在首页显示”与“默认工具缺失但仍保持默认”不能同时成立。

### N05 · 中：更新插件后，权限仍是旧版，空能力／Skill 列表也不能清空

**证据**：`M13Workspace.jsx:77–78`；`m13-model.mjs:63–65、79–89`。

- 更新分支只替换版本、能力、Skill，没有更新 `permissions` 等新包元数据。
- 现有禅道 1.1.0 合成包新增“联网：下载 Bug 附件”，更新页让用户确认这项新增权限；保存后详情里的权限仍是 1.0.0 的三项。按当前更新表达式核对，新增权限确实丢失。
- `cand.capabilities.length ? ... : p.capabilities` 和 Skill 的同类表达式，把合法的“新版删除全部”当成“不修改”；`removedCapabilities` 在候选为空时也直接返回空，无法提示删光能力。

**最小建议**：新包声明整体作为新元数据，连接、项目设置、启停等保留状态单独合并；区分“字段缺失”与“合法空数组”。更新后详情、能力页、权限与确认页必须一致。

### N06 · 中：邮件草稿页没有执行项目关闭与项目发件连接规则

**证据**：`M13Pages.jsx:17–25、35–43`；需求“插件连接与项目使用”“会话生效规则”补记，尤其“项目关闭插件时，页面选到该项目显示已关闭”。

- 邮件页只判断全局 `plugin.enabled`，`hasSender` 只检查全局连接数组里是否存在任意 SMTP；没有读取该草稿项目的 `bindings/defaults/effectiveConnection`。
- 在 AIS 项目关闭邮件插件后，AIS 草稿仍可显示、编辑；只要别处配过一个 SMTP，发送按钮就可用。草稿没有展示本项目当前生效的发件账号，也没有模拟发送前的绑定核对。
- 禅道“我的工作”已经按所选项目判断关闭和生效连接，邮件页却没有相同项目边界。原型内的发送是合成行为，本轮没有发送任何真实邮件。

**最小建议**：按草稿所属项目解析插件状态与发件连接，在关闭／未配置／连接失效时给出对应状态；合成发送也需记录所用连接，不以任意全局 SMTP 代替本项目账号。

### N07 · 中：删除连接的阻止条件用固定任务，停止真实演示任务后仍不能删除

**证据**：`M13Workspace.jsx:86` 调用 `deleteImpact` 未传 tasks；`m13-model.mjs:339–363` 的默认参数 `running=RUNNING_TASKS`。

- `RUNNING_TASKS` 固定包含一个使用公司禅道连接的 `run-1`，与 App 当前任务列表不是同一来源。
- 即使当前已无运行中任务，默认调用仍返回 `blocked:true`；显式传实际空任务数组时才返回 false，已运行原函数核对。
- 反方向，新建的运行中任务若使用其他连接，也不会出现在这个固定数组里，删除检查可能漏掉它。当前 task 还缺新插件连接快照，与 N01 相互关联。

**最小建议**：从真实合成任务及其启动连接快照判断，不重新按最新默认推断旧任务的连接；停止任务后应解除删除阻止。

### N08 · 中：SMG 真实探针可能把失败判成功，且响应体不受超时保护

**证据**：`m13-live.mjs:11–15、30–51`；`M13CodeAgent.jsx:191–204、286–303`。仅对本地 mock fetch 运行反例，**没有连接 SMG、没有读取或使用用户 Key**。

1. **错误流判绿**：`liveClaudeTest` 只用正则看全文包含 `message_start` 和 `tool_use/wy_ping`。本轮构造“开始流 → 工具块开始 → error/overloaded_error”的合成 HTTP 200 SSE，没有工具块结束、`message_stop`，仍返回 `result:ok`。所以现有“7/7 页面通过”不能证明真实测试判定覆盖错误流。
2. **超时只覆盖响应头**：`call()` 在 `fetch` 返回时立即清除定时器；后续 `r.text()`／`r.json()` 未受该计时约束。模拟服务器返回响应头后永不结束正文，结果仍 pending，而有效超时已经为 0。UI 可能一直“测试中”，不会按标称 30 秒退出。
3. **模型下线不移除**：真实 `refresh` 只把新模型追加到旧列表，没有删除上游已下线模型，也不标记引用它的智能体需要改选，与“刷新目录，默认模型下线提示改选”不一致。
4. **凭据删除待补**：真实 Key 存在模块级 Map；删除 Provider 只删页面模型，未清理 `secrets`。建议与删除、重新接入、关闭流程一起明确清理，不能以页面不再显示来证明 Key 已删除。

**最小建议**：按 SSE 事件与完整消息状态判定，出现错误／截断不得标可用；计时与大小限制覆盖整个读取及解析过程，失败能回到可重试状态；模型目录完整对账。真实探针是直接 HTTP 请求，不等于已经用真实 Claude CLI 验证；后者仍按正式开发门槛执行。

### N09 · 中：“重新读取插件”会触发未定义函数错误

**证据**：`M13Workspace.jsx:66、104–114`。

- `PluginCatalog` 没有接收或定义 `notify`，但刷新计时回调调用 `notify('插件状态已刷新')`；父组件调用也没传入。
- 从源码抽取该回调，在只提供 `setRefreshing` 的独立 JS 上下文执行，确定得到 **ReferenceError: notify is not defined**。这不是 UI 完整复现，而是对原回调的离线核对。
- 现有模型测试、历史走查“零错误”没有覆盖该按钮点击后计时完成的路径。

**最小建议**：接入已有提示回调；只补一次刷新按钮完成后的组件／浏览器回归，无需为此重跑真实模型或打包 App。

## 修改建议

优先按三组收口，保留当前原型布局和最新需求决定：

1. **智能体闭环**：N01–N04。共用任务快照、运行器、Provider、模型集合、首页可选集合与导入导出 Schema；不要只校验列表能新增。
2. **插件状态**：N05–N07、N09。更新元数据、项目范围及运行任务连接统一来源；用现有合成包、连接、任务即可复核。
3. **真实探针**：N08。先用本地错误流、挂起流、模型下线响应验证判定器；不需要反复消耗真实 Key 用量。修正后再视范围补一次真实成功请求。

每组保留原红测和修正后结果。用例 T090、T066、导入导出相关条目、任务启动／恢复、连接删除、邮件项目关闭、插件更新后权限、真实探针负例均需补对应判据；现有通过的正常流程继续沿用。

## 风险／待确认点

1. **正式开发仍未获本轮授权**。现有原型认可有效，不需要因为此次审核重做已确认的产品方向；修正的是同一范围内的数据与流程不一致。
2. 需求补记 5 已改为手动新建、模型多选、同组合唯一、默认固定第一、普通配置不显示高级设置、供应商不自动生成智能体。本报告均按这些新决定评审，不将旧的高级设置／自动生成要求当成当前缺陷。
3. 技术方案已经明确：Claude 多选模型会话内切换的载体、已登录 CLI 的状态解析仍待正式开发第 1 步验证。这是已披露的门槛，**不能把只验证默认模型当成多模型切换已通过**；本轮没有要求重新跑全部历史技研。
4. 原型页及部分总说明仍写“全部合成、不发网络请求”，SMG 真实接入虽有局部说明，定稿前应统一当前边界。新旧描述在迭代补记中可追溯保留；提交最终评审前仍须按 AGENTS 合并需求 R1.0，并同步现行原型说明与用例，不依靠读者自行拼接补记。
5. Codex 专用图标、CLI 真实输出、官方 API 的真实调用等已登记的限制继续按既定范围处理，不把“暂无 Key／待用户单独测试”写成通过。
6. **可能未穷尽**：本轮审查覆盖主要新增源码、相关需求／方案／用例和定向反例，但没有完成全量 UI 弹层、焦点、拖动、窄窗、系统操作及真实 CLI 端到端验收。单测 332 项通过不能替代这些层级，也不能抵消上述确定反例。
