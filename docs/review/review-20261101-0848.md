## 2. 问题清单

### A01〔高〕进程归属检查发生在业务处理之后，探针不能证明调用前拦截

证据：[实验 host.mjs:25](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/实验/s0a-codex/host.mjs:25)、[模拟业务 broker.mjs:31](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/实验/cli-identity/broker.mjs:31)、[架构设计:134](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:134)。

`PeerCheckedHost` 先调用 `this.handle(req)`，之后才判断 `inTree` 并覆盖为 `PEER_MISMATCH`。`handle` 已包含业务处理及成功记录。因此树外请求虽然收到拒绝，业务分支可能已经运行，与“入口网关先验证身份再执行”的架构不一致。

本轮纯内存复现：有效的合成写令牌＋无法核验的假 socket，结果同时出现 `responseCode=PEER_MISMATCH`、`businessHandlerRanBeforePeerDenial=true`、业务记录 `OK`。没有监听端口、没有调用原生助手／模型／三方，也没有真实外部写入。**这是实验代码与证据的问题，不是已证实的生产漏洞。**

该探针还只用祖先 PID 做比较，未验证设计写出的启动时间及固定 CLI 可执行身份；后两项不能随“进程树通过”一并算已验证。

### A02〔高〕用基础沙箱模板重建配置，不能保证只追加 socket 权限

证据：[架构设计:149](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:149)、[需求:48](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/需求.md:48)、[交互探针:49](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/实验/s0a-codex/interactive.mjs:49)。

需求要求基于用户有效权限只追加 CLI socket；设计却把工作区模式映射为 `extends=":workspace"`、只读映射为 `:read-only`。用户若使用自定义 profile，其中的拒读路径、额外工作区、域名规则等不等于基础模板。仅保留“可写／只读”两个类别不足以保证原规则仍在。

[OpenAI 配置参考](https://developers.openai.com/codex/config-reference/)明确支持继承其他具名 profile，以及独立的 filesystem、workspace_roots 和 network 规则。**据此推断**，将一个自定义 profile 换成只继承基础模板的新 profile，会遗漏原 profile 独有的规则。此结论是配置继承分析，本轮没有实际放宽用户沙箱。

当前交互探针只证明一个默认配置下的工作区写入保持，不能推广为任意有效配置。V16“可联网用户”的补验还应覆盖自定义文件限制和受管要求，不只是能否联网。

### A03〔高〕统一服务只接受 RunContext，与没有 Agent 运行时的页面使用冲突

证据：[架构设计:43](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:43)、[架构设计:114](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:114)、[tool-service.ts:87](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/tool-service.ts:87)、[execution-context.ts:201](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/execution-context.ts:201)。

设计将 MCP、CLI、页面都接入按 `RunContext` 工作的统一服务，并给出必含 `runId` 的统一请求。现有 `ApplicationToolService.call` 首先要求活动 run；但页面通过 `withUi` 建立独立上下文，`taskId/runId` 为 null，连接管理另走 `withManagement`。用户未启动终端时也能使用页面。

如果直接按该请求形态统一，页面会被迫依赖 Agent 活动或虚构 run，破坏既有独立使用和身份边界。需要明确统一的是业务执行，而不是把所有调用者都伪装为 Agent。

### A06〔中〕跨入口防重的键和回执协议，与当前工具服务并不一致

证据：[架构设计:114](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:114)、[tool-service.ts:94](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/tool-service.ts:94)、[tool-service.ts:138](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/tool-service.ts:138)、[桥请求 schema:4](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/shared/application-bridge.ts:4)。

设计说同一 `operation_id` 换入口提交会返回原回执；但给出的新调用形态只有 requestId，没有 operationId／幂等键或专门回执查询。现有服务按 `runId:requestId` 防重，operationId 在宿主随机生成；缓存不在时返回 `REPLAY_UNAVAILABLE`，并非重建原结果。CLI 能力名与旧 MCP 工具名也会产生不同的原始请求 hash。

这不是说现有邮件必然重复发送——邮件已有意图级保护；问题是框架承诺不能直接等同于现有机制。必须定义逻辑操作身份、规范化输入、作用域及回执协议，才能保证通用跨入口行为。

### A07〔中〕邮件资源一律要求 Foxmail 槽，会阻断现有独立草稿资源

证据：[架构设计:183](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:183)、[mail-read-data-service.ts:95](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/mail-read-data-service.ts:95)、[draft-data-service.ts:35](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/draft-data-service.ts:35)。

当前资源读取先判断是否为项目持久业务资源，是则直接读取；只有原邮件资源才解析 Foxmail。草稿正文、持久附件和发送审阅也使用资源服务，能够不依赖原邮箱。

因此不能把现有统一 `resource_read` 直接映射成表中“资源 → 必需 foxmail”的能力，否则仅配 SMTP／未配来源时，即使草稿仍在，也读不到大正文或审阅资源。需区分资源类别的依赖，或拆为不同能力并明确旧工具兼容映射。草稿修改／附件导入是否需要来源也有条件分支，应补全矩阵。

### A08〔中〕仅配 SMTP 可用与发件地址必须匹配 Foxmail，缺少一致的缺槽规则

证据：[需求:29](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/需求.md:29)、[架构设计:188](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:188)、[T19:43](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/验收/测试用例.md:43)。

证据：[架构设计:102](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:102)、[数据设计:220](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:220)、[session-registry.ts:63](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/session-registry.ts:63)、[session-projector.ts:41](/Users/liubu/Documents/ChatGPT/SmartDD-m10/src/main/core/applications/session-projector.ts:41)。

需明确运行计划的落盘／校验方式、恢复时能否生成新投影，以及网关是否拒绝不属于本次生效入口的调用。只从 Skill 隐藏另一入口，不等于服务端已禁止它。该项应在 S1／S5 前补，不需要改写旧包。

### A12〔低，设计缺项〕上游适配目前只是分类，尚不足以作为接入标准

证据：[架构设计:196](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:196)、[manifest 草案:66](/Users/liubu/Documents/ChatGPT/SmartDD-m10/docs/里程碑/M11_应用接入标准化/技研/架构设计.md:66)。

缺少接入者可以遵循的完整适配协议：连接配置与认证映射、能力命名空间、参数资源范围、上游会话创建／复用／销毁、取消、凭据轮换、CLI 私有配置目录与环境隔离、输出预算及效果状态转换。

例如官方 CLI 默认读取日常配置／钥匙串时，怎样保证它使用本项目的受管连接？两个项目复用上游 MCP 客户端时，停止 A 怎样不取消 B？新增 namespace／vhost／key-prefix 限制在哪里声明并执行？这些不能仅靠输入 JSON schema 或“只映射已声明工具”自动解决。

这里不要求本期接入真实 Nacos／Redis／MQ，也不要求任意代码插件化；要求在 S7 前写出受控 MCP 与 CLI 的两份完整参考适配及生命周期契约。

## 4. 一致性校验

### 4.1 已确认可以保留的设计

- 产品名称继续叫“应用”；SOP／Skill 描述流程，不承担授权。
- MCP 和 CLI 都是受管入口，底层官方 MCP／CLI 复用与 Agent 入口解耦。
- 固定包、旧 MCP v1、历史证据保留；没有通过实验就不标成功。
- 独立 CLI 端点、运行级身份加内核对端校验、版本能力分级的方向有价值；需要修好验证与策略合并，见问题清单。
- L3 不能由本机自检提升；写能力无跨入口降级或自动重发；未知效果保留可追溯记录。
- Story 保留开发与补测责任；当前仅用 Codex 实测，其他 Agent 不写成已支持。

### 4.2 本轮实际验证

1. 读取完整架构正文、R0.7 需求、关联用例／技术方案与关键现状代码；当前代码作为 M10 基线事实，不要求它提前实现 M11。
2. `codex --version`：`codex-cli 0.166.0`。没有登录、模型调用、升级或安装旧版本。
3. A01 纯内存假 socket 验证通过：拒绝响应前业务分支已执行；只使用实验模块与合成令牌，没有打开 socket 或写真实系统。

## 5. 风险／待确认点

- 架构的长期目标是建立扩展边界，不必一步做成动态插件平台。应明确“新增包／受信模块／注册项可以改，宿主通用逻辑不用改”，并用受控样本验证，避免抽象不足或过度工程化。
- 官方工具能否原样复用取决于认证、参数、结果、隔离和生命周期，不能由“支持 MCP／CLI”直接推出。本次没有核验任何真实新三方系统。
- 邮件“仅 SMTP”与账号一致性是需要统一文字的产品边界；本报告不替用户选择，也不撤销已确认的发件一致规则。
- 当前最新版已按用户指令核实为本机 0.166.0；后续版本仍按适配证据与能力等级处理。旧数据兼容不等于重新以旧 CLI 作为开发基线。
- **可能未穷尽**：M11 生产实现尚未开始，本轮以设计和现有代码为依据；实际进程退出竞态、上游协议差异、真实资源范围及新版本日志解析仍需实现后的集成／打包验收。报告不把假设写成生产缺陷。
