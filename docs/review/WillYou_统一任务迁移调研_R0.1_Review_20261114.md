## 1. 结论

**当前调研方向正确，足以指导架构选型、迁移拆分和最小兼容实验；尚不足以单独作为完整开发与验收规格。**

三项目标均已纳入核心范围：统一任务 UI、同一逻辑任务切换 Provider 续聊、单／多 Agent 宿主委派。保留既有浏览器、文件目录、插件、Skill / MCP 等业务也已写成共同前提。没有发现需要推翻推荐方向的依据。

主要问题是：旧详细方案尚未按新范围整合，新增运行／会话／委派契约仍停留在职责层，业务兼容尚缺实际接入映射和验证闭环。用户随后补充了 SVN 为主、单项目 10GB 以上的实际环境，本次一并核对。下面列出 6 项收口事项；其中 R01–R03 及 R06 的核心兼容边界应先于依赖它们的正式开发完成。它们是设计就绪度缺口，不是声称现有程序已经出现对应故障。

## 3. 评审发现

### R01：尚无一份覆盖新范围、口径统一的详细开发基线

**优先级：依赖开发前必须收口。**

- 依据：旧 R0.2 第 24 行仍把跨 Agent 编排、同会话跨供应商切换列为后续；第 150 行仍禁止同会话更换智能体／供应商；§15 仍为后续多 Agent。第 10 行虽已声明这些内容受新目标影响，但正文尚未整合。新调研第 380–394 行也明确记录了这项未完成工作。
- 影响：开发者可能按旧 UI、身份与 SQL 开工，到 P3 / P4 再返工；也可能误把旧单 Agent 用例全部通过视为整体完成。
- 建议：下一轮形成一份新的整体方案主修订，将三核心目标和保留业务的前提落实到正文。旧 R0.2 整稿归历史；调研与本次评审保留为依据。正式需求、技术方案、原型和用例各有一份权威来源，通过链接关联，不把几份全文互相复制。
- 关闭判据：现行正文不再同时存在“本次支持”与“后续再做”的矛盾；每项需求能追踪至设计和用例；新方案入口标明适用基线与未验证范围。无需为完成这次评审擅自分配新的 F / M 编号。

### R02：保留业务的原则尚未转成实际接入契约，文件与浏览器是两个关键缺口

**优先级：相关公共身份与业务接入开发前必须收口。**

调研 §15 的原则正确，第 437 行也诚实地把保留清单列为待建立项。当前 §3 是复用分析，不等于已经具备逐项兼容设计。

**文件／worktree：**调研第 314–319 行规定隔离，第 419 行要求引用支持子任务，但尚未说明切入子会话时文件树展示哪个工作区、父文件引用是否映射到子副本，以及同名路径的内容版本如何核对。

现有 [FileSourceResolver](../../src/main/core/files/sources.ts) 第 15–27 行同时返回 task.cwd 和项目目录；[terminal-context](../../src/main/core/files/terminal-context.ts) 第 34–40 行将文件根 lease 绑定 task / pty，第 100–115 行在实际投递前核对来源及版本。新增 worktree 与聊天输入后，不能仅把 ptyId 换成 runId 就认为目标映射完成。

应明确文件树根、草稿归属、目标 task / binding / run / workspace、父引用到子 worktree 的处理，以及工作区切换后的过期规则。覆盖“父子都有同名文件但内容不同”“引用准备后换 Provider／子会话”“子 worktree 已变更”“未合并产物保留”等场景。

**浏览器：**调研第 418 行只要求正确关联项目和运行，尚未定义子任务默认使用自有浏览器工作区，还是申请访问父任务浏览器；也未细化 Provider 切换后新运行如何取得所需授权。

现有 [BrowserAccess](../../src/main/core/browser/access.ts) 第 30 行将授权绑定 run 生命周期，第 35–45 行明确同项目不等于可以操作其他任务的浏览器；[BrowserService](../../src/main/core/browser/service.ts) 第 164–168 行实际执行该检查；[BrowserAutomation](../../src/main/core/browser/automation.ts) 第 49–53 行在运行结束时清理活动。**保留标签、会话数据和登录状态，与继承旧运行的控制授权是不同事项。**应沿用原授权规则为实际新 run 建立权限，不能默默把父任务或旧 Provider 的 grant 给新身份。

**其他业务也需同一张实际映射表：**插件引用／写审批、Skill / MCP 交付、原话凭据与邮件、数据库／SSH、语音、导入导出等，均按已交付范围核对。现有 [run-registry](../../src/main/core/applications/run-registry.ts) 第 401–410 行仍要求真实宿主运行；程序化路径必须接入这条权威，而非绕过它。

关闭判据：建立“原功能 → 原入口／权威服务 → 已交付证据 → 新目标与接口 → 数据／权限／生命周期 → 正例与负例”的映射；受影响功能无空白接入项。未交付的 M13 计划单列，不冒充现有能力，也不扩大本次回归账。

### R03：多绑定、切换、委派的数据与公共契约尚未达到可实施粒度

**优先级：依赖的 migration 与公共 API 开发前必须收口。**

- 依据：调研第 198 行明确表结构后续定稿，第 271 行明确返回字段、错误码和 Schema 后续设计。旧 R0.2 §5.2 把 runtimeKind 按任务持久化，§9.4 的 agent_sessions 以 task_id 为主键并保存单份 binding_ref；不能原样承担新方案的多 ProviderBinding、交接覆盖和委派投递账本。
- 影响：不同模块容易各自解释 binding、run、turn、当前选择和结果已交付的含义；重启或重试时可能无法判断旧消息是否已接收、目标是否已切换、子结果是否还要唤醒父任务。
- 建议补齐：
  1. 明确实体、外键和唯一性：task、binding、run、turn、规范 item、选择修订、ContextTransfer、Delegation、CompletionDelivery、workspace 之间的关系。
  2. 给出选择／切换、模式修改、委派／取消、审批回答、事件订阅与恢复的版本化输入、回执、错误码、过期目标检查和幂等规则。
  3. 规定持久化与外部动作的边界：创建后尚未 spawn、旧运行已关闭但目标启动失败、注入可能成功但未记账、子结果已保存但父续接不明、取消与结果同时到达时怎样核对。
  4. 定义统一时间线顺序、原生历史导入与 handoff 回显的去重映射，以及旧任务字段的迁移／回退规则。
- 关闭判据：开发者可以从规范判定每种命令的允许状态、事务结果和重试方式；正式 migration 不再依赖单绑定旧假设；失败与恢复能落实成可判定用例。

调研已正确提出“投递未知不能盲目重试”，这不是遗漏；欠缺的是将原则落实到上述持久化与接口细节。

### R04：同一任务单／多 Agent 模式切换缺少明确规则

**优先级：需求与交互评审前补齐。**

- 依据：调研第 21 行示例包含同一任务“进入多智能体模式”，第 189 行保存协作模式，§9.1 说明两种模式，却未定义已有任务如何转换。当前 [共享任务契约](../../src/shared/tasks.ts) 也没有该领域能力。
- 影响：新建时选择单／多模式，与已有任务运行中改变模式会被误作同一个行为。尤其多→单时，排队子任务、活动子任务、结果待投递与旧 run 已取得的编排权限缺少统一处理。
- 建议：分别定义新建默认、任务持久化模式、当前 run 可用工具及生效时点。首轮可建议仅在明确空闲边界单→多；多→单先确认子任务、排队和结果投递均已收口。具体是否支持更复杂转换在产品规格中明确，不从示例自动推导。
- 关闭判据：列出转换表、阻止原因、模式变更后的工具权限、重启恢复与 UI 状态；包括“任务树仍工作时切主 Provider”的支持或明确暂不支持边界。

这不会把 Provider 续聊或宿主委派移出核心范围；只是明确两种核心能力组合使用的边界。

### R05：新增 UI 与兼容组合尚缺正式验收闭环

**优先级：在依赖的设计与兼容实验收口后，开放默认入口前完成。**

- 依据：调研 §11 是区域与状态方向；§12.2 的 V1–V10 是验证场景且明确全部未执行。旧方案 T01–T36 可复用为基础，但不覆盖新增任务树、Provider 分段、模式转换和全部业务组合。§12.3 的 Codex 版本差异、SDK 配置来源、并发配置根等也仍待固定组合证明。
- 影响：仅展示统一聊天或用一次 CLI 调用成功，不能证明三核心目标已在真实 WillYou 中完成；同样不能证明浏览器、文件和插件迁移后仍可用。
- 建议：补同一任务的单 Agent、切换中／失败／遗漏提示、多 Agent 树、问题与审批、部分失败、结果待回收、worktree 文件视图及旧任务入口原型。将 V 场景展开为可判定用例，明确双执行器、同执行器不同配置和受影响旧业务的覆盖矩阵。记录固定程序／SDK／资源版本与证据层级。
- 关闭判据：按所声明支持的组合完成必要协议／集成证明与同一候选包的真实界面验收，能核对实际 Provider／模型与关键上下文；未验证组合保持原路径或明确不开放。回归不能只放在项目结束时，每批相关改动均检查受影响业务。

未做 PoC 是本稿已声明的合理证据边界，不能因此判为调研错误；但也不能在没有证据时写“已经支持／完全兼容”。本次复核没有执行这些场景，不计算任何应用通过率。

### R06：原稿缺少 SVN 主使用场景与大型工作区约束

**优先级：核心需求与工作区设计前明确；本次已补方向，尚未实施。**

原稿 §10 将 Git worktree 用于并行写、非 Git 串行作为兜底，技术上可以成为首轮基线。用户明确接受该方式，因此不应将“没有自动 SVN 并行工作副本”判为缺陷，也不应擅自扩大为 SVN 管理产品。但对多数 SVN、单项目 10GB 以上的公司环境，不能只验 Git，或把整份代码复制当作必要协作步骤。

静态源码确认：现有任务不要求 Git；目录识别支持 SVN；项目可登记多个目录，同一路径也可出现在多个项目。旧 PRD 第 19、32、365–371 行明确了 SVN 业务背景、不初始化 Git、保留原 SVN 操作方式。因此，工作区排队要按真实及重叠路径判断，不能只按 projectId；统一 UI、Provider 续聊和委派完成也不能等待 Git checkpoint 成功。

本次根据用户反馈在调研中追加 [§16 SVN／Git 与大型工作区补充调研](../WillYou_统一任务UI_Provider续聊与多Agent委派迁移调研.md)。推荐仍以原目录串行写为 SVN 基线，评估按需读取＋版本核对的并行分析；全量快照撤出推荐路线。已有独立 SVN WC 可选，自动 checkout／合并不作为首轮前置。

还需将写入交棒、同步等待避免死锁、只读权限验证、读取依据过期、10GB 项目 I/O 和原业务兼容落入正式契约与用例。此项已完成方向补充，未完成工程验证；不能标成“SVN 新运行路径已通过”。

## 4. 建议的后续整合顺序

1. **先统一当前开发基线。** 将本轮目标、旧 R0.2 可复用内容和专项调研整合为新整体方案，保留旧稿与修订关系；正式需求同步去除旧单绑定范围的歧义。
2. **先把业务接入与身份关系设计清楚。** 完成 R02 的实际保留表，明确逻辑任务、ProviderBinding、run、workspace 和原业务授权之间的边界；按 R06 将 SVN／Git／多目录及大型项目纳入核心矩阵。
3. **补齐核心状态、契约和 UI。** 收口 R03、R04，并在原型中展示它们对用户的实际影响。
4. **用最小兼容实验反证设计。** 优先证明同任务 Codex→Claude→Codex、跨执行器委派回收，并覆盖文件引用、浏览器授权、输入来源和未知状态；不安装整套社区工作流来替代宿主能力验证。
5. **再按增量路径开发和验收。** P2 的单 Agent 统一 UI 是中间成果；P3 Provider 续聊、P4 宿主委派及受影响旧业务回归均通过，才满足用户本次整体目标。

本次没有将上述后续建议视为生产开发、安装、发版或真实模型调用授权，也没有替用户更改阶段排期。

## 6. 再次复核：以现有业务实现和 T3 Code 源码为依据

日期：2026-11-14。主要评审对象为[优化方案 R0.2](../统一Agent工作区优化方案.md)，同时参考[迁移调研 R0.1（含 §15–16）](../WillYou_统一任务UI_Provider续聊与多Agent委派迁移调研.md)。本轮重新核对 SmartDD `40ea344a930aec37e36a803b7c621d3632d2d75a` 的代码与 M13 入口；源码基线未变化。T3 参照本地 `f313d0a6cb843551fb60e57a454a71e71a3a8c04`，依据下列实际源码，不以产品界面或 SDK 名称推定能力。

### 6.1 结论与文档定位

**推荐架构适合 WillYou；现有两稿合起来仍不是能直接执行的完整设计基线。** R0.2 可称详细设计评审稿，但仍属于此前单 Agent 范围；专项调研已覆盖最新目标，但没有把现有业务能力登记、加载和授权契约完全迁到多绑定模型。

不需要推翻浏览器、文件系统、插件宿主、Skill 库或 MCP 体系。需要改造的是它们与任务运行之间的适配边界，并明确哪些资源属于逻辑任务、Provider 原生绑定、一次实际运行或文件窗口。保留 UI 入口只是兼容的一部分，运行身份、调用权限、资源留存和退出回收也必须连续。

### 6.2 具体发现（按开发影响排序）

#### B01｜高：多 ProviderBinding 尚未覆盖现有能力登记的一任务一身份约束

**证据：**[session-registry.ts](../../src/main/core/applications/session-registry.ts) 第 30 行按 task_id 查询；第 126–143 行 create 保存任务快照、身份、资源引用及 MCP 名称，已有不同快照报 SNAPSHOT_IMMUTABLE；第 147–151 行禁止替换已绑定的原生 session；第 203–207 行复核 runner、状态根、cwd、sessionId 和发现目录。[task-capability-launcher.ts](../../src/main/core/applications/task-capability-launcher.ts) 第 292–299 行仍按该 task 的快照预留 run、读取资源并交付能力。

**影响：**只新增聊天层 ProviderBinding，随后以同一个 taskId 调旧启动器切换 Codex→Claude，会碰到现有身份冲突。若直接放松校验，又会混淆旧原生会话的能力、资源留存和授权来源。这比只修改 tasks.runner 或新 SQL 更深一层。

**T3 对照：**[Orchestrator.ts](../../../t3code/apps/server/src/orchestration-v2/Orchestrator.ts) 第 1377–1418 行分别处理 providerSessions 与 providerThreads，并按 appThreadId、providerInstanceId 选择原生线程；[ProviderAdapter.ts](../../../t3code/packages/provider-core/src/server/ProviderAdapter.ts) 第 685–735 行以 providerThread 为运行／历史边界。

**需补设计：**明确逻辑 task、ProviderBinding、原生能力会话、run 和资源引用的对应表；决定旧 taskId 键如何映射为兼容绑定，如何保存多个能力快照及其历史；同步规划 MCP 名称、会话镜像路径、资源 hold／删除与旧记录恢复。业务 taskId 保持稳定，不用伪造另一个项目身份绕过检查。关闭判据是同 taskId 的 A→B→A 能通过真实原生身份核验，旧快照仍可追踪且不覆盖。

#### B02｜高：Skill／MCP 的“规则复用”还没有落实为新运行接口的交付合同

**证据：**[task-capability-launcher.ts](../../src/main/core/applications/task-capability-launcher.ts) 第 297–323 行做名称冲突、项目 MCP、run 绑定私有桥、CLI 环境、加载计划、配置文件和诊断；Claude 插件 Skill 通过 --plugin-dir 加载，Codex 使用私有 app-server 与冻结根。[frozen-skills.ts](../../src/main/core/applications/plugins/frozen-skills.ts) 第 62–83 行核对 prepared run 与目录所有权，按 run 回收。[capability-delivery-adapters.ts](../../src/main/core/applications/capability-delivery-adapters.ts) 区分共享 Skill 目录、会话插件、MCP／CLI 入口和原生加载能力。

**影响：**SDK 能读 CLI 配置不等于已经完成 WillYou 业务交付。只传 cwd／env，可能丢失宿主私有桥、冻结插件 Skill、项目能力或 CLI 业务入口；另造 SDK 配置则可能出现重复 MCP、同名能力覆盖和两套启停状态。

**T3 对照：**[ClaudeAdapterV2.ts](../../../t3code/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts) 第 1342–1489 行显式组织 SDK 进程与 MCP 设置，第 2096–2125 行传入工具策略和 MCP；第 2260 行明确区分 allowedTools 的预批准语义与工具可用性。这说明加载、可见和允许执行须分别处理，不能把一份工具名单视为全部语义。

**需补设计：**在现有预检／能力计划之后形成程序化交付结果，逐项映射程序、完整环境、Skill 根、插件根、MCP 服务、业务 CLI 桥、真实进程登记、诊断和释放句柄。原生 CLI 和 SDK 消费同一业务选择；传输适配各自实现。分别验证“发现→交付→加载→真实调用→停止撤销”，包含名称冲突和取消启动负例。不要求将所有已有业务统一改成 MCP。

R0.2 §7 已正确区分插件动态更新与 Skill／MCP 的生效规则，本项要求补齐具体交付契约，并非否定该矩阵。T3 的动态 MCP 实现也不自动成为 WillYou 的产品生效规则。

#### B03｜高：浏览器和插件审批需要明确跨绑定／父子任务的运行作用域

**证据：**[browser/access.ts](../../src/main/core/browser/access.ts) 第 26–41 行将授权绑定真实 run，跨任务要有独立 grant；[browser/automation.ts](../../src/main/core/browser/automation.ts) 第 49–53 行在 run 结束时清理活动。[write-approvals.ts](../../src/main/core/applications/plugins/write-approvals.ts) 第 69–80 行按 taskId＋ptyId 展示与决定，并核对窗口 receipt 与 reviewHash；[plugin-approval.tsx](../../src/renderer/features/applications/plugin-approval.tsx) 第 10–23 行的前端查询和回答也依赖 PTY。

**影响：**更换中央 UI 后，旧审批组件没有 PTY 目标便无法直接沿用；同任务切 Provider 也不能继续使用旧 run 的跨任务浏览器授权。父任务查看子审批，不代表父 Agent 获得替用户批准的能力。

**需补设计：**保留浏览器标签、会话和原业务审批服务；把查询／展示／回答目标扩展为宿主签发的实际运行身份与代际，保留 receipt／hash 校验。分别定义同任务换 Provider、创建子任务、父子切页、停止生成、结束 run 时，哪些数据保留、哪些请求失效、哪些授权需重新取得。父页面聚合子请求时仍把决定送回原子 run。

**T3 对照：**[ProviderContinuationService.ts](../../../t3code/apps/server/src/orchestration-v2/ProviderContinuationService.ts) 第 27–57、174–187 行按结果消息和 generation 校验、排队续接；这种真实归属和过期检查值得复用，但不能替代 WillYou 浏览器／邮件／插件各自的授权合同。

#### B04｜中：MCP 与文件系统的保留范围需明确，避免把文件查看器也迁入 Agent

**证据：**[files/mcp/service.ts](../../src/main/core/files/mcp/service.ts) 第 20–58 行的 FileViewerService 自己是 MCP 客户端，以 owner、文件 ref、generation 管理查看会话；第 64–112 行加载资源和 MCP App 页面。[files/sources.ts](../../src/main/core/files/sources.ts) 第 15–27 行提供任务 cwd 与项目目录；[terminal-context.ts](../../src/main/core/files/terminal-context.ts) 第 34–40 行的引用投递绑定 task／pty 和根 lease。任务终端还在 [task-view.tsx](../../src/renderer/views/task-view.tsx) 第 254 行注册文件投递目标。

**影响：**“SDK 支持 MCP”只回答 Agent 工具接入的一部分。文件查看器的 MCP／MCP App 属于现有文件窗口业务，它的页面、资源和保存权限应继续由文件服务持有。若随 Agent 切换重建或关闭，会影响用户正在查看／编辑的文件。与此同时，聊天引用目标的旧终端注册必须真正替换，不能只保留目录树。

**需补设计：**明确至少四类边界：Agent 外部 MCP、WillYou 业务私有 MCP、文件查看器 MCP、第一方编排 MCP。只将应该供 Agent 使用的入口交付给运行器。文件查看／保存生命周期与 Agent 回合解耦；引用投递使用新的可信草稿目标，标明 task、binding／run、workspace 和版本。覆盖文件窗口保持打开时切 Provider、切子任务、引用准备后目标改变，以及 worktree 同名文件等场景。

#### B05｜高：新范围仍未整合进旧设计，T3 接续机制不能只留在调研中

R0.2 §1.2、§4.3、§9、§15 的旧范围和单绑定结构尚未更新；这是前次 R01／R03 的延续，不能标为已关闭。[ContextHandoffService.ts](../../../t3code/apps/server/src/orchestration-v2/ContextHandoffService.ts) 第 500–560 行记录来源／目标原生线程、历史覆盖与预算；[ContextHandoffDelivery.ts](../../../t3code/apps/server/src/orchestration-v2/ContextHandoffDelivery.ts) 第 83–143 行区分 pending／injected／inline，并处理不确定交付。WillYou 正式设计需要把这些语义落实到表、命令、事务和恢复判据，并接上 B01 的业务能力会话。

宿主委派、任务树整体完成、单／多模式转换和停止范围同样需要进入现行正文。子结果、交接历史和用户真实输入继续分来源，不能为了复用统一聊天输入而改变邮件／插件授权证据。

#### B06｜中：保留 SVN／大型项目基线；T3 的 Git 隔离不应成为任务运行前置

专项调研 §16 已按用户反馈收敛，这项方向正确。T3 [OrchestratorMcpService.ts](../../../t3code/apps/server/src/mcp/OrchestratorMcpService.ts) 第 2598–2625 行的 worktree 分支明确解析父 HEAD 并检查仓库提交；该具体路径不能直接套到 SVN。WillYou 采用共享目录串行写入时，仍需补实际资源锁、父子交棒和背景工作结束判据。10GB 项目不默认复制全量代码、不在每轮全量 hash；只读并发以实际权限和内容版本复核为条件。现有同路径多项目登记不应被禁止来掩盖锁模型缺口。
