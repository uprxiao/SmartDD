### NR02：打开失败的清理路径仍会提前释放未退出的 owner

阶段 1；代码：[AgentRunService.open 的 catch](</Users/liubu/hx/4.uprxiao/SmartDD/src/main/core/agent/agent-run-service.ts:83>)。

正常 close 已改成观察退出、保留 stopping；但 open 失败时仍先 finishRun(failed)、从 runs 删除，再调用 instance.close。若原生进程已经启动，只是握手／线程响应失败，且关闭后仍未观察到退出，该路径不会保留占用。同任务随后可以新开运行，与方案 §3／§9 的 owner 排空合同冲突。

证据：[N02](evidence-20261117-1755/residual-observations.json)：已有登记 PID，close 已请求但未收到 exit，数据库为 failed、内存 owner 已消失。此处为进程对端替身验证，不冒充真实系统进程排空实验。

### NR03：原生回合先结束、start 回执后返回时，排队输入不会继续派发

阶段 2；代码：[回合终结触发 pump](</Users/liubu/hx/4.uprxiao/SmartDD/src/main/core/agent/agent-task-service.ts:40>)、[pump 门闩与 finally](</Users/liubu/hx/4.uprxiao/SmartDD/src/main/core/agent/agent-task-service.ts:194>)。

反例独立控制原生 turn.started／turn.completed 与 startTurn 的返回：第一轮已经结束，第二条已排队，但 start 回执还未返回。turn.ended 触发的 pump 因 dispatching 尚在而退出；之后 finally 只删除门闩，不补查队列，没有下一次调度。任务显示 working，第二条输入长期停在 accepted，直到额外用户动作可能再次唤醒。

这是协议回执与通知交错的故障注入，不是要求执行器改变事件顺序。R01 的队列应在原生空闲后自行推进。

证据：[N03](evidence-20261117-1755/residual-observations.json)：`sent=['first']`、`queued=['second']`、`status=working`。

### NR06：关键审批仍被截断，新增分页也没有落实容量边界

阶段 1／2；代码：[insertNativeRequest](</Users/liubu/hx/4.uprxiao/SmartDD/src/main/core/agent/agent-store.ts:193>)、[snapshot／history](</Users/liubu/hx/4.uprxiao/SmartDD/src/main/core/agent/agent-task-service.ts:277>)、[Claude 批准回传](</Users/liubu/hx/4.uprxiao/SmartDD/src/main/core/agent/drivers/claude-sdk.ts:213>)。

普通输入的 32 KiB 损坏已修，但审批 payload 仍用同一个 boundedJson 截断。40 KiB 的 ExitPlanMode 计划进入数据库后只剩截断摘要，快照中没有 input.plan；面板仍允许“批准并开始”，Driver 因 updatedInput 缺失而沿用内存中的完整原计划。**用户没有看到计划正文，执行器却获准执行完整计划。** 与 §3.1“关键请求不截断”和完整详情就绪后才允许回应的合同直接冲突。

容量还有两个已复现的断点：两个各 150 KiB 的合法输入使 snapshot 响应达到 **615,916 字节**；单个 300 KiB 历史条目使 history 响应达到 **307,465 字节**，均超过 256 KiB 合同。history 的判断只在已有输出项时才截页，第一项过大时直接放行；2000 条限制也不能代替字节限制或 artifact 范围读取。

证据：[N06a/b/c](evidence-20261117-1755/residual-observations.json)：面板计划正文为 0 字节，SDK 返回 allow 并取得完整 40,960 字节计划。实验没有调用模型或写真实项目。
