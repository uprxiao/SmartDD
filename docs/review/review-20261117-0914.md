## 2. 问题清单

### AR01 · 中 · 权限列表与“请求批准”的参数仍有两套口径

- **依据／位置**：[需求 R08][REQ]要求首页与任务页使用同一套按执行器过滤的列表；[App.jsx][APP] 第 505 行使用 M13 `permissionOptions`，[M14TaskArea.jsx][AREA] 第 276 行使用 M14 `PERMISSIONS`；[m13-model.mjs][M13] 第 627–654 行与[方案 §7.2][T] 第 220–225 行定义参数。
- **实际不一致**：首页 Claude 为 `ask/full`，任务页为 `ask/edits/full`；首页 Codex 为 `ask/auto/full`，任务页为 `ask/edits/auto/full`。同名 Codex `ask`，首页快照是 `workspace-write + on-request + reviewer=user`，T1.2 却是 `readOnly + untrusted + reviewer=user`。现有生产[权限定义][PERM]也仍是前一种，不能未经等价说明就当成后一种已接入。
- **影响**：同一个档位在入口、保存的快照和拟开发适配器之间含义不同；“自动接受编辑是否显示由原型决定”也不能解释两个入口显示不同。
- **证据**：[实际权限函数输出](evidence-20261117-0914/cross-artifact-probes.json)，`permission-sources`。这里不替用户新增／删除档位；须统一现行选择，再让所有入口和测试引用它。

### AR02 · 中 · 请求说明复用了普通消息草稿，并且在请求之间串用

- **依据／位置**：[需求 R01、§3][REQ]规定草稿归属任务、来源和请求修订准确；[M14TaskArea.jsx][AREA] 第 263–285 行把 `DRAFTS(taskId)` 同时用作消息草稿、问题回答和审批原因，切换请求只重置 `pick`。
- **反例**：任务原有草稿“检查安装包”；出现请求 r1 后直接批准一次，`onDecide` 收到的原因就是这份原草稿，随后草稿被清空。另一次，在 r1 写了原因、切到 r2，r2 仍显示并可提交 r1 的原因。
- **影响**：普通消息被悄悄消费为审批／问题回答，两个不同请求共享说明。整份消息草稿中的文字还可能被清掉而附件仍留在原处。
- **证据**：[组件真实处理函数复现](evidence-20261117-0914/cross-artifact-probes.json)，`ordinary-draft-as-approval-reason`、`request-reason-scope`。原型状态内即可修复，无须等待生产服务。

### AR03 · 中 · 首页扩展开关没有随新任务带入，恢复边界又被写回“待选择”

- **依据／位置**：[需求 R08][REQ]已确定“关闭后此后新建原生会话不加载个人扩展，已有会话不变”；[M14TaskArea.jsx][AREA] 第 205–214 行按 `taskId:agent` 保存开关；[App.jsx][APP] 第 407–426 行创建快照未携带此选择。
- **反例**：首页关闭 Claude 的开关，实际存入 `EXT['home:cc-sub']=false`；创建任务后选择器读 `EXT['new-task:cc-sub']`，又显示开启。模型／推理强度带入了，扩展选择没有带入。
- **另一个文档冲突**：[方案 §7.2][T] 第 225 行仍把“恢复已有会话沿用旧配置还是按新开关”写为待证事项。**隔离能否实现可以待验证，已有会话不变这一产品规则已经确定**，不应再作为两种均可的行为。
- **证据**：[`extension-home-to-new-task`](evidence-20261117-0914/cross-artifact-probes.json)。选择须进入任务持久状态和新建绑定的冻结输入／兼容判断；不能仅保存选择器局部布尔值。

### AR04 · 中 · Codex 不出计划卡，但方案、归一器和测试仍要求生成计划卡类型

- **依据／位置**：[需求 R02][REQ]、[方案 §6.1][T]、A71 均规定 Codex 不出计划卡；[方案 §4][T] 第 98 行却把 Codex `plan / turn plan update` 映射为 `proposed_plan`。

- **影响**：协议覆盖测试可以全绿，同时固化用户已排除的展示。不能用“当前普通任务没录到该事件”替代明确政策。

### AR05 · 中 · 长等待业务请求与回合结束“关闭所有请求”互相冲突

- **依据／位置**：[方案 §8.1][T] 第 255–261 行规定持久化 `awaiting_user`、MCP 立即返回、Agent 继续工作、用户批准后执行并通知；第 271、283 行又要求回合完成时收口本回合请求、各终态验证所有请求终结。
- **用例也互斥**：A25 要求父回合完成后待请求仍可达；A37/A72 要求超过 60 秒后批准有效；A60 则要求完成时“所有所属工具／请求终结”。当前没有把原生阻塞请求、宿主持久业务请求和独立后台节点区分到这组规则中。
- **具体场景**：Agent 申请发邮件，收到 awaiting_user 后完成本轮；用户随后批准。按 §8.1 应继续执行，按 §9/A60 请求已经结束。若再经过方案 B 的保守 owner 退出交槽，§8.1 的“原 run 仍有效／结果送回原 run”还缺少可操作的承接规则。
- **需处理**：先明确每类请求绑定 turn、run 还是 task／binding，普通回合结束、owner 退出、切换及用户停止分别如何处理；既不能凭旧 run 发业务，也不能把正常回合结束等同用户拒绝。**本项要求先修合同和用例，不要求现在完成 E12 生产改造。**

## 5. 风险、待确定点与后续验证

### 5.1 不应混为“原型阶段都做不了”的事项

| 类别 | 尚缺事项 | 当前该如何处理 |
| --- | --- | --- |
| 开发前可做的独立技研 | E10③–⑤ 的继承／降级、插件一次审批与扩展隔离边界；E11①b/①c 真实装依赖、真实子 Agent；②完整合并矩阵；④原会话打回；⑥目标停止／失败／长等待组合；⑧完全访问计划拦截 | 隔离实验能够补可行性证据，不必等完整产品；受本机权限或账号前置限制的组合如实保留，不能把缺证写成已支持 |
| 必须开发后验收 | E12 请求／业务服务重构，新表／IPC／完整调度器、真实桥接、差异 UI、清理后 M13 回归 | 设计和用例先一致；实际产品结果继续登记未执行，不用研究脚本抵扣 |
| 原型当前可复验 | 深色主题、窄窗口、长文本、请求说明／普通草稿、菜单和终端预填 | AR01–AR08、AR14 中可在合成原型验证的先验证；浏览器服务恢复后补真实交互，本轮未执行不能标通过 |
| 原生／系统层 | 系统中文 IME、系统剪贴板、真实快捷键／焦点与外部打开 | 按前台身份与系统前置取证；页面插入中文、SSR 和截图不能代替 |

Codex 完全访问合并、两端请求批准逐命令合并等仍未执行。本轮没有尝试绕过此前权限边界，也没有向用户重复索要授权。危险 Git 命令强制拦截仍按原决定只评估、不承诺，不因本报告扩大范围。

### 5.2 CC 修订时需要明确、但本轮不替用户擅定的规则

- **权限显示集合（AR01）**：技术方案允许公共 `edits` 能力，现行需求又强调三档。应将当前选择明确成一份对照表；首页／任务页一致是已经确定的要求，不需要再讨论。若最终选择改变产品档位集合，在需求中列明该变化。
- **目标跨绑定政策（AR10）**：保留原生目标归属，还是让逻辑任务目标跨执行器接力，须有明确选择。前者较符合当前“恢复各自原生会话”的合同；后者需要另外定义交接，不得仅凭 taskId 相同自动续轮。
- **工作副本的 cwd／授权根映射（AR12）**：从子目录任务进入整仓库工作副本时，须明确选择和验证范围；不能把 Git 仓库根与原任务目录视为天然相同。
