## 2. 问题清单

严重度按实际影响排序；高/中均指需求、状态或数据流的一致性缺陷。置信度均基于固定快照的确定性复现，不等于已观察到真实用户事故。

### 高

**H1：两个同目录 Codex 任务可认领同一原生会话，恢复时串上下文。**

- 触发：同一代码目录启动多个 Codex 任务，watcher 的异步 rollout 扫描发生重叠；较早任务尚未发消息，另一个任务产生新会话。
- 原因：扫描前分别取 `claimedIds`，await 后不重新校验或原子认领；匹配仅依赖目录、启动时间下界和未认领集合，无法可靠证明候选属于哪个 PTY。
- 结果：两个任务记录同一个 session ID。之后两个任务可能 resume 到同一上下文，破坏任务隔离。
- 代码：[watchCodex](../../src/main/core/tasks/task-service.ts:295)、[pickCodexSession](../../src/shared/codex-session.ts:26)。
- 复现：[review-task-repros.test.ts:111](/private/tmp/smartdd-m3-review-20261015-1033/src/review-task-repros.test.ts:111)。控制两个异步读取共同返回第二个任务的候选，两个任务均认领 `belongs-to-second`。
- 对照：PRD F05 的多会话管理与独立恢复；M0 原拟以 state DB 改进发现路线，当前仍仅扫 rollout。

**H2：任务反馈的 API 错误消息绕过脱敏，可将令牌明文存库并送到界面。**

- 触发：CLI session 的 API 错误消息含已配置的密钥值，例如网关在认证错误中回显该值。
- 原因：主动检查有 `redact`，但任务路径 `SessionTail → health.report → recordCheck / failed event` 原样存储、发布消息。
- 结果：敏感值进入 `ai_profiles.check_message`，通过配置视图、toast、tooltip 暴露，违反 PRD F04 的“令牌不明文保存、不明文显示”。
- 代码：[任务反馈](../../src/main/core/tasks/task-service.ts:343)、[聚合存储与通知](../../src/main/core/ai/profile-health.ts:68)、[checkMessage](../../src/main/core/ai/ai-profile-service.ts:262)；对照 [主动脱敏](/private/tmp/smartdd-m3-review-20261015-1033/src/main/core/ai/profile-tester.ts:60) 和 [PRD](../../docs/SmartDD_V0.2_PRD.md:344)。
- 复现：[review-health-repros.test.ts:45](/private/tmp/smartdd-m3-review-20261015-1033/src/review-health-repros.test.ts:45)。将自造的非真实密钥写入模拟认证错误，确认 DB、配置视图和变更事件均含该值。
- 边界：没有读取或测试真实令牌；本结果不意味着用户真实令牌已经泄露。

- 复现：旧目录存在原 session；换到空的新 `CLAUDE_CONFIG_DIR`，仍带旧 ID 执行 resume；DB 覆盖新 root，任务随后从 resumable 变成 fresh。

- 代码：[open](../../src/main/core/tasks/task-service.ts:170)、[spawn](../../src/main/core/tasks/task-service.ts:259)；对照 [M0 采纳待办](../../docs/M0_技术探针报告.md:140)。

**M4：旧 Codex 进程退出的延迟回调会停掉新一轮 session watcher。**

- 首条消息前退出后安排 3 秒延迟 `stopWatch(taskId)`；若 3 秒内重开任务，旧回调会按同 taskId 停掉新 watcher。
- 复现：新 PTY 仍在运行，但之后生成会话不再扫描，nativeSessionId 为空，任务保持 not-started；再次打开不能恢复该轮上下文。
- 代码：[退出宽限回调](../../src/main/core/tasks/task-service.ts:381)、[重开启动 watcher](../../src/main/core/tasks/task-service.ts:191)。
- 复现：[任务用例:143](/private/tmp/smartdd-m3-review-20261015-1033/src/review-task-repros.test.ts:143)。

**M5：健康结果未绑定启动配置版本，旧测试或旧任务可覆盖新配置状态。**

- 编辑启动参数会触发 auto；若旧检测仍在进行，按 profile ID 合并到旧 Promise，没有为新配置实际检测。
- 结束时不核对启动签名，旧结果写入新 Key / 地址的配置；运行中的旧任务同样仅凭 profile ID 回写。
- 复现：运行旧 Key 检测，编辑为新 Key，再请求 auto；实际只检测旧 Key，最终新配置记录旧 Key 的失败结果。
- 代码：[编辑触发](../../src/main/core/ai/controller.ts:40)、[inFlight 合并和存储](../../src/main/core/ai/profile-health.ts:41)、[任务仅传 ID](../../src/main/core/tasks/task-service.ts:343)。
- 复现：[健康用例:55](/private/tmp/smartdd-m3-review-20261015-1033/src/review-health-repros.test.ts:55)。旧任务版本覆盖是同一根因的代码路径，未另计一个复现用例。

**M6：一个任务首次成功后永久丢弃后续成功，无法纠正其他任务造成的失败。**

- tail 在自身 last=ok 时跳过后续所有普通应答；但配置状态是多个任务和主动测试共享的。
- 复现：A 成功 → B 认证失败使配置 failed → A 再成功，状态仍是 B 的 failed。违反 PRD “以最后一次发生为准”。
- 聚合层虽有十分钟刷新规则，同一 tail 后续正常消息却到不了该层。
- 代码：[永久跳过 ok](../../src/main/core/tasks/session-health.ts:80)、[聚合去重](../../src/main/core/ai/profile-health.ts:68)；对照 [PRD](../../docs/SmartDD_V0.2_PRD.md:338)。
- 复现：[健康用例:74](/private/tmp/smartdd-m3-review-20261015-1033/src/review-health-repros.test.ts:74)。

**M7：恢复旧会话后，首轮轮询前的新应答会被一起跳过。**

- offset 在首次 poll 才取旧文件末尾；启动到首次 poll（默认约 2 秒）期间的新错误/正常结果无法被识别。
- 复现：构造旧文件，创建 tail 后、首次 poll 前追加新 API 错误，poll 不发布任何事件。
- 代码：[首次 offset](../../src/main/core/tasks/session-health.ts:43)、[默认轮询](../../src/main/core/tasks/task-service.ts:345)。
- 复现：[健康用例:90](/private/tmp/smartdd-m3-review-20261015-1033/src/review-health-repros.test.ts:90)。文件创建后推进受控时钟，再构造恢复和快速应答，未启动真实 CLI。
