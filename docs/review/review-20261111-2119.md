## 2. 问题清单

### 中：F01 原智能体 ID 未变、认证来源已变时，旧任务恢复没有提示重新选择

**依据**：需求 [5.3“任务记录与恢复”](../里程碑/M13_应用Skill与MCP插件化重构/需求.md)第 328 行要求：原智能体或其供应商已修改、删除时提示重新选择，不静默换账号。技术方案 §2 TaskSnapshot 也要求 Provider 变更时提示重选；5.3 同时明确编辑智能体可以换供应商。

**实测步骤**：

1. 用“Claude Code · 订阅”新建合成任务，任务信息显示“订阅（CLI 自己的登录）”，随后停止任务。
2. 删除已有“Claude Code · DeepSeek”智能体，释放该组合，避免唯一性校验干扰本次检查。
3. 编辑原来的“Claude Code · 订阅”，把模型来源改为 DeepSeek，保存；其智能体 ID 仍为 `rc-cc-login`，名称保留。
4. 回旧任务打开恢复弹窗：默认仍选这项，并标“原智能体”。没有订阅→DeepSeek 的来源变更提示，“恢复任务”可以直接点击。
5. 点击恢复后，任务信息的“订阅或供应商”变为 DeepSeek，模型变为 DeepSeek V4 Pro。

本次恢复弹窗没有明确告知新的模型来源；它只显示原来保留的智能体名称。因此不能用用户点了一次通用“恢复任务”代替需求要求的身份变化提示与重新选择。

**根因与位置**：

- `prototypes/m6-codex/src/M13TaskDialogs.jsx:29` 只按 `agentId` 预选原项；第 34 行只在 ID 消失时提示删除。
- 第 31–38 行只做模型取舍和缺 Key 校验，没有比较任务快照的 `source`／`providerId` 与当前配置。
- `src/m13-model.mjs:547` 已有来源和 Provider ID 快照，`resumedTask`（第 559 行起）却直接按当前智能体重建运行快照，没有身份变化判断。
- T064 覆盖了主动改选另一智能体、原智能体删除和模型变化，**没有覆盖“同一 ID 的来源／供应商被编辑”**。新 R1.0 在合并核对中已特意恢复此规则，但用例和原型未补上这一分支。

**影响边界**：目前只证明合成原型的恢复行为与需求不一致，没有向真实模型发送会话。正式实现若照此处理，会把旧会话恢复到不同模型服务，认证与会话上下文的去向均可能改变，不能仅凭“Code Agent 相同、ID 相同”认定身份没变。

**证据**：[恢复前弹窗](evidence/m13-20261111-2119/identity-before-resume.png)、[恢复后任务信息](evidence/m13-20261111-2119/identity-after-resume.png)、[原始界面文本](evidence/m13-20261111-2119/identity-review.json)、[离线判定](evidence/m13-20261111-2119/identity-judgment.json)。

### 低：F02 Claude 换智能体恢复时，跨独立配置目录的会话定位／承接方式尚未说明

**已明确的两项设计**：

- 技术方案 §3.1：Claude 第三方供应商使用独立 `CLAUDE_CONFIG_DIR`，**每个 RunConfig 一个目录**；原生登录使用用户原目录。
- 需求 5.3：原智能体删除后，可以选同一个 Code Agent 的其他可用智能体恢复旧任务。

但技术方案 §3.4 目前只写会话 ID 绑定、最后模型解析与显式传参，没有说明选了另一个 RunConfig 后，旧目录中的原生会话如何在目标目录下被找到和延续。保存旧配置目录的位置并不等于已经定义跨目录恢复方法。

现有证据的边界：Claude 实验结论第 6 项明确记录独立目录下的会话不在用户 `~/.claude/projects`；补验 B7 的 `b7-gen-session.mjs` 使用同一份 `env`／配置目录生成并恢复两轮，验证的是模型解析与同目录恢复。它不能直接证明换配置目录的恢复也成立。

**这不是“已实测跨目录必定失败”的结论**。本轮没有执行这项真实 CLI 实验；这是为了支撑当前允许的恢复流程，技术方案还需给出方法与验证边界。建议至少说明：源会话定位、目标运行目录、是否投影／迁移会话材料、缺材料时如何保留原记录和报错。补一个两个独立目录的本机模拟端点实验即可，不需要真实账号或外部模型。
