## 2. 新问题

### R1（高，需用户确认）：Git 项目里独立任务并行后，派子任务前的自动提交会带走其他任务未完成的改动

- 代码：`git-workspaces.ts` 的 `prepareWorktree` 在父任务排空后执行 `commit(..., 'auto_before_delegate')`，其中是对主目录整体 `git add -A`。排空只针对父任务本身，同一仓库里其他独立任务的回合仍在进行。
- 合同：技术方案 §6.1 写“宿主冻结主任务新写入并等到可提交的边界；工作区不干净则 `git add -A` 后提交”。这条是在独立任务串行的前提下写的，P1 改为并行后，“可提交的边界”只对父任务成立。§11 已为并行写入补了差异归属的说明，§6.1 的自动提交没有相应调整。
- 实测（[复现](evidence-20261118-claude-0805-recheck/probe-0805.test.ts.txt)、[观察值](evidence-20261118-claude-0805-recheck/probe.json) `A_autocommit_sweep`）：同一 Git 仓库，独立任务 X 回合进行中，已写出一半的 `other-half-written.txt`；父任务派出写入子任务并结束回合后，宿主的自动提交“willyou: 自动提交（派出子任务前）”只包含这个文件，子任务的工作副本里也有它，而 X 这时仍在回合中。
- 影响：X 改了一半的文件被记成父任务的提交，并作为子任务的起点；子任务可能基于半成品工作，主 Agent 之后合并时也分不清来源。X 后续继续修改同一文件，会在主目录留下与这次提交交织的改动。
- 需要用户确认的规则（建议 ①）：
  1. **自动提交前，等同一 Git 仓库里其他任务的当前回合结束再提交**（只等待、不关会话，等待期间短暂暂停这些任务的新输入，`git worktree add` 完成即放开，依赖安装不在这段时间内）。别的任务已完成但未提交的改动仍会进入这次提交，提交说明注明“可能包含同目录其他任务的改动”。
  2. 照常提交，只在提交说明和子任务说明里写明可能包含其他任务的改动。
  3. 有其他任务正在回合中时，不自动提交，提示用户先处理。

### R2（中）：Git 父任务在排空等待依赖安装期间批准的业务，执行时限从批准开始计算，仍会因等待超时

- 代码：`host-business-requests.ts` 只在 `needsWriteSlot` 为真时延后开始计时；`delegation-service.ts` 的 `businessNeedsWriteSlot` 对派出 Git 子任务的父任务返回假。但 `acquireBusiness` 在任务处于 `draining` 时仍会循环等待，而 Git 父任务的 `draining` 要一直持续到 `prepareChild` 完成，其中包括在新工作副本里安装依赖（默认超时 120 秒）。
- 实测（同一[复现](evidence-20261118-claude-0805-recheck/probe-0805.test.ts.txt)，`B_business_during_git_drain`，执行时限缩为 500 毫秒、依赖安装模拟 1.5 秒）：`needsWriteSlot=false`，批准 518 毫秒后请求退役，提示“业务操作已取消”，零执行。按实际的 60 秒时限，只要 `pnpm install` 超过 60 秒，父任务名下已批准的邮件发送等业务就会被退役，需要重新批准。
- 合同：评审 §5 P3 的关闭条件是“排队等待不计入”。
- 建议：只要调用了 `acquire`，都在它返回后再开始计时（不需要写入槽时 `acquire` 立即返回，与“从批准开始”等价）；或者让 `businessNeedsWriteSlot` 在任务处于 `draining` 时也返回真。补一条 Git 父任务排空期间批准业务的回归。
