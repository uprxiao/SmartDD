# F33 业务逻辑逆向梳理与需求变更分析（需求初稿）

状态：想法整理，**未安排 M 阶段，未立项**。来源：用户 2026-11-19 提出并讨论。本文只记录已确认的思路和待定事项；立项后迁入阶段目录的 `需求.md`，再展开成详细需求。需求池入口见 [F33](需求池.md)。

## 1. 目标

从现有代码逆向还原出原本的 PRD 和业务逻辑，帮助用户尽快熟悉某个功能模块，或一整条功能链路，从而尽快上手相关代码。

- 正常的开发顺序是“PRD → 设计 → 开发”，本需求做的是反过来的过程。
- 产出不追求某种标准的业务规范，核心目标是让人尽快熟悉业务。文档格式可以固定下来。

分两层，先后顺序已确认：

1. **业务梳理（先做）**：从代码还原业务逻辑，生成文档。
2. **需求变更分析（后做）**：在已梳理清楚的业务场景和规则基础上，梳理新需求，产出相关的设计与改动点，作为后续开发和测试的依据。

## 2. 已确认的思路

### 2.1 面向的项目

- 以 Java 项目为主。
- 前端也一起看，但重点是入口处的业务逻辑和规则：
  - **读操作**：以后端的长链路查询逻辑为主。
  - **写操作**：前端通常有详细校验，这部分要梳理出来，后端的处理规则也要梳理。
- 数据库：直接调用现有的项目数据库 Skill 查看。

### 2.2 梳理流程：逐步确认

**怎么开始不需要问用户；梳理什么、梳理多少，由用户来定。**

1. **触发**：用户直接给一个类，或者提一个要求，比如“在项目里找一下某块业务的代码”。不需要先问用户用哪种梳理方式。
2. **定位**：Agent 先大致找一遍，列出候选的代码、接口和表，并说明依据。
3. **确认对象**：找得不对、或者找到多个时，由用户确认是哪一个。
4. **确认范围**：Agent 列出该功能下的各个小功能，由用户选择全部包含，还是只要其中几个。
5. **深入梳理**：按用户确认的对象和范围生成文档。

### 2.3 两种梳理方式

**按流程拆解：**

- 宏观：这一块大体是做什么的，主流程是什么样的。
- 微观：把主流程拆到每个环节，讲清具体的业务逻辑。
- 分析各个环节、小模块之间的相互影响。

**以单个模块为中心辐射：**

- 梳理这个模块本身的业务逻辑。
- 建立树形关系：哪些模块会影响它，它又会影响哪些模块，具体是如何影响的。

两种方式各固定一套文档格式。

### 2.4 质量保证

- 一个模型（如 Codex、Claude Code、DeepSeek）梳理出第一版，再换另一个模型做 review 和校验，检查业务逻辑是否正确、是否全面。简单的低级错误基本能在 review 中发现。
- review 中发现的共性问题，沉淀回 Skill，持续优化。

### 2.5 保持最新

- 文档做版本管理，通过 Git 或 SVN 进行。
- 定期用定时任务重跑“梳理 + 多模型 review”的流程，覆盖盲区；定时任务中加入核对，保证代码和文档一致。

### 2.6 跨服务、跨项目

不做专门处理，看项目如何组织：

- **单项目多模块**：在项目根目录下处理。
- **跨多个项目**：把相关代码放在同一个目录下，在这个根目录下处理。

### 2.7 文档归属

生成的文档归属于 WillYou 的项目管理，在项目中管理。
